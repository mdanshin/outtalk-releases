Архитектура

OutTalk следует классической трёхпроцессной модели Electron с жёстким разделением ответственности и единой доменной моделью, общей для всех процессов.

src/shared/mail-types.ts — доменная модель почты для ВСЕХ процессов.
src/shared/diag-types.ts — контракт диагностики (рядом с моделью, не внутри неё).

Зависимости в main идут только вниз. Модуль ipc/* не импортирует другой ipc/*: общий код (выбор провайдера — providers/access.ts, конверт Result — util/result.ts) лежит этажом ниже и доступен обоим. Раньше ipc/diag.ts тянул приватные хелперы из ipc/mail.ts — зависимость «вбок» между регистраторами каналов; она устранена. См. Модель провайдеров → Слой доступа.

Ключевые принципы

1. Провайдер-агностичное ядро

Всё выше main работает только с доменными типами (MailFolder, MessageSummary, MessageDetail, EmailAddress, Attachment, DraftInput). Бэкенд реализует интерфейс MailProvider. Добавить Gmail/IMAP = новый класс + ветка в registry.ts; UI не меняется. См. Модель провайдеров.

2. Единый источник истины типов

src/shared/mail-types.ts импортируется main, preload и renderer (алиас @shared, настроен в electron.vite.config.ts и tsconfig.*.json). Никакого дублирования и рассинхрона. См. Доменная модель.

3. Result вместо исключений через IPC

Провайдеры бросают MailError с кодом (auth/network/not_found/…); IPC-обёртка превращает это в:

type Result<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; code?: ErrorCode }

Через границу IPC исключения не пробрасываются — только Result. См. Процессы и IPC.

4. Безопасность по умолчанию

contextIsolation: true + OS-песочница renderer (sandbox: true, preload собран CommonJS), узкий typed window.api, шифрование секретов, санитайзинг HTML, CSP, единый харденинг окон (windows/harden.ts), Electron Fuses в упакованной сборке (ADR-0064). См. Безопасность.

5. Демо-провайдер

DemoProvider реализует тот же контракт → весь UI работает без реального сервера. Он выбирается только при OUTTALK_DEMO=1 и явном accountId === 'demo'; пустой, отсутствующий или неизвестный ID завершается ошибкой auth.

6. Fail-closed foundation локальных данных

main/local-data реализует opaque account paths, защищённый per-account key envelope и зашифрованную SQLite-базу с версионированной схемой/миграциями, store_meta binding, WAL validation/recovery и hard size limits. WAL-проверка повторяет recovery-семантику SQLite: валидный префикс, оканчивающийся полным commit frame, восстанавливается даже при stale/preallocated frames или оборванном хвосте после аварийной остановки; повреждение до последнего доказанного commit остаётся fail-closed. Межпроцессный lifecycle lock охватывает key publication, открытие и удаление; открытый handle дополнительно удерживает уникальную crash-sticky lease. Удаление закрывает локальный handle и завершается lock_unavailable, пока существует lease другого процесса; lock/lease не крадутся по PID или возрасту и требуют ручного подтверждённого recovery после crash. Account directory и DB/WAL/SHM до файловых операций проверяются на symlink/junction и containment. На Windows отсутствие настоящего directory flush даёт typed runtime gate, а не подменяется fsync файла. Полный протокол и рунбук — Локальные данные и recovery.

Отправка S/MIME (ADR-0131):
  ComposeDialog → decideSend (lib/smime-compose.ts) → Mail.smimeSend → ipc 'mail:smime:send'
     → smime/send.ts: проверки (понижение, сертификаты) → composeMessage → подпись (ОС/.p12,
       проверяется) → шифрование (получатели + сам) → provider.sendMime → удалить заменённый черновик

Перед сетью стоят два кэша тел писем. Клиентский — DetailCache в store/useMail.ts, вне реактивного состояния, свой у каждого окна: повторные открытия и прогретые соседи открываются мгновенно, единый fetchDetail не допускает дублирующих GetItem. Общий для всех окон — кэш тел main (ipc/detail-sync.ts, 150 писем / 64 МБ), рядом с ним — кэш inline-картинок main (ipc/inline-store.ts, 48 МБ). Инварианты: предзагрузка никогда не метит письмо прочитанным; под одним ItemId тело не меняется, поэтому ни refresh, ни переключение ящика, ни свежий список тела не стирают — отметки «прочитано»/флаг приходят со списком, а забывается только доказанно удалённое, перемещённое, сохранённое и «Черновики»/«Исходящие» (ADR-0145). Полная очистка — удаление ящика или другой ящик за тем же id (reset({ purge: true })). Детали — ADR-0016, ADR-0145, Локальные данные → Тела писем и картинки в памяти main, Интерфейс и состояние.

Тот же путь для любой операции: UI → store → lib/mail → preload → IPC → провайдер → домен → обратно.

Слоевание: stateful-политика в сторе, чистые хелперы в lib/

Правило разделения на примере действий «архив/удаление текущего выделения» (archiveSelection/deleteSelection):

  • Stateful-политика выбора живёт в сторе. Только useMail владеет выделением, открытой беседой и списком папок (selection/conversation/folders), поэтому решение «что именно затронуть» (весь тред vs одиночное письмо, что архивировать) принимает он — единым экшеном для всех точек входа.
  • Чистые доменные хелперы — в lib/ (conversationActions.ts: findArchiveFolder, conversationArchiveIds): без состояния и побочных эффектов, тестируемы, переиспользуются стором и компонентами; раньше эта логика дублировалась по трём компонентам.
  • UI держит лишь видимость. Компоненты используют те же хелперы только для показа/скрытия кнопки (например canArchive), не для выполнения действия. Инварианты слоёв не меняются — отдельный ADR не нужен; детали — Интерфейс → Единый обработчик выделения.
