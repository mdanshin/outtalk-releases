Отладка

Зонды EWS

Все зонды используют креды из .env.local (в .gitignore; шаблон — .env.exchange.example) и работают на чистом Node, без Electron.

Замеры скорости без живого сервера — не зонд, а отдельный стенд: npm run perf гоняет настоящее приложение против имитации Exchange на локальном https. Методика, исходные цифры и что по outtalk.log можно, а что нельзя разделить на «сервер» и «клиент» — Производительность (ADR-0147).

npm run ews:check — автономный зонд

Скрипт scripts/ews-check.mjs работает на чистом Node (без Electron), напрямую через ews-javascript-api + @ewsjs/xhr. Выводит:

  1. Способ определения URL (явный или перебор кандидатов).
  2. Список папок с классами и счётчиками.
  3. Первые письма «Входящих».
  4. Одно письмо целиком (тело + вложения).

Особенности:

  • Перебор кандидатов URL при пустом EWS_URL: mail.<домен>, webmail.<домен>, autodiscover.<домен>, …
  • Защищённое чтение свойств (как в провайдере).
cp .env.exchange.example .env.local   # заполнить email/логин/пароль
npm run ews:check

npm run ews:test — прогон провайдера против реального сервера

Скрипт scripts/ews-provider-test.mjs собирает реальный ExchangeProvider (через общий helper scripts/provider-probe-bundle.mjs, node-зависимости внешние) и прогоняет testConnection → listFolders → listMessages → getMessage. Это проверяет именно тот код, который ships в приложении, а не его двойник. Импорты app/BrowserWindow, транзитивно приходящие из диагностики и логирования, при сборке зонда направляются в scripts/electron-provider-test-shim.mjs: фасад не имитирует сеть или провайдер, возвращает пустой список окон и fail-closed запрещает доступ к Electron profile paths. Без этого plain Node загружал npm-пакет electron как CommonJS launcher и падал до первого EWS-запроса на named export. Credential-free unit provider-probe-bundle.test.ts использует тот же helper, импортирует собранный production provider и проверяет fail-closed фасад, поэтому удаление shim, новый неподдержанный Electron import или расхождение конфигурации сборки ломают обычный CI до обращения к живому ящику.

Ценность в том, что этот прогон ловит баги, специфичные для реального кода (например, недопустимость ToRecipients в FindItems), которых нет в упрощённом зонде.

npm run ews:inline — зонд inline-картинок и S/MIME

Скрипт scripts/ews-inline-check.mjs ищет во «Входящих» письмо с cid:-ссылкой в HTML-теле и печатает диагностику, почему картинка встраивается или нет:

  1. Список cid:-токенов, на которые ссылается тело.
  2. Каждое вложение — Name / ContentType / ContentId / IsInline / Size, причём ContentId до и после Load() (частая причина невстраивания — отсутствующий/несовпадающий ContentId).
  3. Если вложение — S/MIME-блоб (smime.p7m/pkcs7/signed): декодирует его, показывает начало clear-MIME, найденные внутри Content-ID и image-части, и верифицирует алгоритм извлечения (тот же парсер, что в провайдере): сколько картинок извлечено и сколько cid: осталось в теле после замены (0 = всё встроилось).
npm run ews:inline

Именно этим зондом подтверждено извлечение inline-картинок из подписанных писем на живом Exchange (4 картинки, 0 оставшихся cid:). Реализация — маппинг данных → Inline-картинки в S/MIME-подписанных письмах.

npm run ews:conv — зонд бесед

Скрипт scripts/ews-conv-check.mjs проверяет кросс-папочный тред GetConversationItems на живом ящике — детали в Exchange: протокол EWS.

npm run ews:photo — зонд фото контактов

Скрипт scripts/ews-photo-check.mjs бьёт напрямую в REST-эндпоинт GET <ewsUrl>/s/GetUserPhoto?email=&size= (Basic-auth, node:https) и печатает для каждого адреса HTTP <статус>, <content-type>, <байт> и вердикт «фото есть/нет». По умолчанию проверяет свой ящик (EWS_EMAIL) и внешний адрес в размерах HR64x64/HR96x96; можно передать адреса аргументами:

npm run ews:photo                       # свой ящик + пример
npm run ews:photo user@example.com

Именно этим зондом подтверждено, что сервер отдаёт фото для внутренних адресов (200 + image/*) и 404 для внешних → в UI инициалы. Реализация — маппинг данных → Фото контактов.

npm run ews:sent — зонд «Отправленных» (ADR-0095)

Скрипт scripts/ews-sent-check.mjs отвечает на вопрос «почему письма, отправленные с другого устройства, не видны в клиенте», разделяя три разных «не видны»: сервер их не отдаёт; отдаёт, но из другой папки; отдаёт, а клиент кладёт мимо. Печатает:

  1. Саму папку: TotalCount и хвост её идентификатора.
  2. Первые N писем так, как их сортирует клиент — тройка дат (DateTimeReceived / DateTimeSent / DateTimeCreated), родительская папка, есть ли отправитель и длина темы.
  3. Совпадает ли верх списка при двух сортировках — по дате доставки и по дате отправки. Разные вершины = у части писем даты доставки нет, и старая сортировка прятала их в глубине.
  4. Постраничный обход по 200 (как в приложении, до 60 страниц): сколько страниц и секунд, сколько повторов между страницами, менялся ли TotalCount и сколько писем без даты доставки (1601-01-01). Плавающий TotalCount или повторы — и есть причина, по которой обход отбрасывается целиком и папка перестаёт обновляться.
  5. Сколько в ящике папок с похожим названием — если другое устройство пишет в свою «Отправленные», видно сразу.
npm run ews:sent        # 15 первых писем
npm run ews:sent 50

Зонд ничего не пишет в ящик и намеренно обезличен: темы показаны длиной в символах, идентификаторы — последними десятью символами (сравнить строки можно, восстановить письмо — нет), адреса не печатаются вовсе. Вывод можно прислать в отчёте об ошибке, не раскрывая переписку.

Диагностика упакованного приложения

В main встроена диагностика: перехват консоли renderer и ошибок загрузки выводится в stdout. DevTools открываются по флагу окружения:

# macOS
OUTTALK_DEBUG=1 /Applications/OutTalk.app/Contents/MacOS/OutTalk

# Windows (PowerShell) — упакованный бинарь из `npm run reinstall` / `dist:win`
$env:OUTTALK_DEBUG=1; .\release\win-unpacked\OutTalk.exe

Форвардятся события: console-message, did-fail-load, render-process-gone.

С ADR-0155 OUTTALK_DEBUG ещё и включает режим разработчика на время этого запуска (сохранённый выбор человека не меняется; переключатель «Режим разработчика» в это время неактивен с пометкой «задано параметром запуска»).

Режим разработчика: как его включает поддержка

Служебные разделы спрятаны от обычного пользователя в режим разработчика (Настройки → Режим разработчика). Включить его можно двумя способами:

СпособЧто сделатьСколько держится
Семь нажатий«Настройки → О программе» → семь раз нажать на номер версии («OutTalk 1.2.3»), не дольше 3 с между нажатиями. На четвёртом — «Ещё 3 нажатия…», на седьмом — «Режим разработчика включён» с кнопкой «Открыть»сохраняется на этом компьютере, пока не выключат переключателем «Настройки → Разработчик → Режим разработчика»
Параметр запусказапустить с OUTTALK_DEBUG=1 (команды выше)только этот запуск; заодно открывает инструменты разработчика

Что появляется в режиме:

  • «Вид → Диагностика подключения» (⌥⌘ на macOS, Ctrl+ в Windows и Linux) — пункт меню и сочетание есть только в режиме разработчика; без режима панель диагностики открыть нечем. Меню пересобирается сразу при включении и выключении.
  • «Настройки → Разработчик»: «Номер сборки»; «Журнал» — «Окно диагностики» и «Подробный журнал»; «Проверки» — задачи Exchange, доступ к ящику, надстройки Outlook; «Параметры запуска» — какие OUTTALK_* заданы в этом запуске (у флагов 0/1, уровня журнала и темы — значение, у путей и прочего — «задано») и доступны ли инструменты разработчика; «Внутреннее состояние» — выученные шаблоны цитат по ящикам («Посмотреть», «Сбросить»), отметки переноса через ящик, запомненный размер окна письма, размер и место главного окна (каждый сброс — с подтверждением). Окно, «уехавшее» за пределы экрана, возвращается «Внутреннее состояние → Размер и место главного окна → Сбросить».

Режим — только видимость: он не включает инструменты разработчика в упакованной сборке и не даёт новых прав (Безопасность).

⚠️ В упакованной сборке нет --inspect, NODE_OPTIONS и ELECTRON_RUN_AS_NODE — их отключают Electron Fuses, зашитые хуком afterPack (ADR-0064, Сборка → Хук afterPack). Отладчик к main упакованного приложения не подцепить намеренно; OUTTALK_DEBUG=1 продолжает работать, потому что DevTools открываются программно (webContents.openDevTools), а не CLI-флагом. Для отладки main с инспектором используйте dev-режим (npm run dev, electron из node_modules — fuses его не касаются).

Какая именно сборка запущена. Файл журнала — <userData>/logs/outtalk.log (ротация при 8 МБ в outtalk.1.log; полный путь записан в первой строке журнала, поле file; уровень — OUTTALK_LOG=debug|info|warn|error, по умолчанию debug в dev и info в упакованной сборке). Первая запись после старта — app · log started { level, version, build, platform, electron, node, file }: version — semver из package.json, build — точная identity исходника <short SHA>[-dirty] · <UTC-время сборки> (Сборка и запуск → Идентификация сборки). Та же строка показана в «Настройки → Разработчик → Номер сборки» (с кнопкой копирования). Раздел «Разработчик» виден только в режиме разработчика — как его включить, см. «Режим разработчика: как его включает поддержка» выше. Сверяйте её первой, когда поведение не совпадает с ожиданиями: одинаковый 0.1.8 не доказывает, что запущена свежая сборка — реальный случай, когда «пропавшие» предупреждения в карточке приглашения объяснялись стартом старого bundle из release/mac-arm64 вместо /Applications/OutTalk.app.

«Письма приходят с задержкой»: подробный журнал на 15 минут (ADR-0144)

Упакованная сборка пишет в файл только info и выше, поэтому строки отдельных запросов (req) и итоги фоновых операций в файл обычно не попадают. Чтобы измерить задержку на машине пользователя, не перезапуская приложение с OUTTALK_LOG=debug, есть кнопка «Подробный журнал».

Как включить.

  1. Включите режим разработчика (см. выше) и откройте панель диагностики: меню «Вид» → «Диагностика подключения» или сочетание ⌥⌘** на macOS, **Ctrl+ в Windows и Linux. Без режима разработчика этого пункта меню и сочетания нет.
  2. В шапке панели нажмите «Подробный журнал». Кнопка подсветится и покажет оставшееся время («Подробный журнал · 15 мин»).
  3. Повторите то, что тормозит (дождитесь нового письма, откройте пару писем). Через 15 минут уровень сам вернётся к обычному; повторное нажатие выключает раньше. Между запусками приложения состояние не сохраняется.

Тот же переключатель есть в «Настройки → Разработчик → Журнал → Подробный журнал» (с остатком «ещё N мин»); там же строка «Окно диагностики» с кнопкой «Открыть». Раздел «Разработчик», как и пункт меню с сочетанием клавиш, виден только в режиме разработчика — семь нажатий на номер версии в «Настройки → О программе» или OUTTALK_DEBUG=1 на один запуск (Настройки).

Механика: setVerboseLog(true) в util/log.ts поднимает уровень файла до debug на VERBOSE_LOG_MS = 15 мин и заводит таймер возврата; IPC — diag:verboseLog / diag:setVerboseLog, только главное окно (Процессы и IPC).

Где файл. <userData>/logs/outtalk.log (и outtalk.1.log после ротации). Для упакованной сборки это обычно ~/Library/Application Support/OutTalk/logs/ на macOS и %APPDATA%\OutTalk\logs\ на Windows; точный путь — в поле file первой строки app │ log started.

Какие строки прислать (достаточно отрезка за время, пока был включён подробный журнал, от verbose log on до verbose log off):

СтрокаУровеньЧто показывает
app │ verbose log on / app │ verbose log offinfoграницы отрезка ({minutes, base} / {reason}: time is up или switched off)
watch │ events │ {types, lagMs}infoпоток принёс пачку событий: число по типам и lagMs — на сколько самое свежее событие отстало от серверной отметки времени (расхождение часов входит в число — сравнивайте строки между собой)
watch │ new mail │ {count, engine, extra}infoписьмо показано: сколько, каким путём (stream или poll), в выбранном ящике или в дополнительном (extra: true)
op │ watch:new_mail — done │ {ms, reqs, …}debugсколько заняла сводка нового письма от события до списка
op │ <операция> — done │ {ms, reqs, serverMs, queueMs, retries, lane}info для interactive, debug для live/background, warn если > 1,5 с или ошибкаитог любой операции: общее время, число запросов, сумма времени сервера, сумма ожидания в шлюзе, повторы, полоса (шлюз)
req │ <SOAP-операция> │ {ms, queueMs, lane, attempt, n, socket, dnsMs, connectMs, tlsMs, …}debug (warn если > 1,5 с или ошибка)отдельный запрос: ответ сервера, ожидание слота, полоса, номер попытки, сколько id в запросе; с ADR-0149 — новое ли соединение и сколько заняло его открытие (см. Соединения с Exchange)
watch │ streaming connection went silent → treating it as deadwarnсторож по пульсу не слышал сервер дольше окна (~2 мин) и переоткрыл соединение (Exchange: EWS)
watch │ stream failed → fell back to pollwarnпоток не поднялся, ящик перешёл на опрос

Как читать: большой lagMs — задержка на стороне сервера или сети до нас; маленький lagMs, но долгий op │ watch:new_mail — задержка у нас (смотрите queueMs: если он велик, запрос ждал слот шлюза); engine: poll вместо stream — ящик опрашивается (ищите строку fell back to poll или ящик делит вход с соседом, ADR-0144).

Что в журнале нет. Содержимого писем, тем, адресов и id писем: итог op собирается только из чисел и фиксированных слов (opSummary; код ошибки проходит лишь как короткое слово [a-z_-]), n — счётчик имён элементов, а не сами id, события потока — только типы и числа. Подробный журнал меняет только уровень, правила редактирования строк (redactLogMeta) остаются прежними.

Соединения с Exchange: почему одиночный запрос идёт секунду (ADR-0149)

Вопрос, на который отвечает журнал: одиночный GetAttachment на пару килобайт идёт ~1,1–1,4 с, если уходит сразу, и ~0,1 с, если сначала постоял в очереди. Гипотеза — медленные открывают новое соединение (TCP + TLS через прокси или VPN). С ADR-0149 каждая строка req говорит, на каком соединении ушёл запрос, а раз в минуту пишется сводка (Аутентификация и сеть → Диагностика соединений). Поведение сети от этого не меняется.

Как снять.

  1. Включите «Подробный журнал» (см. выше): строки req — уровня debug и без него в файл упакованной сборки не попадают (кроме запросов дольше 1,5 с — они warn). Альтернатива — запуск с OUTTALK_LOG=debug.
  2. Откройте несколько писем с картинками; особенно ценны первые открытия после простоя больше 5 секунд — столько живёт свободное соединение в пуле Node по умолчанию.
  3. Поработайте ещё несколько минут, чтобы в журнал легли минутные сводки.
  4. Возьмите отрезок outtalk.log (где лежит — «Где файл» выше; путь — в поле file строки app │ log started).

Что прислать.

СтрокаУровеньПоля
req │ GetAttachment │ {…}debugsocket (new / reused), для new — dnsMs (имя разрешено; нет у адреса-IP), connectMs (TCP вместе с разрешением имени) и tlsMs (TLS готов), все от начала запроса; queueMs — ожидание слота шлюза; ms — весь запрос
transport │ connections │ {new, reused, handshakeMedianMs, handshakeMaxMs}infoсводка за минуту: сколько запросов ушло по новым соединениям и по живым, медиана и максимум tlsMs новых; пишется только если запросы были

Какой режим подключения в журнале. Сравнивать new/reused имеет смысл не везде:

Режим ящикаЧто видно
Basic, без прокси, с проверкой сертификатаосновной случай: видны и new, и reused
NTLMвсегда new — библиотека создаёт агент на каждый запрос, проба видит первый запрос рукопожатия
«Игнорировать ошибки сертификата» (ignoreCertErrors)всегда new — агент без keep-alive на каждый запрос
Системный проксиconnectMs/tlsMs — участок до прокси; с другими режимами не сравнивать
Потоковая подписка на новые письмапробой не обёрнута и в сводку не входит

Как читать.

  • Медленные одиночные запросы при queueMs: 0 идут с socket: new и tlsMs около 1000 мс, быстрые — с socket: reused, а в сводке много new при медиане рукопожатия под секунду, — гипотеза подтверждена: время уходит на открытие соединения, а не на сервер. Следующий шаг — keep-alive агент по умолчанию (отдельное решение, условия — в ADR-0149); до него можно проверить эффект вручную, запустив с OUTTALK_KEEPALIVE=1 (только Basic, без прокси, с проверкой сертификата).
  • Большой dnsMs (почти весь tlsMs) — медленно разрешается имя сервера, а не TLS.
  • Медленные запросы с socket: reused или с малым tlsMs — время уходит не на соединение: смотрите сервер и serverMs в строках op.

Чего в этих строках нет. Ни хоста, ни адреса, ни порта, ни заголовков — только new/reused и миллисекунды.

Репетиция напоминания о встрече (ADR-0056)

Напоминание открывается за 15 минут до встречи, и ждать реальную встречу для проверки неудобно. Демо-провайдер умеет подложить одну онлайн-встречу «Синк с командой» через N минут (целое 1..180) — только в демо-ящике, реальные аккаунты не затрагиваются:

# macOS/Linux: демо-ящик + встреча через 5 минут → плашка с тоном «soon» сразу после запуска
OUTTALK_DEMO=1 OUTTALK_DEMO_UPCOMING_MINUTES=5 npx electron-vite dev
# упакованная сборка
OUTTALK_DEMO=1 OUTTALK_DEMO_UPCOMING_MINUTES=20 /Applications/OutTalk.app/Contents/MacOS/OutTalk

$env:OUTTALK_DEMO=1; $env:OUTTALK_DEMO_UPCOMING_MINUTES=5; .\release\win-unpacked\OutTalk.exe

Что проверять: N ≥ 16 — плашка появляется ровно в T−15 (тон calm), в T−5 переходит в soon, в T — «Началась» (now, фитиль исчезает), через 10 минут после начала — скрывается; «Подключиться» открывает ссылка онлайн-платформы демо-встречи в браузере (в демо ссылка нерабочая — важен сам факт открытия и hostname в tooltip); клик по телу открывает карточку встречи с любой страницы; × скрывает до перезапуска (синтетическая встреча не ваша — isOrganizer: false, — поэтому перенос, который вернул бы напоминание, в демо недоступен). Момент старта фиксируется один раз при создании провайдера — повторные чтения диапазона не сдвигают встречу. Фиксированные демо-встречи (11:00, 14:00) тоже могут попасть в окно — тогда ближайшая показывается первой, а остальные считаются в «+N». OUTTALK_MEETING_REMINDERS=0 выключает напоминания целиком (preload-флаг, без IPC) — так идёт общий E2E; тумблер пользователя — «Настройки → Уведомления о новой почте → Напоминание о встрече». Таблица переменных — Сборка и запуск → Переменные окружения.

Системный баннер напоминания не пришёл (ADR-0098)

Когда главного окна нет (на macOS приложение остаётся в доке), напоминание показывает main — reminders/notify-meeting.ts. Отказ системы в правах на уведомления делает функцию невидимой без единой ошибки на экране, поэтому проверять приходится по журналу и по списку ниже — сверху вниз.

  1. Платформа. Функция существует только на macOS. На Windows и Linux закрытие окна завершает процесс — напоминать оттуда нечем; это не дефект сборки, а названное ограничение.
  2. Права на уведомления. Системные настройки → «Уведомления» → OutTalk: разрешены ли баннеры, не включён ли «Не беспокоить»/фокус-режим. Если Electron вообще не видит поддержки (Notification.isSupported() === false), в журнал уходит calendar · meeting reminder: notifications are not supported — это единственный след такого отказа.
  3. Журнал, канал calendar. Файл — <userData>/logs/outtalk.log (путь показан в панели диагностики). Показанный баннер: calendar · meeting reminder shown { accountId } — уровень debug, в упакованной сборке по умолчанию info, поэтому запускайте с OUTTALK_LOG=debug. Сбой планировщика: calendar · meeting reminders failed { reason, code }, где reason — что он делал (calendar refresh (timer), meeting reminders (system resume), meeting reminders (calendar changed), … (declared), … (queued)), а code — класс ошибки. Тема и место встречи в журнал не попадают никогда — только ящик и код, поэтому по журналу видно «показали/не смогли», но не «что именно».
  4. Напоминания объявлены? Объявляет их окно (mail:setMeetingReminders), и объявление живёт до выключения тумблера, смены ящика или выхода. Если окно ни разу не открывалось в этом запуске — объявления нет и напоминать не за чем. Тумблер — «Настройки → Уведомления → Напоминать о встречах за 15 минут» (notify.meetingReminders, для ящика из переключателя «Ящик» в шапке страницы); OUTTALK_MEETING_REMINDERS=0 гасит функцию целиком (окно объявит её выключенной), OUTTALK_QUIET_WINDOWS=1 глушит показ (фоновый режим E2E).
  5. Окно было в фокусе в момент наступления. Баннер по замыслу не показывается сфокусированному окну — там висит плашка. Решение принимается один раз: если в момент созревания окно было в фокусе, ключ отмечен отработанным, и системного напоминания по этой встрече уже не будет. Ключ — ящик + id + начало встречи, поэтому повторно проверить ту же встречу можно, перенеся её (начало изменилось — напомнит заново) или перезапустив приложение.
  6. Ящик — тот ли. Main напоминает за одним ящиком, последним объявленным окном. Снос или пересоздание этого ящика гасит напоминания (stopMeetingRemindersFor), и окно объявляет их заново — если окно закрыто, объявления не будет до следующего открытия.
  7. Снимок календаря. Планировщик читает локальный снимок и сам обновляет его не чаще одного раза в 10 минут (CALENDAR_REFRESH_MS). Встреча, созданная на другом устройстве менее чем за десять минут до начала, при закрытом окне может не попасть в снимок вовремя — известное ограничение (Дорожная карта). Сеть после сна ещё не поднялась — планировщик считает по старому снимку и пишет предупреждение, но не молчит.

Как отрепетировать при закрытом окне. Запустите демо-ящик со встречей через несколько минут, откройте приложение, затем закройте окно (⌘W), не выходя из приложения:

OUTTALK_DEMO=1 OUTTALK_DEMO_UPCOMING_MINUTES=3 OUTTALK_LOG=debug npx electron-vite dev

Что проверять: баннер приходит в T−15 (для встречи через 3 минуты — сразу), клик по нему поднимает окно (создаёт его заново, если окна нет) и открывает карточку встречи; повторного баннера по той же встрече нет. Тот же ensureMainWindow чинит и старое поведение: клик по уведомлению о новой почте при закрытом окне раньше не делал ничего.

Фильтр шума в консоли main (util/quietLibs.ts)

ews-javascript-api разбирает каждый SOAP-ответ через xmldom, который печатает [xmldom warning] … / [xmldom error] … даже при успешном разборе — десятки строк на одно открытие письма. src/main/util/quietLibs.ts (сайд-эффектный импорт, первой строкой в main/index.ts) патчит console.log/warn/error процесса и отбрасывает только строки с префиксом [xmldom . Всё остальное идёт в консоль как раньше.

⚠️ Если отлаживаете сам парсер SOAP — временно уберите проверку NOISE в quietLibs.ts, иначе предупреждения xmldom не увидите. Подробности — Exchange: EWS → Шум парсера.

Панель диагностики в приложении (Ctrl/Cmd+\``) — отдельный, более удобный канал: тайминги операций, waterfall трейсов, тест подключения. Она **не** идёт через console` и фильтром не затрагивается. См. Интерфейс → Панель диагностики, ADR-0033.
