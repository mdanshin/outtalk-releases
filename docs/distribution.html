Дистрибуция и обновления

Как OutTalk собирается, публикуется и обновляется. Ключевое решение — ADR-0041.

Две карты местности

Код — приватный, релизы — публичные. Автообновление скачивает файлы само, без участия пользователя, то есть без интерактивной авторизации. Приватный репозиторий отдаёт релизные ассеты только по токену — значит токен пришлось бы зашить в каждую копию приложения и тем самым раздать всем. Поэтому бинарники, фиды обновлений и лендинг живут в отдельном ПУБЛИЧНОМ репозитории mdanshin/outtalk-releases, а исходники остаются в приватном.

Обновляется само — только Windows. Не по капризу: на macOS установку обновления делает Squirrel.Mac, а он проверяет подпись и отказывается ставить сборку без Developer ID + нотаризации. Apple-сертификата у проекта нет, поэтому «автообновление» на macOS не работало бы молча — это хуже, чем его отсутствие. Windows же не требует подписи для установки (Authenticode влияет лишь на предупреждение SmartScreen).

Это различие живёт в контракте, а не в if по коду UI: UpdateState.canAutoInstall (см. src/shared/update-types.ts). Ложно → интерфейс предлагает «Скачать», истинно → «Обновить».

Отдельно от «умею ли ставить» стоит «проверяю ли вообще» — UpdateState.canCheck. Неупакованная сборка (npm run dev) не запрашивает фид: сравнивать не с чем и заменять нечего. Раньше она молча возвращалась из checkForUpdates, и карточка обновлений писала «Установлена последняя версия» — то есть не состоявшаяся проверка выглядела как успешная, а нажатие «Проверить обновления» не давало ничего. Теперь состояние говорит правду: строка «Сборка для разработки — обновления не проверяются», кнопка неактивна. Правило шире одного флага: любой ответ, кроме сравнения версий, — это ошибка, а не «у вас последняя версия» — 200 без поля version (captive portal, сломанный фид) тоже возвращает stage: 'error'.

Как это устроено

  • Контракт — src/shared/update-types.ts: UpdateState { stage, current, build, version?, notes?, percent?, canAutoInstall, canCheck, url?, error? }, где stage: idle | checking | available | downloading | downloaded | error. current — пользовательская semver, а build — точная identity исходника (short SHA, признак dirty, UTC-время сборки), запечённая electron-vite в main bundle. Она показывается в «Настройки → Разработчик → Номер сборки» (раздел виден в режиме разработчика, ADR-0155) и пишется в стартовую строку лога, поэтому две локальные сборки 0.1.8 больше нельзя перепутать.
  • main — src/main/update/updater.ts: одна машина состояний, два движка под ней.
    • electron-updater (Windows/NSIS): autoDownload = false — скачиваем только по явному действию (не съедаем чужой трафик), autoInstallOnAppQuit = true — если пользователь не нажал «Перезапустить», обновление встанет при следующем выходе. События update-available / download-progress / update-downloaded / error переводят состояние и пушатся в renderer.
    • src/main/update/checker.ts (macOS, portable): статический latest.json читается через Electron net.fetch, который уважает системный proxy (Node global fetch его игнорирует и на корпоративной сети может timeout-иться), напрямую с канонического HTTPS-домена https://outtalk.ru/latest.json, без provider redirect и возможности downgrade на HTTP; сравнение версий (isNewer), download-URL — только с наших ориджинов (safeDownloadUrl), иначе подменяем на https://outtalk.ru/. Адрес сначала канонизируется через URL, затем проверяются точные origin/owner/repository/сегменты; raw-prefix не используется, encoded separators и dot-segments закрыты.
  • IPC — src/main/ipc/update.ts: update:check, update:download, update:install, update:openDownload, update:state (все Result<T> через guarded) + push-канал update:status с UpdateState (прогресс загрузки). Renderer никогда не передаёт URL: адрес фида приходит из app-update.yml (его кладёт в сборку electron-builder по блоку publish), адрес страницы загрузки — из allowlist в main.
  • renderer — стор useUpdate (зеркалит состояние main), тост UpdateToast («Доступна версия X» → [Обновить] → прогресс → «Обновление готово» → [Перезапустить]), раздел «О программе» в Настройках (панель about.version, components/settings/AboutPanel.tsx, ADR-0155): строка «Версия» — «OutTalk <semver>» (это кнопка: семь нажатий включают режим разработчика, Настройки) и строка «Новые выпуски» — состояние и кнопка «Проверить обновления» / «Обновить до X» / «Скачать X» / «Перезапустить» с полосой загрузки; номер сборки — в разделе «Разработчик», строка «Номер сборки» (см. Сборка и запуск → Идентификация сборки). Пункт меню Справка → Проверить обновления — openSettings('about') и useUpdate.check(). Ручная команда сначала открывает «О программе» и всегда показывает ход и итог: последняя версия, найденная версия, ошибка сети/сервера либо (в dev-сборке) прямое «обновления не проверяются». Авто-проверка — через ~4 с после старта.
  • Тесты — юнит покрывает оба молчаливых случая (updater.dev.test.ts — dev-сборка ничего не запрашивает и признаётся в этом; checker.test.ts — фид без версии не выдаётся за «последнюю версию»), E2E — весь путь «обновление найдено» до тоста и кнопки «Скачать» (smoke.spec.ts) и поведение dev-сборки (dev-build-updates.spec.ts).

Выпуск релиза

# После merge PR с уже согласованными package.json + package-lock.json:
git tag -a v0.1.4 <ПРОВЕРЕННЫЙ_SHA_MAIN> -m "OutTalk 0.1.4"
git push origin v0.1.4

Дальше всё делает .github/workflows/release.yml:

  1. version проверяет, что тег, package.json и оба поля версии lockfile совпадают, а tagged commit уже входит в main.
  2. verify + electron-e2e заново запускают типы, unit, build и Electron E2E на tagged SHA в Linux, macOS и Windows. Аварийного обхода нет.
  3. build перед упаковкой принудительно пересобирает encrypted SQLite native module под Electron ABI и проверяет workspace load; после electron-builder отдельно загружает native binary именно из platform-specific packaged payload. Только затем сохраняет закрытые Actions artifacts; в публичный репозиторий на этом этапе ничего не отправляется:
    • windows-latest → NSIS + portable, плюс latest.yml (фид electron-updater);
    • macos-14 → .dmg + .zip, плюс latest-mac.yml.
  4. publish требует точный полный набор из девяти непустых файлов, создаёт скрытый draft в GitHub Releases репозитория outtalk-releases, сверяет состав и только затем делает его публичным. Падение одной платформы не оставляет частичный публичный релиз.

Название и краткие заметки публичного GitHub Release задаются в release.yml и перед каждым version-tag синхронизируются с пользовательским changelog.md; предыдущий текст релиза нельзя молча переносить на новую версию. Version-gate получает именно удалённый ref и его peeled target через git ls-remote, принимает только пару tag + ^{} и дополнительно проверяет сохранённый tag object через git cat-file: объект обязан быть аннотированным tag, напрямую указывающим на проверяемый commit. Проверка не зависит от GitHub API: installation token Actions может получить 403 Resource not accessible by integration даже при contents: read. Локальный ref после actions/checkout использовать как доказательство нельзя — checkout по event SHA нормализует его в lightweight tag. Resume-путь считает существующий draft/public release валидным только при точном совпадении tag, title, notes и полного набора assets — повторный запуск не может сохранить устаревшее описание от прежней попытки.

Имена Windows-артефактов закреплены в electron-builder.yml, а не зависят от режима публикации сборщика: OutTalk-Setup-<version>.exe для NSIS и OutTalk-<version>.exe для portable. Это важно для latest.yml, сайта, повторных запусков и совместимости с 0.1.3: локальный --publish never не должен оставлять пробелы в именах, которые GitHub publisher раньше неявно заменял дефисами. 5. verify-public-assets + verify-public без PAT анонимно скачивают все девять публичных файлов, сверяют SHA-256 каждого с закрытым кандидатом, проверяют встроенные Windows/macOS версии, а для macOS ещё подпись и содержимое DMG. 6. verify-windows-update отдельно анонимно скачивает 0.1.3, сверяет её с закреплённым публичным SHA-256 и только в следующем шаге без секретов запускает реальный переход 0.1.3 → новую версию; временные задержки CDN обрабатываются повторами. После download и до install dispatch Node сверяет cached installer с SHA-256 закрытого Windows candidate из этого же run. Уже выпущенная 0.1.3 вызывает assisted NSIS без /S, и изменить её код новым релизом невозможно: acceptance gate требует ровно один запущенный installer в точном %LOCALAPPDATA%\dms-outtalk-updater\pending, непосредственно перепроверяет PID/creation time/path/name, останавливает только этот legacy wizard и ждёт его завершения. Затем cached file копируется в runner temp, а его SHA-256 одновременно связывается с закрытым candidate и анонимно скачанным публичным asset; непосредственно перед запуском hash проверяется ещё раз, после чего те же байты запускаются с --updated /S --force-run. Начиная с 0.1.4 приложение само передаёт эти аргументы; ручная первая установка остаётся мастером. Затем отдельный gate одновременно требует версию файла 0.1.4 и отсутствие всех процессов OutTalk-Setup-*. 7. pages + verify-feed только после этих проверок собирают _site, публикуют latest.json, явно восстанавливают CNAME=outtalk.ru после очистки gh-pages и ждут, пока канонический https://outtalk.ru/latest.json без редиректа действительно начнёт возвращать новую версию. Проверка адреса mdanshin.github.io/outtalk-releases недостаточна: он может продолжать работать через домен пользовательского Pages-сайта, даже если привязка outtalk.ru потеряна.

Локальная установка не является выпуском. npm run reinstall заменяет приложение только на машине, где выполнялась команда. Релиз считается доставленным пользователям лишь после проверки опубликованного тега, полного набора .exe/.dmg/фидов, значения версии в публичном latest.json, встроенных версий опубликованных NSIS/portable/macOS артефактов и реального перехода установленной Windows 0.1.3 на 0.1.4.

Локальный fail-closed fallback без GitHub-hosted runners

Оплата или лимит GitHub Actions не должны блокировать саму возможность выпустить исправление. release.json — общий источник title/notes/version для hosted workflow и локального publisher. После ручной проверки exact main и сборки полного набора девяти артефактов команда

npm run release:local -- verify /absolute/path/to/release-assets
npm run release:local -- publish /absolute/path/to/release-assets

при --platforms=all и mac требует чистый main == origin/main, аннотированный и уже отправленный source tag на exact HEAD, согласованные package*.json/release.json, точные имена и непустые updater feeds (при --platforms=win источник сверяется с тегом, а не с HEAD, — см. «Windows-половина после того, как main ушёл вперёд» ниже). Выпуск по частям (ADR-0076): --platforms=mac публикует только пять macOS-файлов — релиз создаётся как GitHub prerelease, поэтому Windows-клиенты (electron-updater без allowPrerelease берёт releases/latest, а он prerelease не видит) продолжают обновляться с предыдущего полного выпуска, а в latest.json запись downloads.win переносится из текущего фида без изменений; --platforms=win позже дополняет тот же релиз четырьмя Windows-файлами, проверяет latest.yml, снимает флаг prerelease и обновляет фид. По умолчанию --platforms=all — девять файлов сразу. Publish сначала создаёт draft в outtalk-releases, сверяет metadata и полный набор, делает release публичным, анонимно скачивает все девять файлов и сравнивает SHA-256 с локальными кандидатами. Только затем он атомарно обновляет gh-pages, сохраняет CNAME=outtalk.ru и ждёт канонический https://outtalk.ru/latest.json без redirect. Повторный запуск принимает только exact metadata/assets; неожиданную существующую публикацию не перезаписывает.

Windows-половина после того, как main ушёл вперёд (ADR-0141). Windows-файлы собираются на другой машине и приезжают позже, чем в main появляются новые коммиты. Поэтому --platforms=win проверяет источник по тегу, а не по HEAD (validateTagSource в scripts/release-source.mjs). Какая сейчас ветка и где стоит HEAD, не важно. Выпуск пройдёт, только если выполнено всё сразу:

  • рабочее дерево чистое, origin — канонический;
  • тег аннотированный, отправлен, отправленный объект тега совпадает с локальным;
  • коммит тега — предок origin/main;
  • release.json/package.json/package-lock.json из дерева тега согласованы и совпадают с его версией; title, notes и дата выпуска тоже берутся из тега;
  • macOS-пререлиз этого тега уже опубликован: не черновик, помечен как пререлиз, заголовок совпадает с release.json тега, все пять macOS-файлов на месте;
  • тег новее текущего releases/latest и не старше версии в публичном latest.json. Иначе дописанная Windows-половина откатила бы Windows-клиентов или сайт назад. Если любой из этих указателей не прочитался, выпуск не идёт.

Тег задаётся флагом --tag (только вместе с --platforms=win; без флага берётся версия из release.json рабочего дерева):

# сборка — из дерева тега (отдельный worktree или клон)
git worktree add ../outtalk-v0.1.23 v0.1.23 && cd ../outtalk-v0.1.23 && npm ci && npm run dist:win
# публикация — из актуального main: там свежий publisher
npm run release:local -- verify /absolute/path/to/win-assets --platforms=win --tag=v0.1.23
npm run release:local -- publish /absolute/path/to/win-assets --platforms=win --tag=v0.1.23

Повторный publish --platforms=win после сбоя на поздних шагах возобновляет выпуск, а не начинает его заново. Подробно — в «Как довести выпуск после сбоя на поздних шагах» ниже. Если вышел более новый macOS-пререлиз, дописывать Windows к старому тегу нельзя: сайт уже показывает новую версию. Windows догоняет самый новый выпуск. Ограничение: electron-builder не записывает коммит в артефакты, поэтому «собрано именно с тега» проверяется только по версии в именах файлов и в latest.yml. Сборку другого коммита с той же версией в package.json publisher не отличит. Страницы сайта (site/) при любом --platforms берутся из refs/remotes/origin/main через git archive, а не из рабочего дерева: неслитая ветка или старый тег на сайт не попадут. Для --platforms=mac и all проверка прежняя, строгая (validateHeadSource). --tag с all запрещён, а с mac означает только возобновление уже опубликованного mac-пререлиза — см. «Mac-половина: довести сайт после сбоя» ниже. Покрытие — release-source.test.ts: git/gh там подменены, проверены разрешённый случай и каждый отказ.

Указатель «последний выпуск» ставится явно и проверяется с клиентской стороны. electron-updater на Windows спрашивает не тег, а https://github.com/<владелец>/outtalk-releases/releases/latest/download/latest.yml. GitHub не пересчитывает releases/latest сам, когда релиз, созданный предварительным (--platforms=mac), позже повышают до полного: 28.09.2026 из-за этого полный 0.1.19 вышел, а Windows продолжала видеть 0.1.18 и отвечала «установлена последняя версия» — она не врала, ей так сказали. Поэтому после снятия флага prerelease publisher зовёт promoteToLatest(): gh release edit <tag> --latest, затем сверка gh api repos/<owner>/outtalk-releases/releases/latest и — главное — чтение того самого releases/latest/download/latest.yml c cache-busting-параметром, до 10 попыток с паузой 3 с, пока version: в фиде не совпадёт с выпускаемой версией. Проверяем там, откуда читает клиент, а не там, где было наше намерение. При --platforms=mac указатель намеренно не трогается (if (platforms !== 'mac') await promoteToLatest()): он обязан продолжать вести на прошлый полный выпуск, иначе Windows-клиенты получат обновление, которого для них ещё нет. Покрытие — release-workflow.test.ts (source-contract: --latest, запрос releases/latest, чтение latest.yml, и что macOS-only прогон указатель не двигает).

Выпуск с Windows-машины: два подводных камня, найденные на 0.1.24. Первый — publishSite распаковывал архив страниц сайта через tar, а GNU tar в составе Git for Windows принимает путь C:\… за host:path и уходит в сеть: «tar: Cannot connect to C: resolve failed». Лечится ровно парой: --force-local и прямые слеши (с обратными тот же флаг калечит уже -C); флаг добавляется только под Windows, потому что bsdtar на macOS его не знает. Покрыто release-workflow.test.ts.

Второй подводный камень был серьёзнее: половина --platforms=win не умела возобновляться. Она требовала, чтобы релиз был macOS-пререлизом, но сама снимала этот флаг задолго до конца, до публикации сайта и проверки фида. 0.1.24 упал как раз между этими шагами, и повторный запуск отверг себя сам: «release v0.1.24 is not a macOS-only prerelease». Релиз при этом был полным и правильным, автообновление Windows уже работало, а latest.json на сайте остался прежним, и лендинг предлагал старый установщик. Теперь это закрыто путём возобновления (ADR-0141, «Возобновление Windows-половины»), см. следующий абзац.

Как довести выпуск после сбоя на поздних шагах. Publisher идёт так: проверки → загрузка → снятие пререлиза → promoteToLatest() → анонимная сверка → publishSite → verifyFeed. Если он упал после снятия пререлиза (на сайте, на фиде, на сети), запустите ту же команду ещё раз:

npm run release:local -- verify /absolute/path/to/win-assets --platforms=win --tag=vX.Y.Z
npm run release:local -- publish /absolute/path/to/win-assets --platforms=win --tag=vX.Y.Z

Publisher увидит, что релиз уже полный (windowsReleaseState → complete), и примет это, только если совпадает всё сразу:

  • релиз не пререлиз и не черновик;
  • заголовок и описание равны release.json тега;
  • ассетов ровно девять ожидаемых имён этой версии, все непустые;
  • releases/latest указывает ровно на этот тег, и клиентский latest.yml отдаёт эту версию;
  • четыре Windows-файла, скачанные анонимно, побайтно (SHA-256 и размер) совпадают с файлами в локальном каталоге.

Тогда на GitHub ничего не меняется: нет загрузки, нет снятия пререлиза, нет --latest. Publisher сразу собирает фид, публикует сайт и ждёт latest.json, а в отчёте пишет resumed: true. Любое расхождение — отказ с текстом «…refusing to resume»: тогда разбираться руками, publisher такой релиз не трогает. Отдельный случай: прошлый запуск снял пререлиз, но упал до перевода указателя. Тогда релиз полный, а latest ещё на прошлом теге, и возобновление откажет (««latest» points at …»): этот путь указатель намеренно не двигает. Здесь поможет один ручной шаг, gh release edit vX.Y.Z --repo <владелец>/outtalk-releases --latest, а затем та же команда ещё раз. publishSite идемпотентен: если gh-pages уже содержит ровно ожидаемое, он сообщает «nothing to push» и ничего не пушит, повтор не ошибка.

Каталог для возобновления можно собрать из самого опубликованного релиза, например gh release download vX.Y.Z --repo <владелец>/outtalk-releases --pattern 'OutTalk-Setup-*' --pattern 'OutTalk-X.Y.Z.exe' --pattern latest.yml --dir <каталог вне репозитория>. Тогда в каталоге должно быть ровно четыре Windows-файла и ничего больше. Это нормальный путь на машине без Windows-сборки, но честно оценивайте, что он доказывает. Сверка байтов здесь лишь подтверждает, что каталог — точная копия релиза. Проверки, независимые от каталога: latest.yml описывает именно этот .exe (размер, SHA-512, версия), имена и версия всех девяти файлов, указатель latest. То, что файлы собраны с тега, по-прежнему не проверяется (ограничение выше). Сделать сверку независимой можно руками, без изменений кода. Первый, упавший запуск напечатал в начальном отчёте assets[].sha256 файлов исходной сборки. Сравните их с assets[].sha256 из отчёта возобновления: если совпали, в релизе лежит именно то, что было собрано. Каталог держите вне репозитория: publisher требует чистое рабочее дерево.

Mac-половина: довести сайт после сбоя (ADR-0141, поправка 0.1.25). Бывает так: --platforms=mac создал и опубликовал пререлиз со всеми пятью mac-файлами, а потом упал на publishSite. Пока чинили причину, в main попал новый коммит. Обычный повтор --platforms=mac теперь отказывает: ему нужен тег ровно на HEAD, а main ушёл вперёд. Для этого случая у mac-половины есть возобновление по тегу:

npm run release:local -- verify /absolute/path/to/mac-assets --platforms=mac --tag=vX.Y.Z
npm run release:local -- publish /absolute/path/to/mac-assets --platforms=mac --tag=vX.Y.Z

--tag вместе с mac значит только «довести уже опубликованное», новый релиз так не создаётся. Проверки (validateMacResumeSource, assertMacResume в scripts/release-source.mjs) пропускают выпуск, только если совпадает всё сразу:

  • дерево чистое, origin — канонический;
  • тег аннотированный, отправлен, отправленный объект совпадает с локальным, коммит тега — предок origin/main;
  • версии в package.json, package-lock.json и release.json из дерева тега совпадают с тегом;
  • релиз тега существует, не черновик, пререлиз, заголовок и описание равны release.json тега;
  • в релизе ровно пять mac-файлов этой версии и ничего больше, все непустые;
  • пять файлов, скачанные анонимно, побайтно (SHA-256 и размер) совпадают с файлами локального каталога;
  • сайт (latest.json) не показывает версию новее тега, иначе доведение откатило бы его.

Тогда на GitHub ничего не меняется: нет загрузки, нет правки релиза, указатель «последний выпуск» не трогается (mac-половина его и так не двигает). Publisher собирает фид — mac-загрузка из этого релиза, Windows переносится из текущего фида, как обычно, — публикует сайт из origin/main и ждёт latest.json. В отчёте resumed: true. Любое расхождение — отказ с текстом «…refusing to resume». Каталог держите вне репозитория; собрать его можно и из опубликованного релиза (gh release download vX.Y.Z --repo <владелец>/outtalk-releases --pattern 'OutTalk-X.Y.Z-arm64*' --pattern latest-mac.yml --dir <каталог>), но тогда сверка байтов подтверждает лишь, что каталог — копия релиза (то же ограничение, что у Windows-половины выше). Windows-половину потом дописывают обычной командой --platforms=win --tag=vX.Y.Z.

Перед запуском — чистое дерево. Publisher требует строго пустой git status --porcelain, и выходит это чаще всего не из-за правок, а из-за мусора рядом: пустой .hermes-tmp.*, забытый архив с бренд-мастерами, переименованный бэкап сборки вроде release-0.1.15-old на сотни мегабайт. .gitignore закрывает release и release-*/, остальное убирается руками ДО запуска. Сами артефакты держите ВНЕ репозитория — каталог внутри дерева сам становится таким мусором.

Локальный fallback не превращает macOS в Windows test runner: отсутствие Windows E2E и реального updater migration должно быть явно принято ответственным за выпуск и записано в release report. Windows-кандидат можно собрать независимо в pinned electronuserland/builder:wine container; его packaged version/native payload всё равно проверяются отдельно до передачи publisher. Hosted matrix остаётся предпочтительным полным gate, когда runners доступны.

⛔ С 2026-09-18 они недоступны, и это не временно (ADR-0068): hosted-раннеры GitHub Actions недоступны, release.yml живёт на тех же Actions и по тегу не запустится. Значит описанный здесь локальный publisher — не резерв, а действующий путь выпуска, а перечисленные им ручные проверки (exact main, сборка девяти артефактов, отдельный Windows-кандидат) перестают быть исключением. Отсутствие Windows E2E и реального updater migration по-прежнему должно быть явно принято ответственным за выпуск и записано в release report — теперь это будет в каждом выпуске. Что именно закрывается локально до релиза — раздел «Локальная проверка вместо CI» в Процессе разработки; npm audit signatures на машине сборки обязателен и здесь — publisher его не запускает. Полный замер скорости почты publisher тоже не запускает; с 2026-10-08 он не обязателен перед выпуском — см. «Перед выпуском: скорость почты» ниже.

Почему PAT, а не GITHUB_TOKEN. Штатный secrets.GITHUB_TOKEN имеет права только на репозиторий, где выполняется workflow. Мы же пишем в другой репозиторий (outtalk-releases), поэтому нужен персональный токен — секрет RELEASES_TOKEN (fine-grained, только на outtalk-releases, права Contents: Read and write). Он же используется и для релиза, и для деплоя Pages.

Перед выпуском: скорость почты (ADR-0148)

С 2026-10-08 этот шаг не обязателен (ADR-0148, поправка): перед выпуском достаточно зелёного npm run test:unit (в нём бюджет запросов) и, при желании, короткого npm run perf:quick -- S1,S2,S4. Полный прогон ниже — только по просьбе владельца; если он запущен, правила его чтения те же.

PERF_OUT=perf-results/release-X.Y.Z.json npm run perf   # ~1,5–2 ч; сборка + все сценарии при 0/80/300 мс
node scripts/perf-compare.mjs perf-results/release-X.Y.Z.json perf-results/after.json --strict
  • Прошлый результат — perf-results/after.json в репозитории: последний принятый полный прогон. Без PERF_OUT отчёт ляжет в perf-results/latest.json — тогда его и передайте в perf-compare. Отчёт кандидата (release-*.json) в репозиторий не попадает (perf-results/* в .gitignore), поэтому дерево для publisher остаётся чистым.
  • --strict — перед выпуском отчёт обязан быть полным: сценарий или задержка из after.json, которых нет в отчёте кандидата (остался PERF_SCENARIOS от короткого замера, сценарий упал), — тоже код 1, а не «регрессий нет».
  • Код 0 — выпускать. Код 1 — медиана выросла больше чем на 5 % (и 10 мс), запросов на действие или «не появилось» стало больше: выпуск ждёт, пока причину не найдут и не исправят, либо пока рост не обоснован письменно в ADR (тогда это обоснование цитируется в отчёте о выпуске).
  • Другая машина. Цифры after.json сняты на машине владельца; на другой сначала снимите «было» на теге прошлого выпуска той же командой и сравнивайте с ним.
  • Обновить точку отсчёта. Если кандидат быстрее и выпуск состоялся, его отчёт можно сделать новым after.json отдельным коммитом после выпуска — осознанно, с таблицей сравнения в описании; молча подменять «было», чтобы сравнение прошло, нельзя.
  • В отчёт о выпуске — вывод perf-compare (таблица по задержкам) и машина, на которой снят прогон.

Что владелец делает руками (один раз)

  1. Создать публичный репозиторий mdanshin/outtalk-releases (пустой, можно с README).
  2. Завести fine-grained PAT: Repository access → только outtalk-releases; Permissions → Contents: Read and write; срок жизни — конечный, с напоминанием о продлении.
  3. В приватном репозитории кода: Settings → Secrets and variables → Actions → New repository secret → имя RELEASES_TOKEN, значение — этот PAT.
  4. В outtalk-releases: Settings → Pages → Source: Deploy from a branch → ветка gh-pages, папка / (root), Custom domain → outtalk.ru. (Ветку создаст первый успешный прогон workflow — включить Pages можно после него.) Workflow также передаёт cname: outtalk.ru, поэтому каждая полная очистка/публикация ветки восстанавливает доменную привязку.
  5. После зелёных проверок точного объединённого SHA создать явный аннотированный тег по процедуре выше (git tag -a vX.Y.Z <verified-main-SHA> ..., затем отправить только этот тег) и проверить: в outtalk-releases появился Release с .exe/.dmg/latest.yml/latest-mac.yml, а лендинг и фид без редиректа открылись на https://outtalk.ru/ и https://outtalk.ru/latest.json. npm version patch здесь не используется.

Право записи в outtalk-releases = право доставить произвольный код всем пользователям Windows (см. ниже). Держите список коллабораторов этого репозитория пустым и не переиспользуйте PAT.

Подпись: чего нет и что из-за этого происходит

Windows (SmartScreen). Сборка не подписана (нет Authenticode). При первой установке Microsoft Defender SmartScreen скажет «Windows защитила ваш компьютер» / «Неизвестный издатель»: Подробнее → Выполнить в любом случае. Это ожидаемо и на автообновление не влияет — обновление ставится тем же установщиком без нового предупреждения.

Целостность vs подлинность. Без подписи electron-updater проверяет SHA512 из latest.yml, скачанного по HTTPS. Файл не подменить и не повредить в пути — но издатель не подтверждён: доверие держится на том, что latest.yml лежит в нашем репозитории. Отсюда риск, зафиксированный в Безопасности и ADR-0041: кто получил запись в outtalk-releases, тот выполняет код у каждого пользователя.

macOS (Gatekeeper). Apple Developer ID нет, поэтому:

  • Ad-hoc подпись. Хук build/afterPack.cjs после упаковки сначала переключает Electron Fuses (см. Безопасность → Предохранители сборки), затем выполняет codesign --force --deep --sign - OutTalk.app. Без неё скачанное приложение macOS считает «damaged and can't be opened»; валидная ad-hoc подпись превращает это в мягкое «неизвестный разработчик».
  • Первый запуск: правый клик по OutTalk.app → Open → Open. Дальше — как обычно.
  • Если всё же «damaged»: 
    xattr -dr com.apple.quarantine /Applications/OutTalk.app
codesign --force --deep --sign - /Applications/OutTalk.app

⚠️ Косметика DMG на CI. Оформление окна .dmg electron-builder задаёт через Finder, что не работает на headless-раннере → CI-сборка даёт дефолтное окно. Красивый .dmg при желании собирается локально (npm run dist:mac) и заливается в релиз поверх CI-ассета.

Когда появится подпись

  • Authenticode (Windows). Добавить сертификат в win.certificateFile/CSC_LINK — SmartScreen перестаёт пугать, обновление начинает проверять и издателя, а не только хеш. Код в updater.ts не меняется.
  • Developer ID + нотаризация (macOS). Снять identity: null, включить notarize — после этого macOS переходит на тот же electron-updater (фид latest-mac.yml уже публикуется), а checker.ts остаётся только для portable. В updater.ts меняется одна функция — autoInstallSupported().
  • Свой сервер обновлений (S3/Nginx, провайдер generic) — альтернатива публичному репо: меняется только блок publish в electron-builder.yml.

Иконки релиза

Иконки, попадающие в артефакты (.dmg/.app, NSIS/portable .exe), генерируются, а не редактируются: build/icon.png (512×512) и build/icon.icns собираются из бренд-мастеров build/brand/ скриптом python build/make-icons.py. Windows .ico electron-builder выводит из icon.png сам. Правка знака = правка мастеров в build/brand/vector/*.svg → повторный экспорт PNG → make-icons.py → коммит сгенерированных icon.png/icon.icns. Подробнее — Сборка и запуск → Бренд и иконки.

Лендинг

site/ — статическая страница в стиле приложения; кнопка «Скачать» тянет latest.json. Деплоится workflow'ом в gh-pages репозитория outtalk-releases (публичный — Pages на приватном репо в бесплатном плане недоступны) и публикуется на каноническом домене https://outtalk.ru/. Там же лежит latest.json — фид уведомлений для macOS/portable.

Раздел «Документация» на сайте (ADR-0166)

С ADR-0166 документация в приложение не входит — она публикуется разделом сайта https://outtalk.ru/docs/ при каждом выпуске, а раздел «Документация» в приложении показывает её онлайн. На лендинге — ссылки «Документация» в шапке и в подвале (site/index.html → docs/).

Публикует publishSite в scripts/publish-local-release.mjs:

  1. git archive из вершины refs/remotes/origin/main берёт не только site/, но и DOCS_SITE_SOURCES — scripts/docs-site, scripts/check-public-content.mjs, src/renderer/src/content/docs, src/renderer/src/content/docs-manifest.json. Как и лендинг, документация на сайте — из origin/main на момент выпуска, а не из тега: это документация последнего выпуска, а не той версии, что установлена у конкретного человека.
  2. В распакованное дерево ставится ссылка на node_modules рабочего дерева (тип junction, чтобы работало и на Windows) — генератору нужны отрисовщик Markdown и подсветка из devDependencies.
  3. Запускается scripts/docs-site/build.mjs --root=<дерево> --out=<папка>; если на машине есть .public-content.local.json, его путь уходит генератору в OUTTALK_PUBLIC_CONTENT_RULES. Генератор сканирует всё сгенерированное и падает на находке — выпуск останавливается до пуша в gh-pages.
  4. Результат (лендинг + docs/) копируется в checkout gh-pages, дальше как раньше: CNAME, latest.json, коммит и пуш.

Приложение читает с сайта только docs/data/v1/manifest.json и docs/data/v1/<slug>.json (формат версионирован, DOCS_DATA_VERSION = 1); несовместимое изменение генератора требует новой версии формата и её поддержки в приложении — иначе уже установленные копии перестанут показывать документацию. Проверить сайт до выпуска — npm run docs:preview. Подробности генератора — Сборка и запуск, раздел «Документация на сайте, а не в сборке».
