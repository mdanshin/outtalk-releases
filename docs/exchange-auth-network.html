Exchange: аутентификация и сеть

Этот раздел описывает, как OutTalk устанавливает и авторизует соединение с Exchange, и почему сделаны конкретные выборы. Всё это реализовано в src/main/providers/exchange/ews.ts.

XHR-слой для Node

ews-javascript-api изначально писалась под браузер и требует реализацию XHR. В Node её даёт точно закреплённый @ewsjs/xhr@3.1.3 (класс XhrApi, транспорт Axios; версия Axios закреплена overrides.axios = 1.20.0 в package.json, ADR-0140). ConfigurationApi.ConfigureXHR вызывается для совместимости, затем тот же новый account-bound XHR немедленно закрепляется на конкретном ExchangeService.XHRApi; последующая глобальная конфигурация другого аккаунта его не заменяет:

const options = {
  proxy: creds.useSystemProxy ? undefined : false, // см. «Прокси»
  rejectUnauthorized: !creds.ignoreCertErrors,     // XHR строит TLS-agent с этим флагом,
  timeout: 30_000                                  // ЕДИНСТВЕННЫЙ работающий таймаут (дефолт;
}                                                  // GetAttachment — 12 с, пакет картинок — 30 с, см. «Таймауты»
// opt-in keep-alive только для Basic/direct/trusted TLS (см. ниже)
if (process.env.OUTTALK_KEEPALIVE === '1' && scheme !== 'ntlm' && !creds.useSystemProxy && !creds.ignoreCertErrors) {
  options.httpsAgent = keepAliveAgent(true)
}
const xhr = new GatedXhrApi(options)   // подкласс XhrApi: каждый запрос — через шлюз (ADR-0038)
if (scheme === 'ntlm') xhr.useNtlmAuthentication(creds.username, creds.password)
ConfigurationApi.ConfigureXHR(xhr) // compatibility default
service.XHRApi = xhr               // request authority: per service/account

Транспорт: шлюз параллелизма — не больше 4 запросов одновременно (ADR-0038)

Проблема (снята с живого лога, Exchange 2016 / published). Ящик переставал грузиться. В outtalk.log: 7 операций стартуют за секунду, пик — 13 одновременных сокетов, 28 за минуту. Часть запросов отвечает за 130–760 мс, остальные не отвечают вообще и умирают ровно на 30 000 мс (наш timeout). Таймаутил не только жирный GetItem, но и дешёвый GetFolder — значит дело не в объёме данных, а в числе одновременных подключений: on-prem Exchange (или прокси перед ним) обслуживает несколько, а лишние паркует до бесконечности.

В тех же замерах tlsSessionReused: false означал только отсутствие TLS session resumption на новых соединениях. Это не проверка HTTP keep-alive: повторно используемый pooled socket не делает нового TLS-рукопожатия. Шлюз ограничивает всплеск независимо от pooling; фактический socket reuse проверяется по socket open на запрос и отдельным live-gate.

Решение — семафор на уровне HTTP-запроса (main/providers/exchange/gate.ts + подкласс GatedXhrApi в ews.ts):

export const EWS_MAX_CONCURRENT = 4              // эмпирика живого сервера, не «настройка скорости»
export const EWS_MAX_SOCKETS = EWS_MAX_CONCURRENT + 2   // пул ШИРЕ шлюза — иначе он второй, невидимый лимитер

class GatedXhrApi extends XhrApi {
  xhr(o, p)       { return withGate((ticket) => super.xhr(o, p)) }  // все SOAP-вызовы + Autodiscover; ticket = { lane, queueMs }
  xhrStream(o, p) { /* слот освобождается по приходу заголовков */ }
}

Почему именно на XHR, а не на методах провайдера: библиотека гонит через xhr() всё (ServiceRequestBase, AutodiscoverService), поэтому под лимит по построению попадают FindItems, Bind, каждая FileAttachment.Load() inline-картинки и Autodiscover. Шлюз на методах оставил бы fan-out внутри getMessage без ограничения — а это один из двух источников всплеска.

  • Полосы (ADR-0144; до него — двухуровневая очередь high/low). Три очереди, разбираются строго по порядку: interactive → live → background, внутри полосы — кто дольше ждёт. Общий лимит остаётся 4; полосы решают только, кому отдать следующий слот:

    ПолосаЧто в нейСколько слотов может занять
    interactiveоткрыть письмо, картинки, ответ, отправка, «прочитано», перемещение, удаление; умолчание для всего, что не объявило себя иначевсе 4
    liveсводка нового письма из потока (watch:new_mail), подписка/переподписка потока, точечная проверка одной папкиlive + фон вместе ≤ 3 (NON_INTERACTIVE_MAX_SLOTS = EWS_MAX_CONCURRENT − 1)
    backgroundревалидация списка и папок после показа снимка, опрос (watch:poll), поиск базы наблюдения, прогрев (warm_*), «Письма от этого человека»≤ 2 (BACKGROUND_MAX_SLOTS)

    Итог: один слот всегда остаётся клику, а фон не может занять больше половины шлюза. Быстрый путь acquire берёт слот сразу, только если в своей и более срочных полосах никто не ждёт и лимит полосы позволяет; иначе запрос встаёт в очередь своей полосы, и pump() раздаёт освободившиеся слоты по порядку полос с учётом лимитов. Голодание background при активном пользователе — намеренно. Снимок по полосам — gateLaneStats().

    Полоса едет в ALS-контексте рядом с traceId (diag/als.ts), поэтому сигнатуры MailProvider не меняются. API:

    // новая операция в своей полосе (трасса, счётчики, итоговая строка op │ … — done)
runWithTrace(name, fn, windowId?, lane: 'interactive' | 'live' | 'background' = 'interactive')
// часть ТЕКУЩЕЙ операции в другой полосе: traceId и счётчики сохраняются
withLane('background', () => refresh())

    Прежние имена high/low принимаются (laneOf) и означают interactive/background. Фоновый прогрев помечается renderer'ом (Mail.message(id, background) → IPC → runWithTrace('warm_message', …, 'background')); ревалидация после снимка — withLane('background', refresh) в local-data/mail-load.ts.

  • Без дедлоков. Слот держится вокруг одного листового запроса и никогда — пока ждут другой запрос под шлюзом. Инвариант: не оборачивать в withGate составные операции провайдера.

  • Streaming (xhrStream, push новой почты): его промис резолвится только по окончанию подписки, поэтому слот освобождается по приходу заголовков — сервер давится установкой соединений, а не их существованием.

  • Наблюдаемость: ожидание > 100 мс → gate │ queued { waitedMs, lane, inFlight, queued }. Кроме того, шлюз отдаёт запросу «билет» GateTicket { lane, queueMs }, и каждая строка запроса (ADR-0144) выглядит так:

    req │ GetItem │ {ms, queueMs, lane, attempt, n, status, reqBytes, respBytes}

    ms — время ответа сервера, queueMs — сколько запрос ждал слот шлюза, lane — полоса, attempt — номер попытки (withRetry ставит его через withAttempt), n — сколько id назвал запрос (soapBatchSize: считаются только имена элементов ItemId/AttachmentId/FolderId/DistinguishedFolderId, сами id не читаются; тела больше 256 КБ не сканируются). Строка — debug (в файл упакованной сборки попадает только при «Подробном журнале» или если запрос медленнее 1,5 с / упал — тогда warn). Транспорт заодно копит счётчики в контексте операции (noteRequest, noteRetry), и операция заканчивается одной строкой op │ <имя> — done │ {ms, reqs, serverMs, queueMs, retries, lane, status[, code]} — как читать, см. Отладка.

Со стороны renderer прогрев тоже стал скромнее (Интерфейс, useMail.startWarm): один последовательный воркер (было 2+1), старт через 800 мс, пауза 250 мс между элементами, горизонт 12 писем / 6 тредов.

Транспорт: опциональный keep-alive Agent (ADR-0034)

История. Старый @ewsjs/xhr использовал request; после перехода на @ewsjs/xhr@3.1.3 транспортом стал Axios. Первоначальный диагноз «каждый раунд = новое соединение» опирался в том числе на tlsSessionReused, но этот флаг характеризует только новые TLS-соединения и сам по себе не доказывает HTTP socket reuse.

Решение. Для прямого Basic HTTPS с доверенным сертификатом реализован https.Agent({ keepAlive: true }) (keepAliveAgent() в ews.ts), который Axios получает как httpsAgent только при OUTTALK_KEEPALIVE=1. По умолчанию собственный агент выключен после live-наблюдений мёртвых pooled sockets. При ignoreCertErrors=true приложение свой агент не создаёт: @ewsjs/xhr@3.1.3 заменяет его permissive-TLS агентом; прокси и NTLM также управляют транспортом сами. Legacy agent, strictSSL и request-specific gzip не передаются: актуальны Axios httpsAgent и rejectUnauthorized. При opt-in пул имеет maxSockets = EWS_MAX_SOCKETS (6) и keepAliveMsecs: 10000; фактический reuse остаётся release-gate.

Keep-alive и шлюз — разные свойства. Шлюз всегда ограничивает нагрузку. Если opt-in пул включён, maxSockets держится чуть выше EWS_MAX_CONCURRENT, чтобы агент не создавал вторую невидимую очередь. Наличие свободного сокета делает reuse возможным, но не доказывает, что сервер/инфраструктура позволили его.

Диагностика соединений (ADR-0149)

Вопрос. В журнале живого Exchange одиночный GetAttachment на 2 КБ занимал ~1,15–1,4 с, если уходил сразу (queueMs:0), и ~80–100 мс, если сначала ждал в шлюзе. Гипотеза: медленные открывают новое соединение (TCP + TLS, возможно через прокси или VPN), быстрые едут по живому сокету, который только что освободил другой запрос. По умолчанию своего агента нет — работает https.globalAgent Node (keep-alive, простой сокета ~5 с).

Как отвечаем — без смены поведения (exchange/socket-probe.ts). GatedXhrApi.xhr выполняет вызов библиотеки внутри withSocketProbe(probe, …). Модуль подписан на каналы диагностики Node http.client.request.created (до сокета) и http.client.request.start; через AsyncLocalStorage подписчик узнаёт свой EWS-запрос и игнорирует все остальные запросы процесса. Получив сокет, он смотрит ClientRequest.reusedSocket; у нового сокета засекает события lookup, connect и secureConnect. В строку журнала req (socketFields) добавляются:

ПолеЗначение
socketnew — новое соединение, reused — живое повторно
dnsMsтолько для new и только если имя разрешалось (у адреса-IP поля нет): от начала запроса до разрешённого имени — медленный резолвер виден отдельно от TCP
connectMsтолько для new: от начала запроса до установленного TCP (вместе с разрешением имени)
tlsMsтолько для new: от начала запроса до готового TLS

Раз в минуту, если запросы были, — одна строка уровня info:

transport │ connections {new, reused, handshakeMedianMs, handshakeMaxMs}

handshakeMedianMs/handshakeMaxMs — по tlsMs новых соединений за минуту (до 512 замеров); пустая минута не пишется. Ни хостов, ни адресов, ни портов, ни заголовков — журнал можно пересылать. Среда без нужного канала просто даёт меньше диагностики.

Чтение по режимам. Basic без прокси с проверкой сертификата — основной случай (https.globalAgent), видны и new, и reused. NTLM — библиотека создаёт свой агент на каждый запрос, проба видит первый запрос рукопожатия: всегда new. ignoreCertErrors — агент без keep-alive на каждый запрос: всегда new. С системным прокси времена описывают участок до прокси — с остальными не сравнивать. Потоковые подписки (xhrStream) пробой не обёрнуты и в сводку не входят.

Агент, keep-alive и пул не менялись: это только измерение. Следующий шаг — рассмотреть отдельным ADR собственный keep-alive агент по умолчанию для Basic, без прокси и с проверкой сертификата (то, что сейчас OUTTALK_KEEPALIVE=1; maxSockets = EWS_MAX_SOCKETS), и только после живых данных: журнал должен показать socket=new с tlsMs около секунды у медленных запросов и reused у быстрых, а живой прогон с OUTTALK_KEEPALIVE=1 — отсутствие «припаркованных» соединений (ADR-0038). Дополнительные условия из ADR-0149: потоковые подписки — на отдельном агенте (или пул учитывает их число), явный простой свободного сокета короче таймаута IIS и прокси (keepAliveMsecs — интервал TCP-проб, не простой), NTLM, системный прокси и ignoreCertErrors — на прежнем пути, выключатель остаётся. Что прислать — Отладка → Соединения с Exchange.

Таймауты: общий 30 с, GetAttachment — 12 с (ADR-0039)

service.Timeout в ews-javascript-api — no-op: библиотека не переносит его в транспорт. Без timeout в опциях XHR/Axios у EWS-вызова нет таймаута вообще, и «припаркованный» сервером запрос висит. При opt-in pooling он также удерживает сокет. Поэтому timeout задаётся там, где его реально соблюдают. Важный порядок: шлюз ждёт слот до выдачи запроса, поэтому ожидание в очереди не съедает таймаут. Само ожидание в очереди с ADR-0084 ограничено «шлюз не выдал ни одного слота 45 секунд»: запрос со слотом живёт не дольше транспортного таймаута, поэтому более долгое ожидание означает утёкший слот — и вечный спиннер заменяется ошибкой с повтором.

ЧтоТаймаутПочему
Все операции по умолчанию30 с (EWS_TIMEOUT_MS)покрывает и записи (CreateItem/UpdateItem/SendItem с вложениями). Записи withRetry не повторяет, поэтому обрывать их рано опасно: письмо может уйти, а ответа мы не увидим
GetAttachment12 с (EWS_ATTACHMENT_TIMEOUT_MS)замер: успешный GetAttachment отвечает за ~400 мс, а неуспешный не отдаёт ни байта и умирает на полных 30 с. Ждать 30 с чёрную дыру — значит потерять картинку и задержать письмо; 12 с (×25 запаса) превращают это в «повтор, который работает»
GetAttachment с несколькими AttachmentId (пакет картинок письма, ADR-0145)30 с (EWS_ATTACHMENT_BATCH_TIMEOUT_MS)пакет несёт до 8 МБ заявленного размера: бюджет одной картинки оборвал бы честный большой пакет. Ждать его некому — текст письма уже на экране, а упавший пакет отдаёт каждую картинку одиночному 12-секундному пути. Распознаётся по телу запроса: opOverrideFor(soap, body) считает <t:AttachmentId
GetStreamingEvents (висящий, streaming)90 с (EWS_STREAM_TIMEOUT_MS)бюджет длиннее серверного heartbeat (45 с). Axios abort обычно приходит как ECONNABORTED; packaged heartbeat/reset behavior остаётся live-gate. См. Streaming subscription, ADR-0043

Что timeout у Axios значит для этого адаптера. Это transport timeout запроса; точная семантика отличается от прежнего request idle-timeout. Локальный runtime-тест подтверждает срабатывание таймаута, три повтора чтения и итоговую классификацию ECONNABORTED как network. Специальные 12/90-секундные attachment/streaming пути и поведение на живом Exchange остаются обязательным release-gate, а не объявляются уже доказанными.

Как задан per-request таймаут. У @ewsjs/xhr per-request-ручки нет: его xhr() собирает Axios options заново (url/body/headers/method) и мержит поверх них this.requestOptions (getOptions) — что ни положи во входящие опции, оно потеряется. Единственный шов — сам requestOptions: GatedXhrApi.withOpOptions(override, fn) подменяет в нём timeout по SOAP-операции (переопределение выбирает opOverrideFor(soap, body): имя операции, а для GetAttachment ещё и число AttachmentId в теле, ADR-0145) и восстанавливает значение в finally. Мерж синхронен: getOptions отрабатывает внутри super.xhr до возврата управления, Axios получает уже смерженный объект, поэтому параллельный вызов подменённого значения не видит.

⚠️ Расширяя OP_TIMEOUT_MS, помните: укорачивать таймаут можно только идемпотентным чтениям, которые повторяет withRetry. Для записи короткий таймаут не «ускоряет ошибку», а создаёт неопределённость («отправилось или нет»).

Классификация ошибок: Axios ECONNABORTED и legacy-совместимость

Две ловушки транспорта, обе стоили нам повторов (ADR-0038):

  1. @ewsjs/xhr реджектит не Error, а голый объект-«ответ» ({ status, statusText, message, responseText, … } — см. его setupXhrResponse). String(e) даёт "[object Object]", и любая классификация ошибки молча ломается. Поэтому текст ошибки собирает errText(e) — из code/message/statusText/status; на нём держатся toMailError, withRetry и ENDPOINT_DEAD.
  2. Старый request рапортовал «ответа не было» как ESOCKETTIMEDOUT; Axios обычно использует ECONNABORTED/timeout ... exceeded. Классификатор сохраняет оба семейства до подтверждённой миграции всех живых путей; регулярка транзиентности раньше не ловила старый код → "transient":false → «giving up» с первой попытки вместо повтора. Теперь он в списке явно. Повтор READ-операции после таймаута безопасен: GetItem/FindItem/GetFolder/GetAttachment идемпотентны и не помечают письмо прочитанным. Записи (send/move/delete) в withRetry не заворачиваются никогда.

Вводился аккуратно, инварианты сохранены:

  • TLS не ослаблен. rejectUnauthorized = !ignoreCertErrors остаётся единственным источником TLS-политики. Собственный keep-alive агент создаётся только при opt-in и только для trusted Basic direct; permissive TLS использует внутренний агент @ewsjs/xhr без заявления о pooling.
  • NTLM управляет своим соединением. Приложение не передаёт собственный агент; @ewsjs/ntlm-client@3.0.1 создаёт connection-oriented keep-alive агент для handshake. Полный challenge-response остаётся живым release-gate.
  • Прокси — без нашего агента. При useSystemProxy Axios/@ewsjs/xhr выбирает proxy transport; собственный агент мог бы обойти или сломать проксирование.
  • Изоляция аккаунтов. ConfigurationApi.ConfigureXHR задаёт только compatibility default библиотеки; каждый ExchangeService синхронно получает свой XHRApi до первого запроса. Regression удерживает реальный локальный HTTP-запрос sync A открытым, переключает default на foreground B с другими endpoint/credentials/proxy/TLS и после переключения запускает второй запрос A. Серверы проверяют endpoint и Basic Authorization, а test-only wire-marker — какой XHR фактически создал запрос; A сохраняет transport authority на весь lifecycle.

Локальные тесты подтверждают конфигурацию поддерживаемых путей и runtime timeout/stream disconnect. Фактическое повторное использование сокета, proxy, self-signed TLS и полный NTLM handshake остаются release-gates на контролируемом сервере.

Тест подключения (рунбук diagnose.ts)

src/main/providers/exchange/diagnose.ts реализует опциональные describeConnection/diagnoseConnection контракта (Модель провайдеров) — упорядоченный рунбук на «сырых» node:dns/node:net/node:tls + EWS, где каждый шаг тайм-боксирован, так что один сбой не вешает панель.

Эффективный EWS URL — то, вокруг чего строится весь рунбук:

creds.ewsUrl (явный)  →  resolvedUrl (сохранённый результат Autodiscover, ADR-0037)  →  шаг «Autodiscover»

Шаги:

  1. Autodiscover (поиск EWS URL) — свой таймаут AUTODISCOVER_TIMEOUT = 30 000 (не 8 с!). skip, если URL задан явно или уже сохранён (в detail — какой). Дольше AUTODISCOVER_SLOW = 3000 → warn с подсказкой прописать URL явно. Найденный URL возвращается провайдеру колбэком onResolved — тест прогревает кэш, а не выбрасывает результат.
  2. DNS — dns.lookup по хосту эффективного URL.
  3. TCP — net.connect к host:port; > 300 мс → warn (высокий RTT множится на каждый раунд).
  4. TLS — tls.connect, протокол + субъект/срок сертификата; недоверенный серт → fail/warn по rejectUnauthorized.
  5. Проба возобновления TLS-сессии — второе отдельное рукопожатие с сохранённой сессией (tls.connect({ session })): isSessionReused() показывает поддержку TLS session resumption, но не доказывает HTTP keep-alive или повторное использование одного pooled socket. Поведенческая проверка socket reuse остаётся отдельным release-gate.
  6. Авторизация/EWS-раунд — buildService(creds, effective) + FindFolders(Inbox) (лёгкий GetFolder), STEP_TIMEOUT = 8000; заодно снимает версию сервера в ConnectionInfo.

Каждый шаг несёт status/durationMs/detail/hint; из них провайдер (а не renderer) синтезирует вердикт (verdictOf, узкое место). Все поля несекретны — только host, тайминги, коды, cert CN/срок, версия сервера (никогда паролей, тел, id); URL всегда проходит через safeUrl() (срезает userinfo/query).

⚠️ Исторический баг (исправлен). Хост брался только из creds.ewsUrl. У учётки на Autodiscover его нет → шаги DNS/TCP/TLS и проба TLS session resumption молча пропускались, а сам Autodiscover, спрятанный внутри шага авторизации, съедал его 8-секундный бюджет и рапортовал ложный timeout. То есть тест был бесполезен ровно там, где он нужен. Теперь Autodiscover — отдельный честный шаг со своим бюджетом, а сетевая фаза всегда гоняется по эффективному URL.

Изоляция XHR в тесте. buildService вызывает ConfigurationApi.ConfigureXHR только как compatibility default и закрепляет тот же XHR на возвращаемом ExchangeService. Поэтому диагностика и почтовые вызовы разных аккаунтов не могут заменить transport уже созданного сервиса. При opt-in keep-alive объект агента кэширован по rejectUnauthorized; это сохраняет возможность использовать его пул, но сама TLS-проба HTTP reuse не измеряет.

Точечную детализацию сетевых фаз внутри провайдера даёт main-side хелпер span(...) из diag/trace — например span('Autodiscover', 'autodiscover', …) вокруг AutodiscoverUrl, чтобы медленный/падающий Autodiscover был виден в хронологии. Подробнее об инструментации — ADR-0033, Модель провайдеров → Инструментация.

Аутентификация

Exchange-фронтенд (IIS) обычно предлагает несколько схем. Пример заголовков 401 от реального сервера:

WWW-Authenticate: Basic realm="mail.company.com"
WWW-Authenticate: Negotiate
WWW-Authenticate: NTLM

OutTalk поддерживает Basic и NTLM.

Basic (по умолчанию, рекомендуется)

Логин/пароль передаются в заголовке Authorization: Basic <base64> по HTTPS (то есть в зашифрованном канале). Реализуется через WebCredentials:

service.Credentials = new WebCredentials(creds.username, creds.password)

NTLM

Challenge-response без передачи пароля. Обрабатывается XHR-слоем (xhr.useNtlmAuthentication(...)).

NTLM в XHR 3.x. @ewsjs/ntlm-client@3.0.1 вычисляет NT-хэш через js-md4, поэтому сам transport больше не требует OpenSSL legacy provider. Basic по HTTPS остаётся путём по умолчанию. Полный NTLM challenge/type1/type2/type3 в packaged Electron должен быть подтверждён живым release-gate до объявления совместимости новой цепочки.

Обязательный WebCredentials даже для NTLM

ews-javascript-api внутренне проверяет service.Credentials и бросает Credentials are required to make a service request, если он null — даже когда авторизацию по факту делает XHR-слой (NTLM). Поэтому WebCredentials устанавливается всегда:

// baseService()
service.Credentials = new WebCredentials(creds.username, creds.password)

Для NTLM фактический handshake всё равно ведёт XHR-слой; WebCredentials лишь снимает внутреннюю проверку.

Определение EWS URL

Явный URL (рекомендуется)

service.Url = new Uri('https://mail.company.com/EWS/Exchange.asmx')

Только https:// (ADR-0064). WebCredentials шлёт Basic превентивно, поэтому http://-эндпоинт означал бы пароль открытым текстом на каждом запросе. Адрес проверяется общей чистой функцией main/util/service-url.ts → validServiceUrl (https: без userinfo/query/fragment; http: — только для loopback localhost/127.0.0.1/[::1], под локальный стаб и E2E) на двух границах: при сохранении учётки (accounts/secrets.ts → isCredentials/validEwsUrl; пустая строка = Autodiscover) и в точке использования — buildService бросает MailError('EWS URL должен начинаться с https://.', 'network') до new Uri(explicit), так что подменённый на диске account-secrets.json не обходит проверку. mail:accounts:test/add валидируют форму до первого сетевого запроса; подсказка в форме аккаунта («Только https:// — по http:// пароль ушёл бы в сеть открытым текстом») объясняет отказ пользователю. Тесты: util/service-url.test.ts, accounts/secrets-ews-url.test.ts.

Autodiscover (ограниченно, с кэшем URL)

Если URL пуст, делается попытка Autodiscover по email:

await service.AutodiscoverUrl(creds.email, url => allowAutodiscoverRedirect(url, creds.email))

⚠️ В ews-javascript-api Autodiscover реализован не полностью — часто бросает Not implemented. Практическое правило: задавайте EWS URL вручную. Типовые варианты для домена company.com: https://mail.company.com/EWS/Exchange.asmx, https://webmail.company.com/…, https://autodiscover.company.com/….

Политика редиректов Autodiscover — это про безопасность, а не про удобство

Колбэк вызывается перед тем, как последовать редиректу, и следует за ним с кредами аккаунта. Библиотека по умолчанию редиректы Autodiscover запрещает вовсе; мы ослабляем это, но только внутри домена учётки:

// ews.ts
export function allowAutodiscoverRedirect(url: string, email: string): boolean {
  // https + host === domain(email) ИЛИ host.endsWith('.' + domain)
  // (покрывает autodiscover.<домен> и mail.<домен>); иначе — отказ + logWarn
}

Раньше здесь принимался любой https://-URL. Цепочка Autodiscover формируется из сети (DNS, SRV, HTTP-редиректы) — то есть чужой хост, подставленный туда, получал бы Basic-пароль пользователя. Именно endsWith('.' + domain), а не endsWith(domain): иначе evil-company.com прошёл бы для company.com. Если легитимный EWS-хост живёт вне домена почты — вводите EWS URL явно (это доверенный ввод пользователя, ограничение к нему не применяется). См. Безопасность, ADR-0037.

Зонд npm run ews:check умеет перебирать эти кандидаты автоматически — см. Отладка.

Кэш резолвнутого URL: Autodiscover не на каждый вызов и не на каждый запуск (ADR-0037)

Autodiscover медленный (перебирает кандидаты), а service() пересобирает ExchangeService перед каждым EWS-раундом и закрепляет на нём account-bound XHR. Гонять Autodiscover на каждое открытие письма — большая и лишняя цена. Поэтому buildService принимает второй аргумент:

// ews.ts — сигнатура
export async function buildService(creds: ExchangeCredentials, resolvedUrl?: string): Promise<ExchangeService>

// внутри: явный URL из аккаунта ИЛИ ранее автодискаверенный → SKIP Autodiscover
const explicit = creds.ewsUrl?.trim() || resolvedUrl?.trim()
if (explicit) { service.Url = new Uri(explicit); return service }
// Autodiscover только когда обоих нет

Кэш двухуровневый: память + диск. Поле инстанса resolvedEwsUrl умирает вместе с процессом, поэтому раньше каждый запуск приложения заново платил за Autodiscover на первом же EWS-вызове. Теперь найденный URL сохраняется в учётку (accounts.json, поле ewsEndpoint) и подхватывается конструктором провайдера:

// provider.ts — порт персистентности (реализацию инжектит registry; провайдер не знает про Electron)
export interface EndpointStore { get(): string | undefined; set(url: string): void; clear(): void }

constructor(creds: ExchangeCredentials, endpoints?: EndpointStore) {
  if (!creds.ewsUrl?.trim()) this.resolvedEwsUrl = endpoints?.get()   // явный URL всегда приоритетнее
}

private async service(): Promise<ExchangeService> {
  const service = await buildService(this.creds, this.resolvedEwsUrl)
  if (!this.creds.ewsUrl?.trim()) this.rememberEndpoint(ewsSafe(() => service.Url?.ToString() ?? '', ''))
  return service
}
  • Явный creds.ewsUrl (референсная конфигурация) — Autodiscover не запускался и не запускается; кэш не читается и не пишется.
  • Без явного URL — Autodiscover бежит один раз на аккаунт, дальше все вызовы (и все последующие запуски) берут сохранённый URL.
  • Что именно хранится — и только если это НАШ домен. Только сам URL, нормализованный и привязанный к домену учётки: safeEndpointForDomain() (main/util/host.ts) требует https:, запрещает userinfo, отбрасывает query/fragment и проверяет, что хост лежит в домене email этой учётки (сам домен или поддомен). Не прошёл — не кэшируем (Autodiscover просто отработает в следующий раз). Проверка выполняется и при чтении из файла, а не только при записи. Домен берётся из самой учётки (StoredAccount.email по id), не из аргумента вызывающего. Зачем. Адрес приходит из сети, а это адрес, куда уйдёт Basic-пароль — и, будучи сохранённым, уйдёт при каждом следующем старте. Без привязки один момент MITM/подмены DNS превращался бы в постоянную утечку пароля. accounts.json — файл несекретных метаданных (пароль лежит отдельно, зашифрованный safeStorage, в account-secrets.json), но «несекретный» ≠ «неважный»: этот адрес определяет получателя секрета.
  • Наружу не течёт. ewsEndpoint — main-only поле: listAccounts()/getAccount() срезают его и отдают чистый MailAccount, поэтому в renderer EWS-специфика не попадает.
  • Инвалидация (сервер переехал). Все ошибки провайдера идут через один хук fail(e): если ошибка похожа на «эндпойнта здесь больше нет» (ENOTFOUND, ECONNREFUSED, EHOSTUNREACH, ENETUNREACH, 404/410), кэш сбрасывается (память + диск) → следующий вызов заново проходит Autodiscover. Не сбрасывают кэш: 401 (это про пароль), таймауты и ECONNRESET (медленная/моргающая сеть) — иначе любой сетевой чих возвращал бы нас на медленный путь; и любая ошибка сертификата, включая несовпадение имени (altname) — это сигнал безопасности, а не «переезд»: иначе тот, кто способен подменить эндпойнт, одним плохим сертификатом сбрасывал бы проверенный кэш и загонял нас обратно в поиск того, кому отдать пароль. Защита от «шторма»: повторный сброс не чаще, чем раз в 60 с (ENDPOINT_RESET_COOLDOWN_MS).
  • Смена ящика. upsertAccount сохраняет ewsEndpoint только при том же email; при смене — обнуляет.

Предохранитель учётных данных: 401 останавливает discovery и все дальнейшие вызовы (ADR-0077)

Зеркальный случай к инвалидации: 401 кэш адреса не сбрасывает (адрес верный — неверен пароль), но и продолжать с этим паролем нельзя: каждый запрос — ещё один неудачный вход в журнале контроллера домена, а порог lockout в AD типично 5–10. До этой правки один тик наблюдателя при пустом кэше адреса стоил четырёх-пяти неудачных входов (два кандидата, Autodiscover, EWS-вызов), и учётную запись пользователя блокировало по нескольку раз в час.

  • probeEwsEndpoint (перебор кандидатов). Раньше любой отказ FindFolders возвращал false («не тот хост»), resolveByCandidates шёл к следующему кандидату, затем buildService — к Autodiscover, повторяя пароль на каждом шаге. Теперь отказ классифицируется toMailError, и auth пробрасывается наружу — discovery заканчивается на первом 401:
// ews.ts — probeEwsEndpoint
const probe = service.FindFolders(WellKnownFolderName.Inbox, view).then(
  () => true,
  (e: unknown) => {
    const mapped = toMailError(e)
    if (mapped.code === 'auth') throw mapped   // не «следующий кандидат», а конец discovery
    return false
  }
)
  • buildService (ветка Autodiscover). Ошибка Autodiscover раньше всегда заворачивалась в MailError('Не удалось выполнить Autodiscover…', 'network'); теперь auth сохраняет свою классификацию (if (mapped.code === 'auth') throw mapped перед общим network) — иначе предохранитель в провайдере не отличил бы «неверный пароль» от «нет маршрута».
  • Guard в service() и diagnoseConnection(). Порт AuthLockHooks объявлен в общем providers/types.ts (контракт «провайдер ↔ хост», пригодный любому бэкенду) и инжектируется так же, как EndpointStore — провайдер не знает ни про Electron, ни про accounts.json:

Реестр (registry.ts) передаёт хук, который зовёт markAuthLocked(account.id) только если экземпляр всё ещё живой в реестре (providers.get(id)?.provider === provider) — запрос, зависший на экземпляре, уже заменённом mail:accounts:update, не помечает аккаунт заново, и, если запись уже помечена authLocked в accounts.json, вызывает lockAuth() сразу при сборке экземпляра — после перезапуска первый же вызов падает без сети.

  • diagnoseConnection заблокирован тоже. Шаг auth рунбука diagnose.ts (см. Тест подключения) отправил бы отвергнутый пароль; панель диагностики получает ту же ошибку auth.
  • Транспортный предохранитель в GatedXhrApi. Один экземпляр обслуживает один ExchangeService, то есть одну операцию со всем её веером (параллельные Folder.Bind, батчи поиска) и цепочку библиотечного Autodiscover (он после 401 идёт к следующему хосту сам — // skip в GetSettings). Первый 401 (isUnauthorizedError) запоминается в поле unauthorized, и каждый следующий xhr/xhrStream этого экземпляра отклоняется в момент отправки — до сокета, включая запросы, ждавшие слот gate (status: 'refused' в логе req). Следующая операция строит новый сервис и новый экземпляр; между операциями работает предохранитель провайдера. Тест: xhr-auth-fuse.test.ts.
  • Пути мимо service() закрыты. getContactPhoto (raw Basic GET GetUserPhoto) при взведённом предохранителе возвращает null; 401 на нём у Basic-аккаунта взводит предохранитель (fetchUserPhoto(…, onUnauthorized)), у NTLM-аккаунта — нет (Basic на этом пути может быть отключён легитимно). resolveToSmtp, getRoamingConfig/setRoamingConfig/deleteRoamingConfig (ADR-0115), discovery внутри getContactPhoto и начальный Subscribe потока пропускают ошибку через fail(). В service() флаг проверяется и после await this.resolving — параллельный вызов мог взвести предохранитель, пока шла discovery.
  • Долгое чтение потока предохранитель не трогает. Ошибки GetStreamingEvents (OnDisconnect, Open().catch) идут в onError(err, fatal) супервизора watch/watcher.ts, а не в fail(e): 401 на долгоживущем соединении бывает транспортной особенностью NTLM/прокси, поэтому остаётся fallback в poll (ADR-0043, fallbackToPoll). Но «быстрый чистый обрыв» (OnDisconnect без исключения раньше HEALTHY_MS = 60 с — так выглядит 401 посреди потока, чьё HTML-тело парсится в ничто) больше не переоткрывается до MAX_FAILURES = 5 раз с тем же паролем: onError(…, true) сразу, наблюдение уходит в poll. Если пароль действительно неверен, первый же poll (listFolders/listMessages через fail) взводит предохранитель — ровно одна лишняя попытка. Супервизор при этом сам слушает authLockEvents.locked → stopAccount, а setWatch для помеченного аккаунта отвечает effectiveMode: 'off', не создавая ни poll, ни подписки.
  • Проверка отредактированного подключения — одноразовый провайдер. registry.ts → probeProviderFor(id, creds) = new ExchangeProvider(creds, probeEndpointStoreFor(id, creds)): без AuthLockHooks, не кэшируется. probeEndpointStoreFor — обёртка над EndpointStore аккаунта с тремя правилами: get отдаёт закэшированный адрес только если он внутри домена проверяемых учётных данных (safeEndpointForDomain(cached, emailDomain(creds.email)) — https://, без userinfo, хост = домен email или его поддомен; кэш аккаунта хранится под email сохранённой записи, и патч, переносящий ящик в другой домен, не должен унести новый пароль на сервер старого домена — вне домена одноразовый провайдер идёт в доменно-связанную discovery с нуля); set — родной писатель аккаунта (сам отвергает чужие домены); clear — no-op (сетевой сбой во время проверки не должен стереть адрес аккаунта и отправить основной провайдер в discovery). Поэтому при заполненном и «своём» кэше testConnection() — один FindFolders(Inbox, IdOnly) на известный адрес; при пустом — та же доменно-связанная discovery, что и при добавлении аккаунта. С ADR-0078 через него проходит не только новый пароль, а любой патч подключения (mail:accounts:update: адрес сервера, схема, флаги TLS/прокси, логин, email), слитый в main поверх сохранённого секрета, — в том числе dryRun из кнопки «Проверить», который после этого запроса ничего не пишет. Хост-сторона (accounts/auth-lock.ts, accounts/credential-patch.ts, IPC mail:accounts:update/mail:accounts:connection, UI) — в Безопасность, Процессы и IPC и Интерфейс.

Общий ящик или ящик коллеги подключается «теми же данными, что у ящика X» — тем же логином и паролем. Для сети это один вход, поэтому всё, что касается входа, делится между его ящиками:

ЧтоГдеКак делится

Отказ в доступе — не отказ в пароле. Ящик по доступу может ответить ErrorAccessDenied или спрятать закрытые папки (ErrorItemNotFound/ErrorFolderNotFound). Вход при этом принят, поэтому предохранитель не взводится: такие ответы становятся кодом forbidden («нет доступа») только в ящике по доступу (Exchange EWS → Ящик по доступу). Настоящий HTTP 401 по-прежнему взводит предохранитель — уже для всего входа.

Ящик, скрытый из адресной книги. Проверка при подключении сначала ищет адрес в каталоге (ResolveNames, только почтовые ящики). Ящики умышленно скрывают из адресной книги — это не отказ: тогда OutTalk открывает «Входящие» (при отказе — календарь) прямо по введённому адресу и спрашивает ConvertId от id папки, чей это ящик. Основной адрес называет сервер; введённый дополнительный адрес не сохраняется, поэтому один ящик не появится дважды, а свой ящик не станет «по доступу». Сервер не знает такого ящика (ErrorNonExistentMailbox, ErrorInvalidSmtpAddress) — «Сервер не нашёл ящик … Проверьте адрес.»; обе папки закрыты — «нет доступа»; папка открылась, но ConvertId ящика не назвал — просьба указать основной адрес (exchange/mailbox-inspect.ts).

Autodiscover ящика по доступу идёт по адресу входа (creds.email), а не по адресу открываемого ящика: сервер ищется для того, кто входит. Если открываемый ящик в другом домене, найденный адрес в его запись не кэшируется (привязка к домену записи), и при каждом запуске его ищет первый запрос; явный EWS URL у входа снимает вопрос.

Тот же вход — для каталога организации (LDAP, ADR-0153)

Для VIP из каталога main читает Active Directory по LDAP простой привязкой (simple bind) — тем же входом, что у ящика Exchange. Отдельного пароля для каталога нет: секрет берётся в main по номеру входа (loadLoginOf(accountId) → credentialId, как у EWS), в окно не уходит ни логин, ни пароль.

Сервер каталога через Autodiscover: GetUserSettings → ActiveDirectoryServer (ADR-0153, поправка 2026-10-07)

Кнопка «Найти автоматически» в настройках каталога первым делом спрашивает сам Exchange: сервер почты без Active Directory не работает, и служба Autodiscover умеет назвать сервер глобального каталога, которым она пользуется для этого ящика. Это надёжнее DNS: работает при входе DOMAIN\user (из логина домен не извлечь), когда домен почты не совпадает с доменом каталога и когда VPN раздаёт свои серверы имён только для «своих» зон. Код — src/main/providers/exchange/autodiscover-ad.ts, вызывает его проводка directory/vip-runtime.ts; DNS-часть цепочки — Безопасность → VIP из каталога.

Запрос. Один SOAP-вызов на https://<узел EWS>/autodiscover/autodiscover.svc — схема, узел и порт берутся из адреса EWS ящика (autodiscoverUrlFor; адрес должен пройти validServiceUrl и, сверх того, быть именно https:// — даже loopback-http://, который validServiceUrl пропускает для локального стаба, здесь отвергается: пароль открытым текстом не уходит никогда). Адрес EWS — введённый в ящике или найденный и сохранённый провайдером (getEwsEndpoint, кэш выше). Тело — ровно одна настройка для одного адреса:

<soap:Header>
  <a:RequestedServerVersion>Exchange2010</a:RequestedServerVersion>
  <wsa:Action>http://schemas.microsoft.com/exchange/2010/Autodiscover/Autodiscover/GetUserSettings</wsa:Action>
  <wsa:To>https://mail.company.com/autodiscover/autodiscover.svc</wsa:To>
</soap:Header>
<soap:Body>
  <a:GetUserSettingsRequestMessage><a:Request>
    <a:Users><a:User><a:Mailbox>user@company.com</a:Mailbox></a:User></a:Users>
    <a:RequestedSettings><a:Setting>ActiveDirectoryServer</a:Setting></a:RequestedSettings>
  </a:Request></a:GetUserSettingsRequestMessage>
</soap:Body>

Адрес и wsa:To экранируются (escapeXmlText). Привязка SOAP — SOAP 1.1 с WS-Addressing: действие задаёт wsa:Action, отдельный заголовок SOAPAction не нужен; RequestedServerVersion — Exchange2010 (минимальная версия, где есть GetUserSettings). Ответ (parseAdAnswer; parseActiveDirectoryServer — та же функция, только имя узла): ErrorCode всего ответа (до UserResponses) и ErrorCode ответа пользователя должны быть NoError (или отсутствовать), затем из UserSettings (не больше 64 элементов UserSetting) с Name = ActiveDirectoryServer берётся Value — только имя узла (буквы, цифры, точки, дефисы, без точки в конце). Префиксы пространств имён допускаются любые. Разбор идёт без регулярных выражений с возвратами — только indexOf, то есть линейно даже на враждебном ответе в 256 KiB. Всё прочее, включая ответ-перенаправление Autodiscover (RedirectUrl/RedirectAddress), — «сервер не назван» (empty). Для диагностики (журнал, зонд владельца) наружу выходят только код HTTP при сбое и код ошибки Autodiscover из фиксированного списка AUTODISCOVER_CODES (InvalidUser, SettingIsNotAvailable, RedirectUrl… — неизвестный становится Other; если настройку не вернули, берётся код из UserSettingErrors) — ни имён, ни содержимого ответа.

Транспорт (postThroughMailboxTransport) — тот же, что у почты ящика, но для одного запроса:

ПараметрЗначение
ВходBasic — заголовок ставит тот же WebCredentials.PrepareWebRequest, что у EWS; NTLM — useNtlmAuthentication(username, password)
TLS и проксиbuildXhrRequestOptions(creds, false): rejectUnauthorized = !ignoreCertErrors, прокси — как у ящика (по умолчанию выключен); keep-alive одноразовому запросу не нужен
Перенаправления HTTPвыключены: maxRedirects: 0
Пределытайм-аут 10 с (AUTODISCOVER_TIMEOUT_MS), ответ и тело не больше 256 KiB (AUTODISCOVER_MAX_BYTES)
Ответ 401исход failed с пометкой auth (в итоге поиска — refused, в тексте неудачи — «почтовый сервер Exchange не принял вход ящика для этого вопроса»); предохранитель почты не взводится — у виртуального каталога Autodiscover бывает своя настройка входа; одна попытка на нажатие

Почему не библиотечный AutodiscoverService. Его GetUserSettings сам ходит по перенаправлениям: RedirectUrl — на любой URL, RedirectAddress — заново ищет узлы по домену нового адреса, в том числе через DNS и HTTP, — и на каждом шаге отправляет туда вход ящика. Для поиска EWS URL эта цепочка ограничена политикой редиректов внутри домена учётки, но здесь она не нужна вовсе: нам нужен ответ ровно того узла, которому ящик уже доверяет пароль. Поэтому запрос собран вручную, а любой уход в сторону считается «не назвал».

Когда не спрашиваем. Нет адреса EWS (ни введённого, ни сохранённого), нет сохранённого пароля, адрес ящика без @ или вход уже отвергнут почтой (isAuthLocked, предохранитель выше) — шаг Exchange пропускается, поиск идёт сразу в DNS. Весь шаг ограничен 12 с (DEFAULT_EXCHANGE_DEADLINE_MS в ldap-discover.ts); зависший ответ не мешает DNS-шагу.

Что может прийти. ActiveDirectoryServer сервер отдавать не обязан: на локальном Exchange 2016 настройка бывает пустой или с кодом SettingIsNotAvailable, в Microsoft 365 её нет вовсе. Это не ошибка — исход empty, и поиск идёт в DNS.

Доверие к названному узлу. Узел принимается как есть (только имя, не IP-адрес) только если у ящика включена проверка сертификата (ignoreCertErrors !== true; vip-runtime.ts → exchangeTrusted). С флагом «Игнорировать ошибки сертификата» — у Basic и у NTLM одинаково — узел принимается только внутри доменов-кандидатов поиска: иначе разовая подмена ответа на непроверенном канале сделала бы чужой узел постоянным получателем пароля — найденный сервер сохраняется, каталог читается раз в сутки, и после смены пароля туда уйдёт уже новый. Найденный сервер проверяется открытием TCP (636 → 3269 → 389 → 3268, без логина и пароля) и сохраняется с serverFound: true — его сертификат при чтении каталога проверяется строго всегда.

Проверить шаг на своём ящике без приложения — npm run ews:directory-server (Сборка и запуск): только чтение, Exchange спрашивается один раз, имена узлов печатаются только в терминал.

Прокси

@ewsjs/xhr@3.1.3 работает поверх Axios. При proxy: undefined Axios использует proxy-discovery из HTTP_PROXY/HTTPS_PROXY/NO_PROXY; в корпоративной среде это может ломать соединение с внешне опубликованным Exchange (прокси отдаёт 403/502, ошибка вида tunneling socket could not be established).

Решение: по умолчанию прокси отключается для EWS-запросов, потому что on-prem Exchange доступен напрямую:

proxy: creds.useSystemProxy ? undefined : false

Опция useSystemProxy (галочка «Через системный прокси» в Настройках) включает использование системного прокси, если Exchange доступен только через него.

TLS / сертификаты

Валидацией сертификата в Axios/XHR управляет Node TLS-флаг rejectUnauthorized:

rejectUnauthorized: !creds.ignoreCertErrors

Галочка «Игнорировать ошибки сертификата» ставит rejectUnauthorized: false — для внутренних/самоподписанных CA. Канал остаётся зашифрованным (TLS), проверяется лишь доверие к цепочке. В этом режиме OutTalk не передаёт собственный keep-alive agent: permissive agent создаёт сам @ewsjs/xhr, и socket pooling не заявляется.

Тот же флаг входа учитывается и при чтении каталога организации по LDAP, но только для сервера каталога, введённого руками, и только у входа с Basic. Для сервера, найденного «Найти автоматически» (через Exchange или DNS SRV), проверка сертификата остаётся строгой всегда — подменённый DNS-ответ с любым сертификатом иначе получил бы пароль простой привязки. У входа с NTLM флаг на каталог не переносится: при подмене узла почты NTLM отдаёт лишь «вызов — ответ», а простая привязка LDAP отдала бы сам пароль (ADR-0153, выше).

Ретраи транзиентных ошибок

Чтения с сервера оборачиваются в withRetry(fn) (ews.ts): до 3 попыток при транзиентной ошибке с линейным бэкоффом (300/600 мс). Транзиентными считаются ESOCKETTIMEDOUT (отдельной строкой — см. ловушку выше), ETIMEDOUT/timeout/ECONNRESET/socket hang up/EAI_AGAIN (временный DNS) и HTTP 502/503/504. Не повторяются 401/unauthorized, schema, certificate, а также ECONNREFUSED/ENOTFOUND (обычно конфиг/постоянный сбой) — они не восстановятся повтором, повтор лишь задержит ошибку.

  • Только идемпотентные чтения. Обёрнуты listFolders, listMessages, getMessage, search, searchAll, getConversation, getAttachment, а также — внутри getInlineImage — и Bind коллекции вложений, и сам GetAttachment каждой картинки (ADR-0039, ADR-0040). Последнее не тонкость, а починка живого бага: без своего withRetry картинка, потерянная на «припаркованном» сервером GetAttachment, терялась навсегда (в логе — ноль строк retry), хотя следующий такой же запрос отвечал за ~400 мс. Теперь у каждой картинки свой запрос, свой ретрай и свой исход: не пришла одна — заглушка только на её месте, письмо уже открыто. Писатели (sendMessage/saveDraft/moveMessages/deleteMessages/markRead/setFlag) никогда не повторяются — повтор мог бы выполнить операцию дважды. Уточнение ADR-0145: внутри markRead/setFlag чтение ревизий (BindToItems, IdOnly) — идемпотентное чтение и обёрнуто withRetry, сам UpdateItem — нет; единственный повтор записи — по структурированному ответу сервера «ревизия устарела» (ErrorInvalidChangeKey, ErrorChangeKeyRequired…, ErrorIrresolvableConflict, ErrorStaleObject — последним Exchange 2016 отвечает на устаревший ReferenceItemId с текстом «The current ChangeKey is required for this operation», второе исправление ADR-0146) для этого письма: правка IsRead/Flag идемпотентна. Тот же отказ ревизии разрешает ровно один повтор CreateItem ответа/пересылки после свежего Bind(IdOnly): отказ доказывает, что черновик не создан. Отказ узнаётся в обеих формах — ответом на элемент (ServiceResponseException) и SOAP-ошибкой всего запроса (SoapFaultDetails с кодом в ResponseCode), isRejectedChangeKey (ADR-0146, исправление 2026-10-06). Пакет картинок getInlineImages (GetAttachment с несколькими AttachmentId) withRetry не оборачивается: его запасной путь — одиночный getInlineImage со своим повтором. Умышленные MailError внутри чтения (напр. «Вложение не найдено») не матчат транзиентный набор и не повторяются.
  • Каждая попытка ограничена таймаутом из таблицы выше (30 с, для GetAttachment — 12 с): иначе три попытки против «чёрной дыры» заморозили бы UI на минуты. (service.Timeout = 30000 в baseService выставлен для порядка, но библиотекой не применяется — работает только timeout в опциях XHR/Axios.)
