Быстрый старт

Требования

  • Node.js v24 (см. .nvmrc). Проект кросс-платформенный — разработка ведётся на macOS и Windows.
  • macOS: Node иногда не в PATH → export PATH="$HOME/.local/nodejs/bin:$PATH". Для сборки .app — Xcode Command Line Tools.
  • Windows: Node 24 через fnm/nvm-windows или установщик с nodejs.org; готовая сборка — x64.

Разработка

# macOS
cd ~/outtalk
# Windows (PowerShell)
cd $HOME\src\outtalk

npm install
npm run dev        # electron-vite dev с горячей перезагрузкой (обе ОС)

Готовое приложение

npm run reinstall  # кросс-платформенно (scripts/reinstall.mjs)
  • macOS — собирает .app, ставит в /Applications с ad-hoc подписью; запуск через Launchpad/Spotlight.
  • Windows — собирает release/win-unpacked/OutTalk.exe и печатает путь; для NSIS-установщика/portable — npm run dist:win.

Подробности — в разделе Сборка и запуск.

Первый запуск

Без подключённого аккаунта приложение сразу открывает экран подключения (Настройки → «Ящики», форма «Подключить Microsoft Exchange» раскрыта сразу) — никаких примеров писем, которые можно принять за настоящие.

Демо-режим (opt-in)

Для превью интерфейса без реального ящика есть встроенный демо-провайдер (DemoProvider, тот же контракт, что и Exchange). Он выключен по умолчанию и выбирается только сочетанием OUTTALK_DEMO=1 и явного внутреннего accountId === 'demo':

npm run dev:demo      # dev-режим с демо-ящиком

Тот же режим использует E2E (npm run e2e) для офлайн-детерминированных тестов. В main resolveProvider из providers/access.ts требует одновременно флаг и ID demo; пустой, отсутствующий или неизвестный ID всегда возвращает ошибку auth. Поэтому реальному пользователю фейковые письма не покажутся. Решение и его мотивация — ADR-0032.

Подключение Exchange

Настройки → Подключить Microsoft Exchange:

ПолеОписание
EmailАдрес ящика, напр. user@company.com
ЛогинDOMAIN\user или user@company.com (как в Outlook)
ПарольПароль ящика
EWS URLНапр. https://mail.company.com/EWS/Exchange.asmx. Пусто → попытка Autodiscover (ограниченно)
АвторизацияBasic (по умолчанию); NTLM — режим совместимости с обязательной packaged live-проверкой перед релизом
Через системный проксиПо умолчанию выкл. — прямое соединение
Игнорировать сертификатДля внутренних/самоподписанных CA

Почему Basic по умолчанию? Это основной проверенный путь. Текущий @ewsjs/ntlm-client@3.0.1 считает NT-хэш через js-md4, поэтому NODE_OPTIONS=--openssl-legacy-provider больше не нужен; однако полный NTLM challenge-response в packaged Electron остаётся отдельным live release-gate. Подробности — в разделе Аутентификация и сеть.

Пароль шифруется средствами ОС (safeStorage: Keychain на macOS, DPAPI на Windows) и хранится только локально — см. Безопасность.

Отладка подключения

Если подключение не удаётся, используйте зонды (креды берутся из .env.local):

cp .env.exchange.example .env.local   # заполнить
npm run ews:check   # автономная проверка EWS: папки, письма, одно письмо
npm run ews:test    # прогон реального ExchangeProvider против сервера

Подробнее — в разделе Отладка.
