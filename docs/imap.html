IMAP / SMTP

IMAP / SMTP: протокол, маппинг и подводные камни

ImapProvider (src/main/providers/imap/) подключает любой стандартный почтовый ящик: Яндекс, Mail.ru, Gmail с паролем приложения, корпоративный Dovecot, IMAP-доступ Exchange. Чтение и всё, что меняет ящик, — по IMAP, отправка — по SMTP. Решение и его обоснование — ADR-0127; здесь — как это устроено и где грабли.

Библиотеки: imapflow 2.0.6 (IMAP) и nodemailer 10.0.10 (SMTP-транспорт и MailComposer). Версии закреплены точно.

Протокол в двух словах

IMAP (RFC 9051, исторически RFC 3501) — текстовый протокол поверх TCP/TLS, порт 993 (TLS с первого байта) или 143 (+ STARTTLS). Клиент шлёт команды с тегом (a1 SELECT INBOX), сервер отвечает нетегированными строками (* 12 EXISTS) и завершающей тегированной (a1 OK). Большие значения передаются литералами {12345}\r\n<байты> — объявленный размер приходит от сервера, и именно его враждебный сервер может раздуть (см. «Пределы»).

Ключевые понятия:

  • Папка (mailbox) — путь вида INBOX/Отчёты с разделителем, который объявляет сервер (/ или .). Имена на проводе — modified UTF-7, imapflow переводит их в обычный UTF-8.
  • UID — номер письма в папке, растёт и не переиспользуется… пока не сменился UIDVALIDITY папки. Пара UIDVALIDITY + UID однозначно называет письмо.
  • Номер последовательности (seq) — позиция письма в папке внутри текущего SELECT (1…EXISTS), в порядке возрастания UID.
  • Флаги — \Seen (прочитано), \Flagged (флажок), \Draft, \Deleted (помечено к удалению, исчезает только после EXPUNGE).
  • Расширения, на которые мы опираемся, если сервер их объявил: MOVE (RFC 6851), UIDPLUS (COPYUID/APPENDUID, UID EXPUNGE), SPECIAL-USE (RFC 6154), LIST-STATUS, IDLE (RFC 2177), ID (RFC 2971). Без них imapflow откатывается на базовые команды.

SMTP (RFC 5321) — отправка: EHLO → STARTTLS/TLS → AUTH → MAIL FROM → RCPT TO (по одному на адресата) → DATA (готовое письмо RFC 5322). Порт 465 — TLS с первого байта, 587 — STARTTLS (submission, RFC 6409). Получатели берутся из конверта, а не из заголовков: именно так Bcc доходит до адресата, не появляясь в письме.

Учётные данные и форма

type MailSecurity = 'tls' | 'starttls'

interface ImapCredentials {
  type: 'imap'
  email: string
  username: string          // обычно совпадает с email
  password: string          // для Gmail/Яндекса/Mail.ru/iCloud — пароль приложения
  imapHost: string; imapPort: number; imapSecurity: MailSecurity
  smtpHost: string; smtpPort: number; smtpSecurity: MailSecurity
  ignoreCertErrors?: boolean   // по умолчанию false
  saveSentCopy?: boolean       // по умолчанию true
}
  • Режима «без шифрования» нет намеренно. tls — TLS с первого байта, starttls — обязательный апгрейд: сервер, не предложивший STARTTLS, обрывает подключение, а не продолжает открытым текстом.
  • config.ts → isImapCredentials проверяет точный набор ключей, хост (DNS-имя или IP — не URL, без схемы, пути и порта), порт 1–65535 и режим защиты. Её вызывают хранилище секретов (accounts/secrets.ts) и слияние правки (accounts/credential-patch.ts) — до любого сетевого вызова.
  • Секрет хранится тем же путём, что у Exchange: safeStorage в main, файл account-secrets.json (Безопасность).
  • Личность ящика = тип + email + логин + imapHost. Тот же логин на другом сервере — другой ящик: правка, меняющая сервер, перестраивает локальное хранилище (ADR-0078).

Форма в «Настройках» — переключатель «Microsoft Exchange | IMAP / SMTP», пресеты и проверка полей; см. Интерфейс → Подключение ящика.

Пароли приложений

Ссылки сверены с официальными справочными страницами сервисов (октябрь 2026). У iCloud пресета нет: сервис узнаётся только по адресу или вручную введённому серверу imap.mail.me.com, серверы и порты человек вводит сам (пресет «Другой»). У строки ещё есть подпись «чей обычный пароль не подойдёт», длина кода (16 у Gmail и iCloud), короткий плейсхолдер поля и три шага «Как это сделать».

  • Как форма узнаёт сервис. detectAppPasswordProvider({ email, imapHost }): если IMAP-сервер введён — решает только он (точное совпадение имени без учёта регистра и конечной точки); пока сервера нет — домен адреса после последнего @. Сервер важнее адреса: вход идёт туда, где сервер, поэтому адрес на gmail.com с сервером mail.company.com подсказки не получает, а любой адрес на imap.gmail.com — получает. Пресет заполняет сервер, поэтому выбор «Gmail» тоже показывает подсказку сразу.
  • Подсказка появляется до ошибки, а не после неё — см. Интерфейс → Подключение ящика.
  • Ссылки открываются во внешнем браузере через существующий app:openExternal (Процессы и IPC); адрес берётся только из таблицы (appPasswordLinkFor(id) — null для любого id не из таблицы), из ввода человека адрес не собирается. Новых IPC-каналов нет.
  • Ошибка входа. Отказ сервера во входе (MailError.code === 'auth', см. «Ошибки») для сервиса из таблицы окно дополняет строкой «Похоже, введён обычный пароль — нужен пароль приложения» со ссылкой на ту же страницу.

Жизненный цикл соединений

вызов → run() ─ предохранитель взведён? → MailError('auth'), в сеть не идём
         │
         ├─ imap(): живой client? → он ; иначе один общий connect() на всех ждущих
         ├─ inBox(path): getMailboxLock(path) → SELECT → работа → release
         ├─ соединение умерло под ЧТЕНИЕМ (NoConnection/ECONNRESET/…) → один повтор
         └─ последний вызов закончился → через 60 с LOGOUT
  • Командное соединение — одно на аккаунт. Несколько одновременных вызовов разных папок не мешают друг другу: getMailboxLock ставит их в очередь, и каждый работает со «своей» выбранной папкой. Отсюда правило реализации: внутри одной блокировки нельзя брать вторую — очередь на одном соединении будет ждать вечно. Поэтому, например, поиск письма в целевой папке после MOVE выполняется уже после выхода из блокировки исходной.
  • Закрытие по тишине (60 с). Висящее соединение после сна ноутбука — источник «первый клик после пробуждения падает». Новое соединение стоит один LOGIN.
  • Повтор только для чтений. Записи (MOVE, EXPUNGE, APPEND) не повторяются: если обрыв случился после того, как сервер команду выполнил, повтор сделал бы вторую копию или удалил лишнее.
  • Смена экземпляра. Реестр вызывает dispose?.() у старого провайдера, когда тот заменяется (сменились креды) или забывается (forgetProvider при удалении аккаунта). ImapProvider.dispose() закрывает командное соединение.
  • false — это отказ. imapflow 2.x сообщает о неудаче STORE, EXPUNGE, MOVE, SEARCH, APPEND значением false (и при NO сервера, и при обрыве посреди команды). Каждый такой false превращается в MailError (refused()): соединения нет — network, иначе unknown «Сервер не выполнил операцию». Иначе окна объявили бы изменение, которого на сервере не было.
  • testConnection открывает отдельное одноразовое IMAP-соединение (connect + LOGOUT) и делает verify() SMTP-транспорта. Проверка формы перед сохранением идёт тем же путём.

Идентификаторы

IPC и локальное хранилище принимают id только из алфавита [A-Za-z0-9+/=_-] длиной ≤ 4096 (util/ids.ts → isValidItemId). Путь IMAP-папки — произвольный UTF-8 с разделителем, поэтому ids.ts упаковывает всё в base64url:

ЧтоIdПример содержимого
папкаf + b64url(путь)INBOX/Отчёты
письмоm + b64url(UIDVALIDITY:UID:путь)1700000000:42:INBOX
вложениеp + номер части, . → _p2_1 (часть 2.1)
  • Путь — не длиннее 512 символов, без управляющих символов; номер части — до 16 уровней по 4 цифры. Иначе — not_found ещё до сети.
  • UIDVALIDITY в id письма. Если сервер пересоздал папку (смена UIDVALIDITY), старый id даёт stale, а не открывает другое письмо, получившее тот же UID. stale — штатный сигнал, что строка списка устарела (ADR-0047): при открытии письма main убирает её из снимка и перечитывает окно папки, окно показывает «Этого письма больше нет на сервере» (поправка «Письма, которых нет» к ADR-0154).
  • Id — это место, а не личность. Перенос выдаёт новый id (новая папка, новый UID). Устойчивая личность — Message-ID (ADR-0074): readInternetMessageId и findByInternetMessageId реализованы через ENVELOPE и SEARCH HEADER Message-ID (ровно одно совпадение — иначе null, угадывать нельзя).

  • Одна папка на роль. Если special-use нет, imapflow угадывает роль по имени (Sent, Отправленные, …); серверная пометка (specialUseSource: 'extension') побеждает догадку.
  • \Noselect и \NonExistent пропускаются, их дети переподвешиваются к ближайшему выбираемому предку. Типичный случай — Gmail: [Gmail] не выбирается, а [Gmail]/Sent Mail становится папкой верхнего уровня «Отправленные».
  • Порядок: Входящие, Черновики, Отправленные, Архив, Спам, Удалённые, затем остальные по алфавиту (localeCompare('ru')), дерево — в глубину. Не больше 2000 папок.
  • Папка, путь которой нельзя закодировать в id (длиннее 512 символов, управляющие символы), пропускается — одно враждебное имя не роняет весь список.
  • Создание — CREATE с разделителем родителя; на верхнем уровне — с префиксом личного пространства имён (INBOX. у некоторых Dovecot/Courier). Имя не может содержать разделитель, %, * и управляющие символы.
  • Удаление — только пользовательской папки: переименование внутрь «Удалённых» (при совпадении имени — Имя (2)). Папка уже в корзине удаляется окончательно; корзины нет — отказ с подсказкой.

Список и поиск

SELECT <папка>                       → EXISTS = N, UIDVALIDITY
FETCH <N-offset-limit+1>:<N-offset> (UID FLAGS ENVELOPE INTERNALDATE BODYSTRUCTURE
                                     BODY.PEEK[HEADER.FIELDS (IMPORTANCE X-PRIORITY)])
  • Страница — срез по позиции в порядке UID. Внутри одного SELECT номера последовательности — ровно UID по возрастанию, поэтому срез с конца — «новые сверху». total = EXISTS, hasMore — есть ли письма до начала среза. Страница — до 200 писем (по умолчанию 50).
  • Письма с \Deleted не показываются: их пометил другой клиент, но ещё не вычистил.
  • Строка списка (MessageSummary): тема и отправитель из ENVELOPE; to: [] и displayTo (имена получателей) — как у Exchange; isRead = \Seen; isFlagged = \Flagged; hasAttachments — есть ли в BODYSTRUCTURE настоящее (не inline) вложение; важность — из Importance: или X-Priority: (1–2 → high, 4–5 → low).
  • Дата (ADR-0095): во «Входящих» и прочих — INTERNALDATE (время доставки), в «Отправленных»/«Черновиках» — заголовок Date: (время написания). Пустая, нераспознанная или раньше 1970-01-01 — это «даты нет»: 1970-01-01T00:00:00.000Z.
  • Порядок страницы ≠ порядок дат (осознанно). Страница берётся в порядке UID — порядке попадания в папку, а date в «Отправленных»/«Черновиках» — заголовок Date:. Письмо с датой в прошлом (импорт, сбитые часы отправителя, давний черновик) окажется внутри страницы не на своём месте, а при листании — на соседней странице. Это отступление от ADR-0095, принятое для MVP; исправление — SORT (DATE) (RFC 5256) там, где сервер его объявил.
  • preview — пустая строка, как у Exchange: превью стоило бы ещё одного FETCH на письмо.
  • Беседы. Идентификатора беседы у IMAP нет: conversationId не заполняется, и список всегда в режиме писем; getConversation возвращает само письмо.
  • Поиск — UID SEARCH TEXT "<запрос>" (заголовки + тело) и/или FROM, для «от этого человека» (ADR-0081). Неудавшийся SEARCH — ошибка, а не пустой результат: «ничего не найдено» здесь было бы ложью. Учитываются первые 10 000 совпадений, запрос — до 256 символов; страница — по найденным UID, новые сверху. searchAll обходит переданные папки по очереди — до 128 (MAX_SEARCH_FOLDERS, тот же потолок, что main ставит поиску по отправителю, RELATED_MAX_FOLDERS), пропускает исчезнувшие (not_found) и сливает результат по дате; любая другая ошибка папки — ошибка всего поиска. Срез длинного списка не молчаливый: в ответе foldersSearched — сколько папок реально обойдено, foldersFailed всегда 0 (поправка к ADR-0081).

Чтение письма

Письмо не скачивается целиком. FETCH BODYSTRUCTURE говорит, из каких частей оно состоит, а download() достаёт нужную часть уже декодированной (base64 / quoted-printable, format=flowed, charset → UTF-8) и не больше заданного предела.

Правила mime.ts → walkStructure:

  1. multipart/* — спускаемся в детей (не глубже 32 уровней и не больше 2000 узлов — защита от «бомбы» из вложенных частей).
  2. text/html или text/plain без Content-Disposition: attachment и без имени файла — текст тела. Берётся первая HTML-часть, иначе первая текстовая. multipart/alternative перечисляет сначала plain, потом HTML, поэтому «первая HTML» — именно то, что ждёт читатель.
  3. Всё остальное — вложение: картинки, PDF, календари, а также текст с именем файла.
  4. Часть с Content-ID из безопасного алфавита (shared/cid.ts → isSafeCid) и не attachment — inline-картинка: isInline: true + contentId. Через неё работает getInlineImage(messageId, cid) (ADR-0040).
  5. message/rfc822 — вложение .eml, внутрь не спускаемся. BODY[n] такой части — всё вложенное письмо (заголовки + тело). Встроенная читалка берёт его обычным getAttachment и разбирает в main (ADR-0129, Интерфейс → Письмо во вложении); провайдеру для этого ничего не нужно.
  • Тип очищается до токена тип/подтип (иначе application/octet-stream), имя файла — без управляющих символов и / \, до 255 символов; размер — оценка декодированного (base64 × 3/4).
  • Тело — до 4 МБ. Длиннее — показывается начало и пометка «Письмо слишком большое — показано начало». Простой текст экранируется и переводится в HTML с сохранением переносов строк (white-space: pre-wrap).
  • HTML тела не санитайзится в main: как и у Exchange, единственное место санитайзинга — DOMPurify в renderer прямо перед вставкой (Безопасность).
  • Inline-картинка отдаётся, только если её тип из белого списка растровых (INLINE_IMG_TYPES, без SVG) и она не больше 8 МБ; иначе not_found — renderer рисует тихую заглушку.
  • Картинки письма — одной сессией (ADR-0145, ADR-0149). getInlineImages(id, cids, opts?) — пакетный метод контракта, который main зовёт после текста, по просьбе окна (mail:prefetchInlineImages) или при первом промахе картинки: один SELECT папки, один FETCH BODYSTRUCTURE, затем части по очереди в порядке cids (верх письма первым) на том же соединении (download, предел 8 МБ на картинку), вместо сессии и структуры на каждую картинку. Каждая прочитанная картинка сразу уходит в opts.onPart. С opts.allInline после названных добавляются все остальные inline-части письма с безопасным cid. Бюджет на всё письмо — 24 МБ (MAX_INLINE_BATCH_BYTES, как предел письма у Exchange) или меньше по opts.maxBytes (фоновый прогрев — 3 МБ); cid вне isSafeCid отбрасываются, совпадение — без учёта регистра, одна часть на cid. Картинка не того типа, сверх предела или с ошибкой чтения просто отсутствует в ответе — main спросит её через getInlineImage. Результат ложится в кэш картинок main (общий для провайдеров), поэтому переоткрытое письмо картинки с сервера больше не тянет — своего кэша картинок у IMAP-провайдера нет.
  • Вложение — до 50 МБ; больше — понятный отказ invalid с советом открыть письмо в веб-интерфейсе.
  • Выборка идёт через BODY.PEEK[…]: открытие письма не ставит \Seen — прочитанным письмо делает только явный markRead из renderer.

Черновики, отправка, ответ и пересылка

saveDraft:   MailComposer(Bcc сохранён) → APPEND «Черновики» (\Draft \Seen) → [удалить старую версию]
sendMessage: MailComposer(без Bcc) → SMTP ─┬─ saveSentCopy=false или Gmail → готово

sendDraft:   заголовки цепочки + вложения черновика → sendMessage → удалить черновик
  • Сборка письма — providers/compose.ts → composeMessage. Тело проходит общий providers/outgoing-body.ts: cid: вне безопасного алфавита заменяются прозрачной заглушкой, наши data-cid/data-inline-state вычищаются, вставленные data:-картинки становятся inline-частями с cid: (8 МБ на картинку, 10 МБ на письмо). Добавляется text/plain-альтернатива (util/html-text.ts → htmlToText, линейный разбор). Message-ID — <uuid@домен-отправителя>, без имени компьютера; X-Mailer не ставится; важность — X-Priority/Importance.
  • MailComposer без доступа к файлам и URL (disableFileAccess, disableUrlAccess): все части передаются байтами из памяти.
  • SMTP. secure — по smtpSecurity; при starttls — requireTLS (без апгрейда AUTH не уйдёт); EHLO [127.0.0.1] вместо имени компьютера; журнал выключен. Транспорт создаётся на одну отправку и закрывается.
  • Копия в «Отправленных». Gmail кладёт копию сам — повторный APPEND дал бы дубль, поэтому для хостов gmail.com/googlemail.com и при выключенной галочке копия пропускается. Для остальных сначала ищем копию по Message-ID, и только если её нет — APPEND. Если сам SEARCH не удался, копия не дописывается вслепую (могла бы получиться вторая) — шаг пропускается с записью в журнал. Сбой этого шага не делает письмо неотправленным: оно уже ушло, ошибка уходит в журнал. Копия ложится до ответа на отправку, а IDLE слушает только «Входящие», поэтому открытые «Отправленные» догоняет не наблюдение, а main: после успешной отправки он сам перечитывает папку с ролью sent через 1,5 с и 5 с (ADR-0143, Процессы и IPC). Если копию кладёт сам сервер и дольше 5 с — письмо появится при следующем открытии папки.
  • Черновики. Править письмо на месте IMAP не умеет: новая версия дописывается (APPEND), старая удаляется окончательно. Нет папки «Черновики» — создаётся Drafts в личном пространстве имён.
  • Ответ (createReplyDraft):
    • адресаты — Reply-To, иначе From; «Ответить всем» добавляет остальных из To/Cc без себя; ответ на своё письмо из «Отправленных» адресуется его получателям;
    • тема Re: … без наслоения префиксов (Re:/Ответ: уже есть — не добавляем);
    • In-Reply-To: <Message-ID оригинала>, References: — цепочка оригинала + его Message-ID (до 20 последних);
    • тело — цитата в стандартном виде Outlook / Exchange 2016, тем же видом, каким композер показывает предварительную цитату (ADR-0150): quoteHtml → buildQuoteHtml(src, DEFAULT_QUOTE_TEMPLATE) из @shared/quote-template — линия <hr>, блок <div id="divRplyFwdMsg"> с шапкой «От / Отправлено / Кому / [Копия] / Тема» в <font face="Calibri, sans-serif"> 11 pt (строка «Копия» — только если у письма есть копия; «От» — «Имя <адрес>», списки — имена через ; ; дата — Intl.DateTimeFormat('ru-RU'), full + short, в часовом поясе устройства; все значения экранированы — их пишет отправитель), пустая строка и исходное тело в <div> (из полного документа берётся содержимое <body> — bodyInner; поиск — indexOf, без регулярных выражений с откатом: вход чужой, а код синхронный в main). Пустую строку для текста над цитатой и подпись ставит композер;
    • в черновик переносятся только inline-картинки, на которые цитата ещё ссылается.
  • Пересылка (createForwardDraft): тема Fwd: …, цитата с той же шапкой, что у ответа (как в Outlook; отдельной строки «Пересланное сообщение» больше нет, ADR-0150), все вложения оригинала — но не больше 25 МБ вместе (иначе invalid «Вложения слишком большие, чтобы переслать их»). In-Reply-To не ставится.

S/MIME (ADR-0130)

Письмо помечается по корню BODYSTRUCTURE (smimeHintOfStructure, imap/mime.ts), без скачивания: application/(x-)pkcs7-mime → smime.hint = 'pkcs7', multipart/signed с protocol=application/(x-)pkcs7-signature → 'multipart-signed' (PGP/MIME не помечается). Для помеченных писем main просит исходник: ImapProvider.getMessageMime(id) → download(uid) без номера части (BODY.PEEK[], не ставит \Seen) с maxBytes и readCapped ≤ 32 МБ; больше — MailError('invalid'). Расшифровка и проверка подписи — в main, S/MIME.

Отправка S/MIME (ADR-0131)

ImapProvider.sendMime(mime, info) отдаёт SMTP готовые байты (sendMail({ envelope, raw })) — ничего не пересобирает; конверт SMTP — из info.envelope (To + Cc; Bcc для S/MIME отклоняется в main). Копия в «Отправленные» — те же байты с \Seen по обычным правилам: не дублировать, если сервер уже положил письмо (поиск по Message-ID), не класть для Gmail и при выключенной настройке. Зашифрованная копия открывается своим ключом — main всегда шифрует и на отправителя. saveMimeDraft — APPEND в «Черновики» с \Draft \Seen, только зашифрованный на себя MIME. Пометка строки списка (MessageSummary.smime) — из корня BODYSTRUCTURE, который список и так запрашивает ради «есть вложения» (бесплатно, без лишнего запроса и без заголовка Content-Type): application/(x-)pkcs7-mime → encrypted, а с smime-type=signed-data → signed; multipart/signed с протоколом PKCS#7 → signed. После ответа/пересылки main зовёт markResponded: STORE +FLAGS (\\Answered) для ответа, ключевое слово $Forwarded (RFC 5788) для пересылки — только если PERMANENTFLAGS ящика разрешают (нет списка или есть \\*); ошибка не отменяет отправку. Индекса беседы у IMAP нет — Thread-Index ответа строится из заголовка оригинала, если он там был. Ответ на зашифрованное письмо createReplyDraft не строит (на сервере остался бы черновик с открытой цитатой) — его собирает main из расшифровки. Тест на поддельном SMTP/IMAP: imap/provider.test.ts («sendMime»).

Подводные камни

  • Пароль приложения. Gmail, Яндекс, Mail.ru и iCloud не пускают по IMAP с обычным паролем. Ответ — тот же AUTHENTICATIONFAILED, что и на опечатку, поэтому текст ошибки (toImapMailError, imap/errors.ts) сразу подсказывает: «Для Gmail, Яндекса, Mail.ru и iCloud нужен пароль приложения, а не обычный пароль», а форма подключения для сервиса из таблицы добавляет строку со ссылкой (см. «Пароли приложений»). У Яндекса ещё нужно включить доступ по IMAP в настройках почты.
  • Gmail сам кладёт копию отправленного. Отсюда пресет с выключенной галочкой и проверка по хосту.
  • Gmail: удаление — это перенос в корзину. \Deleted + EXPUNGE во «Входящих» Gmail лишь снимает ярлык, письмо остаётся во «Вся почта». Мы удаляем переносом в \Trash — Gmail понимает это как настоящее удаление.
  • Gmail: [Gmail] — не папка. \Noselect-родитель пропускается, дети поднимаются наверх.
  • EXPUNGE без UIDPLUS вычищает все письма с \Deleted в папке, в том числе помеченные другим клиентом. С UIDPLUS (почти все современные серверы) — только наши (UID EXPUNGE).
  • Смена UIDVALIDITY (пересоздание папки, миграция сервера) делает все сохранённые id писем этой папки stale. Локальный снимок перечитывается, задачи находят письма заново по Message-ID.
  • Бесед нет. IMAP THREAD поддерживают не все серверы, а X-GM-THRID — только Gmail; MVP не группирует письма.
  • IMAP у Exchange часто выключен. Администраторы Exchange нередко отключают IMAP и Basic-вход по нему. Для такого ящика правильный путь — провайдер Exchange (EWS).
  • Разделитель в имени. Создать папку a/b на сервере с разделителем / нельзя — это была бы папка b внутри a; форма отвечает понятным отказом.
  • Внутри одной блокировки ящика — никаких других. См. «Жизненный цикл соединений».

  • E2E e2e/imap-account.spec.ts проверяет, что форма IMAP рисуется и валидирует ввод; кнопки «Подключить» и «Проверить подключение» тест не нажимает — в сеть он не ходит.
  • Пароли приложений. Unit lib/app-password.test.ts — распознавание сервиса по адресу и серверу (сервер важнее адреса, регистр и конечная точка не мешают), ссылки только из таблицы (appPasswordLinkFor), очистка пробелов (дефисы iCloud остаются). E2E e2e/app-password-hint.spec.ts — у адреса компании подсказки нет, у адреса Gmail подсказка, ссылка и подпись поля «Пароль приложения» появляются сразу; хватает и пресета или имени сервера, у каждого сервиса своя ссылка; скриншоты обеих тем и узкого окна — в e2e/.artifacts/app-password-*.png. Ссылку тест не нажимает — она открыла бы внешний браузер.
  • Проверка на живом ящике — вручную владельцем: «Настройки» → «Добавить» → «IMAP / SMTP» → пресет → пароль приложения → «Проверить подключение».

Пароль приложения с пробелами. Gmail, Яндекс и Mail.ru показывают пароль приложения группами через пробел («abcd efgh ijkl mnop»), а вход принимают только без пробелов. Форма подключения убирает пробельные символы из пароля, если IMAP-сервер есть в таблице паролей приложений (lib/app-password.ts, раздел «Пароли приложений»; у iCloud пароль вида xxxx-xxxx-xxxx-xxxx — дефисы остаются); пароль любого другого сервера уходит ровно как введён — настоящий пароль может содержать пробел. Смена пароля у уже подключённого ящика этого пока не делает.
