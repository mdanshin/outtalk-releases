Локальные данные: ключи, блокировки и восстановление

Статус: schema v10 и main-only модели подключены для списков папок/писем и календарных диапазонов реальных аккаунтов. Со schema v7 (ADR-0097) база хранит ещё и собственную память приложения о том, что оно сделало с приглашением на встречу (mail_invitation_answers) — знание, которого у сервера нет в принципе; со schema v9 (ADR-0149) — картинки cid: уже открывавшихся писем (mail_inline_images); со schema v10 (ADR-0154) — состояние синхронизации папок по изменениям (mail_folder_sync). Почта хранит атомарные поколения — с ADR-0096 поколение папки это окно (префикс папки), которое прокрутка может удлинить, а не обязательно вся папка; календарь — атомарно заменяемые покрытые интервалы с snapshot-first UI. Тела, вложения, поиск, FTS и offline-очередь ещё не подключены; Demo намеренно остаётся на прямом provider path.

Файловая модель

Для каждого main-owned accountId вычисляется непрозрачный SHA-256 каталог. Исходный идентификатор не входит в путь. Внутри каталога публикуется key.json: внешний JSON содержит только formatVersion и ciphertext safeStorage; защищённый payload связывает ключ с expectedAccountHash, storeUuid, principalHash, accountGeneration и точным cipher profile.

Перед чтением, публикацией или удалением account directory проверяется через lstat и realpath: symlink/junction, не-каталог или выход из настроенного root дают typed unsafe_path. Сам key.json перед чтением отдельно проверяется как обычный файл: open выполняется без следования по symlink, identity файла сверяется до и после bounded handle-read, а размер ограничивается до аллокации и повторно во время чтения. Непосредственно перед SQLite open та же fail-closed проверка повторяется для account directory и существующих cache.db, cache.db-wal, cache.db-shm: разрешены только обычные файлы с каноническим parent внутри account directory; symlink и подмена типом отклоняются до вызова SQLite. Файлы по небезопасному пути не открываются. Это fail-closed boundary, а не защита от процесса с правом одновременно менять каталог приложения; права на local-data root всё равно должны принадлежать пользователю.

Lifecycle lock и гонки

Перед account-level механизмами действует отдельный process-wide рубеж: main получает Electron requestSingleInstanceLock() для уже выбранного userData до app.whenReady() и initializeLocalMailRepositories(). Второй процесс того же профиля не открывает repository вообще, а только активирует окно владельца и завершается. Обычный dev использует отдельный <production-userData>-dev; явный --user-data-dir сохраняется для изолированных тестовых/операторских профилей. После crash OS освобождает этот global lock, но описанные ниже lifecycle lock и lease не крадутся автоматически: single-instance admission не доказывает целостность account artifacts и не заменяет binding/storeUuid проверки.

На весь load/read/create/publish/open/remove берётся один и тот же атомарно создаваемый каталог:

.<expectedAccountHash>.key.lock

Lock не крадётся по PID, возрасту или mtime: эти признаки дают TOCTOU после crash/PID reuse. Если владелец не освобождает lock за bounded timeout, операция возвращает typed lock_unavailable. При успешном open до освобождения lifecycle lock атомарно создаётся уникальная lease .<hash>.open.<uuid>; она живёт до фактического закрытия SQLite handle. Поэтому EncryptedAccountStore.remove сначала закрывает совпадающий process-local handle, затем под lifecycle lock требует отсутствия любых lease, повторно сверяет envelope UUID и лишь после этого удаляет cache.db, WAL, SHM, account blobs/artifacts, envelope и account directory. Открытый foreign-process handle или crash-sticky lease дают lock_unavailable; никакой PID/age auto-steal не выполняется. Публичного arbitrary-admission callback и envelope-only destroy нет. Omitted, пустой или malformed expectedStoreUuid отклоняется как store_mismatch, а stale caller не может удалить replacement identity.

Temp имеет UUID-имя .key-<uuid>.tmp. Процесс удаляет только созданный им temp; чужой, в том числе живой, temp не считается DB artifact и не удаляется автоматически.

Ручное восстановление abandoned lock/lease

Автоматического удаления stale lock или open lease намеренно нет. Оператор выполняет recovery только в таком порядке:

  1. Полностью закрыть OutTalk и подтвердить отсутствие владельца: проверить, что нет main/utility процессов OutTalk и процессов, удерживающих handle внутри соответствующего local-data root. Одного старого mtime недостаточно.
  2. По доверенному account registry заново вычислить expectedAccountHash и перечислить точные coordination entries: lifecycle lock .<hash>.key.lock и lease .<hash>.open.<uuid>. Не использовать wildcard и не удалять account directory, key.json, DB/WAL/SHM или .key-*.tmp.
  3. Для каждой выбранной entry убедиться, что это пустой каталог, а не symlink/junction/файл. Удалять только точные каталоги, владельцы которых гарантированно отсутствуют; чужую live lease удалять запрещено.
  4. До reopen проверить envelope: bounded JSON, только {formatVersion, encryptedPayload}, успешная расшифровка системным backend и совпадение expectedAccountHash, storeUuid, principalHash, accountGeneration, cipher profile. Если account DB уже существует на следующем этапе, отдельно открыть её одобренным offline diagnostic, проверить cipher/integrity и точное совпадение DB metadata с envelope. Не создавать новый ключ поверх непроверенной DB.
  5. Только после обеих проверок снова открыть аккаунт. Любое несовпадение/повреждение оставляет store закрытым и передаётся в диагностический recovery; оно не лечится удалением envelope.

Durability по платформам

На POSIX temp-файл синхронизируется до hard-link publication, затем синхронизируется account directory; после удаления собственного temp directory синхронизируется повторно. Это сохраняет no-overwrite publication и метаданные каталога при crash/power loss в пределах гарантий файловой системы.

Node.js не предоставляет переносимого способа открыть и flush-нуть Windows directory handle, а fsync(key.json) не эквивалентен directory fsync. Production win32 поэтому использует статический PowerShell/C# interop к exact CreateFileW(FILE_FLAG_BACKUP_SEMANTICS) и FlushFileBuffers: directory path передаётся только через process environment и не интерполируется в команду. PowerShell запускается без PATH lookup из фиксированного C:\Windows\System32, без profile и execution-policy bypass; у child process case-insensitive варианты SystemRoot/WINDIR удаляются и задаются заново, поэтому spoofed parent environment не выбирает executable. Нестандартный Windows root пока fail-closed получает durability_unavailable, как и ошибка запуска, открытия handle, flush или timeout. Внешний helper ограничен 30 секундами: прежние 10 секунд дважды истекали именно на холодном PowerShell/.NET старте загруженного hosted runner, тогда как повторный прогон того же exact SHA проходил; это bounded startup allowance, а не ретрай и не ослабление обязательного FlushFileBuffers. Реальные Windows regressions публикуют envelope через production factory и повторяют это со spoofed environment; прямой AccountKeyStore без внедрённого directory sync по-прежнему останавливается до account filesystem work.

Зашифрованный SQLite store

Runtime dependency зафиксирована exact как better-sqlite3-multiple-ciphers@12.11.1. Для каждого аккаунта существует только cache.db в его hash-каталоге; renderer/preload не получают ни handle, ни SQL, ни путь, ни ключ. Исполнимый profile sqlite3mc-sqlcipher-legacy4-v1 всегда означает последовательность cipher=sqlcipher → legacy=4 → key(Buffer) до первого schema/data SQL. Неизвестный profile отклоняется до создания файла; plaintext-create/rekey пути нет.

Каждый open проверяет cipher_integrity_check, integrity_check, migration checksums и exact совпадение store_meta с защищённым envelope: account hash, store UUID, principal hash и generation. Для существующей schema сначала проверяется точный уже применённый migration prefix и binding, и только затем разрешается следующая migration; tampered v1 поэтому не может быть побочно изменён до fail-closed отказа. Несовпадение, wrong key, tamper или будущий user_version закрывают handle и не превращаются в cache miss. Existing DB/WAL/SHM без envelope даёт missing_key, а не генерацию replacement key.

После проверки включены foreign_keys=ON, secure_delete=ON, temp_store=MEMORY, synchronous=FULL, WAL, busy_timeout=5000 (на время admission/миграции — 30 с: несколько процессов могут открывать один store одновременно, и первый мигрирует его под BEGIN IMMEDIATE), wal_autocheckpoint=1000, journal_size_limit=16777216 и жёсткий max_page_count, соответствующий максимуму 512 MiB. Это не hint: запись сверх лимита завершается SQLITE_FULL. Перед open существующий WAL читается bounded-образом и fail-closed проверяется по формату, page size, salts и SQLite rolling checksums; abrupt-kill WAL с валидными committed frames восстанавливается, повреждённый frame отклоняется как integrity_failed до SQLite open.

Close идемпотентен и сериализован явным состоянием. Ошибка checkpoint/lease release не отменяет попытку закрыть handle; если handle физически закрылся, open-map и account repository entry очищаются, хотя caller получает исходную ошибку, а следующий обычный доступ открывает свежий usable repository. Если сам close не удался и handle остаётся жив, map/entry сохраняются fail-closed, обычный get не возвращает недоступный repository, а следующий явный remove/close повторяет попытку.

Schema v1 содержит foundation-таблицы store_meta, schema_migrations, не-STRICT sync_sessions и coverage_intervals. Schema v2 расширяет sync_sessions полями runtime-owner и добавляет пять STRICT-таблиц mail_*. Schema v3 добавляет STRICT-таблицы calendar_events, calendar_coverage и calendar_refresh_range. Schema v4 (ADR-0069) добавляет индекс mail_message_aliases_by_local на mail_message_aliases(local_id): по этой колонке идёт ON DELETE CASCADE из mail_messages, и без индекса каждое удалённое при публикации снимка письмо заставляло SQLite сканировать всю таблицу псевдонимов через шифр (на кэше ~150 МБ — минуты заблокированного main-процесса; замер: 15 000 удалений — 94 с без индекса, 0,7 с с ним). Schema v5 (ADR-0095) добавляет индекс mail_messages_folder_snapshot_date на mail_messages(folder_local_id, active_generation, received_at DESC, sort_order): с этой версии список выдаётся по дате письма, а не по позиции в обходе папки (см. ниже про readMessages). Миграция только создаёт индекс — данные не трогаются, переустановка кэша не нужна. Schema v6 (ADR-0096) добавляет STRICT-таблицу mail_message_window — состояние окна списка: с этой версии снимок папки не обязан быть папкой целиком, он хранит её префикс, а таблица помнит, где остановился обход и был ли он доведён до конца. Миграция только создаёт таблицу; отсутствие строки в ней читается как «поколение построено сборкой до v6», то есть папка целиком — прежняя семантика, переносить ничего не нужно. Schema v7 (ADR-0097) добавляет STRICT-таблицу mail_invitation_answers — что это приложение сделало с приглашением на встречу. Миграция только создаёт таблицу и индекс: у прежних приглашений записи просто нет, и они читаются ровно как до v7 (подпись под карточкой без уточнения «сообщали ли организатору»). Schema v8 (ADR-0131) добавляет в mail_messages колонку smime TEXT (NULL или encrypted|signed) — пометку S/MIME строки списка. Это факт уровня списка, который сервер сообщает без вскрытия письма (класс элемента Exchange, корень BODYSTRUCTURE IMAP); содержимого расшифровки в базе нет и не будет. Миграция — один ALTER TABLE … ADD COLUMN: у строк, записанных до v8, там NULL, и следующая синхронизация папки их перезапишет. Schema v9 (ADR-0149) добавляет STRICT-таблицу mail_inline_images — картинки cid: прочитанных писем (см. ниже); миграция только создаёт таблицу и индекс, у прежних писем картинок на диске просто нет. Schema v10 (ADR-0154) добавляет STRICT-таблицу mail_folder_sync — состояние синхронизации папки по изменениям (см. ниже); миграция только создаёт таблицу и индекс: у папок строки нет, они живут прежним окном, пока не пройдут первичный проход. Сборка до v10 открыть такую базу не может (future_schema), как при любом откате схемы. Набор migrations валидируется до создания account directory, envelope или DB и обязан заканчиваться ровно на CURRENT_SCHEMA_VERSION; набор из будущего бинарника отклоняется без filesystem mutation. Каждая migration получает межпроцессный write admission через BEGIN IMMEDIATE; после ожидания внутри этой transaction заново читаются и проверяются user_version, binding и migration prefix. Поэтому одновременные openers не применяют один и тот же шаг дважды. Migration и её user_version фиксируются одной transaction; ошибка откатывает DDL, metadata и version вместе, сохраняя читаемое состояние N−1. До перехода N→N+1 проверяются binding и точные checksums всех N уже применённых строк, после перехода повторно проверяется полная история. Отдельный regression создаёт настоящий зашифрованный v1 store, обновляет его до текущей версии (CURRENT_SCHEMA_VERSION, сейчас v10), проверяет сохранность foundation-строк и повторное открытие; подмена checksum любой применённой migration отклоняется как schema_mismatch.

Внутренняя модель почтовых снимков — schema v2

LocalMailReadModel существует только в main process и получает уже открытый EncryptedAccountStore вместе с точной привязкой principalHash + accountGeneration. Перед каждым доступом к БД повторно проверяются эта привязка, storeUuid и состояние open: состояние closing/close_failed/closed запрещает новые операции. Renderer и preload не получают SQL, локальный путь, ключ или серверные реквизиты.

Registry authority использует opaque string tokens, поэтому main-only localDataBindingForAuthority переводит их в физический v1 binding детерминированно и с domain separation. Production principal — 64-символьный hex SHA-256 digest. Полные principal + generation вместе входят в отдельный 256-битный composite digest, который записывается в физическое поле principalHash; поэтому 52-битное числовое отображение generation служит только дополнительным SQLite discriminator и его возможная коллизия не ослабляет identity binding. Credential revision намеренно не входит в disk binding: смена пароля/повторная авторизация не ротирует локальную БД, а смена mailbox principal или полного incarnation generation приводит к fail-closed identity mismatch. На этом держится замена пароля и любая правка подключения, не меняющая принципал, через mail:accounts:update (ADR-0077, ADR-0078): revision (отпечаток учётных данных с ключом процесса, ADR-0140) меняется, менеджер репозиториев переоткрывает handle под новой authority, но файл БД и локальная копия писем остаются — удалять и заново подключать ящик не нужно. Смена же email или логина (принципала) под тем же accountId — это другой ящик: его локальная копия не переиспользуется, а перестраивается через барьер удаления — removeLocalMailRepository(id, authority, authorize, commit), тот же путь, что у mail:accounts:remove, только шаг commit внутри барьера переписывает реестры (saveSecret + upsertAccount с новым generation) вместо их удаления; провал уничтожения откатывает барьер, а после коммита новая полная authority получает свежую БД (ADR-0078). Malformed principal/generation отклоняются до открытия local-data store. Ящик по доступу (ADR-0138). Он входит теми же логином и паролем, что и свой ящик-источник, поэтому прежний трёхчастный principal (тип, адрес, логин входа) у двух ящиков мог бы совпасть по смыслу. buildAccountAuthority (accounts/account-authority.ts) для mailboxContext: 'delegate' дописывает к частям принципала 'delegate' и адрес самого ящика: локальная копия ящика по доступу привязана к собственной личности и никогда не откроется под личностью своего ящика того же входа. У своего ящика принципал прежний, существующие БД остаются привязанными. Отдельный accountId даёт ящику по доступу и собственный каталог хранилища.

Физический контракт таблиц mail_*

Пять таблиц пришли со schema v2 (у mail_messages со schema v8 — ещё колонка smime), шестая (mail_message_window) — со schema v6, седьмая (mail_invitation_answers) — со schema v7, восьмая (mail_folder_sync) — со schema v10 (картинки mail_inline_images schema v9 описаны ниже отдельно). Все — STRICT; TEXT-лимиты ниже считаются по UTF-8 bytes через length(CAST(... AS BLOB)), если явно не сказано иное.

  • mail_folders: local_id TEXT PRIMARY KEY (repository генерирует UUID; SQL проверяет только 36 символов); provider_id TEXT NOT NULL UNIQUE (1–4096 bytes); nullable parent_provider_id TEXT (1–4096); name TEXT NOT NULL (≤512); role TEXT NOT NULL из inbox|sent|drafts|deleted|junk|archive|outbox|custom; unread_count и total_count INTEGER NOT NULL в диапазоне 0…2,147,483,647; depth INTEGER NOT NULL 0…1024; sort_order INTEGER NOT NULL 0…499; active_generation INTEGER NOT NULL > 0. Индекс mail_folders_snapshot_order(active_generation, sort_order) задаёт snapshot-order read path.
  • mail_folder_aliases: provider_id TEXT PRIMARY KEY (1–4096 bytes); local_id TEXT NOT NULL → mail_folders(local_id) ON DELETE CASCADE; last_seen_generation INTEGER NOT NULL > 0. Индекс mail_folder_aliases_local(local_id) поддерживает bounded pruning по локальной identity.
  • mail_messages: local_id TEXT PRIMARY KEY (repository генерирует UUID; SQL проверяет только 36 символов); provider_id TEXT NOT NULL (1–4096 bytes); folder_local_id TEXT NOT NULL → mail_folders(local_id) ON DELETE CASCADE; nullable conversation_provider_id TEXT (1–4096); subject TEXT NOT NULL ≤998; nullable from_name TEXT ≤512 и from_address TEXT ≤320; recipients_json TEXT NOT NULL ≤32,768; nullable display_to TEXT ≤2,048; preview TEXT NOT NULL ≤4,096; received_at TEXT NOT NULL ≤32; is_read, is_flagged, has_attachments INTEGER NOT NULL ∈ {0,1}; importance TEXT NOT NULL ∈ low|normal|high; sort_order INTEGER NOT NULL 0…99,999; active_generation INTEGER NOT NULL > 0; UNIQUE(folder_local_id, provider_id). Индекс mail_messages_folder_snapshot_order(folder_local_id, active_generation, sort_order) обслуживает pinned folder-generation reads, а mail_messages_folder_snapshot_date(folder_local_id, active_generation, received_at DESC, sort_order) (schema v5, ADR-0095) — выдачу страницы списка. received_at — это дата письма, а не обязательно дата доставки: в папках с ролями sent/drafts/outbox провайдер кладёт туда дату отправки (Exchange: маппинг → Дата письма). Пустая дата недопустима: canonicalInstant в normalizeMessagePage отвергает страницу целиком, а вместе с ней срывается весь обход папки, поэтому провайдер обязан отдавать хоть какую-то дату. Nullable smime TEXT ∈ {encrypted, signed} (schema v8, ADR-0131) — пометка S/MIME строки списка, без содержимого.
  • mail_message_aliases: folder_local_id TEXT NOT NULL → mail_folders(local_id) ON DELETE CASCADE; provider_id TEXT NOT NULL (1–4096 bytes); local_id TEXT NOT NULL → mail_messages(local_id) ON DELETE CASCADE; last_seen_generation INTEGER NOT NULL > 0; составной PRIMARY KEY(folder_local_id, provider_id). Индекс mail_message_aliases_local(folder_local_id, local_id) поддерживает folder-scoped alias pruning.
  • mail_message_staging: folder_local_id TEXT NOT NULL → mail_folders(local_id) ON DELETE CASCADE; refresh_generation INTEGER NOT NULL > 0; provider_id TEXT NOT NULL (1–4096 bytes); sort_order INTEGER NOT NULL 0…99,999; payload_json TEXT NOT NULL ≤65,536 bytes; составной PRIMARY KEY(folder_local_id, refresh_generation, provider_id) и UNIQUE(folder_local_id, refresh_generation, sort_order). Отдельного индекса нет: обе auto-index constraints покрывают locator и page-order uniqueness.
  • mail_message_window (schema v6, ADR-0096): folder_local_id TEXT PRIMARY KEY → mail_folders(local_id) ON DELETE CASCADE; generation INTEGER NOT NULL > 0 — поколение, к которому окно пришпилено; next_offset INTEGER NOT NULL 0…100 000 — серверное смещение, с которого продолжит прокрутка; server_total INTEGER NOT NULL 0…100 000 — сколько писем сервер насчитал в папке на момент снимка (та самая оценка, которую показывает и Outlook); complete INTEGER NOT NULL ∈ {0,1} — обход дошёл до «больше нет», то есть снимок равен папке целиком; extended_at TEXT NOT NULL ≤32 (канонический ISO). Ровно одна строка на папку: публикация поколения её перезаписывает (ON CONFLICT(folder_local_id) DO UPDATE), догрузка хвоста обновляет next_offset/server_total/complete/extended_at по совпадению (folder_local_id, generation). Отдельная таблица, а не поле в sync_sessions: та общая с папками и календарём, не STRICT и без внешнего ключа на mail_folders, а её page_cursor уже означает «незавершённый обход, продолжить с этого смещения» — опубликованный курсор окна был бы от него неотличим после падения. Отсутствие строки = поколение построено сборкой до v6 (или снимок папки заведён переносом письма) и читается как полный снимок; строка от другого поколения тоже читается как «окна нет» — fail-safe в прежнюю семантику.
  • mail_invitation_answers (schema v7, ADR-0097): internet_message_id TEXT PRIMARY KEY 1–998 bytes — устойчивая личность письма-приглашения (RFC 5322 Message-ID, ADR-0074); action TEXT NOT NULL ∈ add|accept|tentative|decline — что человек попросил сделать; response_sent INTEGER NOT NULL ∈ {0,1} — ушёл ли при этом ответ организатору; answered_at TEXT NOT NULL ≤32 (канонический ISO). Индекс mail_invitation_answers_by_time(answered_at) обслуживает подрезку. Запись — upsert (ON CONFLICT(internet_message_id) DO UPDATE), причём response_sent только поднимается (max(старое, новое)): «организатору сообщили» — свершившийся факт, письмо уже ушло, и последующее тихое добавление его не отменяет. Подрезка оставляет 500 последних строк (ORDER BY answered_at DESC, internet_message_id DESC, удаление хвоста через LIMIT -1 OFFSET 500) — это подсказка под карточкой, а не архив. И запись, и чтение (recordInvitationAnswer / readInvitationAnswer в LocalMailRepository) глотают свои ошибки: потеря памяти возвращает прежнее поведение, и ронять из-за неё уже совершённую запись приглашения нельзя.
    • Почему ключ — личность письма, а не идентификатор элемента. ItemId Exchange перевыпускает при каждом перемещении (Exchange: EWS → Личность письма), а ответ на приглашение письмо как раз перемещает — Accept/Decline уносят его в «Удалённые», откуда провайдер возвращает его Move-ом обратно. Ключом по ItemId строка протухала бы ровно в тот момент, ради которого заводилась. Внешнего ключа на mail_messages нет: память ключуется личностью письма, а не строкой снимка, и поэтому переживает и перестройку поколения, и отсутствие письма в окне списка (ADR-0096). Аккаунт в ключе тоже не нужен — база своя у каждой учётной записи.
  • mail_folder_sync (schema v10, ADR-0154): folder_local_id TEXT PRIMARY KEY → mail_folders(local_id) ON DELETE CASCADE; phase TEXT NOT NULL ∈ catchup|live — первичный проход идёт или папка уже узнаёт изменения синхронизацией; nullable sync_state TEXT 1–2 097 152 bytes — непрозрачное SyncState сервера (base64; в live обязательно — CHECK); nullable opened_at TEXT ≤32 — когда папку открывали (кандидаты первичного прохода, индекс mail_folder_sync_by_open); updated_at TEXT NOT NULL ≤32. Состояние никогда не покидает main: ни в окно, ни в журнал (там только его длина stateBytes). Пишется только одной транзакцией с применёнными изменениями страницы (applyFolderChanges) или шагом первичного прохода (saveCatchupPage). Счётчики сбросов, паузы «сервер занят» и «папка выключена до перезапуска» — в памяти репозитория, не в таблице.
  • Существующая не-STRICT v1 sync_sessions получает nullable owner_pid INTEGER и owner_token TEXT. Для нового building refresh оба поля обязательны на уровне repository contract: PID процесса и случайный UUID token экземпляра; завершение/failure очищает оба. Nullable DDL нужен для совместимого ALTER TABLE, но missing/invalid tuple считается unknown и не может быть автоматически reclaimed.
  • Порядок выдачи списка (readMessages, ADR-0095) — ORDER BY message.received_at DESC, message.sort_order. До schema v5 строки отдавались ORDER BY sort_order, то есть в порядке обхода папки, а обход шёл в том порядке, в каком письма вернул сервер. Для «Отправленных» это расходилось с датой письма, и свежая отправка с другого устройства лежала в базе на девятитысячной строке — скачанная, но невидимая. sort_order остался вторым ключом: при одинаковых датах он делает порядок устойчивым, поэтому постраничная догрузка по LIMIT/OFFSET не даёт ни дублей, ни пропусков. Серверный OrderBy и этот ORDER BY согласованы по смыслу одного и того же поля.
  • Чтение усечённого окна (readMessages, ADR-0096). Если строка mail_message_window принадлежит активному поколению и в ней complete = 0, снимок — префикс папки, и ответ это признаёт: в total уходит max(server_total, число локальных строк) — серверная оценка на момент снимка, то есть то же число, что показывает Outlook, — а hasMore истинно и за краем загруженной страницы, и за краем всего окна (offset + items.length < total || truncated): дальше ответит сервер, и следующий запрос в режиме paginate дотянет хвост. У полного снимка (complete = 1) и у поколения без строки окна всё как раньше: total — число строк снимка, hasMore — только «загружено не всё, что лежит локально». Одно и то же LIMIT/OFFSET читает при этом локальные строки в порядке received_at DESC, sort_order, а next_offset окна — это серверное смещение обхода; величины разной природы, и путать их нельзя.

Папка и письмо имеют случайный локальный UUID, отдельный от изменяемого идентификатора провайдера. Он сохраняется при явной замене provider ID через trusted previousId в том же folder scope, а для подтверждённого приложением переноса — и между folder scopes. Контракт MailProvider.moveMessages возвращает ordered per-item результаты: подтверждённый {status: 'moved', previousId, id, folderId} или {status: 'failed', ...}. Exchange вызывает MoveItems(..., returnNewItemIds=true), канонизирует provider-owned response ровно один раз и проверяет cardinality, result, ID и дубли; успешные siblings не теряются при частичном сбое. Demo возвращает неизменившийся ID только для реально найденной записи. LocalMailReadModel.applyMessageMove принимает только подтверждённый transition, сверяет прежний ID с активным снимком и одной SQLite transaction переносит существующую mail_messages.local_id, сохраняет исходный alias как tombstone против stale source refresh, записывает новый target-scoped alias, переключает target generation в stale и обновляет folder counters. Batch подтверждённых transitions оборачивается общей внешней transaction: ошибка позднего элемента откатывает всю локальную проекцию. Если server move уже необратимо подтверждён, но локальная проекция не принимается, IPC сохраняет provider results как server truth, помечает опубликованные snapshots stale и не превращает успех сервера в общий transport failure.

Для одной локальной папки или одного локального письма при snapshot refresh сохраняются не более восьми последних locator-значений; более старые удаляются атомарно при успешной публикации. Публикация конфликтующих alias или попытка свести две записи к одному локальному UUID отклоняется целиком. Message aliases остаются folder-scoped: подтверждённый приложением move уже сохраняет identity явно, но перенос, выполненный другим клиентом и обнаруженный только двумя независимыми full snapshots, пока нельзя надёжно сопоставить. Синхронизация по изменениям (ADR-0154) видит такой перенос как Delete старого id в исходной папке и Create нового id в целевой, но склейку двух записей в одну локальную identity не делает — это по-прежнему следующий этап. Первый tracer bullet сохраняет совместимость renderer: наружу по-прежнему выдаются server IDs, а локальный UUID остаётся внутренним identity; атомарная смена всего renderer/IPC ID-контракта ещё не выполнена.

Снимки папок публикуются поколениями. Для сообщений поколение ведётся отдельно на каждую папку. Каждый незавершённый refresh имеет owner {pid, token}: другой живой repository не может перехватить или очистить его. Graceful close сначала атомарно переводит store в closing, поэтому новые read/refresh операции запрещены до первого cleanup hook; затем переводит только принадлежащие этому store refresh в stale/error. Ошибка cleanup оставляет SQLite handle открытым в close_failed, сохраняет hooks для явного retry и не освобождает lease. Constructor recovery очищает только owner с PID, для которого ОС подтверждает ESRCH, и перепроверяет token внутри транзакции. Живой, переиспользованный или недоступный для проверки PID считается активным fail-closed: автоматическое разрушение его staging запрещено. beginMessageRefresh возвращает immutable handle с локальным UUID folder scope и исходным remote ID: продолжение, завершение и failure cleanup не ищут заново mutable alias после сетевого ожидания. Полное чтение sync_sessions + count + rows закрепляется одной SQLite read transaction, поэтому параллельная публикация другим process не смешивает поколения. Начало обновления и очистка старого staging выполняются одной транзакцией. Страницы сетевого результата сначала попадают в mail_message_staging; reader продолжает видеть последнее опубликованное активное поколение. Где остановиться, решает синхронизатор, а не арифметика страницы (ADR-0096): appendMessagePage только копит страницу в staging и возвращает {staged, nextOffset, hasMore, total}, а отдельный publishMessageWindow одной транзакцией переносит весь накопленный набор в опубликованные строки, переключает active generation и записывает строку mail_message_window. Окно — WINDOW_PAGES страниц по 200 (пять, то есть тысяча писем) либо вся папка, если она короче; с ADR-0143 поколение публикуется уже после первой страницы, а остальные страницы окна дописывает фоновый хвост (см. «Свежесть после собственных действий» ниже). Прежние требования «TotalCount не менялся весь обход» и «число staged-строк равно total» сняты: у живого ящика число писем меняется прямо во время чтения, и «неизменный TotalCount семьдесят секунд» невыполнимо в принципе. Осталось то, что от этого дрейфа не зависит: инварианты личности в нормализаторе (fail-closed, не тронуты), запрет повтора внутри обхода (он же первичный ключ staging), совпадение ожидаемого смещения (page_cursor теперь хранит только {offset}, без total) и терминатор от синхронизатора. Проверять «страница обязана убывать по дате» при этом нельзя: дата строки берётся по цепочке запасных полей (ADR-0095), а сервер сортирует одним полем — письмо с пустым ведущим полем законно приезжает не на своём месте, и такое правило забраковало бы из-за него всю папку. Когда обход дошёл до конца папки (complete), «сколько писем» берётся из факта (stagedCount), а не из серверной оценки, — иначе число в шапке разошлось бы со списком прямо под ним.

Инвариант поколения теперь звучит так: опубликованное поколение — префикс папки в порядке ADR-0095, целый либо старый; прокрутка может удлинить хвост, и каждое удлинение атомарно само по себе и пришпилено к тому поколению, из которого читали. Ошибка, перезапуск, пропуск или повтор страницы по-прежнему не публикуют частичный набор, а частичную страницу догрузки читатель не видит никогда. Ослабление настоящее, но узкое: extendMessageWindow только дописывает строки в хвост живого поколения (sort_order продолжается от max(sort_order) + 1) и не переписывает ни одной уже опубликованной, а следующая публикация сносит хвост целиком. Пришпиленность проверяется дважды — sync_sessions.active_generation и mail_message_window.generation обязаны совпасть с тем поколением, из которого читали: если пока догрузка ходила в сеть, обновление опубликовало новое, она отказывает typed stale_refresh, а не дописывает в чужое. Потолок окна намеренно равен прежнему пределу снимка (MAX_WINDOW_MESSAGES = MAX_MESSAGES, 100 000 писем на папку): прокрутить папку можно ровно до того места, где раньше заканчивался полный обход; переполнение — typed window_exhausted.

Асимметрия «отвергнуть против поджать» — намеренная, а не недосмотр. Публикация отказывает окну, у которого серверная оценка меньше его же строк (Message window total is below its own rows) или курсор отстал от его же строк: на публикации это означает сломанный обход, и публиковать его нельзя. Догрузка в том же случае молча поднимает оценку до факта (Math.max(page.total, rows + appended)) — потому что отказ заклинил бы прокрутку навсегда: оценка падает сама собой, стоит удалить письма из папки. По той же причине догрузка пропускает письмо, уже известное этому окну, а не отвергает страницу с перекрытием: удаление выше окна сдвигает серверные смещения, и перекрытие страниц законно. Смещение при этом двигается на сырую длину серверной страницы, включая пропущенные строки, — сервер считает их своими. Обратный случай (пропуск строки при сдвиге смещений) арифметикой по-прежнему не виден: повторы ловятся, пропуски нет. Окно лишь сокращает экспозицию с семидесяти секунд до одной страницы; снимает её совсем только инкрементальная синхронизация.

После recovery staging очищается, а последний полный снимок остаётся читаемым со статусом stale; без предыдущего снимка статус становится error.

Production tracer bullet

После process-wide single-instance admission и app.whenReady() main создаёт один AccountRepositoryManager. Factory использует только Electron safeStorage, account-hash root под userData и точную registry authority. Manager сериализует открытия по accountId, переиспользует repository только для полного совпадения {accountId, generation, revision, principal}, закрывает старый handle до открытия replacement и повторно проверяет authority после каждого await. Если authority сменилась во время открытия, новый handle закрывается и не публикуется. Удаление аккаунта синхронно ставит admission barrier до входа в account queue: новые get/read/refresh не могут встать за destruction и переоткрыть только что удалённую БД. Barrier остаётся активным внутри той же account queue после локального destruction вплоть до успешного commit удаления registry authority; только после этого прежняя authority блокируется как завершённо удалённая, а новая полная authority (replacement generation/revision/principal) получает новый repository. Ошибка destruction или registry commit атомарно снимает admission barrier: surviving authority может открыть новый пустой encrypted store и повторить удаление, а не остаётся заблокированной до restart. Повторный concurrent remove того же владельца дедуплицируется. Удаление фиксирует полную authority, открывает/сверяет точный store при необходимости, закрывает repository и под lifecycle lock вызывает EncryptedAccountStore.remove с exact storeUuid. Cache/WAL/SHM, blobs, envelope и account directory удаляются до registry credentials; authority replacement или ошибка destruction отменяет удаление registry. before-quit дожидается закрытия всех repository перед повторным app.quit().

Для реального аккаунта mail:folders и mail:messages открывают account repository. При отсутствии опубликованного снимка или при незавершённом building handler ожидает provider refresh (с ADR-0096 это обход окна, а не всей папки; с ADR-0143 ожидание кончается на первой опубликованной странице, остальные страницы окна дописывает хвост в фоне); при готовом/устаревшем снимке сразу возвращает последнее опубликованное поколение (с ADR-0096 — окно папки, см. ниже) и запускает атомарный refresh в фоне. После успешной фоновой публикации main повторно проверяет exact account authority и отправляет только главному renderer mail:events с {accountId,generation,revision,principal} и folderSnapshot либо первой страницей messageSnapshot; вторичные окна не получают этот PII payload. Renderer принимает replacement только для exact active authority и folder, а snapshot epoch не позволяет более старому cache-first invoke-response перезаписать push. При drift первая страница заменяет loaded viewport целиком и сбрасывает pagination: смешивать её со старым tail нельзя, потому что insertion/deletion меняет ownership смещений и приводит к пропускам/дублям. Частичная страница с hasMore=true при этом не доказывает исчезновение выбранного tail item: reading pane сохраняется до полного authoritative списка или terminal detail result. Отдельный messageOffset описывает continuation текущего provider state: IDs, скрытые после подтверждённого local move/delete, вычитаются даже если поздний pre-mutation snapshot ещё содержит их. Поэтому следующий loadMore не пропускает строку после удаления. У mail:messages три режима (MailListMode в mail-load.ts, выбирает IPC-обработчик по opts.offset): revalidate — первая страница, она одна владеет видимым поколением, запускает фоновое обновление окна и рассылает push; paginate — прокрутка: она это поколение только читает и конкурирующий full refresh не запускает, но с ADR-0096 может сходить в сеть сама — если offset + limit не влезает в окно, а папка на сервере длиннее (readMessageWindow → не complete и rows < need), repository.extendMessages → MailSnapshotSynchronizer.extendWindow дотягивает хвост, и страница перечитывается уже из удлинённого снимка; cached — отдать, что есть, и никуда не ходить. Догрузка ограничена: не больше WINDOW_PAGES страниц за вызов (одно «Показать ещё» не превращается в обход всей папки) и не больше одной идущей догрузки на пару «папка + запрошенная глубина» (ключ дедупликации включает need, иначе второе нажатие получило бы ответ на первое). Если строки окна нет (поколение от сборки до v6 либо снимок, заведённый переносом письма) или окно уже complete — paginate в сеть не идёт и ведёт себя как прежде. За разрывом догрузка не гонится: если offset оторвался от загруженного (offset > rows), main отдаёт кэш и в сеть не идёт. Прокрутка идёт подряд, поэтому такой запрос — не прокрутка, а смещение приходит из окна рендерера, и доменная модель допускает сколь угодно большое; гнаться за ним значило бы отдать рендереру рычаг «сделай сколько хочешь запросов к серверу». Revalidation по-прежнему принадлежит первой странице. Успешные локальные move/delete держат authority-scoped FIFO hidden-ID overlay (до 2 048 IDs на authority) против более старого push; failed/partial элементы снимаются с overlay. Foreground и background replacement очищают завершённые body entries в main detail LRU; сравнение двух полных поколений одной папки выдаёт exact removed IDs, и admission epochs отклоняют только их летящие detail requests, не затрагивая другие папки. Частичная первая страница не отменяет возможный tail request. Если snapshot приходит во время optimistic mutation, failed/partial rollback перечитывает последнее локальное поколение вместо восстановления pre-snapshot viewport. Provider adapter проверяет authority до и после сетевого ожидания. Все refresh и mutation одного repository проходят через общий mutex. Demo не создаёт persistent store.

mail:move канонизирует ordered per-item DTO повторно на IPC boundary, применяет только moved transitions для уже известной локальной identity, удаляет/broadcast только подтверждённые старые IDs и возвращает полный partial result renderer. Provider-owned arrays на обеих границах имеют один раз захваченный bounded length, после чего читаются только по фиксированному числу индексов. Renderer при частичном результате оставляет удалёнными только подтверждённые элементы и восстанавливает failed siblings из optimistic snapshot. Account/folder/operation epoch отбрасывает ответ, пришедший после reset, удаления или переключения аккаунта/папки. Письмо из server search, которого ещё нет в локальном snapshot, переносится сервером, но локальный transition не применяется до последующей синхронизации.

Границы ingest проверяются до записи: до 500 папок, до 200 писем и 2 MiB UTF-8 на сетевую страницу, до 100 000 писем и 64 MiB staged JSON на снимок. Окно папки — пять таких страниц (WINDOW_PAGES, тысяча писем) либо меньше, если папка короче (первая публикуется сразу, остальные дописывает хвост, ADR-0143), а предел в 100 000 писем на папку служит теперь и потолком окна, до которого его может дотянуть прокрутка (ADR-0096). На финальной публикации staging читается внутри той же транзакции ограниченными batch по 100 строк, а не материализуется целиком в памяти. Provider ID ограничен 4096 байтами; subject, preview, адреса, получатели, даты, счётчики, глубина и enum-поля имеют отдельные пределы. Размеры текста проверяются в UTF-8 и повторно закреплены SQL CHECK(length(CAST(value AS BLOB))); значения не обрезаются. Один некорректный элемент или превышение cumulative quota отклоняет страницу целиком и не продвигает cursor/поколение.

Текущее состояние с tracer bullets — не объявление полной автономной почты. В него ещё не входят тела писем, attachment metadata/blobs, долгоживущий tombstone retention, FTS, account-wide storage/quota controls и offline mutation queue. Окно списка (ADR-0096) снимает стоимость обхода, но само не обнаруживает удаления и смену флагов за своими пределами — это делает синхронизация по изменениям (SyncFolderItems + SyncState, ADR-0154, раздел ниже) для папок, прошедших первичный проход; остальные папки живут прежним окном. Ухудшения здесь нет: provenRemovedIds и до окна доказывал удаление только для папок короче страницы. Побочный эффект перехода: папки в несколько тысяч писем, прежде «известные целиком», становятся усечёнными, и ветка подрезки кэша тел по ним перестаёт срабатывать — кэш и так ограничен по объёму, корректность не страдает. Folder/message list IPC уже читают локальное последнее поколение, но detail/search и остальные мутации продолжают работать напрямую через провайдера. Если online getMessage возвращает stale/not_found для строки старого снимка, reading pane завершает loading терминальным состоянием «перемещено, удалено или недоступно», запускает revalidation папки и удаляет stale body/image entry только после server signal/snapshot. network и auth показываются отдельно: offline metadata не удаляется, бесконечного spinner нет, retry остаётся явным. Успешный detail с пустым bodyHtml считается валидным письмом без тела, а не ошибкой.

Картинки писем на диске — schema v9 (ADR-0149)

Тела писем по-прежнему живут только в памяти, а картинки cid: уже открывавшихся писем с ADR-0149 лежат ещё и в базе ящика. Демо-ящик своей базы не имеет и диск не использует.

AND cid = ?): одиночный запрос картинки не поднимает байты всего письма; удаление письма — один DELETE … RETURNING bytes.

Общий список не заводит ни таблиц, ни нового IPC: renderer читает «Входящие» каждого ящика тем же mail:folders/mail:messages, что и папку, — из его локальной базы, с фоновым обновлением и messageSnapshot по ящику. Свежесть после собственных действий (ADR-0143, P1)

Схема хранилища не меняется; меняется то, когда и как снимок обновляется.

  • Публикация после первой страницы. MailSnapshotSynchronizer.refreshFirstPage(folderId, mayPublish) начинает обход, берёт одну страницу (200) и сразу публикует поколение — complete по её «есть ещё», serverTotal = max(total, staged). Остальные страницы окна (WINDOW_PAGES) дописывает fillWindow → extendWindow — тот же путь, что у прокрутки, поэтому инвариант ADR-0096 прежний: опубликованное — префикс в порядке ADR-0095, хвост только удлиняется. Хвост идёт в фоне, на низком приоритете (runWithTrace('fill_message_window', …, 'low')), и спрашивает proceed() перед каждой страницей и перед каждой записью: новый обход той же папки (номер обхода refreshTokens) или своя запись в ящик его останавливают. «Сервер сказал, что папка кончилась, но насчитал больше на страницу» по-прежнему попадает в журнал — теперь на первой странице.
  • Очереди. Обновление и догрузка писем — в очереди своей папки (inFolder); общая exclusive() осталась за деревом папок и календарём (mutateFolders, mutateCalendar, их обновления — как прежде). Перемещение и удаление — mutateMessages: записи писем друг за другом, но не за чужими обходами. close() сначала ставит признак «закрываемся» (новые обходы, догрузки и записи отклоняются, хвосты останавливаются), затем дожидается очередей папок и записей.
  • Повтор вместо присоединения. refreshMessages во время идущего обхода той же папки возвращает один назначенный повтор (follow), который начнётся после текущего; все, кто пришёл за это время, получают его. Раньше запрос получал уже идущий обход, снятый, возможно, до только что отправленного письма.
  • Счётчик своих записей. messageEpoch растёт до и после каждой mutateMessages (перемещение, удаление), так что нечётное значение значит «запись идёт» — обход тогда сначала ждёт её. Обход запоминает чётное значение перед сетью; mayPublish()/proceed() сверяют его синхронно прямо перед публикацией или дописыванием. Не совпало — MailSnapshotStaleError, поколение отменяется (failMessageRefresh), обход повторяется (до трёх попыток; затем остаётся прежний снимок). Так обход, снятый до перемещения, не публикуется после него — без ожидания сети под общей блокировкой.
  • Прибытие — в живое поколение. LocalMailRepository.noteArrivals(folderId, messages) → LocalMailReadModel.insertArrivals: та же нормализация страницы, что у обхода (в том числе запрет «письмо из другой папки»), sort_order продолжается от max + 1, next_offset не трогается (сервер сдвинул свои смещения на ту же единицу, перекрытие следующей страницы догрузка пропускает), у усечённого окна server_total растёт на число добавленных. Известное окну письмо пропускается, письмо, которое снимок числит переложенным (mail_message_aliases в другой папке), не воскрешается, папка без опубликованного поколения не трогается, предел окна соблюдается. Репозиторий держит до 50 недавних прибытий на папку: если обход шёл в момент прибытия, после публикации письмо дописывается снова; обход, начатый после прибытия, — правда о нём, и память о письме снимается. Вызывает это watcher через setArrivalRecorder (ipc/mail-freshness.ts), только для настоящих ящиков и только письма той папки, о которой сказал наблюдатель. Прибытие, которое сервер успел убрать до следующего запроса изменений, синхронизация удалённым не назовёт — такие строки убирает уборка пропавших писем (см. ниже, «Письма, которых нет на сервере»).
  • Где лежит письмо. findMessageFolderRemoteId(remoteId) — папка письма по живым поколениям (одна строка — ответ, иначе null); служит только для области эха своей записи (см. Процессы и IPC).

  • страница применяется, только если в базе лежит то же состояние, с которым её брали (expectState), а папка — live; иначе stale_refresh и ничего не записано;
  • идёт обход окна (building) — refresh_in_progress (в жизни не бывает: проход и обход — в одной очереди папки);
  • окна нет (снимок ещё не публиковался) — записывается только состояние: следующий обход заведомо новее;
  • известное письмо переписывается на месте (тема, отправитель, дата, «прочитано», флаг, вложения, важность, S/MIME, беседа) — только если что-то отличается; read меняет одно «прочитано»; delete удаляет строку (письмо уходит в removedIds, их кэши тел забываются);
  • полное окно (complete = 1): новое письмо вставляется, оценка «сколько писем» = числу строк;
  • усечённое окно: граница — самая старая дата в нём; новое письмо старше границы не вставляется (оценка +1), изменённое так, что ушло ниже границы, из окна выходит; удаление письма, которого окно не знает, — оценка −1. Смещение хвоста после вставок и удалений: max(0, min(next_offset + вставки − удаления, строки) − 20) — перекрытие догрузка пропускает как известное, а дыру не заметила бы;
  • письмо, которое снимок числит перенесённым нами в другую папку (findMovedIdentity), не воскрешается;
  • негодная строка (дата не в каноне, текст длиннее предела) пропускается и считается (skipped), остальная страница применяется — одна странная строка не должна навсегда заклинить состояние;
  • итог: { changed, removedIds, skipped, upsertedIds, read, leftIds }. changed = 0 — окну ничего не публикуется. Построчные поля — для изменений окну (этап 2): upsertedIds — строки, вставленные или переписанные; read — строки, у которых поменялось только «прочитано»; leftIds — строки, ушедшие ниже границы усечённого окна (письмо в папке осталось, поэтому это не removedIds и кэши тел его не теряют).

Своя запись. LocalMailRepository.markWrite(ids, marks, write) для «прочитано» и флага: счётчик markVersion растёт до и после записи (отдельно от messageEpoch переносов — обходы окна «прочитано» не ждут), поля этих писем на время записи защищены от перезаписи страницей (overlayPendingMarks), подтверждённая правка сразу переписывает строки снимка (patchMessageMarks, по всем папкам). Страница, снятая, пока запись шла, не применяется — MailSnapshotStaleError, и тот же запрос повторяется с тем же состоянием после записи (не больше трёх попыток).

Проход. syncFolder(folderId, provider, validate, reason): идёт в очереди папки (inFolder, вместе с обходами и догрузкой — порядок «окно не старше состояния» держится очередью); до 8 страниц; один проход на папку, причина во время прохода — ровно ещё один после, открытие присоединяется; открытие в течение 5 с после прохода (20 с после прохода по событию сервера) — ничего. Отказы синхронизации проход не бросает, а решает сам (сброс, «папки нет», пауза ящика, «папка выключена») и сообщает слушателю (FolderSyncListener: changed, catchupNeeded, retryLater), которого ставит main (ipc/mail-sync.ts). Шаги первичного прохода идут мимо очереди папки (окна не трогают), но закрытие репозитория их дожидается.

Письма, которых нет на сервере (ADR-0154, поправка «Письма, которых нет»)

Дыра между прибытием и синхронизацией. Письмо, пришедшее потоком, ложится в окно мимо синхронизации (noteArrivals, см. выше). Если сервер убрал его раньше следующего запроса изменений (типичный случай — приглашение, на которое ответили в другой программе: сервер перекладывает или удаляет его сам), SyncFolderItems его не назовёт удалённым никогда: для состояния синхронизации письма не было. Окно live-папки не перечитывается, «сверка» — тот же запрос изменений, поэтому до правки такая строка жила вечно, в том числе через перезапуск. Подробности протокола — Exchange (EWS) → Синхронизация папок.

Доказательство — ответ сервера по id письма. ErrorItemNotFound при чтении письма (MailError('stale')) или на элементе записи (missingIds, статус переноса item_not_found, см. Возвращает MissingMessagesRemoved[] — { folderId, removedIds } по папкам; строки, которых снимок не знает, — пустой результат, и дальше ничего не происходит (ни снимка, ни запросов). Сбой базы — пустой список и запись в журнал. До этого те же id вычёркиваются из памяти недавних прибытий (мостик ADR-0143 P1), иначе публикация идущего обхода дописала бы призрак обратно. Уборка идёт мимо mutateMessages и счётчика своих записей — осознанно: это не запись в ящик, а уборка доказанно пропавшего; обход, снятый до пропажи, исправит перечитывание окна (шаг 4).

  4. Перечитывает окно папки (refreshMessages, runWithTrace('reconcile_missing', …, 'background')) и публикует снимок ещё раз — настоящая сверка: если «призраков» в окне несколько, уходят все. Не чаще раза в REREAD_COOLDOWN_MS = 60_000 на папку: прогрев может наткнуться на несколько призраков подряд.

Local-first календарь — schema v3

LocalCalendarReadModel использует ту же account binding, encrypted store, owner {pid, token} и close/recovery discipline, что почтовая модель. calendar_events хранит только allowlist-копию лёгкого CalendarEvent: provider ID, строгие UTC ISO-границы, sort order и bounded JSON (до 16 KiB на событие, до 999 элементов и 8 MiB JSON в одном refresh). calendar_coverage отличает известный пустой снимок от cache miss и хранит покрытые полуинтервалы [start,end) с собственными synced_at и freshness; failure диапазона A не делает stale диапазон B. calendar_refresh_range сохраняет точные границы незавершённого поколения. Constructor recovery и поздний takeover владельцем, который увидел смерть foreign PID уже после своего создания, сначала атомарно помечают stale именно прерванный persisted диапазон и только затем публикуют новое building-поколение.

Успешный refresh одной SQLite transaction удаляет все события, пересекающие авторитетный диапазон, вставляет полный provider result и заменяет соответствующее покрытие. Поэтому удалённая на сервере встреча исчезает, пустой ответ сохраняется как известный пустой снимок, а соседние части более широкого покрытия не теряются. Чтение объединяет пересекающиеся coverage-сегменты, не допускает дыр и возвращает события один раз по глобально уникальному provider ID. Некорректный ID, duplicate, событие вне диапазона, oversized payload, длительность события более 180 суток или interval более 366 суток отклоняют публикацию целиком. Диапазон ограничен 1900–2200 годами, rolling cache — 50 000 rows и 4 096 coverage intervals. Ровно 1 000 элементов считается неоднозначным cap CalendarView: такой результат НЕ публикует coverage, а оставляет прежний snapshot stale. С ADR-0056 allowlist-копия включает joinUrl (MAX_JOIN_URL = 2048): значение обязано быть канонической формой — normalizeExternalHttpUrl(joinUrl) === joinUrl (тот же shared/external-url.ts, что у провайдера и у renderer), иначе публикация всего диапазона отклоняется («Calendar event contains an invalid join link»), как и при javascript:, userinfo, пробеле в пути, отсутствии схемы или нестроковом значении. Строки старых снимков без поля остаются валидными — миграция схемы не нужна. Лимит нормализатора действует и на percent-encoded форму, чтобы одна не-ASCII ссылка не могла сделать снимок непубликуемым. Это единственная валидация ссылки на пути «диск → renderer»: из SQLite в shell-границу попадает только то, что уже прошло провайдера и повторно пройдёт safeOpenExternal в main (Безопасность). С ADR-0167 allowlist-копия включает и myResponse — мой ответ на встречу (organizer | accept | tentative | decline | noresponse | unknown, проверка по CALENDAR_RESPONSES в calendar-read-model.ts): значение вне списка отклоняет публикацию диапазона («Calendar event contains an invalid response»), отсутствующее поле — норма (строки, записанные до него, читаются; копия поле просто не получает). Миграция схемы не нужна.

Счётчик изменений календаря: поход «до записи» не присоединяется (ADR-0167). refreshCalendar(start, end, …) дедуплицирует походы одного диапазона: второй вызов присоединялся к уже идущему. Это ломалось на записи, которая идёт мимо очереди снимка: ответ на приглашение пишет в календарь на сервере не через mutateCalendar (как создание и перенос), и если поход начался до записи, перечитывание после неё получало его результат — календарь без только что принятой встречи — и публиковало как свежий. Теперь у LocalMailRepository есть счётчик calendarWriteGen, и запомненный поход хранит поколение, при котором начат (calendarRefreshes: Map<key, { gen, refresh }>):

noteCalendarChange(): void { this.calendarWriteGen += 1 }

refreshCalendar(start, end, provider, validateAuthority) {
  const key = `${start}\u0000${end}`
  const gen = this.calendarWriteGen
  const current = this.calendarRefreshes.get(key)
  if (current && current.gen === gen) return current.refresh // присоединяемся только к «свежему»
  // иначе — новый поход в очереди за прежним (this.exclusive), запомненный с текущим gen
}

noteCalendarChange() зовёт main (noteCalendarChanged в ipc/mail.ts) в двух случаях: после зафиксированного ответа на приглашение — до рассылки mail:calendarInvalidated — и при изменении папки «Календарь» на сервере (Процессы и IPC, «Изменения календаря на сервере»). Сам клик «Принять» в общую очередь хранилища не ставится — там же идёт синхронизация почты. Демо-ящик счётчик не трогает: он читает календарь мимо снимка. Покрытие — local-data/repository-calendar.test.ts (поле ответа в снимке; поход до изменения не присоединяется, после изменения — второй запрос).

mail:calendar для холодного диапазона ожидает первую полную публикацию, включая concurrent exact-range запрос: building вызывает ожидание repository-deduplicated refresh и повторное чтение, а не возвращает псевдо-fresh пустой список. Глобальная sync_sessions.phase=building не превращает другой cache miss в building: uncovered range получает этот статус только при точном совпадении с persisted calendar_refresh_range, а disjoint range остаётся empty и запускает собственную serialized загрузку. Ошибка target range очищает renderer events и всю связанную freshness metadata (refreshing=false, syncedAt=null), поэтому состояние предыдущего диапазона не переносится на новый key. Для тёплого диапазона main немедленно возвращает CalendarRangeData {items,state,refreshing,syncedAt}, запускает refresh в account repository mutex и после authority-check публикует mail:calendarUpdated. Renderer применяет push только при точном совпадении accountId + start + end; поздний результат другого аккаунта или диапазона не может вернуть себе viewport. Сетевая ошибка переводит видимый снимок в offline, прочая ошибка revalidation — в stale; события не очищаются, UI остаётся интерактивным и предлагает «Повторить». Toolbar/mode navigation сразу рисует prefetched page или date-correct placeholder и не ждёт cold provider response. Успех атомарно заменяет список и снимает статус.

Adjacent prefetch использует тот же pipeline. Пока холодный сосед ждёт сеть, renderer создаёт date-correct пустую страницу со статусом refresh: Month/Day/Week direct manipulation не зависит от завершения провайдера. Placeholder не считается гидратированным снимком и не подавляет foreground load после перехода. Тёплая prefetched page с refreshing=true также не подавляет foreground load: её background push мог завершиться до adoption и быть отброшен exact-range store, поэтому после перехода page обязательно повторно гидратируется.

Native runtime gates

**С ADR-0065 (биндинг v13, Node-API prebuild) описанная ниже дисциплина «rebuild под Electron ↔ rebuild под host Node» стала страховкой, а не необходимостью: один и тот же prebuilds/<platform>-<arch>.node грузится и в Vitest, и в Electron 44, и в упакованном приложении. Шаги CI сохранены как есть.

Vitest проверяет реальные encrypted pages/WAL: кириллический marker и SQLite format 3 отсутствуют в raw bytes, wrong key не читает строку, правильный ключ проходит оба integrity check. Перед Electron smoke CI выполняет явный electron-rebuild -f -w better-sqlite3-multiple-ciphers: обычный install-app-deps не считается доказательством, потому что может оставить установленный под host Node ABI бинарник. После Electron smoke CI обязательно восстанавливает native module под host Node ABI и подтверждает это Node smoke до запуска Vitest; перед упаковкой отдельно повторяет Electron rebuild/smoke, чтобы package не захватил восстановленный Node binary. На Linux и macOS каждый Electron job до первого rebuild повторяет полную local-data matrix, включая process races и symlink containment. На Windows production factory подключает проверенный CreateFileW/FlushFileBuffers directory-sync и выполняет реальную публикацию encrypted envelope; отдельный raw-constructor contract по-прежнему доказывает durability_unavailable до любого account filesystem work без такого adapter; общий unit-набор исключает только POSIX-only keys.test.ts/store.test.ts, уже заменённые этими явными Windows gates. Для Windows unpacked native smoke CI отключает только PE metadata editing/signing через win.signAndEditExecutable=false: это устраняет зависимость тестового gate от Developer Mode/admin symlink privilege при распаковке winCodeSign, не меняя app.asar, app.asar.unpacked или Electron-ABI payload. Полноценное редактирование/подпись Windows executable остаётся отдельным release gate. Затем packaged smoke на всех трёх ОС проверяет кириллический marker в живом WAL до checkpoint, encrypted DB bytes, wrong/right key и оба integrity check; macOS локально дополнительно загрузила точный .node из app.asar.unpacked под Electron 33.4.11 / Node 20.18.3 / ABI 130, а после ADR-0065 — под Electron 44.4.1 / Node 24.21.0 / ABI 149 (better-sqlite3-multiple-ciphers 13.0.3). Результаты Ubuntu и Windows считаются доказанными только после успешного intended-workflow run или эквивалентного изолированного exact-SHA host gate с опубликованными командами и runtime evidence.

Проверяемая process-матрица

Vitest запускает физически независимые child processes и проверяет:

  • simultaneous fresh load/create/publish сходятся на одном storeUuid и ключе;
  • stale destroy waiter не удаляет replacement;
  • crash владельца оставляет lock и следующий open получает lock_unavailable, без автоматического stealing;
  • live foreign temp переживает publication другого процесса;
  • foreign child, открытый до remove, удерживает lease: удаление получает lock_unavailable и не трогает DB/WAL/envelope до его close;
  • racing child open блокируется на полном remove и после него получает только новый storeUuid; stale UUID не удаляет replacement;
  • abrupt child death с committed WAL восстанавливает данные, а побитый WAL отклоняется до открытия DB;
  • removal закрывает активный handle и удаляет DB/WAL/SHM, blobs, envelope и account directory целиком;
  • четыре процесса одновременно открывают один v1 store: мигрирует ровно один, остальные под BEGIN IMMEDIATE видят уже текущую версию, все сходятся на одном storeUuid.

Как устроены эти тесты, чтобы не быть хрупкими. Каждый child — холодный vite-node (трансформация TS, загрузка native SQLite, выработка ключа SQLCipher); на сильно загруженной машине — а полный npm run test:unit нагружает её именно так — один такой старт занимал 7–9 с ещё до кода хранилища. Поэтому: (1) бюджет каждого process-теста — CHILD_PROCESS_TEST_TIMEOUT_MS (90 с), а не 15 с: это проверки межпроцессной корректности, а не скорости старта; (2) одновременный старт гонки — барьер на событиях: child пишет ready в stdout, родитель ждёт все четыре и отпускает их разом через stdin; опроса файлов и фиксированных пауз нет, а смерть родителя закрывает stdin и завершает child; (3) child-ожидание release-файла в hold-open ограничено часами (120 с), а не числом попыток; (4) afterEach убивает оставшиеся child, чтобы упавший тест не держал lease во временном каталоге. Прежний вариант падал под нагрузкой по таймауту теста в 15 с (воспроизведено: 4 из 48 прогонов при 24 параллельных копиях и 48 потоках нагрузки на 12 ядрах), а кроме того child ждал release-файл лишь ~5 с (500 попыток по 10 мс), тогда как родитель ждал готовности соседей до 15 с. Гонки в коде миграции при этом не найдено: трассировка фаз показала, что admission строго сериализован и мигрирует один процесс.

Removal admission начинается синхронно до account operation queue и остаётся закрытой через close, уничтожение exact store и commit удаления registry. После committed removal main broadcast вызывает account-scoped calendar.resetAccount() до асинхронного перечитывания registry. Renderer сразу инвалидирует load/detail/move epochs, очищает events, detail cache, pending move и freshness metadata и ставит tombstone на удалённый account ID. Поэтому отказ последующего accounts.list, поздний IPC response или уже поставленный в очередь UI action не возвращают календарную PII и stale controls; другой account viewport не очищается. Ошибка registry commit откатывает registry и снимает removal barrier, позволяя безопасный retry.

Отдельный Electron/Playwright process gate запускает два настоящих main-процесса на одном temp userData: второй обязан завершиться (Linux Electron может сообщить signal termination вместо числового exit code), а owner — иметь одно главное окно; на macOS перед этим последнее окно закрывается, чтобы second-instance доказал recreation, а не только focus. Затем первый принудительно убивается (SIGKILL на POSIX, полный Electron process tree через taskkill /T /F на Windows), и новый процесс обязан получить освобождённый OS lock и открыть окно на том же профиле; Windows gate повторяет admission в ограниченном 15-секундном окне, поскольку kernel/Chromium могут освободить profile singleton немного позже события exit main-процесса. Behavioral unit regression закрепляет, что rejected admission не вызывает startup callback; source-order regression связывает реальный index.ts с этим callback раньше registerPluginSchemes() и initializeLocalMailRepositories(). Многопроцессные migration/removal gates используют явный deadline 15 секунд: на Windows четыре конкурентных encrypted SQLite child-процесса штатно могут превышать общий Vitest default 5 секунд, а timeout не должен превращать корректную сериализацию в EBUSY cleanup failure. Electron E2E удаляет временный профиль с bounded Windows rmSync retry, потому что Chromium LevelDB может освободить последний file handle уже после завершения Playwright app.close(). Остаточный EBUSY/EPERM после исчерпания retry не подменяет результат lifecycle gate: ephemeral CI runner владеет temp root и удалит его целиком; на остальных ОС cleanup остаётся строгим.
