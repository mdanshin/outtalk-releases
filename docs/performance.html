Производительность: стенд замеров и исходные показатели

Решение — ADR-0147; три уровня проверки скорости (бюджет запросов, короткий замер, полный прогон перед выпуском) — ADR-0148 и Процесс разработки → Скорость почты.

Раздел о том, как мы меряем скорость OutTalk и какие цифры у нас сейчас. Цифры нужны, чтобы любое ускорение доказывалось сравнением «до» и «после» в одинаковых условиях, а не впечатлением.

Четыре жалобы, ради которых стенд построен:

  1. После отправки письмо не появляется в «Отправленных» без ожидания или «Обновить». То же после перемещения, удаления и «прочитано».
  2. Новые входящие появляются с задержкой.
  3. Письма долго открываются, особенно с картинками.
  4. «Ответить» снова долго грузит уже открытое письмо.

Как устроен стенд

Демо-ящик (OUTTALK_DEMO=1) для замеров не годится: он отвечает мгновенно и идёт другим путём кода. Поэтому стенд — это имитация сервера Exchange (EWS) на локальном https, а приложение работает с ней через настоящий ExchangeProvider: тот же SOAP, тот же Basic, та же библиотека EWS, тот же шлюз запросов (не больше 4 одновременно, ADR-0038), те же кэши и тот же фоновой прогрев списка.

Синхронизация папок (ADR-0154). Стенд понимает SyncFolderItems: состояние у клиента (base64(JSON{f, e, cn, g}) — папка, эпоха папки, номер последнего выданного изменения, диапазоны выданных писем, поэтому размер растёт от «дыр» удалений, как у настоящего), Create/Update/ReadFlagChange/Delete по общему счётчику изменений хранилища, типы вперемешку в одной странице, MaxChangesReturned/IncludesLastItemInRange, порядок первичного прохода syncOrder: oldest | newest | shuffled, стоимость страницы latencyMs + syncPerItemMs × изменений. Тело или адресаты в наборе свойств — ErrorInvalidPropertyRequest, как у живого. Отказы по заказу (failSync): ErrorInvalidSyncStateData (и invalidateStates(папка) — «восстановили из бэкапа»), ErrorSyncFolderNotFound, ErrorFolderNotFound, ErrorAccessDenied, ErrorServerBusy с BackOffMilliseconds, ErrorMailboxMoveInProgress, ErrorInternalServerTransientError, неизвестный элемент в странице. Правки «другим клиентом» с событиями потока: externalMarkRead, externalFlag, externalMove, externalDelete; волна правок сервера — bulkUpdate(папка, n). Письмо, удалённое externalDelete до следующего запроса изменений, синхронизация не называет удалённым — как живой сервер; на этом стенд воспроизводит «призрака» из поправки «Письма, которых нет» (запись по его id отвечает ErrorItemNotFound на элементе). Попутно исправлено: в событии переноса OldItemId теперь прежний id письма, как у живого сервера (раньше стенд писал туда новый).

Операции стенда. GetFolder, FindFolder, FindItem (страницы, сортировка по дате получения или отправки, поиск подстрокой по теме, ограничение по ConversationId), GetItem (ровно заказанный набор свойств: тело и вложения — только если их попросили), GetAttachment, GetConversationItems, CreateItem (SendAndSaveCopy, черновик SaveOnly, серверные ReplyToItem/ReplyAllToItem/ForwardItem с цитатой и копиями встроенных картинок), UpdateItem (поля, «прочитано», флаг, отправка черновика), SendItem, MoveItem и DeleteItem (перемещённое письмо получает новый id, как у Exchange), CreateAttachment, ConvertId, Subscribe и висящий GetStreamingEvents с событиями NewMail/Created/Modified/Moved/Deleted. На GetUserConfiguration стенд отвечает «не найдено», на ResolveNames — «нет совпадений», на остальное — ошибкой EWS ErrorInvalidOperation с записью в unknownOps (в отчёте прогона).

Данные. Только демо-адреса company.com / example.com.

Ручки стенда (переменные окружения прогона): PERF_LATENCIES — задержка ответа на каждый запрос, мс (по умолчанию 0,80,300 — «быстрая сеть», «обычная», «медленная»); PERF_MAX_CONCURRENCY — предел одновременных запросов, как EWSMaxConcurrency у Exchange: лишние ждут очереди (по умолчанию выключен); PERF_KBPS — полоса пропускания ответа, кбит/с (по умолчанию выключена); PERF_INBOX — размер «Входящих».

Безопасность и упакованная сборка. Стенд живёт в процессе Playwright и в приложение не попадает: каталог e2e/ в сборку не входит (electron-builder.yml берёт только out/**). Продуктовый код для замеров не менялся — ни флагов, ни точек замера. Пароль ящика стенда случайный на каждый запуск и лежит только во временном профиле; профиль удаляется после прогона (PERF_KEEP_PROFILE=1 — оставить, чтобы прочитать outtalk.log). Запись encrypted:false в account-secrets.json — штатный путь неупакованной сборки (accounts/secrets.ts): упакованная такую запись не создаёт и пароль открытым текстом не сохраняет.

Методика

  • Одна задержка — один запуск приложения с чистым профилем. Между замерами ждём, пока стенд не затихнет на 1,2 с (settle): фон предыдущего действия (прогрев соседей, обновление папки) не должен попадать в следующий замер.
  • Время — по событиям, без фиксированных пауз. Наблюдатель в окне ловит изменение DOM (MutationObserver), загрузку картинок и, на всякий случай, проверяет условие каждые 10 мс. Момент — performance.timeOrigin + performance.now(): это эпоха в мс на тех же часах, что Date.now() теста и стенда, поэтому время сервера и время окна сравнимы. Щелчок выполняется внутри окна (element.click()), его момент — начало замера. Окна в прогоне скрыты (OUTTALK_QUIET_WINDOWS=1 из playwright.perf.config.ts; на Windows — прозрачны и без фокуса, ADR-0142), но рисуют (backgroundThrottling: false). Отмечается появление в DOM, а не кадр на экране: до глаза добавьте ~16 мс.
  • Журнал — на уровне debug. Стенд запускает приложение с OUTTALK_LOG=debug (чтобы outtalk.log при PERF_KEEP_PROFILE=1 годился для разбора), а debug пишет строку на каждый запрос — на горячем пути. Упакованная сборка по умолчанию пишет info (Отладка), поэтому «клиент» стенда немного пессимистичнее пользовательского. Сравнивая «до/после», не меняйте уровень между прогонами; задать другой можно своим OUTTALK_LOG.
  • «Сервер» и «клиент». Для каждого замера стенд знает, когда приходил и уходил каждый запрос. «Сервер» — сколько миллисекунд окна замера у стенда был в работе хотя бы один запрос (объединение интервалов, висящий поток событий не в счёт). Всё остальное — «клиент»: IPC, разбор XML, очередь шлюза в main, React, создание окна. В S2 к «серверу» добавляется путь события от стенда к клиенту (половина задержки).
  • Запросы на действие считаются от щелчка до результата (запросы, начатые позже, — это уже фон и в действие не входят). Отдельно считаются повторные GetItem того же id в окне действия и повторно скачанные картинки: вложение, содержимое которого этот запуск приложения уже получал (у копии картинки в черновике ответа новый id, но то же происхождение).
  • p95 и медиана — ближайший ранг (значение из самих замеров, без интерполяции). При N = 10 p95 — это максимум (ceil(0,95·10) = 10-й по величине), медиана — пятый, нижний из двух средних. Для настоящего хвоста нужно N ≥ 20 (PERF_RUNS=20); сравнивая «до/после» по p95 при N = 10, вы сравниваете худший случай.
  • Сценарии.
    • S0 — запуск → первая строка «Входящих» (справочно, один замер на запуск; снимается всегда, PERF_SCENARIOS на него не влияет).
    • S1 — окно «Написать» → «Отправить» → строка письма в открытых «Отправленных». Отдельно — момент, когда окно письма закрылось (отправка завершена). Ждём до 75 с; не дождались — «не появилось». Два режима слежения за почтой: поток событий и опрос (у приложения по умолчанию — опрос раз в 60 с, Настройки → «Уведомления»).
    • S2 — стенд кладёт письмо во «Входящие» и пишет событие в поток → строка видна. Время — от момента, когда письмо легло на сервер. В режиме опроса событий нет — письмо находит очередной опрос.
    • S3 — щелчок по строке → виден текст письма; для письма с картинками — ещё и момент, когда видны все 5 картинок. Три состояния: холодное (клиент этого письма ещё не касался — стенд это знает), текст прогрет фоном (фоновый прогрев списка уже забрал текст, а картинки нет — так выглядит письмо под только что открытым) и повторное (письмо уже открывали). Замер «текст прогрет фоном» снимается, только если такое письмо в этом повторе нашлось, поэтому замеров в нём может быть меньше PERF_RUNS; это не отбраковка.
    • S4 — на открытом письме с картинками «Ответить» / «Всем» / «Переслать» → новое окно письма: нет «Готовлю…», редактор доступен, получатели стоят (1 / 3 / 0), цитата содержит текст исходного письма, черновик сервера на месте (в окне нет [data-compose-preparing] — иначе это ещё предварительная цитата, ADR-0150). Отдельно — момент, когда видны все картинки цитаты, и момент, когда история переписки видна (метка историяВидна): берётся из метки окна outtalk:compose-history (performance.mark в ComposeDialog в кадре, где под подписью встала предварительная цитата), а в старой сборке без метки — наблюдателем composeHistory (текст исходного письма в .compose-body). Метка окна нужна потому, что наблюдатель стенда ставится в новое окно позже, чем история там появляется. Метки сценария печатаются в строке замера (историяВидна=… готов=… картинкиЦитаты=…) и лежат в отчёте у каждого замера (marks); perf-compare их не сравнивает. После замера окно закрывается без сохранения.
    • S6 (ADR-0154) — своя сессия: «Входящие» на PERF_S6_INBOX писем (по умолчанию 3000; у живого ящика — около 40 000), без писем с картинками, поток событий. Приложение само начинает первичный проход через минуту после запуска; сценарий ждёт его конца (до 6 минут) и пишет в вывод число страниц и время прохода. Затем: чужое «прочитано» видимой строки (стенд — externalMarkRead + событие потока) → строка перестала быть непрочитанной; чужое изменение глубоко в папке (флаг самого старого письма, далеко за краем окна) → стенд ответил на SyncFolderItems. Бюджет обоих: ровно один SyncFolderItems, ни FindItem, ни GetItem.
    • S5 — на новом непрочитанном письме: прочитано (открыть → счётчик «Входящих» уменьшился на 1; отдельно — когда сервер подтвердил UpdateItem), в архив (строка ушла; когда сервер подтвердил; щелчок по «Архиву» → письмо видно), удалить из «Архива» (строка ушла; подтверждение; щелчок по «Удалённым» → письмо видно).

Готовые команды для правила скорости — npm run perf:quick и perf-compare, см. следующий раздел.

Каждая задержка — отдельный тест Playwright (до 2 ч на задержку); отчёт перезаписывается после каждой, так что прерванный прогон не теряет уже снятые задержки. Прогон печатает каждый замер и таблицу. В отчёте есть раздел quality: сколько замеров отбраковано (фон коснулся «холодного» письма раньше щелчка — такой замер не записывается под чужим именем), сколько раз стенд не затих за 30 с перед замером и какие операции стенд не понял — непустой список роняет прогон. Сырые цифры (все замеры, счётчики по каждому) — JSON по PERF_OUT. «До/после» сравнивают так: прогон на main → perf-results/baseline.json (в репозитории), прогон на ветке → perf-results/latest.json (не коммитится), сравнение по медиане и p95 одних и тех же сценариев. На другой машине «до» нужно снять заново — абсолютные цифры зависят от машины.

Короткий замер и сравнение

Правило «скорость почты — охраняемое свойство» (ADR-0148, Процесс разработки) пользуется стендом на двух уровнях: короткий замер на правку, которая меняет порядок запросов, и полный прогон перед выпуском. Обоим нужен один и тот же шаг — сравнить новый отчёт с принятым.

Короткий замер — npm run perf:quick (scripts/perf-quick.mjs):

npm run perf:quick -- S3,S4            # сценарии аргументом
PERF_SCENARIOS=S5 npm run perf:quick   # или переменной
  • Делает npm run build, затем стенд с PERF_RUNS=3, PERF_LATENCIES=80 и выбранными PERF_SCENARIOS (S1, S2, S3, S4, S5, S2poll; S0 снимается всегда). Явно заданные PERF_RUNS/PERF_LATENCIES уважаются — например, PERF_LATENCIES=80,300, если правка касается медленной сети.
  • Отчёт — PERF_OUT, по умолчанию perf-results/quick-<время>.json (каталог perf-results/ в .gitignore, кроме baseline.json и after.json). PERF_MERGE здесь не действует: у короткого замера всегда свой отчёт.
  • В конце сравнивает отчёт с PERF_BASE (по умолчанию perf-results/after.json) и выходит с кодом сравнения: 1 — скорость ухудшилась. Нет отчёта «было» — только замер и подсказка, как его снять. Без сценариев или с неизвестным сценарием скрипт сразу выходит с кодом 2.
  • Рассчитан на ~3–5 минут; S2poll (режим опроса) долгий — до 75 с на замер, его берут, только если правка касается опроса.

S1 стал в 7–60 раз быстрее — побочный выигрыш этапа 2: «Отправленные» синхронизируются, событие Created о копии письма запускает запрос изменений сразу (без склейки 1,2 с), строка приходит изменениями. Раньше копию приносила проверка через 1,5 с (ADR-0143).

Строки «хуже» сравнения — разбор честно, по каждой:

  • S0 запуск при 0 мс: 900 → 3708 мс, 26 → 30 запросов (один замер на задержку). Лишние запросы — Subscribe, CreateUserConfiguration×2 и ещё два GetUserConfiguration: подписка потока и создание личных настроек ящика в чистом профиле попали в окно запуска. Синхронизации в запуске нет вовсе (первичный проход — через минуту), путь запуска этап 2 не трогал; при 80 мс — 1448 мс и 25 запросов, как было; при 300 мс +7 % — шум одиночного замера. Принято как шум, перепроверка — повторный perf:quick S0 перед выпуском.
  • S4 при 80 и 300 мс: «запросов 2 → 3/4». Добавились фоновые SyncFolderItems и FindFolder: черновик ответа (CreateItem) даёт событие Created в «Черновиках», папка синхронизируется, и её проход теперь идёт сразу, а не через 1,2 с — поэтому он попал в окно замера; FindFolder — счётчики папок по folderStale с synced. Это те же запросы, что были и на этапе 1, только раньше; на путь «редактор готов» они не влияют (медианы S4 те же или ниже). Строки бюджета S4 (request-budget.test.ts) не изменились.
  • S2 поток при 300 мс: «1 → 2». GetItem сменился на SyncFolderItems (новое письмо через синхронизацию — «Входящие» к этому замеру уже прошли первичный проход), второй — фоновый GetConversationItems прогрева беседы, который при новом порядке событий начинается до того, как замер увидел строку. Время то же (475 → 477 мс).
  • S4 «Ответить» / «Ответить всем» при 0 мс: +22 / +14 мс. Первые три замера сессии (323–397 мс, ResolveNames) — холодный старт; остальные 181–196 мс. Шум.

Портреты получателей в шапке письма (ADR-0163, 2026-10-07)

Открытие письма теперь дополнительно запрашивает фото видимых получателей (обычно 3–6 на письмо; каждый адрес — один раз за сеанс, «нет фото» помнится 10 минут) — отдельным GetUserPhoto через общую очередь фото окна (не больше 4 одновременно). Бюджет запросов EWS при открытии письма (request-budget.test.ts) не изменился: фото идут вне EWS SOAP и не задерживают показ письма — место под лицо занято инициалами с первого кадра. Замер стендом не проводился.

Что стенд НЕ воспроизводит

Стенд отвечает на вопрос «сколько круговых обходов и сколько работы клиента стоит действие» и проверяет поведение (появилось ли письмо вообще). Абсолютные цифры живого сервера он не предсказывает.

  • Время сервера одинаково для всех операций. Живой Exchange 2016 отвечает по-разному: GetItem узким набором ≈85 мс, FirstClassProperties ≈1170 мс на холодное письмо (ADR-0031), GetAttachment 400–430 мс (ADR-0039). У стенда задержка одна на любой запрос, и размер ответа на неё не влияет (если не включить PERF_KBPS; и тогда каждый запрос едет «по своему каналу» — делёж полосы не моделируется).
  • Сеть. Loopback: TCP- и TLS-рукопожатия почти бесплатны, нет потерь пакетов, нет «чёрных дыр» GetAttachment (ADR-0039), нет обратного прокси, который «паркует» лишние соединения (ADR-0038) — только опциональный предел PERF_MAX_CONCURRENCY.
  • Вход. Только Basic: NTLM-рукопожатие, Autodiscover и поиск адреса сервера не участвуют (EWS URL задан явно).
  • Троттлинг. Нет ErrorServerBusy/503 и пауз по просьбе сервера (ADR-0125) — кроме SyncFolderItems, где отказы заказываются тестом (failSync); в сценариях замера их нет.
  • Поток событий. Стенд пишет событие сразу после действия (+ половина задержки) и по одному конверту на запись. Живой Exchange может группировать события и задерживать их; сердцебиение раз в 45 с есть, а 30-минутного разрыва потока в пределах прогона не бывает.
  • ChangeKey. Стенд меняет его при каждой записи, но не отклоняет устаревший — конфликтов и ErrorInvalidChangeKey не бывает.
  • Данные. Дерево из 13 папок (у живого ящика их сотни), одна беседа — одно письмо, тела короткие, нет вложенных писем, S/MIME, приглашений; календарь, контакты, задачи пустые; роуминговые настройки «не найдены», адресной книги и фото нет (GetUserPhoto — 404). Поиск — подстрока темы, а не AQS.
  • Машина. Приложение, стенд и Playwright делят один процессор; фоновая нагрузка машины сдвигает цифры. В отчёте прогона — модель процессора и средняя загрузка.
  • Экран. Окна скрыты: время — до появления в DOM, без кадра отрисовки.

Журнал живого сервера: можно ли отделить сервер от клиента

Обновление 2026-10-06. Большая часть предложений ниже сделана в ADR-0144: итог каждой пользовательской операции op │ … — done │ {ms, reqs, serverMs, queueMs, retries, lane} пишется на уровне info, в строках req есть queueMs/lane/attempt, у событий потока — lagMs, а кнопка «Подробный журнал» в панели диагностики включает debug на 15 минут. Метки окна (ui │ …) пока не добавлены.

Проверено по outtalk.log прогона стенда (PERF_KEEP_PROFILE=1) и по коду журнала (util/log.ts, diag/trace.ts, providers/exchange/ews.ts, ipc/mail.ts, watch/watcher.ts).

Что в журнале есть. Строка на каждый запрос EWS: req │ GetItem │ {"ms":91,"status":"200","reqBytes":…,"respBytes":…} — ms меряется от выхода запроса из шлюза до ответа, то есть это сеть + сервер без очереди. Строки операций op │ load_messages — done │ {"ms":…} и trace=<id> у запросов внутри операции. Ожидание в шлюзе — gate │ queued │ {"waitedMs":…} (только если больше 100 мс). События потока — watch │ server-side change │ {"folders":N} (уже после склейки событий, 1,2 с). У каждой строки — время с миллисекундами.

Почему владельцу этого недостаточно.

  1. В упакованной сборке по умолчанию уровень info, а req и op … done пишутся на debug (кроме медленных, > 1,5 с, и ошибок). Без запуска с OUTTALK_LOG=debug строк для подсчёта нет.
  2. Отправка, ответ, пересылка, «прочитано», перемещение, удаление не обёрнуты в операцию (mail:send, mail:createReply, mail:createForward, mail:markRead, mail:move, mail:delete вызывают провайдера без runWithTrace). Их запросы идут без trace=, строки op … done нет — сумму «сервер» не к чему привязать, а длительность всего действия не видна.
  3. Окно не пишет ничего. Время от щелчка до IPC, отрисовка, создание окна письма для ответа (в S4 это больше половины времени даже при 0 мс сети), склейка событий и перечитывание списка в окне в журнале отсутствуют.
  4. S1 и S2 не связаны в цепочку. Между «отправлено» (CreateItem), «событие пришло», «окно перечитало список» нет общего ключа и нет длительностей этапов — только времена строк, которые нужно сопоставлять вручную, и только на debug.

Итог: при OUTTALK_LOG=debug для S3 (открытие письма) можно сложить req ms внутри trace и вычесть из op … done ms — получится время main сверх сети. Операции называются open_message (фоновое чтение — warm_message), load_conversation и inline_image. Для S1, S2, S4 разделить сервер и клиент по журналу нельзя.

Предложение (не сделано): минимальные метки этапов — только имена, длительности и счётчики, без тем, адресов, тел и id писем.

  • Обернуть в runWithTrace оставшиеся записи (send, send_draft, create_reply, create_forward, mark_read, move, delete) — у их запросов появится trace=.
  • В строку op … done добавить сводку запросов операции: {"ms":412,"reqs":3,"reqMs":255,"queuedMs":0} — сколько запросов, сколько суммарно ждали сеть/сервер и сколько стояли в шлюзе. Строку завершения операции писать на info (она одна на действие), тогда разбивка есть в журнале упакованной сборки без OUTTALK_LOG=debug.
  • Метки окна одним IPC-сообщением на действие: ui │ open_message │ {"trace":…,"toTextMs":…,"toImagesMs":…,"images":5}, ui │ compose_ready │ {"kind":"reply","windowMs":…,"draftMs":…,"toReadyMs":…}, ui │ list_refresh │ {"reason":"server-change","folderRole":"sent","eventToRowMs":…}.
  • В наблюдателе: watch │ event │ {"kinds":"NewMail,Created","folders":1,"serverLagMs":…} (по TimeStamp события — с оговоркой о расхождении часов) и watch │ folder stale │ {"debounceMs":…,"echoSuppressed":true|false} — видно, что событие пришло, но было погашено как «своё эхо» (ADR-0063, OWN_ECHO_MS = 8 с).
