Хранение секретов

Один владелец профиля до открытия секретов и локальных БД

src/main/index.ts вызывает startApplicationIfAdmitted() до регистрации схем, whenReady, логов, IPC и initializeLocalMailRepositories(). Сначала обычный dev-запуск переносится с production userData на отдельный путь с суффиксом -dev; только непустой явный --user-data-dir=<path> сохраняется, а пустой/whitespace switch не обходит изоляцию. Затем Electron requestSingleInstanceLock() выдаёт admission ровно одному main-процессу выбранного профиля. Startup передан callback-ом, который функция вызывает только после успешного lock; rejected-process unit test проверяет, что callback не вызван. Не получивший lock процесс вызывает app.quit() и не регистрирует startup/shutdown lifecycle, не читает accounts.json/account-secrets.json, не сканирует плагины и не открывает key envelope/SQLite.

Событие second-instance обрабатывает только владелец через readiness-coordinator: до окончания startup запрос не создаёт окно на полусобранных IPC/storage зависимостях; после success существующее главное окно проходит focusMainWindow(), а отсутствующее (типичный macOS lifecycle после закрытия последнего окна) создаётся заново. Любая синхронная ошибка startup попадает в централизованный redacted log и вызывает app.exit(1), поэтому невидимый owner не удерживает lock; malformed/unreadable plugin root отдельно деградирует к пустому реестру. Аргументы командной строки и deep links пока намеренно игнорируются; это не скрытый IPC-вход. OS lock автоматически исчезает вместе с умершим процессом, поэтому crash не требует удаления lock-файла. При этом process admission — только внешний рубеж: binding-aware account authority, lifecycle locks, open leases, storeUuid guards и запрет автоматического stealing после crash остаются обязательными внутри local-data.

Секреты отделены от метаданных аккаунтов:

  • accounts.json — публичные MailAccount (email, displayName) + main-only кэш ewsEndpoint (адрес EWS, найденный Autodiscover’ом, ADR-0037). Без паролей. Кэш нормализуется и привязывается к домену учётки перед записью (см. ниже) и срезается на выходе (listAccounts()/getAccount() отдают чистый MailAccount), поэтому в renderer не уходит.
  • account-secrets.json — карта accountId → { enc, encrypted }, права 0600.
  • plugin-secrets.json — секреты плагинов (ADR-0060): карта pluginId → { key → { enc, encrypted } }, та же схема шифрования и та же политика packaged-отказа (plugins/plugin-settings.ts). Читается только main-обработчиком встроенного плагина (readPluginSecret); через IPC уходит лишь boolean «сохранён/нет». Обычные значения настроек — plugin-data/<id>.settings.json, без секретов. Оба файла проходят runtime-схему при чтении, malformed → ошибка без пути к файлу; fs-ошибки чтения/записи (EACCES, EISDIR, …) тоже не несут абсолютный путь профиля в UI — withoutPath пишет его в лог main и отдаёт общий текст (ADR-0064).

Адрес, куда уходит пароль, обязан быть привязан к домену учётки

Отдельная угроза, которую легко не заметить: ewsEndpoint — не секрет, но он определяет ПОЛУЧАТЕЛЯ секрета. Значение приходит из сети (Autodiscover: DNS, SRV, HTTP-редиректы), а по этому адресу мы затем шлём Authorization: Basic …. Пока адрес жил только в памяти, цена ошибки была одна сессия; с персистентным кэшем (ADR-0037) разовая подмена (MITM, отравленный DNS, чужой SRV) сохранялась бы в файл и молча переиспользовалась при каждом запуске — то есть превращалась в постоянную утечку пароля. Поэтому сетевой адрес принимается только если он принадлежит организации, которую назвал сам пользователь — домену его email:

// main/util/host.ts — общий хелпер для обоих мест
hostInDomain(host, domain)   // host === domain || host.endsWith('.' + domain)
                             // ('.' + domain, не endsWith(domain): иначе evil-company.com пройдёт для company.com)

Два места применения, оба обязательны:

  1. Редирект Autodiscover (allowAutodiscoverRedirect, ews.ts): библиотека по умолчанию редиректы Autodiscover запрещает; мы разрешаем — но только https: и только внутри домена учётки (покрывает autodiscover.<домен>, mail.<домен>). Чужой хост → редирект отклонён + logWarn.
  2. Кэш эндпойнта (safeEndpointForDomain, accounts/store.ts): https:, без userinfo, хост — в домене учётки (домен берётся из самой учётки по id, не из аргумента). Не прошёл — не кэшируем. Проверка идёт и на чтении файла: значение, переставшее удовлетворять привязке, не должно использоваться лишь потому, что когда-то прошло.
  3. Прямой перебор кандидатов (resolveByCandidates/candidateEwsUrls, ews.ts): при пустом EWS URL, ДО библиотечного Autodiscover, пробуем https://mail.<домен>/EWS/Exchange.asmx и https://autodiscover.<домен>/… — потому что библиотечный Autodiscover не достаёт AD/SCP-путь доменного Outlook, а mail.<домен> обычно отвечает сразу. Список сознательно сужен до mail/autodiscover (это же — доверенные хосты редиректа из п.1); webmail и голый apex убраны как более вероятные dangling-записи. Каждый кандидат — строго в домене учётки (hostInDomain).

Анонимный гейт перед паролем. WebCredentials в ews-javascript-api шлёт Authorization: Basic преемптивно (в первом же запросе), поэтому наивная проба кандидата отдала бы пароль хосту ещё до подтверждения, что там Exchange. Перед авторизованной пробой делаем анонимный GET без Authorization (presentsAsEwsEndpoint): кандидат допускается к отправке пароля, только если ответил 401 + WWW-Authenticate. Это отсекает пассивные цели: припаркованные страницы, catch-all хостера, не-Exchange сервисы, чёрные дыры (у гейта свой таймаут с req.destroy()).

⚠️ Честный остаточный риск. Анонимный гейт не защищает от активного subdomain-takeover: атакующий, реально захвативший mail.<домен> (dangling DNS → его сервер + валидный TLS-сертификат, который он может получить, контролируя хост), тривиально отдаёт 401 WWW-Authenticate: Basic — и наша авторизованная проба преемптивно отправит ему Basic-пароль. Гейт поднимает планку лишь против захватов, где атакующий не контролирует HTTP-ответы. Это неотъемлемо от преемптивного Basic и принято осознанно: сужение до mail/autodiscover, привязка к домену, TLS-проверка и single-flight (provider.service()) минимизируют поверхность; полное закрытие потребовало бы отказаться от Basic (challenge-only) или от автоопределения. Кто хочет строгой гарантии — вводит EWS URL вручную.

Мелочи с последствиями для безопасности/поведения (в комментариях кода): (а) авторизованная проба (FindFolders) идёт после гейта, но сама не отменяется по 6-секундному таймауту гонки — на «медленном» хосте запрос с паролем может висеть до EWS_TIMEOUT_MS (30с), затем детачится (утечки нет, но слот занят); (б) анонимный гейт использует «сырой» https.request и не учитывает useSystemProxy — на сетях, где хост доступен только через прокси, быстрый путь молча выключается и отрабатывает Autodiscover (он прокси учитывает). Пароль при этом никуда лишнему не уходит.

Сюда же — сертификатные ошибки не сбрасывают кэш: altname (несовпадение имени в сертификате) убран из ENDPOINT_DEAD (Exchange: аутентификация и сеть). Плохой TLS — первейший признак того, что эндпойнт подменяют; трактовать его как «сервер переехал» значило бы позволить атакующему выбить проверенный адрес и загнать нас в повторный поиск того, кому отдать пароль.

Цена (осознанная). Если EWS-хост организации лежит вне домена почты, Autodiscover-редирект туда отклоняется и адрес не кэшируется — лечится вводом EWS URL вручную в форме подключения (доверенный ввод пользователя; на него ограничение не распространяется).

Шифрование — Electron safeStorage (Keychain на macOS, DPAPI на Windows, libsecret на Linux).

Отказ от молчаливого plaintext-фолбэка (packaged). UI обещает шифрование через связку ключей ОС. Если в собранном приложении шифрование недоступно или выбран небезопасный бэкенд (isEncryptionAvailable() на Linux возвращает true даже для basic_text, чьё «шифрование» — фиксированный ключ; планка та же, что у хранилища ключей local-data — keys.ts → SAFE_BACKENDS, ADR-0064), saveSecret (main/accounts/secrets.ts) бросает MailError («Системное шифрование недоступно — пароль не сохранён…») вместо тихой записи пароля в base64. Секреты никогда не попадают в renderer и не пересекают границу IPC в открытом виде — провайдер собирается в main, где и остаются учётные данные.

Целостность реестров и изоляция аккаунтов

accounts.json и account-secrets.json читаются не через TypeScript-cast, а через runtime-схемы с лимитами полей и размеров. Повреждённый JSON или неизвестное поле завершают операцию ошибкой; приложение не подменяет повреждение «пустым списком аккаунтов». Credentials проходят ту же строгую схему до шифрования и публикации, поэтому приложение не может записать объект, который само затем откажется читать.

Публикация использует уникальный .<pid>.<uuid>.tmp, права 0600, fsync содержимого и атомарный rename. На POSIX после rename выполняется fsync каталога; на Windows открытие каталога для fsync не поддерживается, поэтому результат честно отмечает directorySynced:false, но не выдаёт уже состоявшуюся публикацию за отказ. Любая ошибка до rename удаляет temp и сохраняет прежний файл.

Удаление из двух реестров rollback-safe: перед удалением secret загружается в main-memory; если последующая публикация accounts.json не состоялась, secret записывается обратно. Если не проходит и откат, наружу возвращается совокупная ошибка. Управление списком аккаунтов (list/test/add/remove/connection/update) и глобальным буфером диагностики (setEnabled/snapshot/clear) разрешено только зарегистрированному main window; события диагностики отправляются только тому webContents.id, который включил панель, и не рассылаются другим renderer-процессам. Account-scoped mail и connection-diagnostics IPC проходят через единый guardedAccount, который до provider/cache сверяет event.sender с accountId, а после каждого асинхронного чтения повторяет sender + authority check. Standalone MessageWindow имеет доступ только к привязанному при создании аккаунту. После успешного удаления main останавливает watcher, уничтожает provider, удаляет body/photo caches и рассылает mail:accountRemoved во все окна. Рассылка fault-isolated: уничтоженное окно не мешает очистке остальных и не превращает уже опубликованное удаление в ошибку. Main window очищает reading pane, detail/conversation/inline caches и account-owned compose; поколение renderer-cache отвергает ответы, завершившиеся после reset/removal, а compare-before-delete у single-flight не позволяет старому finally удалить новый запрос. Отдельное окно письма очищает inline-байты и остальное account-owned состояние, затем закрывается.

Тела писем в main хранятся в ограниченном LRU. Его security key — не один accountId, а полный непрозрачный authority token: accountId + generation + revision + principal. generation меняется при новом воплощении записи, revision связывает результат с текущими credentials, principal — SHA-256 нормализованного владельца ящика и не раскрывает PII. revision — не хеш данных входа, а HMAC-SHA256 с ключом, который живёт только в памяти main этого процесса (util/secret-fingerprint.ts): все поля данных входа, кроме пароля, окну известны, и простой хеш позволил бы подобрать пароль офлайн (аудит 2026-10-02, ADR-0140). Даже cache hit сначала повторно авторизует аккаунт; после сетевого await authority проверяется ещё раз перед admission, поэтому удалённый, повторно созданный или перелогиненный во время запроса аккаунт не оставляет PII в кэше. IPC sender также авторизуется: main window регистрируется как доверенное, а standalone MessageWindow привязывается к одному accountId. Привязка хранится по стабильному webContents.id и удаляется при destroyed; это не зависит от идентичности JavaScript-обёртки event.sender. Demo получает фиксированный authority только при одновременных OUTTALK_DEMO=1 и accountId === 'demo'; пустой renderer-id канонизируется в demo до привязки отдельного окна, а вне demo-режима отвергается.

Каждое MailMutation содержит тот же accountId + generation + revision + principal; main отправляет account-owned mutations, watcher events и removal только главному окну и secondary-окнам с совпадающей stable scope, а renderer дополнительно применяет событие лишь при полном совпадении с активным account snapshot. Единственное исключение — встроенный демо-ящик: у него нет записи аккаунта и authority-кортежа, поэтому App.tsx принимает mail:mutated с accountId === 'demo', только когда активной записи нет и включён demo-режим (accounts.isDemo()); main и так рассылает такие мутации лишь окнам, привязанным к 'demo'. После асинхронной мутации main повторно проверяет authority до broadcast. Это исключает раскрытие события окну другого аккаунта и запоздалые результаты прежнего владельца, прежних credentials или удалённого и заново созданного аккаунта.

Журналирование проходит через единый recursive redactor, включая renderer console, load failure и render-process-gone события — прямой вывод сырых Electron diagnostics запрещён. Значения ключей с secrets, account/principal/address, endpoint/URL, user, host, domain, origin, source и полным path маскируются; email (включая внутрисетевые адреса без точечного TLD), DOMAIN\\user, помеченные local-part identity, hostname, URL, абсолютные POSIX/Windows/UNC-пути и acc_* удаляются даже из произвольного текста сообщения. Для абсолютного пути с пробелами или двоеточиями редактор fail-closed скрывает остаток строки, а не оставляет часть PII. Для диагностики сохраняются безопасное имя файла без каталога, а у Error — очищенные name, code, message и stack; циклические структуры не сериализуются. Поэтому журналы остаются полезными без сохранения PII удалённого аккаунта.

Пароль не «залипает» в renderer-состоянии. В форме подключения ящика (components/settings/AccountsPanel.tsx, closeForm) кнопка «Отмена» сбрасывает форму (setForm(blankForm)) и скрывает пароль (setShowPwd(false)), чтобы введённый пароль не оставался в состоянии React после закрытия формы.

Предохранитель учётных данных: отвергнутый пароль не отправляется повторно (ADR-0077)

Угроза здесь — не утечка, а самоблокировка: пользователь сменил доменный пароль, в OutTalk остался старый, и каждый тик наблюдателя, открытие папки или письма отправляли его на сервер заново (при пустом кэше адреса — ещё и через всю discovery: два кандидата, Autodiscover, EWS-вызов). Контроллер домена считает такие попытки (порог lockout в AD типично 5–10), и клиент сам блокировал учётную запись пользователя по нескольку раз в час. Правило теперь одно: первый отказ сервера (code: 'auth') — последний запрос с этим паролем.

Секрет и запись двигаются вместе: если upsertAccount упал, saveSecret(id, stored) возвращает прежний секрет (иначе новый пароль вечно уходил бы в discovery по домену старого ящика), а провал и отката даёт AggregateError из обеих ошибок — та же дисциплина, что у removeAccountRegistries. В renderer состояние формы сбрасывается сразу после успешного ответа (closeForm → setForm(blankForm), инлайн-форма пароля — setPwdEdit(null)), чтобы пароль не оставался в состоянии React.

Почему streaming-401 не взводит предохранитель. Ошибки долгоживущей streaming-подписки не проходят через fail(e) — они приходят в onError(err, fatal) супервизора, и там 401 бывает транспортной особенностью (NTLM/прокси на долгом соединении), поэтому остаётся fallback в poll (ADR-0043). Первый poll с настоящим 401 приходит в fail() и взводит предохранитель — цена ровно одна лишняя попытка. pollOnce дополнительно останавливает watch сам при MailError с кодом auth — на случай провайдера без предохранителя или пропавших учётных данных.

Принятая асимметрия. Ложное срабатывание (сервер вернул 401 не из-за пароля, например временный сбой IIS-аутентификации) стоит одного ввода пароля в Настройках; пропущенное — блокировки учётной записи в домене. Поскольку вердикт теперь пишется на диск, классификатор ужесточён (ews.ts → isUnauthorizedError): для response-объектов @ewsjs/xhr решает только status === 401 (500 с словом «credentials» в тексте — не auth), для текста — слово 401 целиком (не user401@… внутри цитаты schema-validation) или unauthorized; слово credentials не считается вовсе — SOAP-fault ErrorAccessDenied («Access is denied. Check credentials and try again») приходит по HTTP 200, логон прошёл, и блокировать по нему аккаунт нельзя. Вторая линия — транспортный предохранитель в GatedXhrApi: первый 401 на экземпляре (один на ExchangeService) отклоняет все последующие запросы этого экземпляра до сокета — так внутренний перебор хостов библиотечного Autodiscover и параллельный веер одной операции не отправляют пароль повторно. Пути мимо service() закрыты: getContactPhoto при взведённом предохранителе возвращает null (а 401 на его Basic GET у Basic-аккаунта взводит предохранитель), resolveToSmtp/roaming-настройки/discovery в фото идут через fail(). Сообщения NTLM-рукопожатия со словами unauthorized/credentials всё же взведут предохранитель — принимается осознанно. Через TLS 401 может выдать только сам сервер (или его фронт при недоступном контроллере домена — тогда и новый пароль отвергнут: сбивает с толку, но безопасно); при включённом «Игнорировать ошибки сертификата» подменённый сервер может ответом 401 добиться блокировки и на повторном вводе получить новый пароль — риск самой опции, у которого появился активный сценарий. Побочный выигрыш: удаление аккаунта с устаревшим паролем больше не зависает за барьером локального хранилища — провайдерные вызовы в полёте падают мгновенно.

IMAP / SMTP: тот же предохранитель, общий на два протокола (ADR-0127)

ImapProvider повторяет схему Exchange: lockAuth() взводится из общего fail(e), после этого ни одна операция (включая открытие нового соединения и отправку SMTP) не уходит в сеть, командное соединение закрывается, хост помечает аккаунт authLocked. Взводит только настоящий отказ сервера: у IMAP — тегированный ответ на LOGIN/AUTHENTICATE (authenticationFailed вместе с ответом сервера, коды AUTHENTICATIONFAILED/AUTHORIZATIONFAILED), у SMTP — только EAUTH с 535/534. AuthenticationFailure imapflow без ответа сервера (нет общего способа входа, LOGINDISABLED) — unknown: пароль тут ни при чём, и предохранитель заставил бы бесконечно перевводить верный. Временные отказы, которые некоторые серверы оформляют как неудачный вход ([UNAVAILABLE], [INUSE], [LIMIT], [SERVERBUG], [OVERQUOTA], SMTP 454), — network: иначе перегрузка сервера стоила бы человеку ввода пароля. Прочие SMTP EAUTH — unknown. Наблюдатель IDLE на отказе в пароле останавливается фатально (onError(err, true)) и не переподключается. Одноразовый экземпляр проверки (probeProviderFor) хуков не имеет.

Проверка задач Exchange из настроек (ADR-0123 §15)

Проверка пишет в ящик: создаёт помеченные тестовые задачи и удаляет их. Поэтому она устроена так:

  • Пароль не покидает main. Сессии строит ExchangeProvider.probeTasks через service(), то есть обычным путём аккаунта. Секрет не расшифровывается отдельно и в renderer не передаётся. Для запуска не нужны ни .env.local, ни ввод пароля.
  • Кто может запустить. Все каналы diag:tasksProbe:* принимаются только от главного окна (authorizeMainWindow). start дополнительно проходит guardedAccount: sender и authority сверяются до и после прогона. Одновременно идёт один прогон. Ответы на ручные шаги и остановку принимает только окно, которое начало прогон, и только по закрытым спискам шагов и ответов. Прогресс уходит только этому окну. Если окно закрылось, прогон останавливается.
  • Что можно удалить. Уборка удаляет только помеченное: тема начинается с [OutTalk-probe-tasks] или OutTalk.TaskId начинается с probe-, в «Задачах» и «Удалённых». Задачу владельца с OUTTALK-PROBE удаляет только явный ответ «Да» на отдельный шаг delete-owner-task. «Остановить» и закрытое окно её не трогают.
  • Предохранитель учётных данных (ADR-0077). Если сервер отверг пароль, fail() провайдера взводит блокировку, и прогон больше ничего не отправляет, в том числе на уборку. Уже заблокированный аккаунт отказывает до сети. Кроме того, транспортный предохранитель GatedXhrApi каждой сессии отказывает всем запросам после первого 401.
  • Что видно в отчёте. Только статусы, числа, даты тестовых задач и коды ошибок (probeErrorCode). Тем, тел, id, адресов и текста ошибок сервера (в нём бывает имя хоста) в отчёте нет. Строки подробностей ограничены по числу и длине. Это закреплено тестами tasks-probe.test.ts.

Проверка ящика по доступу из настроек (ADR-0138, п. 7)

Проверка обращается к другому ящику под входом выбранного аккаунта; по выбору человека она пишет туда тестовый черновик и отправляет письмо себе от имени этого ящика. Поэтому:

  • Пароль не покидает main. Окно передаёт только accountId, адрес ящика-цели и две галочки. Сессии строит ExchangeProvider.probeMailboxAccess через service() — тот же путь, что у почты. Секрет отдельно не расшифровывается.
  • Кто может запустить. Оба канала diag:accessProbe:* — только главное окно (authorizeMainWindow); start дополнительно проходит guardedAccount. Один прогон на процесс. Остановку принимает только окно, начавшее прогон, прогресс уходит только ему; закрытие, падение или перезагрузка окна останавливают прогон.
  • Входные данные проверяются в main. Адрес — normalizeAccessTarget: ровно один email, без имени, скобок, пробелов, переводов строк и &, поэтому он не ломает SOAP-разметку и не подставляет второго адресата. Параметры — ровно два булевых поля, лишние ключи отклоняются.
  • Без олицетворения. Другой ящик адресуется только FolderId + Mailbox; ImpersonatedUserId и X-AnchorMailbox не используются. Что разрешено вошедшему, решает сервер.
  • Запись и отправка — только по явному выбору. Обе галочки по умолчанию выключены. Удаляется только созданное самой проверкой и только по ItemId (HardDelete): черновик — по id из ответа CreateItem, копии письма — по id, найденным поиском по точной случайной теме [OutTalk probe] <12 hex> с повторной сверкой; больше трёх совпадений — не удаляется ничего. Черновик удаляется и при остановке.
  • Предохранитель учётных данных (ADR-0077). Первый отказ во входе на EWS взводит блокировку через fail(); после этого прогон не отправляет ни одного запроса, в том числе на уборку. Отказы по ящику-цели (ErrorAccessDenied и др.) — ответ, а не «неверный пароль», и блокировку не взводят (ADR-0125). 401 от Autodiscover и от чтения потока останавливают прогон без блокировки.
  • Autodiscover без перенаправлений. Шаг «Список ящиков» ходит только на https://<хост EWS>/autodiscover/autodiscover.svc того же сервера; перенаправления не выполняются, не-https адрес не опрашивается (NO_HTTPS).
  • Что видно в отчёте. Коды ответа, числа и два адреса (вошедшего и цели — человек их и так знает). Пароля, тем, тел, id элементов и текста ответов сервера (в нём бывает имя хоста) нет. Адреса из списка доступных ящиков показываются в отчёте и нигде не сохраняются. Закреплено тестами providers/exchange/access-probe.test.ts и ipc/access-probe.test.ts.

Проверка адресной книги из настроек (ADR-0170)

Проверка читает каталог организации под входом выбранного ящика. Заменяет консольный зонд npm run ews:addressbook, который брал пароль из .env.local и устаревшим паролем заблокировал учётную запись владельца в домене.

  • Только чтение. Операции — FindPeople, GetFolder, GetRoomLists, GetRooms, ExpandDL, GetMailTips, GetPersona, ResolveNames, GetUserAvailability, Autodiscover GetUserSettings, GET oab.xml, GET полного файла автономной адресной книги (галочка) и GET фото. Ничего не создаётся, не меняется и не удаляется; unit-тест проверяет, что в теле запросов нет ни одной записывающей операции.
  • Пароль не покидает main. Окно передаёт только accountId, два необязательных адреса и две галочки. Сессия — service() выбранного ящика, своя на прогон (пределы ответа 4 МиБ и запрет перенаправлений ставятся только на её транспорт); фото — тем же путём, что у аватаров (Basic, только https, при NTLM с выключенной проверкой сертификата запроса нет вовсе).
  • Не больше одного отказа во входе. Первый 401 на любом запросе останавливает прогон целиком; транспорт сессии и без того не пускает запросы после 401 (ADR-0077). 401 от EWS и от фото у Basic-входа взводит предохранитель пароля; 401 от Autodiscover и от фото у NTLM-входа — только останавливает (там бывает другой способ входа). Окно показывает «Сервер не принял вход — проверка остановлена».
  • Входные адреса проверяются в main (normalizeOptionalAddress: один email, без имени, скобок, пробелов, переводов строк и &) и уходят только текстом SOAP-элемента через escapeXmlText. Назад в окно они не возвращаются.
  • oab.xml запрашивается только по https и только с узла EWS: адрес от Autodiscover с другим узлом, логином в URL или не по https пропускается — пароль туда не уходит. Сам адрес в отчёт не попадает (только «есть / нет»).
  • Полный файл автономной адресной книги (галочка, выключена) — те же правила узла и https; имя файла из oab.xml — только простое *.lzx (OAB_FILE_NAME: без /, .., ?), итоговый URL обязан лежать в той же папке. Предел 200 МиБ: по атрибуту size файл больше предела не запрашивается, транспорт обрывает чтение сверх предела (maxContentLength). Предел, кодировка latin1, тайм-аут простоя и сигнал отмены ставятся только на транспорт сессии этого прогона и снимаются сразу после запроса; «Остановить» и истёкший срок (10 мин) закрывают само соединение, а не только ожидание. Файл живёт в памяти, пока разбирается заголовок, и никуда не пишется. Пик памяти — примерно втрое больше файла: при пределе 200 МиБ — до ~600 МиБ в main на время разбора (тело ответа, строка latin1, байты). Это принятый риск проверки только для режима разработчика; адресной книге нужен потоковый GET (ADR-0170, дополнение 1). Распаковка — свой разборщик lzxd.ts на недоверенных данных: каждое чтение и запись проверены по границам, распаковывается только первый блок (не больше 2 МиБ распакованных и 2 МиБ + 64 КиБ сжатых), блоков в потоке — не больше 16 + ⌈размер/1 КиБ⌉ (too-many-blocks: поток из крошечных блоков иначе занял бы главный процесс на секунды), испорченный поток даёт код ошибки, а не зависание.
  • Текст ошибки сервера (MessageText, faultstring) показывается только в шагах «FindPeople: почему не работает» и только если не может нести имя или адрес (safeServerText): латиница, цифры, знаки .,:;'()-_/, до 200 символов, без @, без шести цифр подряд и без строки поиска и адреса ящика. Иначе — «текст скрыт». Из MessageXml — только имена элементов.
  • Что видно в отчёте. Только числа, да/нет, коды ответа, время, размеры, имена свойств схемы EWS ([A-Za-z] до 60 знаков) и имена свойств MAPI из заголовка файла автономной книги. Имена, адреса, должности, телефоны, названия групп, PersonaId, ETag, id списков OAB, имена файлов и SHA из oab.xml, содержимое записей файла книги и строки поиска (начало адреса ящика) разбираются только в памяти. Закреплено тестом providers/exchange/addressbook-probe.test.ts (поддельный каталог с узнаваемыми значениями: ни одно не встречается ни в снимках, ни в тексте отчёта).
  • Нагрузка — только по галочке; на ErrorServerBusy или BackOffMilliseconds останавливается сразу. Пауза, которую попросил сервер, общая для ящика (ADR-0125): почта этого ящика тоже подождёт — карточка об этом говорит.

Проверка надстроек Outlook из настроек (ADR-0139, этап 0)

Проверка читает список надстроек вошедшего и разбирает их манифесты — чужой XML поставщика, который администратор развернул на сервере, — а по выбору человека запрашивает у сервера пропуск для надстройки и заглядывает в её страницу в интернете. В ящик она не пишет и код надстроек не исполняет. Подробно — Exchange: надстройки Outlook.

  • Пароль не покидает main. Окно передаёт только номер ящика и две булевы галочки (validateAddinsOptions: ровно ключи tokens и page, лишний ключ или иной тип — отказ). Сеанс строит ExchangeProvider через service(), как для почты.
  • Кто может запустить. Оба канала diag:addinsProbe:* — только главное окно (authorizeMainWindow); start проходит guardedAccount. Один прогон на процесс; снимки состояния — только окну-инициатору, остановка — только от него; закрытие, падение или перезагрузка окна останавливают прогон.
  • Манифест — недоверенный ввод. Разбор (main/addins/manifest.ts) — чистая функция, которая не бросает: строгий base64 с проверкой обратным кодированием, не больше 512 КБ и 100 манифестов, строгий UTF-8/UTF-16, <!DOCTYPE и <!ENTITY — отказ до парсера (никаких сущностей и внешних ссылок; @xmldom/xmldom их и так не загружает), строки ≤ 256 символов без управляющих, адреса — только https: без логина и пароля в адресе, ≤ 2048 символов, кнопок ≤ 50. Ошибки собираются кодами.
  • Что уходит в окно. Разобранное описание AddinInfo (toAddinInfo) — без адресов поставщика и без сырого XML. В состоянии проверки дополнительно — только имена узлов (без пути и параметров) с классом «компания / Microsoft / внешний», коды и числа. Значений токенов, их утверждений и текста ответов сервера в окне нет никогда. Названия и узлы в отчёте по умолчанию заменены на «Надстройка 1», «домен A»; показать их можно переключателем, который живёт только в памяти окна.
  • Токены. GetClientAccessToken вызывается только с галочкой; addinId — только GUID, проверенный перед SOAP. Значение возвращается вызывающему в main, не логируется и сразу превращается в форму (tokenShape: длина, alg, имена утверждений), после чего отбрасывается.
  • Страница — во временной сессии. Своя сессия addins-probe без persist: (только память; имя одно на процесс, прогон тоже один), используется лишь когда страницу действительно открывают, и стирается в finally (хранилище, кэш, кэш входа, кэш DNS). Запрос — net.request с credentials: 'omit': ни кук, ни HTTP-входа, в том числе встроенного входа Windows; событие login (и вход на прокси) — отказ; разрешения ОС и загрузки — отказ; только https, переходы вручную и каждый снова только https, не больше 3; IP-адреса, localhost, *.localhost и *.local не запрашиваются ни сразу, ни через переход — манифест не может направить запрос к службам на самом компьютере; имя узла резолвится перед каждым запросом и после каждого перехода (dns.lookup, все адреса), и если хоть один адрес — loopback (127/8, ::1), link-local (169.254/16 — адрес метаданных облака, fe80::/10) или «нулевой» (0/8, ::), в том числе внутри IPv6 (::ffff:127.0.0.1, ::ffff:0:…, NAT64 64:ff9b::…), запроса нет (PAGE_BLOCKED_HOST; проверка общая с иконками надстроек — main/addins/address-guard.ts); частные сети (10/8, 172.16/12, 192.168/16) разрешены — там живут корпоративные надстройки (ADR-0140, остаток риска — в разделе аудита ниже); не больше 1 МБ и 10 секунд на страницу; поиск office.js линейный и только в первых 256 КБ; User-Agent без меток приложения; без Referer. Прокси — системный (в отличие от EWS, где он выключен по умолчанию). Флаг «не проверять сертификат» учётной записи сюда не переносится. Окна, WebContents и скриптов нет — только заголовки и начало разметки.
  • Предохранитель учётных данных (ADR-0077). Первый отказ во входе останавливает прогон — ни одного запроса больше, в том числе между двумя пропусками одной надстройки. Уже взведённый предохранитель — отказ до сети. ErrorAccessDenied — ответ «нет прав», предохранитель не взводится.
  • Ящик по доступу и не-Exchange — без сети. Фасад ящика по доступу методов надстроек не пропускает, и проверка только объясняет, что надстройки принадлежат вошедшему. Провайдер без методов (IMAP) получает отказ до создания сессии и до первого запроса.
  • Закреплено тестами main/addins/*.test.ts, providers/exchange/addins*.test.ts, ipc/addins-probe.test.ts и e2e/addins-probe.spec.ts (отчёт по умолчанию не содержит ни названий, ни example.com).

Общий вход и ящик по доступу (ADR-0138, этапы C1–C2)

Ящик по доступу открывается тем же логином и паролем, что и другой ящик. Отсюда новые правила хранения и границы:

  • Секрет — по номеру входа. account-secrets.json — по-прежнему карта { ключ: зашифрованный секрет }, но ключ теперь — номер входа (credentialId, тот же формат acc_…). У записи ящика необязательное поле credentialId (только main; toPublic его снимает, в окно и в IPC оно не уходит никогда). Нет поля — номер входа равен номеру ящика: так хранились все прежние ящики, поэтому перенос не трогает ни один файл, а пароль остаётся на месте (accounts/login.ts, тест login.test.ts). Формат номера проверяется на чтении и записи (CREDENTIAL_ID), испорченная запись делает файл невалидным целиком, как и прежде.
  • Окно не видит вход. Главному окну публичная запись несёт только sharesLoginWith — номера других ящиков этого входа (для предупреждения «пароль обновится и у …»); окнам одного ящика (письмо, раздел, композер) это поле не отдаётся. Номер входа, логин и пароль окно не получает ни при каком вызове.
  • IPC принимает номер ящика, а не адрес и не вход. mail:accounts:addByLogin(sourceId, address) — только главное окно; адрес проходит normalizeAccessTarget (тот же фильтр, что у проверки доступа: один email, без разметки). Main сам выбирает вход источника, сам проверяет ящик (inspectMailbox: точное совпадение в каталоге, основной SMTP, ConvertId, настоящее чтение папки) и закрепляет адрес из ответа сервера в записи. Все последующие вызовы — по номеру ящика; провайдер берёт адрес ящика из записи, а не из окна. Олицетворения нет: права на чужой ящик проверяет Exchange.
  • Граница записи — в main. Провайдер ящика по доступу отдаётся наружу только через фасад providers/delegate.ts со списком разрешённых методов; новый метод провайдера по умолчанию закрыт. C2 открывает запись почты (отправка, ответ, пересылка, черновики, флаги, «прочитано», удаление в «Удалённые» этого ящика, перемещение, новая папка); календарь на запись, удаление папок, скрытые записи, задачи и личные контакты по-прежнему закрыты (read_only без запроса либо метода нет вовсе). Неактивные кнопки в окне — удобство, а не граница.
  • Принадлежность id — до записи (C2). Окно присылает id писем и папок; испорченное окно могло бы подсунуть id из другого ящика того же входа (например, своего) — и запись ушла бы туда под видом действия в общем ящике. Фасад берёт id из аргументов каждого метода записи (MAIL_WRITE_REFS, полнота — при компиляции) и требует от провайдера доказать, что все они из ЭТОГО ящика (verifyMailboxOwnership); чужой или недоказанный id — forbidden, на сервер не уходит ни один запрос записи. Провайдер без такой проверки записей с id не получает. Exchange доказывает одним ConvertId (сервер называет ящик, где живёт элемент; во входе — адрес вошедшего, поэтому «эхо» запроса не может дать ложное «да») и помнит только доказанные id — в том числе созданные им самим в папках этого ящика (Exchange: протокол EWS → Запись в ящик по доступу).
  • Копии и черновики — в папки ЭТОГО ящика (C2). Вызовы библиотеки, которые без явной папки пишут в ящик вошедшего (SendAndSaveCopy(), Save(), временный черновик письма с вложениями), в провайдере запрещены контрактным тестом well-known-addressing.test.ts; DeleteMode.MoveToDeletedItems разрешён только в перечисленных местах, куда ящик по доступу не пускается, а «Удалить» в ящике по доступу — явный перенос в wk(DeletedItems). Отправитель — закреплённый основной адрес ящика (From), а не значение из окна.
  • Отказ в праве — не отказ в пароле (C2). ErrorSendAsDenied и ErrorAccessDenied на записи — forbidden с понятным текстом; предохранитель пароля не взводится, а настоящий 401 на любой записи или проверке принадлежности — взводит.
  • Предохранитель — по входу. Отклонённый пароль одного ящика взводит предохранитель у всех ящиков входа (markAuthLocked проходит по всем, реестр тормозит уже созданные экземпляры соседей): ни один из них не отправит отклонённый пароль ещё раз. Отказ в доступе к ящику (ErrorAccessDenied, спрятанные папки) — код forbidden, вход сервер принял, предохранитель не взводится (тест registry-login.test.ts). Проверка при добавлении идёт сохранённым паролем, поэтому её настоящий 401 тоже взводит предохранитель входа.
  • Смена пароля и удаление. Новый пароль, принятый сервером, записывается под номер входа и действует у всех ящиков входа; их экземпляры и потоки пересоздаются. Смена логина или адреса в форме отделяет ящик на новый номер входа (при сбое записи реестра новый вход удаляется — он никому не принадлежит). Удаление ящика удаляет секрет, только если входом больше не пользуется ни один ящик (isLoginInUse); иначе секрет остаётся, и соседний ящик продолжает работать. У ящика по доступу форма меняет только пароль и имя.
  • Кэш адреса сервера — по входу, привязка к домену — прежняя. Адрес, найденный одним ящиком входа, служит и соседям, но в каждую запись попадает только при совпадении с доменом её адреса (ADR-0037).
  • Локальный снимок — отдельная личность. principal ящика по доступу включает его адрес: снимок общего ящика не привязан к личности своего ящика того же входа. У своего ящика личность прежняя — снимки уже подключённых ящиков не отвязываются.

VIP из каталога организации (LDAP) (ADR-0153)

Чтобы встречи с VIP красились сами, main раз в сутки читает из каталога организации (Active Directory по LDAP) адреса сотрудников с пометкой — например, атрибут extensionAttributeN со значением-пометкой. Это новый получатель пароля ящика: каталог открывается простой привязкой (simple bind) тем же логином и паролем, что и почта. У простой привязки пароль идёт в запросе как есть, без хеширования, поэтому всё, что ниже, сводится к двум вопросам: пароль не должен уйти без шифрования или не тому серверу, и фоновая работа не должна блокировать учётную запись. Модуль — src/main/directory/, провайдер-агностичный: ему дают сервер, имя входа, пароль и признак, он отдаёт набор адресов.

Путь, запрос, логин в адресе (user@host), IPv6-литералы, любые другие схемы — отказ: из поля в запрос попадают только узел и порт.

Строгая проверка сертификата и системные корни

Параметры TLS (tlsOptionsFor): host и servername — узел из поля (имя сверяется с сертификатом и в ldaps://, и в startTLS), minVersion: 'TLSv1.2', rejectUnauthorized по правилу ниже, ca — trustedRoots(): встроенные корни Node (tls.rootCertificates), tls.getCACertificates('default') (встроенные плюс NODE_EXTRA_CA_CERTS, если организация его задала) и системные (tls.getCACertificates('system')), без повторов. Контроллеры домена обычно выпускает корпоративный центр сертификации; организация кладёт свой корень в системное хранилище, и строгая проверка проходит без исключений — без этого единственным выходом было бы отключать проверку. Ошибка сертификата — вид tls с текстом «Нужен корневой сертификат организации в системном хранилище»; следующая попытка по расписанию — через сутки.

Флаг «игнорировать ошибки сертификата» — только для сервера, введённого руками, и только у Basic

У входа Exchange есть флаг ignoreCertErrors (Exchange: аутентификация и сеть). Для каталога он действует так же (rejectUnauthorized = false), но только если сервер введён руками и вход использует Basic:

// src/main/directory/vip-service.ts
const rejectUnauthorized = !(
  login.ignoreCertErrors === true &&
  login.authScheme !== 'ntlm' &&
  rec.config.serverFound !== true
)
  • Введён руками — тот же человек тем же решением уже доверил узлы своей организации; без этого у входа, которому флаг нужен для почты, каталог не заработал бы вовсе.
  • Вход с NTLM (authScheme === 'ntlm') — флаг на каталог не переносится. Человек, включивший флаг для почты с NTLM, рисковал меньшим: при подмене узла почты NTLM отдаёт лишь «вызов — ответ», а не пароль. Простая привязка LDAP отдала бы подменённому узлу сам пароль — это другой уровень риска, на который он не соглашался. У Basic пароль и так уходит узлу почты целиком, поэтому решение «доверять узлам организации без проверки» для каталога ничего не ухудшает.
  • Найден автоматически (serverFound: true — через Exchange или DNS SRV) — флаг не действует никогда. DNS не защищён: подменённый SRV-ответ указал бы на чужой узел, а с выключенной проверкой любой сертификат прошёл бы, и чужой узел получил бы пароль простой привязки. Узел, названный Exchange, тоже получает строгую проверку: ответ пришёл по каналу, который мог быть непроверенным.
  • Признак serverFound решает main, а не окно. discover() запоминает находку в памяти по ящику (discovered); setConfig ставит serverFound, только если адрес совпадает с последней находкой «Найти автоматически» или это прежний найденный сервер без изменений. Значение serverFound из окна игнорируется, любая правка адреса признак снимает. Так испорченное окно не может снять строгую проверку с найденного автоматически сервера, выдав его за введённый руками.

Вывод считается чужим: домены проверяются по форме имени (mDNS local и обратные зоны отбрасываются), серверы имён — только IP-адреса без зоны интерфейса; не больше 32 резолверов, 16 доменов поиска, 4 серверов имён на резолвер. Любая ошибка — пустые настройки, поиск идёт дальше. На Linux читается /etc/resolv.conf, на Windows дочерних процессов нет (домен машины — USERDNSDOMAIN).

Якоря доверия для DNS. Домены-кандидаты (не больше 8): суффикс UPN логина, домен входа машины, родительские домены узла EWS (до «сайта», публичные суффиксы вроде co.uk не спрашиваются), домены разделённого DNS (их задаёт VPN или администратор), домен адреса ящика. Домены поиска выдаёт любая сеть по DHCP, поэтому они берутся, только если родственны якорям (тот же «сайт») или это внутренняя зона (.local, .corp, .lan, .internal, home.arpa и т. п.), на которую публичный сертификат не выдают: иначе чужая сеть назвала бы свой домен, свой SRV и узел с честным публичным сертификатом — и строгая проверка не спасла бы пароль. Узел из SRV-ответа принимается, только если лежит внутри спрошенного домена; не больше 32 записей на ответ.

Узел от Exchange. Принимается как есть (только имя, не IP) только если у ящика включена проверка сертификата (ignoreCertErrors !== true). С «игнорировать ошибки сертификата» — и у Basic, и у NTLM — только внутри доменов-кандидатов. Довод: у Basic разовая подмена узла почты и так получает пароль, но один раз; названный ею узел каталога стал бы постоянным получателем — сервер сохраняется с serverFound, каталог читается раз в сутки, после смены пароля туда уходит и новый. Код Autodiscover и код HTTP в журнал и зонд — только из фиксированного списка, без содержимого ответа.

Журнал. DirectoryVipService.discover пишет только счётчики и источник: найдено ли, via, исход шага Exchange, число доменов и узлов, сколько ответов дали системные серверы имён и Node — без имён узлов и доменов. Удачная находка помнится в памяти 30 минут по ящику (сбрасывается при смене входа и удалении ящика), неудача не запоминается. Зонд npm run ews:directory-server печатает имена узлов только в терминал владельца — его вывод в репозиторий не попадает.

Простая привязка и пустой пароль

  • Имя входа — логин ящика, если он в виде DOMAIN\user или UPN (validBindName); иначе — адрес ящика (часто совпадает с UPN). Переводы строк и NUL — отказ. Логин, совпадающий с именем механизма SASL (PLAIN, EXTERNAL), проверку формы не пройдёт — ldapts принял бы его за SASL.
  • Пустой пароль — отказ до сети. По RFC 4513 простая привязка с именем и пустым паролем — это «unauthenticated bind», которую сервер «принимает» без проверки. Привязка бы «удалась», а дальше поиск шёл бы анонимно — такой вход не доказывает ничего. Нет сохранённого пароля у входа — вид config, в сеть не идём.
  • Секрет — только в main. Логин и пароль берутся по номеру входа ящика (loadLoginOf → credentialId, ADR-0138), в окно и в IPC не попадают ни при каком вызове.
  • Фильтр поиска строится из проверенных частей (ldap-filter.ts): имя атрибута — ^[A-Za-z][A-Za-z0-9-]{0,63}$ без опций ;…, objectClass/objectCategory/userPassword/unicodePwd запрещены; значение экранируется по RFC 4515 (*, (, ), \, NUL и всё вне печатного ASCII → \XX по UTF-8). Результат — (&(objectCategory=person)(objectClass=user)(<attr>=<value>)(mail=*)); дописать к нему своё условие через значение нельзя. Читаются только mail и proxyAddresses (из второго — лишь SMTP:/smtp:), displayName и прочие персональные данные не запрашиваются.
  • Пределы: операция 15 с, TCP 8 с, весь проход 60 с; постраничный поиск по 500; не больше 5000 записей — дальше «список обрезан».

Хранение: только на устройстве, зашифровано, не роумится

userData/directory-vip.json — карта { [accountId]: { enc, encrypted } } (vip-store.ts). Запись ящика — настройки каталога, адреса, отметки времени, ошибка, пауза — шифруется safeStorage при том же условии, что ключи локальной БД: шифрование доступно и бэкенд — из SAFE_BACKENDS. Без надёжного шифрования в упакованной сборке файл не пишется — данные живут в памяти до выхода; в разработке — base64, как у секретов. При чтении конверт и расшифрованная запись проходят проверку формы (номер ящика acc_…, ≤ 20 000 адресов, адрес обязан совпадать со своей нормализованной формой, известные виды ошибок); испорченный файл — пустой кэш, его можно перечитать из каталога. Сбой записи файла — MailError('Не удалось сохранить список VIP на этом компьютере.'); текст ошибки файловой системы (в нём путь профиля) уходит только в журнал, в окно — нет.

  • Через ящик не переносится. Адреса VIP — персональные данные о людях организации; на другом устройстве список за минуту перечитывается тем же входом, и держать его копию в ящике незачем.
  • Настройки каталога — тоже здесь, а не в общем settings.json (он переносится, ADR-0067): какой атрибут и какое значение означают «VIP» — внутреннее дело организации. По умолчанию поля пустые.
  • Забывание. Ящик удалён или за его номером теперь другой ящик — forget(id) стирает запись, а заодно забывает идущий проход (inflight) и последнюю находку «Найти автоматически» (discovered).
  • Правило поколения. forget() и смена настроек каталога увеличивают поколение записи ящика (epochs, только память). Проход, начатый в прежнем поколении, по возвращении ничего не пишет — ни успех, ни ошибку. Иначе удалённый ящик ожил бы на диске, а новый ящик за тем же номером унаследовал бы прежний сервер каталога и при следующем проходе отправил бы туда свой пароль.

Личный ключ записей в ящике разделяет, но не прячет (ADR-0136, этап A2)

Скрытые записи OutTalk в ящике лежат под именем OutTalk.<ownerKey>.<имя>, задачи несут свойство OutTalk.TaskOwner: так в общем ящике записи одного человека не смешиваются с записями другого. Это не защита: значения не шифруются, ключ — короткий хеш адреса, а человек с полным доступом к ящику (и администратор почты) прочтёт любые записи в нём; задачи общего ящика видны коллегам в Outlook. Ключ считает main (ConvertId, при сбое связи — отказ, а не догадка), в окно он не уходит; чужие задачи main не показывает и не правит, а в ящике по доступу не берёт старые общие записи владельца ящика.

OutTalk.TaskOwner — разметка, а не аутентификация. Ключ вычисляется из адреса, его не подписывает ни сервер, ни OutTalk. Коллега с правом записи в общий ящик (через Outlook, EWS или свою копию OutTalk) может создать задачу с вашим ключом или переписать ключ у существующей — и ваш OutTalk примет её как вашу. Целостность задач и скрытых записей в общем ящике не гарантируется: OutTalk разделяет записи честных участников, но не защищает их друг от друга. Кто может писать в ящик, тот может и подменить в нём «мои» записи — это свойство прав Exchange, а не OutTalk (аудит 2026-10-02).

Санитайзинг HTML писем

Тело письма — недоверенный HTML. Перед рендером оно проходит DOMPurify (lib/sanitize.ts):

Плюс хук afterSanitizeAttributes усиливает ссылки, проверяет data-cid, проверяет атрибуты нумерации списков (ниже) и нейтрализует удалённый контент (см. Удалённый контент):

Так вырезаются скрипты, формы, стили, iframe; ссылки открываются во внешнем браузере без доступа к window.opener.

Отступы из <style> письма: три свойства, только числа (ADR-0162)

Блок <style> письма по-прежнему вырезается (FORBID_TAGS), в документ из него не попадает ни одного правила. Применение — первым хуком afterSanitizeAttributes (зарегистрирован раньше остальных), внутри прохода DOMPurify, тем же способом, что хук нумерации пишет list-style-type: объявления дописываются в начало style элемента, поэтому собственный inline-стиль письма побеждает, а следующие хуки (удалённый контент, position: fixed|sticky) видят итоговый style. Таблица правил письма живёт в модульной переменной только на время одного синхронного вызова: присваивается внутри try, finally её обнуляет — даже если pre-pass бросит исключение, правила одного письма не попадут на другое.

Что это не открывает: ни селекторов, которые письмо может направить на элементы приложения (правила применяются только к узлам самого письма и только по тегу и классу), ни позиционирования, ни загрузки ресурсов, ни новых свойств, кроме вертикальных полей и интервала, которые письмо и так может задать inline. Потолки не дают письму раздвинуть карточку на экраны пустоты одним правилом.

Проверка. sanitize.spacing.test.ts, блок «безопасность копирования CSS»: expression(), url() в значении и рядом, position:fixed в том же правиле и через \;/\3b, кавычки и ><img onerror> в значении, отрицательные и огромные значения, calc/var/vh/inherit, пять частей margin, @media/@import, */#id/body/img/p > span/псевдоклассы; </style><script> между блоками; удалённый background:url() и position:fixed inline по-прежнему снимаются рядом с нашими полями; правила не переносятся между письмами; враждебный объём (150 000 незакрытых <style>, 70 000 незакрытых /*, 200 000 {) читается быстрее 500 мс.

Скорость. В jsdom, медиана 15 прогонов: письмо Outlook 195 КБ с ~1 800 абзацами MsoNormal — 102 мс без правил отступов, 130 мс с ними (+28 % на этом крайнем случае: style получает каждый абзац). Письмо без <style> или без правил отступов платит один регэксп. Первая версия делала отдельный DOM-разбор (×2 к времени) и была заменена хуком.

Письмо не может нарисовать «свой» интерфейс поверх приложения (ADR-0064)

Тело письма отрисовывается inline в DOM приложения (EmailBody.tsx → <div class="email-body">), а DOMPurify сохраняет атрибут style. Без ограничений письмо с position:fixed; inset:0; z-index:2147483647 закрыло бы всё окно OutTalk фальшивым экраном («сессия истекла — войдите» со ссылкой на фишинг-сайт: формы вырезаны, но https://-ссылка ушла бы в браузер через safeOpenExternal). Два рубежа:

  • CSS containment (index.css, .email-body): contain: paint делает карточку письма containing block для position: fixed-потомков и клипует их по её границам; isolation: isolate не даёт z-index внутри письма всплыть над хромом приложения; position: relative. Ширина таблиц не меняется (overflow-x: auto как был).
  • Санитайзер (lib/sanitize.ts, второй хук afterSanitizeAttributes, работает на каждом проходе — оверлей не «удалённый контент»): из inline-style вырезаются объявления position: fixed|sticky (после cssUnescape, который снимает CSS-комментарии /**/ и hex-escape вроде \66 ixed, чтобы обфускация не проскочила; тот же нормализатор укрепляет и проверку удалённых url()).

Инвариант: DOMPurify — ПОСЛЕДНИЙ шаг перед инъекцией

Любое преобразование HTML-строки письма выполняется ДО DOMPurify.sanitize; переписывать уже очищенный HTML запрещено. Это ключевой инвариант: постобработка очищенной строки (regex-замены, конкатенация, повторный парс→сериализация) — классический источник mXSS, когда безопасный после очистки текст при повторном парсинге превращается в исполняемую разметку.

export function sanitizeEmailHtml(html: string, opts?: { allowRemote?: boolean }): string {
  allowRemoteContent = opts?.allowRemote ?? false
  const prepared = markInlineCids(normalizeWordLists(html ?? ''))   // ← обе трансформации ДО очистки
  // внутри try: letterSpacing = readLetterSpacing(html ?? '')  — только метаданные (ADR-0162); finally обнуляет
  return DOMPurify.sanitize(prepared, { … })
}

  • normalizeWordLists (пересборка плоских mso-list-параграфов Word/Outlook в настоящие <ul>/<ol><li> — см. Интерфейс → Списки Word/Outlook, ADR-0036) работает внутри sanitizeEmailHtml, до очистки. Парсинг там инертен (new DOMParser().parseFromString(html, 'text/html') — не исполняет скрипты и не грузит подресурсы), узлы только перемещаются между элементами, новой разметки из строк не собирается; всё, что перенесено, затем всё равно проходит DOMPurify. Дополнительной mXSS-поверхности это не добавляет.

  • readLetterSpacing / applyLetterSpacing (ADR-0162, выше) — HTML не переписывает: правила отступов читаются из сырой строки как метаданные, а пишутся хуком внутри прохода DOMPurify (только margin-top/margin-bottom/line-height с пересобранным числом), до остальных хуков.

  • markInlineCids (парковка <img src="cid:…"> → data-cid + прозрачный src, ADR-0040) — тоже до DOMPurify, и по необходимости: DOMPurify удаляет атрибут с неизвестной схемой, так что к моменту хука src="cid:…" уже не существует и восстановить ссылку было бы не из чего. Парсер тот же инертный; новых узлов не создаётся, значение cid проверяется по SAFE_CID ([A-Za-z0-9._%+=@/-], ≤ 256 символов) — не прошедший cid просто не записывается, картинка остаётся пустым слотом.

  • Последнее слово — за DOMPurify. data-cid — единственный data-*, который переживает очистку (ADD_ATTR, при ALLOW_DATA_ATTR: false), и хук afterSanitizeAttributes перепроверяет его значение тем же SAFE_CID (это ловит и data-cid, написанный самим письмом, а не нами) и, если атрибут остался, гарантирует безопасный src-плейсхолдер. Инвариант не нарушен: строку после очистки никто не переписывает.

  • Единственное послабление инварианта — пост-инъекционная мутация СВОЙСТВ узлов. Формулировать честно: HTML после очистки не переписывается (ни строкой, ни innerHTML, ни повторным парсингом) — но по уже вставленному, уже очищенному DOM мы ходим и правим отдельные свойства существующих узлов. Таких мест ровно два, и оба играют по одним правилам:

    КтоЧто правитОткуда значение
    applyEmailDarkMode / clearEmailDarkMode (lib/emailDarkMode.ts)inline-свойства цвета (color, backgroundColor, borderColor, colorScheme); оригиналы — в data-odm*вычисляется нами из прочитанных цветов
    hydrateInlineImages (lib/inlineImages.ts, ADR-0040)img.src = data:<тип>;base64,<байты> и img.dataset.inlineState (+ title/alt заглушки)тип — из фиксированного allowlist растровых типов, байты — прошли base64-алфавит; повторно, после провайдера

    Правило, которое делает это безопасным: правим свойства уже существующих узлов, никогда не вставляем разметку заново — ни innerHTML, ни insertAdjacentHTML, ни createContextualFragment. Ни один узел не создаётся из строки, поэтому нового прохода парсера — а с ним и mXSS-поверхности — не появляется. Значения, попадающие в атрибуты, собираются только из проверенных нами величин (allowlist типов + base64-алфавит), а не из строк письма.

  • Правило для правок: нужна новая трансформация разметки тела письма — вставляй её в sanitizeEmailHtml перед DOMPurify.sanitize (и только с инертным парсером). Нужно поменять свойство узла после отрисовки (цвет, src картинки) — это допустимо, но только по схеме из таблицы выше: живой узел + значение из фиксированного набора. Промежуточных вариантов («немножко переписать HTML после очистки») нет.

  2. Подмена на цитату сервера (lib/quote-swap.ts → swapQuote) вставляет уже очищенный HTML черновика; единственное, что переносится из предварительной цитаты, — живые элементы <img> с теми же cid (значения src — из той же схемы «allowlist типов + base64», см. таблицу выше), с атрибутами серверной цитаты. hint main разбирает поле за полем (hintOf в main/compose-intents.ts: тема ≤ 1000, дата ≤ 64 и должна разбираться Date.parse, адрес — тем же разбором, что адресаты); поле, не прошедшее разбор, молча отбрасывает весь hint (неразбираемая дата — только саму дату), и просьба открыть окно из-за этого не отказывает.

Тело приходит из getCalendarEvent (Item.Body, ветвление plaintext/HTML — как у письма) и до рендера не переписывается.

Renderer шлёт сырой innerHTML; экранирование тела письма для SOAP делает escapeBody(html) в providers/exchange/provider.ts (&/</> → сущности) при построении MessageBody. Это не про безопасность, а про корректность провода: EWS встраивает тело живым XML в SOAP-конверт, а не-экранирующий writer либы иначе даёт серверу читать HTML-теги как XML-элементы (тело обрезается до первой строки). Прежний renderer-хелпер htmlToXhtml из lib/sanitize.ts удалён (был ошибочным — см. ADR-0029). Детали — Exchange: EWS → Исходящие, ADR-0029.

Безопасность рассылки приглашений при переносе встречи (ADR-0048)

Перенос встречи-собрания может разослать участникам реальные письма (обновление о новом времени). Такая рассылка «от имени пользователя» — действие с последствиями, поэтому она обставлена контрактом.

  • Контракт: main НИКОГДА не выводит all сам. Провайдер рассылает участникам (SendToAllAndSaveCopy) только при notify === 'all'; этот параметр main не вычисляет и не угадывает — он приходит из renderer уже подтверждённым. Единственный «страж подтверждения» — модалка «Разослать участникам?» в renderer (Интерфейс): пока пользователь не нажал «Разослать обновление», в main уходит none.
  • IPC коэрсит к безопасному дефолту. На границе (ipc/mail:calendarUpdate, Процессы и IPC) notify приводится к 'none' для любого значения, кроме точного 'all' — «не рассылать» это дефолт, а не рассылать нужно осознанно выбрать.
  • Почему это осознанный defense-in-depth, а не защита от «злого renderer». В модели угроз Electron (contextIsolation, чужой код в renderer не исполняется, HTML санитайзится DOMPurify, CSP) renderer доверенный — он часть нашего приложения. Контракт «main не выводит all» — это дисциплина «опасное действие только по явному, ретранслируемому подтверждению», а не барьер против скомпрометированного UI.
  • Серверный слой — дополнительный. Обновление участникам на Exchange рассылает только организатор, а форма переноса в карточке и так доступна только организатору (canEdit = isOrganizer && !isCancelled) — второй, серверный, рубеж поверх renderer-стража.
  • Строгая валидация дат — тоже про рассылку. Даты переноса недоверенны; их round-trip-проверка (validInstant, Процессы и IPC) отклоняет молча-нормализуемые значения, чтобы кривой payload не перенёс встречу и не разослал участникам обновление на другую дату.
  • Открытая опция. При желании усилить можно добавить main-медиированное подтверждение (нативный диалог из main перед рассылкой), но при текущей модели угроз renderer-страж достаточен.

Рассылка приглашений при создании встречи (ADR-0048, этап 3)

Новая встреча с участниками сразу рассылает им приглашения (Appointment.Save(SendToAllAndSaveCopy)), поэтому запись начинается только по явному действию человека в редакторе MeetingComposeDialog — одном на оба пути: «Создать встречу из письма…» и «Новая встреча» в календаре.

  • Подтверждение — сама кнопка. При участниках она называется «Создать и отправить приглашения», без них — «Создать встречу» (SendToNone, писем нет). Открытие редактора (кнопка в шапке, двойной клик, выделение на сетке, пункт контекстного меню) ничего не пишет и не отправляет; ⌘/Ctrl+Enter равносилен нажатию той же кнопки.
  • Граница — main. mail:calendarCreate проверяет authority ящика и окна (guardedAccount), нормализует недоверенный черновик (normalizeCalendarCreateInput: строгий UTC-ISO, end > start, длины, XML-безопасный текст, каждый адрес) и перед записью ещё раз зовёт sameAuthority. Проверка в окне (lib/meeting-draft.ts) только объясняет ошибку заранее.
  • Без повторов. Запись не обёрнута в retry: потерянный ответ не должен породить вторую встречу и вторую рассылку.
  • ⌘/Ctrl+Enter — только из самого диалога. Слушатель живёт, пока редактор открыт, и срабатывает лишь когда фокус внутри него: будущая панель надстройки (ADR-0139) не сможет отправить встречу своим нажатием.
  • Демо мимо локального снимка. Ветка isDemoAccountId в mail:calendarCreate пропускает только шифрованный репозиторий (у демо его нет, как и у mail:calendar); guardedAccount, нормализация, sameAuthority и рассылка mail:calendarInvalidated по окнам ящика остаются. Реальные id (acc_<uuid>) в эту ветку не попадают; демо-ящики по доступу всё равно идут через фасад read_only.
  • Ящик по доступу (ADR-0138, до этапа C3): замок в useMeetingCompose.openNew/begin и отказ read_only в фасаде providers/delegate.ts (DELEGATE_CLOSED_METHODS) — в чужой календарь встреча не пишется.

Отмена и отказ при удалении встречи (ADR-0168)

Удаление встречи бывает тремя записями, две из которых пишут людям: cancel (участникам уходит отмена) и decline (организатору уходит отказ). Контракт тот же, что у переноса: письма уходят только по явному выбору человека.

  • Подтверждение — в окне. Режимы, которые пишут людям, предлагаются только в диалоге DeleteMeetingLayer с явными кнопками («Отменить встречу», «Отклонить и удалить», «Отменить и уведомить участников»); без вопроса уходит только remove простой встречи (без участников или отменённой) — и то через 5 с с «Отменить», в течение которых на сервер не уходит ничего. Отмены и отказы не бывают «оптимистичными»: окно отмены не может отправить письмо людям за спиной.
  • IPC коэрсит к безопасному дефолту. mail:calendarDelete пропускает cancel/decline только при точном значении; всё остальное — remove, который никому не пишет (Процессы и IPC). Текст — только для этих двух режимов, обрезается до 4000 символов.
  • Сервер решает роль. Провайдер перед cancel/decline перечитывает элемент (Bind) и отказывает режиму, противоречащему роли (cancel приглашённого, decline организатора), — режим не подменяется молча, поэтому «отклонить» не может стать «отменить для всех».
  • Текст экранируется на проводе (plaintextToHtml, ADR-0029) — пользовательский текст не становится разметкой письма.
  • Без повторов и без ложной ошибки. Запись не обёрнута в retry; отправка идёт мимо обёртки библиотеки, которая могла бросить исключение уже после рассылки (пустой <m:Items/>) и тем подтолкнуть к повторной рассылке (Exchange: EWS → Удаление встречи).
  • Граница authority. guardedAccount + assertAuthority провайдера непосредственно перед записью + sameAuthority перед рассылкой mail:calendarInvalidated — как у остальных календарных записей.
  • Ящик по доступу — deleteCalendarEvent в DELEGATE_CLOSED_METHODS (отказ read_only без запроса), в окне удаление не предлагается.

Приглашение в письме: authority на границе записи, fail-closed статус, явное подтверждение (ADR-0054, ADR-0059)

В письме-приглашении два вида необратимых записей на Exchange (Exchange: маппинг данных): тихое «Добавить в календарь» (MeetingRequest.Accept(false) — ответ организатору не отправляется, но повторный Accept создаёт вторую встречу) и ответ организатору «Принять / Под вопросом / Отклонить» (Accept(true) / AcceptTentatively(true) / Decline(true) — исходящее письмо реальному человеку, ADR-0059). Оба пути обставлены так же строго, как рассылка при переносе, и делят один и тот же механизм записи.

  • Одна запись на письмо, на оба канала. mail:addInvitationToCalendar и mail:respondToInvitation проходят через общий commitInvitationWrite: single-flight с ключом accountId + generation + revision + principal + messageId (invitationWrites) без действия в ключе — пока по письму идёт одна запись, второй вызов (любой — тихий или RSVP) присоединяется к ней и получает её честный результат, а не запускает параллельную запись в EWS; сам calendar action не обёрнут в withRetry — сетевой сбой не порождает повторный Accept и не отправляет организатору второй ответ.
  • Authority на границе commit. Оба канала передают провайдеру колбэк () => sameAuthority(authority). ExchangeProvider вызывает его в общем applyMeetingAction после всех чтений (MeetingRequest.Bind, Folder.Bind(DeletedItems), Appointment.Bind связанного события) и синхронно перед первой записью (Accept/AcceptTentatively/Decline) — без await между проверкой и записью; после завершения main проверяет authority ещё раз до инвалидации кэша и broadcast. Порядок закреплён source-contract тестом meeting-invitation.test.ts (assertAuthority?.() раньше respondToBoundMeetingRequest, между ними нет await).
  • Валидация ответа на привилегированной границе. mail:respondToInvitation принимает response как unknown и до capability-gate и до провайдера проверяет isMeetingRsvp(response) (shared/mail-types.ts: ровно 'accept' | 'tentative' | 'decline'); иначе MailError('Неизвестный ответ на приглашение.'). Неизвестная строка из renderer не превращается в вызов EWS; в контракт mail-ipc-auth-contract.test.ts канал добавлен как account-guarded.
  • Смена ответа через письмо запрещена до записи. Провайдер (assertMeetingActionAllowed) отказывает RSVP по письму, чей ответ уже Accept/Tentative/Organizer, до любого обращения к серверу: на Exchange 2016 повторный AcceptItem по восстановленному письму давал дубликат, DeclineItem по материализованному письму живьём не проверен — лучше честный отказ, чем полуприменённый ответ. Карточка тот же переход не предлагает (availableInvitationActions), демо-провайдер повторяет правило.
  • Статус ответа — server-authoritative и fail-closed. Идемпотентность («уже принято → no-op») решается не по MeetingRequest.MyResponseType (после Accept+restore Exchange 2016 может оставить NoResponseReceived), а по MyResponseType связанного Appointment (AssociatedAppointmentId). В write-path ошибка этого bind прерывает операцию: нет ветки «не удалось прочитать → значит не принято → примем ещё раз». Единственное исключение — структурно распознанная «висячая» ассоциация (ServiceResponseException, ErrorCode === ErrorItemNotFound: элемент или вхождение календаря удалён, материализовать нечего) — тогда Accept(false) выполняется как для нового приглашения; проверка по коду ошибки, а не по тексту (isMissingAssociatedAppointmentError). В read-path (getMessage) ошибки лишь логируются кодом без PII (debug для висячей ассоциации, warn для прочих), письмо остаётся читаемым.
  • Явное подтверждение в renderer — для каждого действия. Любая кнопка открывает один и тот же alertdialog; запись начинает только подтверждение. Для тихого добавления в тексте явно сказано «ответ организатору отправлен не будет», для RSVP — кому и какой ответ уйдёт («…отправит организатору «Имя» <адрес> ответ «Принято»»); прошедшая встреча отмечена отдельно («Всё равно добавить / принять / отправить / отклонить»). Клик = отправка, как в Outlook, отклонён намеренно: исходящее письмо реальному адресату должно быть подтверждено (как рассылка при переносе, ADR-0048). Синхронный claim writeInFlightRef в карточке + main single-flight → двойной клик не даёт двух записей. Как и у рассылки при переносе, это defense-in-depth в модели «renderer доверенный», а не барьер против скомпрометированного UI.
  • Имя организатора в диалоге — недоверенные данные, обезвреженные дважды. Display name и адрес организатора приходят из письма и попадают в единственное предложение, по которому пользователь решает, отправлять ли письмо реальному человеку. (1) Разметка: invitationRsvpConfirmation собирает обычную строку из provider-normalized CalendarInvitation (не из HTML письма), React рендерит её как текст ({confirmation.text}) — без dangerouslySetInnerHTML, <img onerror=…> в имени отображается буквально. (2) Подмена смысла: safeOrganizerText(value, max = 60) схлопывает переводы строк и пробелы, удаляет управляющие, zero-width, bidi и форматирующие символы (\u0000–\u001f, \u007f–\u009f, \u200b–\u200f, \u2028–\u202e, \u2060–\u2069, \ufeff) и ограничивает длину (имя 60, адрес 254, с «…»); имя всегда в «кавычках» и всегда рядом с адресом — «отправит организатору «Имя» <адрес> ответ «Принято»», так что display name вида Иван) ответ «Отклонено». Ничего не отправляя( или RTL-override не может переписать фразу, а подделанное имя не скроет реальный адрес получателя.
  • Отказы сервера — по коду, без утечки текста. Типовые причины, по которым Exchange не принимает ответ (устаревшее приглашение, отменённая встреча, копия делегата, вы организатор), распознаются структурно по ServiceError-коду (meetingResponseRefusal) и заменяются фиксированными русскими фразами; при них ничего не отправлено, и identity-recovery не запускается. Если же ответ уже ушёл, а вернуть письмо из «Удалённых» не удалось, текст ошибки прямо говорит «Отвечать повторно не нужно» — чтобы пользователь не отправил организатору второй ответ.
  • Ответ не подменяется ни одним слоем. response идёт от провайдера через InvitationCalendarResult → InvitationUpdate → стор/карточка/окно без hardcoded accept; tentative/organizer/decline остаются собой. Renderer не передаёт в main ничего, кроме авторизованного opaque messageId и (для RSVP) одного из трёх литералов MeetingRsvp, — даты, организатор и HTML письма не участвуют в выборе серверной встречи и адресата ответа: кому отвечать, решает Exchange по своему MeetingRequest.
  • Собственная память об ответе не перебивает сервер и не проверяется его словом (ADR-0097). ownAnswer едет рядом с response, а не вместо него: она добавляет то, чего сервер сказать не может, — сообщили ли организатору (состояние приглашения этого не различает). Записывается она по факту от провайдера (action и committed из результата, не из просьбы нажавшего), поэтому холостой повтор и запрос, присоединившийся к чужому уже идущему, не приписывают себе чужого действия. Ключ памяти — устойчивая личность письма, а её пишет отправитель: чужое приглашение может назваться уже отвеченным. Поэтому память привязана ещё и к организатору, несовпадение читается как «памяти нет» (прежнее поведение, без подписи), а внутреннее имя отправителя сравнивается как есть, а не схлопывается в пустую строку. Подделка не вызывает записи и не меняет ответ — потолок вреда — неточная подпись под карточкой.
  • Push — только authorized окнам. mail:invitationUpdated/mail:calendarInvalidated идут через broadcastAccountSafely (главное окно + окна, привязанные к этому аккаунту); потребители дополнительно сверяют accountId с активным/маршрутным, поэтому запоздалый update прежнего владельца не трогает same-id письмо другого аккаунта.

VIP-список цветов календаря — предпочтение презентации, в SOAP почты не попадает (ADR-0049, пересмотрено ADR-0067)

Цветовое кодирование встреч делит сигналы по границе процессов. Доменные факты (isOnline, EventAttendee.isExternal, hasExternal) провайдер вычисляет и отдаёт в @shared-модели — они описывают событие. Предпочтения презентации (цвета категорий, ручные цвета, VIP-адреса) живут в renderer (store/useCalendarPrefs, файл settings.json через mainSettingsStorage) и применяются чистым движком resolveEventColor; провайдер их не знает и в запросы к серверу (поиск, письма, календарь) они не попадают. С ADR-0067 список VIP пересекает IPC ровно одним путём — mail:setConfig → UserConfiguration OutTalk.CalendarPrefs в собственном ящике пользователя, чтобы переезжать между его устройствами; значение из ящика при чтении проходит те же разборы, что и локальный файл (replaceMailbox в store/useCalendarPrefs.ts: sanitizeCategoryColors, sanitizeWorkDay, sanitizeManualColors, sanitizeVipList), и ложится только в запись этого ящика (ADR-0155 п. 6) — копия одного ящика не меняет цвета и рабочий день другого.

Два источника, один эффективный список (ADR-0153). С появлением VIP из каталога организации всё сказанное выше относится к ручной половине списка (vipByAccount). Окно красит встречи и отмечает письма по эффективному списку ящика — ручной ∪ каталог (useVipList → mergeVipLists), но границы у половин разные: ручная живёт в settings.json и переезжает через ящик (OutTalk.CalendarPrefs), адреса из каталога лежат только в main (directory-vip.json под safeStorage), в окно приходят по directoryVip:addresses, хранятся в памяти стора useDirectoryVip и ни в settings.json, ни в ящик не попадают — в том числе через mail:setConfig: объединение строится только при отрисовке и никуда не записывается. Как и ручной, список из каталога в запросы провайдера (поиск, письма, календарь) не подставляется. Подробности — VIP из каталога организации.

Супер-VIP — та же граница (ADR-0161). Ручной уровень супер-VIP хранится рядом с ручным VIP — superVipByAccount в outtalk-calendar-prefs v6 — и пересекает IPC тем же единственным путём: поле superVip среза OutTalk.CalendarPrefs в собственном ящике пользователя. Разбор недоверенный и строгий: тот же sanitizeVipList/normalizeVip, что у VIP, плюс правило «каждая запись супер-VIP есть и в VIP того же ящика» — при чтении файла (sanitizeSuperVipByAccount) и при приёме копии из ящика (replaceMailbox) лишние записи выбрасываются; копия без поля (её записала прежняя версия) не стирает свой уровень, а только сверяется с пришедшим vip. Отметка внутри самого ручного списка (*адрес) отвергнута: прежний разбор принял бы её за годный адрес. В запросы провайдера супер-VIP не подставляется; сети нет нигде.

«Как выделять»: вид VIP — недоверенный ввод на каждой границе (ADR-0164). Выбор вида (цвет, палитра, сила, движение, «Где выделять») — предпочтение презентации без персональных данных: запись outtalk-vip-look в settings.json этого компьютера, ни один срез roaming-slices.ts её не читает — в ящик она не уходит, в запросы провайдера не попадает, main её не разбирает (значение — непрозрачная строка, как у прочих записей). Но из неё строятся CSS-переменные и атрибуты, поэтому путь до стиля закрыт с трёх сторон:

Кнопка «Подключиться» напоминания о встрече: ссылка проверяется на каждой границе (ADR-0056)

Плашка напоминания (Интерфейс → Напоминание о встрече) — первая поверхность, где ссылка из ящика открывается одной кнопкой с любой страницы приложения, поэтому путь ссылки закреплён отдельно:

  1. Провайдер. Серверный JoinOnlineMeetingUrl — недоверенный контент ящика (организатор — кто угодно). ExchangeProvider кладёт его в CalendarEvent.joinUrl только через normalizeExternalHttpUrl: new URL()-канонизация, только http:/https:, непустой hostname, без username/password, ≤ 2048 символов и в исходной, и в канонической (percent-encoded) форме — последнее добавлено в shared/external-url.ts этим ADR, потому что одна не-ASCII ссылка иначе делала бы снимок диапазона непубликуемым (DoS на собственный кэш). Невалидное значение не «чинится», а отбрасывается (undefined) — и в списке, и в детали (Exchange: маппинг данных).
  2. Local-data. LocalCalendarReadModel при записи снимка проверяет boundedText(joinUrl, 2048) и normalizeExternalHttpUrl(joinUrl) === joinUrl; иначе публикация отклоняется целиком. Из SQLite в renderer не попадёт значение, которое не прошло бы провайдера (Локальные данные).
  3. Renderer. meetingJoinUrl(event) (lib/event-location.ts) ещё раз прогоняет joinUrl через normalizeExternalHttpUrl и только при isOnline откатывается к первому валидному URL из location (splitEventLocation) — очная встреча со ссылкой на схему проезда кнопку не получает. Нет валидной ссылки — нет кнопки (не «disabled», а отсутствует). platformLabel/joinHost парсят hostname через URL и сравнивают exact/поддомен: домен в path/query не выдаёт себя за Teams/ktalk. Всё, что видит пользователь (тема, время, место, hostname в tooltip и aria-label), — только JSX-текст, без dangerouslySetInnerHTML.
  4. Main. Кнопка вызывает существующий app:openExternal; safeOpenExternal повторяет normalizeExternalHttpUrl непосредственно перед shell.openExternal — renderer/preload не считаются доверенными. Ответ boolean; отказ показывается в мета-строке плашки 5 с (openEventLocation сначала очищает старую ошибку).

Что плашка не делает: не читает тело приглашения, не грузит ничего по сети сама (иконка платформы — локальный lucide, favicon сервиса не запрашивается), не хранит ссылки на диске отдельно от календарного снимка и не передаёт даты/тему обратно в main — карточка встречи открывается по авторизованному opaque id через тот же mail:calendarEvent. Kill-switch OUTTALK_MEETING_REMINDERS=0 — статический preload-флаг, а не IPC: renderer не может включить напоминания в тесте, где они выключены.

Шаблон цитаты ящика — перечисления, а не HTML (ADR-0150)

Чтобы предварительная цитата выглядела как серверная, окно узнаёт по черновику сервера, как тот оформляет цитату, и отдаёт это в main на хранение (compose:learnQuoteTemplate). Черновик — производное от письма постороннего отправителя, поэтому хранится не кусок его HTML, а структурный шаблон QuoteTemplate (@shared/quote-template):

  • Нет адресов, имён и разметки. Подписи полей — 1–40 символов без <>&"@, без управляющих и без пробелов по краям; язык, стиль даты, стиль времени и склейка — из закрытых списков (QUOTE_LOCALES, QUOTE_DATE_JOINS); вид имён и разделитель — перечисления; шрифт — [A-Za-z0-9 ,'-]{1,64}, размер 6–36 pt, цвет #rrggbb; lead — целое 0–4. Лишнее поле — шаблон не принят.
  • Проверка на обеих сторонах. parseQuoteTemplate вызывает main при записи (main/quote-templates.ts; не прошло — invalid) и окно при чтении снимка настроек. Канал — guardedAccount: писать шаблон можно только для ящика, на который у окна есть права.
  • Сборка экранирует всё ещё раз. Подписи, шрифт и значения шапки попадают в HTML только через escapeQuoteText; результат идёт через sanitizeEmailHtml (п. 2а выше).
  • Хранение. settings.json, запись outtalk-quote-templates, пишет только main; ключ — непрозрачный id ящика ([A-Za-z0-9._:@-]{1,128}), не больше 64 ящиков (самые давние вытесняются); удаление ящика или подмена ящика под тем же номером забывает его шаблон (forgetQuoteTemplate). Испорченная запись читается как пустая.

Подпись письма — вставленный rich-HTML, санитайзенный на входе И на сборке (ADR-0044)

Подпись пользователь вставляет из Outlook как форматированный HTML (жирное ФИО, цветной текст, линия-разделитель), и она встраивается в HTML-тело исходящего письма — то есть уходит к получателям. Единственный контроль — sanitizeEmailHtml (DOMPurify), применённый дважды: на входе (useUi.setSignatureHtml санитайзит вставку/blur, поэтому в persist попадает уже инертный HTML) и на сборке (buildSignatureHtml, lib/signature.ts, пересанитайзит внутренность — belt-and-suspenders, защита даже от вручную правленого localStorage). Форматирование (inline-style, <hr>, <b>/<strong>, таблицы) переживает; <script>/onerror=/<iframe>/<object>/<form> и event-handler-атрибуты вырезаются — инъекции активной разметки к получателю нет. Удалённый контент (логотип https://, CSS url()) блокируется той же политикой, что и трекинг-пиксели (ADR-0027): паркуется в data-remote-src/data-remote-style + прозрачный gif, удалённый логотип из вставленного Outlook-блока не подгружается (никакого fetch). Конкатенация двух санитайзенных фрагментов (responseLead(accountId) + sanitizeEmailHtml(quote)) новой mXSS-поверхности не создаёт; обёртка <div class="outtalk-signature"> — фиксированный литерал. Предпросмотр в настройках использует ту же buildSignatureHtml, поэтому его dangerouslySetInnerHTML безопасен, а «предпросмотр = то, что уйдёт получателю». Хранение — в useUi.signatureByAccount (с ADR-0136 — своя у каждого ящика; ящик без своей получает пустую, подпись соседнего не подставляется) и через ящик (OutTalk.Signature, ADR-0067): пришедшая из ящика подпись проходит тот же sanitizeEmailHtml в replaceSignature, а прежняя общая подпись при обновлении (migrateUiState) очищается ещё раз и достаётся одному ящику; размер ограничен 1 MB (SIGNATURE_MAX, поднят с 50 KB под встроенный логотип) в сеттере; новых сетевых путей, IPC и секретов фича не вводит.

Логотип в подписи — растр-only data: + canvas-переэнкод (ADR-0044.1). sanitizeEmailHtml теперь проводит растр-only политику data: на атрибутах картинок: в src/background/poster/svg-href остаётся только data:image/(png|jpe?g|gif|bmp|webp), а data:image/svg+xml (скрипт/onload) и любой не-растровый data: — вырезаются (для <img> → прозрачный gif). data: в CSS url() не ограничиваем — картинка из CSS грузится в не-скриптовом контексте (svg не исполняет onload), то есть скрипт-инертна; режем там только удалённые http(s). Это ужесточение, не послабление: DOMPurify 3.4.11 по умолчанию пропускает любой data: на <img src> без проверки MIME — хук в afterSanitizeAttributes (константы IS_DATA_URI/DATA_IMG_RASTER, аллоулист согласован с провайдерным INLINE_IMG_TYPES) его ограничивает и побочно закрывает латентную брешь для ВХОДЯЩЕЙ почты (svg/не-растровые data: раньше доходили до DOM). Сам логотип пользователь встраивает через lib/signatureImage.ts: даунскейл до 600 px и переэнкод через <canvas> в чистый image/png/jpeg (сам по себе контроль безопасности — срезает чужие метаданные/скрипты), кап 256 KB на картинку. На отправке логотип-data: подхватывает существующий путь data:→cid: (ADR-0035/ADR-0040) и уходит inline-вложением.

Изоляция renderer

webPreferences: { contextIsolation: true, sandbox: true }

Renderer не имеет доступа к Node API. Единственный канал наружу — window.api, собранный в preload через contextBridge. Каждый метод — явно объявленный тонкий вызов IPC.

OS-песочница включена в обоих окнах (ADR-0064). Renderer рисует недоверенный HTML писем и хостит плагин-фреймы; ошибка Chromium в разборе письма/картинки без sandbox: true означала бы выполнение кода с правами пользователя. Preload для этого собирается CommonJS (out/preload/index.cjs, electron.vite.config.ts → preload.build.rollupOptions.output.format = 'cjs'): sandboxed-preload грузится как обычный скрипт и ES-модулем быть не может. Preload использует только contextBridge, ipcRenderer, process.platform/process.env.OUTTALK_*/process.contextIsolated — всё это доступно в песочнице. Контракт закреплён тестом plugin-navigation-security.test.ts (sandbox: true в main/index.ts и windows/messageWindow.ts, sandbox: false запрещён).

Единый харденинг окон — windows/harden.ts. Гарды навигации (setWindowOpenHandler, will-navigate, will-frame-navigate) собраны в одной функции hardenWebContents(webContents), которую вызывает каждое окно — новое окно не может «забыть» гард. Там же — отказ открывать window.open из плагин-фрейма: если details.referrer.url начинается с outtalk-plugin://, URL не уходит в safeOpenExternal (иначе системный браузер стал бы GET-каналом утечки данных брокера). Это дополнительный, best-effort слой: Chromium может не передать referrer для кастомной схемы, поэтому настоящая стена — sandbox iframe без allow-popups (PluginHost.tsx), и её менять нельзя.

IPC-параметры проверяются в main как недоверенный ввод. Помимо assertId/assertIds/assertCid (см. ниже), имя настройки в mail:getConfig/mail:setConfig (роуминг через ящик, ADR-0042) прогоняется через assertConfigName — регэксп ^OutTalk\.[A-Za-z0-9._-]+$; с ADR-0115 он же отвергает имена задач (^outtalk\.tasks(\.|$), без учёта регистра): задачи ездят через ящик только из main, и окно не должно ни читать, ни переписывать опись или часть в обход движка. Эскалации до этого не было (удаление и так недоступно), это защита в глубину. Каналы отдают доступ к произвольным объектам UserConfiguration почтового ящика; ограничение имени пространством OutTalk. не даёт скомпрометированному renderer прочитать или затереть чужие объекты конфигурации (OWA.UserOptions, CategoryList, …) через этот путь — defense in depth. Значение при этом остаётся непрозрачной строкой (base64(JSON) в BinaryData).

Свободный текст и размеры (ADR-0064). mail:search/mail:searchAll прогоняют folderId через assertId, а строку поиска — через assertQuery (строка ≤ MAX_QUERY_LEN = 1024; содержимое не фильтруется — это AQS, провайдер XML-экранирует его перед <m:QueryString>). Адрес для «Писем от этого человека» (opts.from) в AQS не попадает вовсе: assertRelatedKey проверяет его как адрес на границе IPC, а Exchange-провайдер кладёт его в атрибут Value="…" ограничения Contains по 0x5D02/0x5D01 через escapeXmlAttr (providers/exchange/sender-filter.ts) — тот же двухслойный подход, что у Message-ID ниже. mail:send/mail:sendDraft/mail:saveDraft перед assertAddresses/assertAttachments проходят assertDraftText: subject ≤ 2048, bodyHtml ≤ 32 МБ (inline-картинки едут внутри как data:-URI, отсюда щедрый потолок) — скомпрометированный renderer не заставит main держать гигантское тело. mail:accounts:test/mail:accounts:add вызывают validateCredentialsForStorage(creds) до первого сетевого запроса: форма (длины, authScheme, ewsUrl только https://) проверяется раньше, чем WebCredentials ушли бы на сеть.

Окно композера — права только на свой ящик (ADR-0133). Привязка compose { accountId, composeId }: данные своего ящика — да, чужого — нет; управление учётными записями, разделы, данные плагинов — нет (authorizeMainWindow, authorizePluginSurface отказывают); общие настройки окно не пишет — это договорённость renderer (settings-storage узнаёт его по адресу #compose/), а не граница main: settings:set по-прежнему принимает любое знакомое окно (как для окна письма и раздела, ADR-0104); значения непрозрачны и проверяются при гидратации. Выход из приложения окно композера может отменить не больше одного раза подряд — повторный выход в течение минуты уже не отменяется (ComposeQuitGate), зависшее окно закрытие и выход не держит (unresponsive, тайм-аут 10 с). Что открыть, окно не выбирает само: в адресе — непрозрачный randomUUID(), намерение лежит в main и отдаётся compose:intent по привязке окна, а не по аргументу — чужое намерение не получить, даже зная его номер. compose:open разбирает намерение поле за полем (режим из списка, размеры, лишние поля отбрасываются), канонизирует ящик и проверяет права просителя до создания окна. Содержимое письма между окнами не ездит: ответ и пересылку окно композера читает само по номеру со своими правами; единственное содержимое — заготовка нового письма (mailto:, карточка), и её текст окно ещё раз пропускает через sanitizeEmailHtml. compose:done/compose:quitReady принимаются только от окна композера. Заголовок окна ОС — только тема: page-title-updated перехватывается, и main пропускает заголовок через composeWindowTitle (вырезает управляющие символы и переключатели направления текста, ≤ 120 символов). Окно получает тот же sandbox, contextIsolation, CSP, preload и hardenWebContents, что остальные. Черновик зашифрованного письма и на закрытии окна, и на выходе сохраняется только зашифрованным (ADR-0131). Удаление ящика и подмена ящика под тем же номером закрывают его окна композера (closeComposeWindowsFor), намерения ящика стираются.

Поле «От:»: окно не назначает себе ящик (ADR-0137). Письмо может переехать в любой подключённый ящик — значит, окно композера, у которого права только на один ящик, получает права на другой. Граница:

  • Номер нового ящика — только из билета меню main. Список ящиков окну не отдаётся: его показывает main системным меню (compose:pickFrom → Menu.popup). Выбор человека окно получает одноразовым билетом (issueTicket, main/compose-from.ts): randomUUID(), привязан к webContents.id окна и к ящику, ИЗ которого письмо уезжает, живёт 2 минуты, новый выбор отменяет прежний. compose:moveFrom берёт номер ящика только из билета (takeTicket); чужой, повторный, просроченный билет или билет, выданный для другого исходного ящика, — отказ auth. Испорченный renderer окна письма не может ни назвать номер ящика сам, ни воспользоваться чужим билетом, ни перепрыгнуть дальше одного выбора человека. Ящик без доступа к почте в меню неактивен и повторно отвергается после выбора (forbidden).
  • Кто может. composeAccountOf (ipc/window-account-auth.ts): окно композера — только о своём письме, ящик берётся из привязки окна (аргумент не читается вовсе); главное окно — о письме в диалоге, ящик из аргумента с канонизацией и authorizeWindowAccount (главному окну и так открыты все ящики); окно чтения, вынесенный раздел и незнакомое окно — auth.
  • Перепривязка заменяет права, а не добавляет. rebindComposeWindow меняет accountId в той же привязке окна (обработчик destroyed из bind продолжает её узнавать): после переезда окно работает только с новым ящиком, а старый больше не трогает — ни читать, ни писать. Только main, только окно композера (scope.kind === 'compose', иначе auth), только вместе с удачным переездом; привязка, запись окна и намерение меняются синхронно, без await между шагами (retargetComposeWindow), — они не расходятся ни на миг. Покрытие — window-account-auth.test.ts.
  • Переезжает только черновик. Номер черновика приходит из окна и не доверяется: переезд удаляет оригинал насовсем, и окно, назвавшее номер обычного письма своего ящика, увезло бы его копию, а само письмо стёрло бы. carryDraft первым шагом сверяет папку письма (MessageDetail.folderId) со списком папок старого ящика (listFolders(), assertInDrafts): роль не drafts — отказ invalid («Это письмо не черновик…») до чтения вложений, сохранения и удаления; папки не прочитались — тоже отказ. Признак общий для Exchange, IMAP и демо, без флагов конкретного провайдера (повторный аудит 2026-10-05).
  • Переезд — только методами MailProvider. carryDraft снимает черновик провайдером старого ящика (getMessage, listFolders, getInlineImage, getAttachment); картинки, на которые ссылается текст, встают data:-ссылками только при безопасном растровом типе (INLINE_IMG_TYPES), чистом base64 (^[A-Za-z0-9+/]*={0,2}$ — значение ляжет внутрь атрибута src) и размере в пределах MAX_INLINE_BYTES; cid проходит SAFE_CID; тип вложения — только type/subtype, иначе application/octet-stream; имя ≤ 255; всё вместе ≤ 25 МБ (MAX_CARRY_BYTES). Сбой сохранения в новом ящике — старый черновик не тронут; сбой удаления старого — не откат (ещё одна запись могла бы молча оставить две копии), а явное предупреждение человеку. Один переезд на окно за раз; черновик под арендой main (ответ ещё готовится) не переезжает.
  • DraftInput.thread ставит только main. Заголовки In-Reply-To/References ответа из другого ящика — из связи (createLink), которую main завёл сам, прочитав Message-ID исходного письма провайдером исходного ящика; номер проверяется isInternetMessageId (заголовок написал отправитель исходного письма). Окно получает только непрозрачный replyLink, привязанный к окну и к текущему ящику письма; на mail:send/sendDraft/saveDraft и mail:smime:send/saveDraft main (linkedDraft) всегда снимает thread, пришедший из окна, и ставит свой; связь чужого окна или другого ящика — auth. Exchange пишет InReplyTo/References с тем же escapeXmlText, что тему (пустой References не пишется) (Текст пользователя в SOAP); IMAP и S/MIME — заголовками MIME после проверки «ровно один msg-id». Исходное письмо окно композера не называет — main знает его по намерению окна; отметку «Вы ответили» ставит main провайдером исходного ящика (у ящика по доступу — через фасад с проверкой принадлежности id). Связи ограничены (200, старейшая вытесняется) и забываются с окном и со сносом любого из двух ящиков.
  • S/MIME. Ответ на зашифрованное письмо, собранный из расшифровки, в другой ящик не переезжает (его текст расшифрован ключом исходного ящика). Main не полагается на флаг окна smimeOrigin: исходное письмо (из намерения окна композера или из source диалога, id — isValidItemId) само проверяется isSmimeEnvelope, и конверт — отказ; черновик-конверт тоже не переезжает. Зашифрованный черновик сохраняется в новом ящике только зашифрованным — на сертификат НОВОГО ящика (saveSmimeDraft); сертификат подписи и шифрования ищется по адресу ящика из «От:» (selfOf, main/mailbox-self.ts).
  • Зонд демо для e2e. __outtalkDemoInspect (main/demo-probe.ts: что демо-«сервер» запомнил о письме — папка, «Вы ответили», In-Reply-To) ставится на globalThis main только при OUTTALK_DEMO=1 и только в неупакованной сборке (app.isPackaged); preload его не отдаёт, окна его не видят, в выпуске его нет вовсе. Так же устроен счётчик __outtalkDemoCalls (providers/demo.ts, ADR-0145): сколько раз демо-«сервер» реально спросили — getMessage, getConversation, getInlineImage, getInlineImages, markRead (и по id письма) — уже после всех кэшей main; читает его только e2e через app.evaluate.
  • Журнал вызовов демо для замеров ответа (ADR-0146). __outtalkDemoCallLog / __outtalkDemoCallLogReset (providers/demo-latency.ts, ставит main/demo-probe.ts): метод демо-провайдера и его первый аргумент (номер письма), не больше 2000 записей. Те же условия, что у зондов выше: только OUTTALK_DEMO=1 и неупакованная сборка; preload его не отдаёт. Обёртки withDemoInstrumentation в упакованной сборке нет вовсе (провайдер возвращается как есть), настоящие ящики через неё не ходят; OUTTALK_DEMO_LATENCY_MS (0…2000) задерживает только ответы демо-провайдера.

Файл настроек settings:load/settings:set (ADR-0067): только зарегистрированные окна; main валидирует имя записи и размер, а записи, которыми владеет сам main (MAIN_OWNED_SETTINGS: режим разработчика, шаблоны цитат, размер окна письма и главного окна, ADR-0155 этап 4), через settings:set не пишутся вовсе — см. «Режим разработчика и настройки плагинов» ниже; значение — непрозрачная строка (схему и санитайзинг ведёт renderer при гидратации: sanitizePersistedCalendarPrefs, sanitizeFolderConversationModes, sanitizeEmailHtml для подписи). Значения, пришедшие из ящика при переносе между устройствами, проходят те же валидаторы, что и локальный файл — blob в UserConfiguration не доверен так же, как и localStorage. Лимит mail:setConfig — 256 КБ, для OutTalk.Signature — 1,5 МБ (встроенный логотип). У этого правила есть одно исключение, и оно намеренное: перенос задач между устройствами (ADR-0094) идёт к провайдеру из main напрямую, минуя mail:getConfig/mail:setConfig, — значит мимо assertConfigName и мимо этого лимита. Оба инварианта на том пути держатся сами: имена записей (OutTalk.Tasks, OutTalk.Tasks.<gen>.1…8) собирает движок, и ни кадр, ни renderer их не называют; единственная изменчивая часть — поколение <gen> из описи в ящике (ADR-0115) — недоверенный ввод и принимается только по ^[a-z0-9]{8,32}$, так что имя остаётся в пространстве OutTalk.Tasks.. Третья операция того пути — удаление отслуживших частей (deleteRoamingConfig) — в renderer не выставлена вовсе, а порт в ipc/plugins.ts дополнительно пропускает только ^OutTalk\.Tasks\.[a-z0-9.]+$: опись и чужие объекты UserConfiguration так не удалить. А тот же потолок 256 КБ на запись движок проверяет на своей стороне (MAX_PART_CHARS, после нарезки по 160 КБ и не больше восьми частей) — не влезло, не пишется вовсе. Приехавший документ разбирается как недоверенный ввод: части сверяются по sha256 из манифеста, пределы («не больше 1000 задач и 4000 связей») проверяются по ходу склейки, до слияния, негодная задача выбрасывается поштучно, а сравнение коллекций идёт по ключам личности, а не перебором — квадратичный проход по чужому документу был бы заморозкой всего процесса main. Подробности пути — Модель провайдеров → Опциональный роуминг настроек. VIP-список теперь хранится и в собственном ящике пользователя (пересмотр ADR-0049).

Счётчик на иконке window:setUnreadBadge (ADR-0066) принимается только от главного окна и нормализуется (normalizeBadgeCount: целое ≥ 0, потолок 99 999; строки/NaN/дроби игнорируются) — скомпрометированный renderer может лишь нарисовать неверное число.

Конфиг наблюдения за ящиком mail:watch(accountId, config) (ADR-0043) тоже валидируется и клампится в main, а не принимается на веру: интервал опроса зажимается в [30, 3600] с (renderer не может задать 0-секундный опрос и устроить DoS на сервер), а режим stream деградирует к poll, если бэкенд/сервер не умеет стримить. Ответ несёт фактический режим (effectiveMode).

Объявление напоминаний mail:setMeetingReminders(accountId, enabled) (ADR-0098) проверяется на той же границе и fail-closed: непустой accountId проходит authorizeWindowAccount(e.sender, id) и дополнительно accountAuthority(id) — объявление на несуществующий ящик отвергается сразу, а не живёт как фоновая задача, падающая раз в десять минут в журнал; null (выключить) требует главного окна. enabled принимается только как строгий true — любое иное значение выключает напоминания, а не включает их. Никакие сроки, диапазоны и тексты renderer не передаёт: правило «когда напоминать» целиком в @shared/meeting-reminder, данные — из локального снимка ящика. Единственное, что приходит из окна сверх ящика и флага, — отметки «Не напоминать» (ADR-0132): только ключи, проверяются в main muteSetFromDeclaration (массивы строк без управляющих символов, ≤ 1024/480 символов, ≤ 120/100 штук; неверная форма — пустое множество). Отметка может лишь убрать напоминание о встрече своего же ящика, добавить или изменить показ она не может. Та же проверка (sanitizeMeetingMutes) стоит на входе отметок из settings.json и из ящика (OutTalk.MeetingMutes): значение в ящике мог записать любой, у кого есть к нему доступ.

Настройки плагинов (этап 3).

  • Только встроенные плагины. Сторонний манифест по-прежнему не объявляет настроек (settings: undefined): доверенная страница не нарисует от его имени строку «введите токен».
  • Текст поля — только обычный текст. label, description, help, keywords, подписи вариантов выводятся React-текстом; ни HTML, ни Markdown не разбираются. Однострочные поля без переводов строк, пределы длины — в main (validateField); поле с любым неверным новым атрибутом отбрасывается целиком.
  • Условие показа ссылается только на поле выше и не на секрет: значение секрета окну неизвестно, а цикл условий невозможен.
  • Значения ящика (scope: 'mailbox') живут в byAccount файла плагина. Номер ящика проверяется (^[A-Za-z0-9._:@-]{1,128}$, имена __proto__, constructor, prototype и подобные отвергаются), ящиков — не больше 64, чтение — только собственных ключей (Object.hasOwn), так что испорченный файл не дотянется до прототипа. plugin:getSettings / plugin:setSettings принимают accountId через todoAccount: известный ящик, право окна на него. Снимок для ящика несёт значения только этого ящика. Удалённый ящик или номер, перешедший к другому ящику (ADR-0078), забывает свои значения (forgetPluginAccount).
  • Секреты по ящикам не делятся. scope: 'mailbox' у secret запрещён проверкой манифеста; секрет хранится одним значением в plugin-secrets.json через safeStorage, окну — только «сохранён ли».
  • Каналы настроек плагинов — по-прежнему только главное окно.

Content Security Policy

В index.html:

default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline';
img-src 'self' data: https: cid:;
font-src 'self' data:;
  • script-src 'self' — исполняется только код приложения.
  • img-src … https: data: cid: — внешние картинки писем и inline-картинки. Схема cid: в DOM больше не появляется (ADR-0040): санитайзер паркует ссылку в data-cid и ставит прозрачный GIF, а hydrateInlineImages подставляет готовый data:-URI, который пропускают и DOMPurify, и CSP. cid: в директиве оставлен намеренно, как рудимент-предохранитель (письмо может сослаться на cid: из места, куда мы не смотрим), но рабочий путь картинки — data:. Тем же data: пользуются аватары контактов (ContactPhoto → data:${contentType};base64,…): contentType берётся не из ответа сервера напрямую, а нормализуется в main к фиксированному image-типу (image/jpeg|png|gif) перед подстановкой в URI — граница доверия для этого data:-URL (см. маппинг данных → Фото контактов, ADR-0021).
  • 'unsafe-inline' для стилей нужен Tailwind/инлайновым стилям; скриптам инлайн запрещён.

Удалённый контент писем: блокировка по умолчанию + opt-in

Статус: закрыто. Ранее — осознанный follow-up (см. историю в ADR-0026); реализовано в ADR-0027.

Трекинг-пиксель — 1×1-картинка (или CSS-background) с уникальным http(s)-URL: браузерный движок при рендере письма автоматически запрашивает её, раскрывая отправителю факт и время прочтения и IP-адрес получателя. Классический канал слежки в маркетинговых и фишинговых письмах. OutTalk блокирует его по умолчанию.

Что блокируется

Хук afterSanitizeAttributes (lib/sanitize.ts) при allowRemote=false нейтрализует все удалённые ссылки на ресурсы, охватывая и protocol-relative формы (//host/…, разрешаются в протокол документа):

Проверка учитывает нормализацию адреса браузером: https:host, неполные слеши, обратные косые черты и ASCII tab/newline не обходят запрет. Атрибуты src / background / poster и SVG resource href проверяются до вставки в документ. Заблокированный адрес переносится в data-remote-src; для <img> остаётся прозрачный GIF.

Из CSS удаляется целиком декларация с удалённым url() / image-set(), включая hex- и simple-escape формы; остальные декларации сохраняются. Невалидный Unicode escape преобразуется в U+FFFD по правилам CSS, а не вызывает RangeError. Узел помечается data-remote-style="1". Запрет position: fixed|sticky также проверяется после декодирования и действует при разрешённых удалённых картинках.

Что не затрагивается: inline-картинки письма (data-cid + data:-байты, которые подставит hydrateInlineImages, — в т.ч. извлечённые из smime.p7m). Они приезжают по нашему IPC-каналу к нашему серверу и в сеть от имени письма не ходят — трекинг-пикселем cid:-картинка быть не может: она уже лежит вложением. Поэтому хук её и не трогает (data-cid проверяется в том же afterSanitizeAttributes, но и при allowRemote=false). Ссылки <a href> не трогаются (переход — явное действие пользователя, уходит в браузер).

Opt-in «Загрузить»

Блокировка — per-message. EmailBody (единственный компонент рендера тела, Интерфейс → ReadingPane/EmailBody) делает первый проход sanitizeEmailHtml(html, { allowRemote: false }); если результат содержит data-remote-src/data-remote-style, над телом показывается баннер «Удалённые изображения заблокированы для защиты приватности. [Загрузить]». По клику EmailBody ре-санитайзит то же письмо с allowRemote: true и рендерит с загрузкой картинок. Флаг showRemote сбрасывается в false при смене письма (useEffect(…, [html])) — доверие не «залипает» между письмами. Так как все пути рендера (одиночное письмо, тред ConversationView, окно письма MessageWindow) идут через EmailBody, блокировка действует везде.

Место заблокированной картинки помечается. Санитайзер меняет src на прозрачный 1×1, поэтому раньше слот был невидим — баннер сообщал о блокировке, но найти картинку в теле было нельзя. Теперь .email-body img[data-remote-src] (CSS в index.css) рисует на этом месте пунктирную заглушку с иконкой «изображение скрыто» (в цвет баннера). ⚠️ Важно для приватности: заглушка не грузит заблокированный URL — фон это статичный data:-URI SVG, а сам data-remote-src остаётся неиспользованным атрибутом (никакого fetch до явного «Загрузить»). Маркер исчезает после «Загрузить» (ре-санитайз с allowRemote:true не проставляет data-remote-src).

CSP как второй рубеж

CSP img-src … https: сохранён намеренно: он нужен, чтобы opt-in-загрузка работала после согласия пользователя. Первый и решающий рубеж — санитайзер (удалённых src в DOM просто нет, пока пользователь не нажал «Загрузить»); CSP остаётся резервом и точкой контроля для data:/cid:.

Та же политика для страницы вики: картинки тянет main, кадр получает data: (ADR-0072)

Страница Confluence в читалке плагина живёт по тому же правилу приватности, что и тело письма, только строже — кадр вообще не может сходить в сеть (connect-src 'none', Content Security Policy), поэтому «загрузить потом» там не бывает: картинка либо уже в модели как data:-URL, либо её нет и на её месте стоит текстовая пометка «Изображение доступно в браузере».

  • Забирает main, токеном пользователя. Картинки Confluence закрыты авторизацией; ConfluenceClient.image() делает GET с тем же Authorization, что и REST-вызовы, redirect: 'error', credentials: 'omit', таймаутом 15 с, и отдаёт байты в data:<тип>;base64,…. Тип — из белого списка image/* (включая image/svg+xml: в вики это диаграммы, а SVG внутри <img src="data:"> под CSP кадра рисуется, но не исполняется и внешних ресурсов не грузит).
  • Внешние картинки не запрашиваются вовсе. Адрес приводится к абсолютному относительно baseUrl, и всё, что не начинается с baseUrl + '/', отбрасывается до сетевого вызова. Картинка с чужого хоста в вики-странице — такой же трекер, как в письме (ADR-0027), и здесь он не получает ни запроса, ни opt-in-баннера.
  • Белый список путей поверх same-origin — позитивный и полнопутевой. Адрес должен целиком совпасть с одним из шаблонов выдачи статики: /download/(attachments|thumbnails)/<id>/<файл>, /download/temp/<файл> (картинки макросов), /images/…, плейсхолдеры плагинов, /rest/api/content/<id>/child/attachment/<файл>/download. Сверх того путь отвергается, если в нём есть ;, %2e, %2f, %5c или сегмент ./..: Confluence Server/DC стоит на Tomcat, а тот срезает ;… из каждого сегмента до разбора .., поэтому /download/..;/rest/api/user/current для URL выглядит путём под /download/, а до сервера доходит как REST-вызов. Без этого автор страницы мог бы обычным <img src="…"> заставить клиент читателя выполнить авторизованный GET к любому эндпоинту своего Confluence — CSRF от имени пользователя.
  • X-Atlassian-Token: no-check на картинках НЕ шлётся. Этот заголовок — опт-аут из XSRF-фильтра Atlassian, он нужен REST-вызовам плагина и не нужен статике; отключать защиту на запросе, адрес которого пришёл из чужого документа, — ровно то, чего делать нельзя.
  • Потолки. 2 МБ на картинку (MAX_IMAGE_BYTES, проверяется и по content-length, и потоково в util/bounded-body.ts → readBoundedBytes), 6 МБ суммарно на страницу, не больше 5 загрузок одновременно и общий дедлайн 20 с на страницу. Ответ без читаемого потока отвергается: content-length может солгать, а поток — единственное место, где потолок реально держится.
  • HTML-строка во фрейм плагина не передаётся никогда. confluence.content отдаёт ConfluenceBlock[]/ConfluenceInline[], кадр строит DOM через createElement/textContent. Это отличие от почты осознанное: письмо показывается как есть (DOMPurify в renderer — Санитайзинг HTML писем), а страницу вики мы разбираем в main в данные, поэтому у разметки вики нет поверхности исполнения ни во фрейме, ни в хосте. Подробности контракта — Доменная модель → wire-контракт Confluence, разбор — Архитектура плагинов.

OS-уведомление о новой почте не тянет удалённый контент (ADR-0043)

Системное уведомление на новое письмо (watch/notify.ts, Notification в main — Процессы и IPC → mail:events) строится только из сводки MessageSummary: title = отправитель, body = тема. Никакой сети: тело письма, фото отправителя, иконка — из сети НЕ грузятся. Это та же политика приватности, что и блокировка удалённого контента при рендере тела (ADR-0027): показ уведомления не должен незаметно дёргать трекинг-пиксель или подтягивать удалённое фото и тем самым выдавать факт доставки/прочтения. Уведомление показывается только когда приложение не в фокусе; всплеск писем коалесится в одно «N новых» (не шторм тостов). Клик по нему зовёт ensureMainWindow() — до ADR-0098 это был focusMainWindow(), который при закрытом окне молча ничего не делал (см. ниже).

Напоминание о встрече из main: что видно на заблокированном экране и что попадает в журнал (ADR-0098)

Планировщик напоминаний живёт в main и показывает баннер, когда главного окна нет вовсе (reminders/notify-meeting.ts). Это второй фоновый ходок в сеть после наблюдения за почтой, и обращаться с ним приходится как с первым:

  • Содержимое ящика на возможно заблокированном устройстве. В баннер попадают только тема встречи (title, обрезается до 120 символов) и строка «через сколько» + место (body, место — до 60 символов). Тело приглашения, участники и вложения не показываются и из сети не подтягиваются — та же политика, что у уведомления о новой почте.
  • В журнал не уходит ни тема, ни место — никогда. logDebug('calendar', 'meeting reminder shown', { accountId }) пишет только ящик; ошибки планировщика — logWarn('calendar', 'meeting reminders failed', { reason, code }), где code — класс MailError, а не серверный текст. Инициатора-окна у этих операций нет, показать ошибку некому, поэтому журнал — единственный их выход, и он обязан быть безопасным.
  • Отвергнутый пароль повторно на сервер не уходит. Своей подписки на блокировку учётной записи у планировщика нет: каждая его попытка гасится предохранителем учётных данных до сети (ADR-0077). Авторитет ящика (sameAuthority) проверяется до и после каждого ожидания, а поколение объявления — после каждого, поэтому поздний ответ после смены ящика ничего не покажет и ничего не запишет.
  • Правило показа — по фокусу, и это осознанно. shouldNotifyMeeting({ exists, focused, quiet }): quiet (OUTTALK_QUIET_WINDOWS=1) глушит всегда, окна нет — показываем (ровно тот случай, ради которого всё и делалось), окно есть — показываем, только если оно не в фокусе. «Окно не видно» честно определить нельзя, а приблизительная догадка стоила бы пропущенной встречи; ошибка правила по фокусу — лишний баннер рядом с плашкой, и это безопасная сторона.
  • Выключатель сборки гасит функцию целиком. При OUTTALK_MEETING_REMINDERS=0 окно объявляет напоминания выключенными (setMeetingReminders(id, false)), а не просто не рисует плашку, — иначе баннер продолжал бы приходить там, где напоминания считаются отключёнными.

Клик по уведомлению поднимает окно из main; канала «поднять окно» у renderer не появилось (ADR-0098)

Чтобы клик по баннеру открывал приложение, windows/mainWindow.ts получил ensureMainWindow() — показать окно, а если его нет, создать. Важно, чего при этом не сделано: нового IPC-канала «поднять/создать окно» renderer не получил, поверхность атаки со стороны недоверенного содержимого письма не выросла. Создание окна инициирует только main, и только из обработчика клика по системному уведомлению, которое сам же main и показал. Координатор создания окна передаётся внутрь процесса ссылкой (setMainWindowActivator), через IPC не проходит и в window.api не попадает. ensureMainWindow() первым делом уважает quietWindows(): в фоновом прогоне E2E окно не всплывает даже по клику.

Намерение, ради которого клик сделан, не проталкивается в окно: только что созданный renderer ещё не готов принимать push, и это была бы гонка. Оно кладётся в одну ячейку в main (intents.ts), окно забирает его каналом app:takeIntent (только главное окно, authorizeMainWindow) один раз. Нагрузка — { kind: 'calendarEvent', accountId, eventId }: идентификаторы, а не данные встречи; карточку renderer грузит обычным авторизованным путём (mail:calendarEvent), поэтому чужой или несуществующий ящик отсекается там же, где всегда. Снос учётной записи очищает ячейку (forgetIntentsFor(id)) вместе с остальным её рантаймом.

Жизненный цикл streaming-подписки (ADR-0043)

Режим «Мгновенно» держит долгоживущий серверный канал (EWS streaming subscription, watchMail в ExchangeProvider), но он строго ограничен по времени жизни и области:

  • Явный teardown. Канал закрывается, когда ящик уходит из объявления окна (удалён, переподключён) или уступает поток соседу по входу (stopAccount), при выключении наблюдения и на before-quit (stopAll → MailWatch.stop() → Close()/Unsubscribe()/Dispose()) — не оставляем висящий сокет после закрытия приложения. Простая смена выбранного ящика поток не рвёт: с ADR-0144 наблюдаются все ящики окна. Сторож по пульсу бросает соединение, от которого сервер молчит дольше ~2 мин, и открывает новое (Exchange: EWS).
  • В push нет секретов. По каналу приходят только ItemId новых писем; сводки дотягиваются отдельным BindToItems тем же аутентифицированным сервисом. Учётные данные в поток не попадают.
  • Потолок на всплеск. Одна нотификация после массового импорта/восстановления может нести тысячи ItemId; pushSummaries резолвит живьём только новейшие MAX_PUSH_SUMMARIES = 50, а для остатка зовёт onChanged([folderId]) — папка тихо перечитается списком, гигантский GetItem не строится (ADR-0064).
  • Один поток на вход (ADR-0144; заменил инвариант «один поток = один аккаунт»): наблюдаются все ящики окна, каждый — после authorizeWindowAccount + accountAuthority в mail:watch (ADR-0126); поток получает первый ящик каждого входа, ящики того же входа опрашиваются, поэтому число висящих соединений на одного пользователя сервера не растёт. В журнал поток пишет только типы событий и числа (watch │ events │ {types, lagMs}), без id и адресов. Каждый watcher использует ExchangeService с собственным account-bound XHRApi; поздний Close() рвёт именно его transport и не зависит от того, какой compatibility default был настроен последним.

Внешние ссылки

HTTP(S)-ссылки в письмах, документации и поле Location календарной встречи открываются в системном браузере, а не в окне приложения. mailto: остаётся внутри OutTalk:

  • Письма, HTTP(S): target="_blank" + setWindowOpenHandler в main → shell.openExternal, окно не создаётся.
  • Письма, mailto:: delegated click-handler EmailBody отменяет top-frame navigation, разбирает bounded RFC 6068 URL через parseMailtoHref и открывает composer точного аккаунта письма. Адресаты To/Cc проходят строгую SMTP-валидацию и dedupe (≤50), тема/тело ограничены по размеру и XML-safe символам, plain-text body HTML-экранируется; bcc fail-closed отклоняется, потому что скрытого поля в composer нет. В privileged shell эта схема не попадает.
  • Документация, календарь и напоминание о встрече: renderer вызывает window.api.openExternal(url) (канал app:openExternal). Calendar Location сначала делится на text/URL-сегменты; кликабельным становится только URL, прошедший общий normalizeExternalHttpUrl. Кнопка «Подключиться» плашки напоминания открывает провайдерный joinUrl либо (только для онлайн-встречи) первый валидный URL из Location — см. выше (ADR-0056).

normalizeExternalHttpUrl выполняет canonical new URL() parsing, принимает только http:/https:, требует непустой hostname, запрещает embedded username/password и ограничивает 2048 символами как исходную строку, так и каноническую (percent-encoded) форму — url.toString() не-ASCII адреса может вырасти втрое (ADR-0056). Та же проверка повторяется в privileged main boundary safeOpenExternal непосредственно перед shell.openExternal: renderer/preload не считаются доверенными. IPC всегда резолвится в boolean (true — системный API принял URL, false — deny/ошибка); calendar UI очищает старую ошибку перед новой попыткой и объявляет отказ через role="alert".

Гард навигации top-frame (will-navigate). Поверх setWindowOpenHandler (который ловит только window.open/target=_blank) в обоих окнах — главном (main/index.ts) и окне письма (main/windows/messageWindow.ts), через общий windows/harden.ts → hardenWebContents (ADR-0064) — стоит defence-in-depth: контент письма не может увести сам top-frame прочь из приложения. Любая попытка навигации отменяется, а http(s)-адрес уходит наружу через safeOpenExternal:

wc.on('will-navigate', (e, url) => {
  e.preventDefault()
  safeOpenExternal(url)
})

Так <a href> без target, <meta http-equiv=refresh>, location.href-редиректы из санитайзенного тела не подменяют оболочку приложения (file:///app://) чужой страницей — вместо этого https-ссылка честно открывается в браузере. Валидный пользовательский клик по mailto: раньше доходил сюда и затем молча отбрасывался HTTP-only safeOpenExternal; теперь он перехватывается раньше и открывает composer, а остальные схемы по-прежнему игнорируются.

Гард навигации суб-фреймов (will-frame-navigate). Плагины рендерятся в sandbox-iframe (см. Архитектура плагинов), а sandboxed-фрейм способен навигировать сам себя на внешний origin — канал эксфильтрации, который CSP connect-src/img-src/frame-src не закрывают. В windows/harden.ts суб-фреймы заперты в схеме outtalk-plugin://; всё внешнее отменяется без safeOpenExternal, потому что открытие attacker URL в браузере само создало бы GET-канал утечки. Детали — Архитектура плагинов → Закрытые каналы эксфильтрации.

OS-разрешения (permissions) для недоверенных фреймов

Электрон по умолчанию что-то выдаёт на запросы прав ОС (notifications, clipboard, media, geolocation, …), если не задан обработчик. В main/index.ts на session.defaultSession навешены оба хендлера — запрос и проверка. Политика — deny-by-default с коротким аллоулистом для first-party app-origin (APP_PERMISSIONS = {clipboard-sanitized-write}; уведомления показывает main через Notification, renderer их не запрашивает) и полный отказ плагин-origin outtalk-plugin://:

session.defaultSession.setPermissionRequestHandler((_wc, permission, callback, details) => {
  const fromPlugin = (details?.requestingUrl ?? '').startsWith('outtalk-plugin://')
  callback(!fromPlugin && APP_PERMISSIONS.has(permission))
})
session.defaultSession.setPermissionCheckHandler((_wc, permission, origin) => {
  return !origin.startsWith('outtalk-plugin://') && APP_PERMISSIONS.has(permission)
})

Аллоулист вместо «всё для приложения» — потому что permission-хендлер уже обманывали насчёт запрашивающего фрейма (advisories Electron, origin главного фрейма вместо iframe): даже в таком случае плагин-фрейм получит не больше, чем само приложение, — то есть почти ничего. Различение идёт по origin (все фреймы пока в defaultSession — осознанный пробел, см. Архитектура плагинов → остаточные риски). Первый узкий capability-гейт реализован для встроенного ToDo: включённый id + capability из манифеста + точный first-party/account scope. Все прочие права ОС и возможности остаются deny-by-default.

Вложения: временные файлы (просмотр/открытие)

Быстрый просмотр (attachment:preview → Quick Look) и открытие (attachment:open → shell.openPath) требуют файла на диске. В main вложение сохраняется во временный файл (userData/attachment-temp/attachment-<random>/<имя>, права 0600):

  • Имя файла санитайзится (вырезаются / \ ? % * : | " < > и управляющие символы) — защита от path traversal; расширение сохраняется (нужно Quick Look/открытию).
  • Каждое открытие получает новый подкаталог через mkdtempSync: одинаковые имена и идентификаторы разных аккаунтов не перезаписывают друг друга. Корень находится внутри приватного профиля, а не в предсказуемом общем OS temp.
  • Карантин: на temp-файл ставится com.apple.quarantine (как у скачанного из сети), чтобы Gatekeeper проверял его при открытии и предупреждал на исполняемых (.command/.pkg/.dmg/скрипты). Best-effort: карантин не гарантирован на всех платформах/ФС.
  • Очистка: каталог userData/attachment-temp удаляется при старте приложения и в before-quit (cleanupAttachmentTemp, экспорт из ipc/mail.ts) — расшифрованные вложения не накапливаются между сессиями.
  • Скачивание («Скачать») идёт через Blob в renderer и не пишет во временный каталог.

Права и повторная запись. util/attachment-temp.ts отказывает, если корень — симлинк или не каталог; корень и случайные подкаталоги имеют 0700, файл создаётся с wx и 0600. Существующий файл не удаляется и не перезаписывается. Очистка ограничена текущим профилем и выполняется после single-instance admission. Старый общий OS-temp путь больше не используется; остатки аварийно завершённой старой версии автоматически не мигрируют. При обычном завершении старая версия сама очищала его.

Опасные вложения: reveal-not-open

Карантин — лишь предупреждение Gatekeeper и best-effort. Поверх него attachment:open (main/ipc/mail.ts) никогда не запускает автоматически потенциально исполняемый файл через shell.openPath. По расширению проверяется денилист DANGEROUS_EXT (isDangerousAttachment):

const DANGEROUS_EXT = new Set([
  '.command', '.sh', '.bash', '.zsh', '.app', '.pkg', '.mpkg', '.dmg', '.scpt',
  '.scptd', '.applescript', '.term', '.workflow', '.action',

Тем же путём идёт и Outlook .msg (ADR-0129): OutTalk этот формат не разбирает, а «открыть» отдало бы недоверенный составной файл любому приложению, которое за него возьмётся. Проверка вынесена в общий deliverTempAttachment(sender, saved, 'open' | 'preview') — им пользуются и attachment:open/attachment:preview, и attachment:openAttachedPart.

При совпадении вместо открытия файл показывается в файловом менеджере (shell.showItemInFolder), а IPC возвращает ошибку-предупреждение («Файл может быть исполняемым и не открыт автоматически…»). Так двойной клик по опасному вложению не приводит к молчаливому запуску: пользователь открывает файл вручную из Finder/Explorer, только если доверяет отправителю (и тут же срабатывает предупреждение Gatekeeper по карантину). Обычные документы (PDF, docx, картинки) открываются как раньше — shell.openPath.

Открытие файла системным приложением — всегда явное действие пользователя (двойной клик по обычному вложению или ручное открытие раскрытого в Finder опасного файла), при этом Gatekeeper ветит недоверенный файл благодаря карантину.

Письмо во вложении: разбор в main, тело — тем же санитайзером (ADR-0129)

.eml, часть message/rfc822 и элемент Outlook во вложении открываются встроенной читалкой. Байты письма — недоверенный ввод от любого отправителя, поэтому:

  • Разбор — только в main (main/attached-message/parse.ts, postal-mime). Renderer не получает ни сырого MIME, ни доступа к файлам; ему уходит AttachedMessage через Result<T>.
  • Пределы до и во время разбора:
    • 32 МБ на письмо; лишний base64 отклоняется до декодирования;
    • глубина MIME — 50;
    • заголовки — 1 МБ;
    • вложений — 200, дальше пометка;
    • тело — 2 млн символов;
    • вложенные письма не разбираются заодно; глубже — только по щелчку и до 4 уровней.
  • Граница IPC. assertAttachedRef проверяет messageId/attachmentId (assertId) и путь (isAttachedPath: p0…p999, длина ≤ 4) и пересобирает объект. partId проверяет isAttachedPartId, cid — тот же assertCid. Все каналы — через guardedAccount.
  • Тело — тот же EmailBody. Тот же DOMPurify последним шагом, тот же запрет удалённого содержимого с явным «Загрузить», тот же CSP. Обойти их нечем: у читалки нет своего пути к DOM (тест AttachedMessageDialog.security.test.ts).
  • Картинки cid: — тем же правилом, что и у письма (ADR-0040): безопасный cid, растровый белый список (без SVG), до 8 МБ, тип отдаётся из таблицы.
  • Вложения вложенного письма открываются через тот же временный файл, карантин и deliverTempAttachment — reveal-not-open для исполняемых.
  • Кэш разобранного — ключ «ящик + письмо + вложение + путь», до 8 записей и 96 МБ, 10 минут. Стирается при удалении ящика. Скачивается и разбирается не больше двух писем одновременно: байты в полёте кэш ещё не посчитал, и очередь не даёт пачке разных запросов набрать в main десятки разборов по 32 МБ.
  • Inline — только картинки. Часть с Content-ID прячется из списка файлов, только если это image/*; PDF с Content-ID остаётся файлом, который можно сохранить.
  • Отправитель без «подтверждения». Читалка показывает имя и адрес, но не фото и не карточку из справочника: письмо во вложении мог сочинить кто угодно. Если адреса нет (From: "ceo@company.com" без самого адреса), рядом с именем написано «(адрес не указан)» — имя, похожее на адрес, не выдаёт себя за проверенный адрес.

Кэш inline-картинок: почему ключ — «письмо + cid», а не cid

Чтобы черновик ответа не перекачивал inline-картинки, которые пользователь только что видел в исходном письме (каждая — холодный EWS-раунд ~1.2 с), провайдер держит кэш встроенных изображений: InlineImageCache в main/providers/exchange/provider.ts. Живёт в main, на экземпляре провайдера (один на аккаунт, registry.providerForAccount), ограничен 24 МБ с LRU-вытеснением. Между аккаунтами не разделяется; forgetProvider(id) сбрасывает его при удалении аккаунта и при смене учётных данных. См. ADR-0031.

Ключ — пара (id письма, ContentId), и черновик может брать картинки ТОЛЬКО из письма, из которого он создан (DraftSourceMap; связь пишется в createReplyDraft/createForwardDraft).

Ключ по одному ContentId был бы дырой спуфинга. ContentId, Content-Type и заявленный Size целиком контролирует отправитель: подогнать размер тривиально (хвостовой паддинг PNG/GIF). Злоумышленник, приславший письмо с cid, совпадающим с cid из доверенного письма жертвы (например, логотип корпоративной подписи, повторяющийся во многих письмах), подменил бы картинку внутри доверенного письма. Это не XSS — data:-картинка безопасна для CSP и DOMPurify — но это подмена содержимого, которую пользователь не может заметить.

Происхождение черновика отправителю неподконтрольно, поэтому сужение области видимости до исходного письма закрывает вектор. Для картинок самого письма Content-Type и Size сверяются как дешёвая проверка согласованности, а Size == 0 считается промахом.

Черновик → исходное письмо: cid + тип, без Size (ADR-0146). Exchange может сообщить копии картинки в черновике другой Size (вложение пересериализовано), и раньше это был промах — повторный холодный GetAttachment картинки, которая уже в памяти. Теперь InlineImageCache.getForDraft(источник, cid, тип) сверяет только ContentId и тип. Новой поверхности это не открывает: ключ по-прежнему (id исходного письма, cid), id источника пишет сам провайдер в createReplyDraft/createForwardDraft (не письмо и не окно), и картинка, которую получит черновик, — картинка ровно того письма, которое человек открыл и на которое отвечает. Подменить её может только автор этого же письма — а он и так владеет всем его содержимым. Чужое письмо с тем же cid из кэша источника ничего не получает (проверено тестом reply-fast-path.test.ts). Неизвестный тип ('') — промах.

Ограничения остаются прежними: строгий allowlist растровых типов (INLINE_IMG_TYPES, SVG исключён), валидация base64 (^[A-Za-z0-9+/=]+$) перед вставкой в data:-URI, лимит MAX_INLINE_BYTES (8 МБ на картинку). Кэш их не обходит: в него попадает только то, что прошло проверки.

То же правило — у прогрессивной загрузки (ADR-0040). getInlineImage(messageId, cid) разрешает cid только против своего письма (renderer передаёт messageId открытого письма, main никогда не ищет картинку «где-нибудь ещё»), а кэш черновика по-прежнему ограничен исходным письмом через DraftSourceMap. Renderer-кэш data-URI (lib/inlineImages) ключуется (accountId, привязка этого ящика — generation/revision/principal, messageId, cid) — картинки одного ящика или входа не могут «протечь» в другой, в том числе у неактивного ящика; с ADR-0145 он переживает переключение ящика и стирается при удалении ящика или смене ящика за тем же id (useMail.reset({ purge: true })).

Восстановление устаревшего id не ослабляет ключ (ADR-0047). Если ItemId письма устарел (сервер переложил письмо; Bind падает ErrorItemNotFound), провайдер отдаёт Result с кодом stale, и renderer переразрешает актуальный id того же письма (тред — по стабильному conversationId; одиночное — корреляцией по conversationId + subject + from.address в перечитанной папке, строго уникальное совпадение). При этом forgetMessageImages(accountId, staleId) выбрасывает записи кэша по старому id — новый id получит собственную тройку-ключ. Область видимости не расширяется: картинки по-прежнему грузятся getInlineImage только против своего (теперь свежего) письма, а корреляция никогда не подставляет телу чужой id (неоднозначность → заглушка, а не подмена содержимого).

Кэш картинок в main для всех провайдеров (ADR-0145)

С ADR-0145 картинки писем, уже показанные хоть одному окну, хранит ещё и main (ipc/inline-store.ts) — для Exchange, IMAP и демо одинаково. Правила те же, что у кэша провайдера, и проверяются тестами (inline-store.test.ts):

  • Ключ — (полная привязка ящика, id письма, cid). Привязка — accountId, generation, revision, principal: картинка не переходит ни в другой ящик с тем же ItemId, ни к другому входу того же id. Id письма в ключе — по той же причине, что и у провайдера: cid выбирает отправитель, и ключ «только cid» позволил бы чужому письму подменить картинку внутри доверенного.
  • Записывается только ответ провайдера на картинку ЭТОГО письма — одиночный (getInlineImage(messageId, cid)) или пакетный (getInlineImages(messageId, cids)); оба прошли allowlist растровых типов, MAX_INLINE_BYTES и проверку алфавита base64 в провайдере. Окно не может положить в кэш ничего: канал mail:inlineImage только читает, mail:warmInlineImages лишь просит main загрузить картинки письма, тело которого main уже держит (окно передаёт только id; cid берутся из тела в main), с низким приоритетом. С ADR-0149 окно может ещё назвать картинки своего письма (mail:prefetchInlineImages) — это тоже только просьба загрузить: байты по-прежнему приходят от провайдера и проходят его проверки. Все три канала — через guardedAccount (окно авторизовано для ящика) и assertId/assertCid.
  • Расшифрованное не попадает сюда никогда. Картинка расшифрованного S/MIME-письма отдаётся из памяти SmimeService до этого кэша (ADR-0130); пакет для S/MIME-писем не запускается вовсе.
  • Опоздавшие байты не принимаются. Если за время загрузки письмо забыли (перемещение, удаление, сохранение черновика) или сменился вход ящика, ответ отдаётся тому, кто ждал, но в кэш не ложится (версии письма и ящика, проверка привязки после ожидания).
  • Ограничение и время жизни. 48 МБ base64 на все ящики, LRU; одна картинка больше четверти предела не хранится. Удаление ящика или смена его подключения (tearDownAccountRuntime → forgetMailbox) стирает его тела, признаки S/MIME и картинки.
  • Черновик ответа по-прежнему получает картинки исходного письма только через провайдерный InlineImageCache с проверкой происхождения (DraftSourceMap), типа и заявленного размера — в пакете так же, как в одиночном пути; кэш main ключуется id самого черновика и ничего у исходного письма не берёт.

Признак S/MIME письма (smimeHints, там же) влияет на запрет «ответ сервера на зашифрованное письмо» и «открытый текст поверх зашифрованного черновика» (ADR-0131): он берётся из того же ответа провайдера, что и тело, и забывается вместе с ним. Для писем из «Черновиков» и «Исходящих» он не запоминается вовсе (как и их тела): черновик могут пересохранить зашифрованным под тем же id, поэтому проверка перед записью поверх черновика всегда спрашивает сервер. Строгая проверка переезда черновика между ящиками (ADR-0137) этим признаком не пользуется.

Картинки на диске и заранее (ADR-0149)

С ADR-0149 у кэша картинок main есть дисковый уровень (local-data/inline-images.ts, таблица mail_inline_images, схема v9), а картинки нового письма и верха списка скачиваются заранее. Что это не ослабляет:

  • Шифрование и изоляция — от базы ящика. Таблица лежит в той же базе SQLCipher, что снимки списков (ADR-0050, Локальные данные): ключ — в системном хранилище ключей, база своя у каждого ящика и привязана к владельцу. Перед каждым чтением и записью проверяются storeUuid, principalHash и accountGeneration; чужой владелец или закрытая база — ни чтения, ни записи. Удаление ящика удаляет файл, смена владельца открывает другую базу. Тест проверяет, что байтов картинки в файле базы в открытом виде нет.
  • Ключ — (id письма, cid в нижнем регистре), по той же причине, что в памяти: ключ «только cid» позволил бы чужому письму подменить картинку.
  • Только cid:. Внешние картинки (http(s)) заранее не скачиваются никогда — только по кнопке «Загрузить» (ADR-0040): иначе прогрев выдавал бы отправителю факт и время прочтения. Прогрев касается только картинок, вложенных в само письмо.
  • S/MIME не пишется. На диск попадают только картинки писем, которые main сам держит в кэше тел (не черновик, не «Исходящие», не приглашение) и которые не S/MIME; расшифрованные картинки живут только в памяти SmimeService (ADR-0130). Новые письма-S/MIME не прогреваются (по признаку строки), канал mail:prefetchInlineImages для S/MIME-письма пакет не запускает.
  • Allowlist — на записи и на чтении. Пишется только тип из списка растровых (png, jpeg, gif, bmp, webp, tiff, x-icon), cid безопасного алфавита, валидный base64, не больше 2 МБ; при чтении строка с типом вне списка пропускается — подложенная в базу запись не превратится в data:-URI чужого типа. SQL-ограничения (CHECK на длины и размер) дублируют это на уровне схемы.
  • Удаление следует за письмом. Удалённое, перемещённое, доказанно исчезнувшее из папки, пересохранённое письмо уносит свои картинки и с диска, включая ещё не записанные из очереди.

Новый канал mail:prefetchInlineImages(accountId, messageId, cids) — под guardedAccount (окно авторизовано для ящика, тест mail-ipc-auth-contract.test.ts), messageId через assertId, cids — массив не длиннее 120 (INLINE_BATCH_MAX_CIDS из @shared/cid, окно само обрезает список до него), каждый через assertCid; иначе MailError. Возвращает только число картинок в пакете; байты — по-прежнему через mail:inlineImage.

Диагностика соединений без хостов. Поля socket/dnsMs/connectMs/tlsMs строки req и минутная сводка transport │ connections (Аутентификация и сеть) содержат только new/reused и миллисекунды — ни хоста, ни адреса, ни порта, ни заголовков (тест socket-probe.test.ts). Подписка на каналы диагностики Node видит только запросы, запущенные внутри withSocketProbe, и ничего в них не меняет.

Состояние синхронизации папок (ADR-0154)

С ADR-0154 база ящика хранит ещё и SyncState сервера для папок, которые синхронизируются по изменениям (таблица mail_folder_sync, схема v10, Локальные данные). Строка непрозрачная, но по ней сервер отдаёт изменения папки, поэтому обращаемся с ней как с данными ящика:

  • Только в зашифрованной базе ящика (та же SQLCipher-база, тот же ключ и та же привязка к владельцу, что у снимков списков, ADR-0050). Удаление папки уносит строку каскадом, удаление ящика — вместе с файлом базы.
  • Не покидает main. Типы синхронизации (FolderChange, FolderChangePage) живут в providers/types.ts, в @shared их нет; в окно идёт обычный messageSnapshot либо (этап 2) messageChanges — те же строки списка в той же форме (серверные id, без тел), только тронутые проходом, плюс id удалённых и ушедших из окна; ни SyncState, ни ChangeKey, ни локальных id базы. Адресат и проверка у messageChanges те же, что у снимка: только главное окно, полномочия ящика сверяются целиком (Процессы и IPC). В журнале — только длина состояния (stateBytes), роль папки вместо имени, числа и коды; ни id, ни тем, ни самого состояния. Зонд npm run ews:sync печатает так же.
  • Проверка формы на входе и на выходе. На сервер уходит и в базу пишется только base64 длиной от 1 байта до 2 МиБ (isWellFormedSyncState в провайдере, validSyncState в модели, CHECK таблицы); всё остальное не отправляется и не записывается.
  • Ящик по доступу. Отказ в доступе или скрытая папка — не повод начинать проход с нуля: состояние забывается, папка живёт прежним окном, повторов нет (иначе бесконечный полный проход по закрытой папке).

cid — строка отправителя, поэтому проверяется трижды

ContentId авторит тот, кто прислал письмо, и теперь он путешествует дальше, чем раньше: попадает в атрибут DOM (data-cid), уезжает обратно в main как ключ выборки, и — для ответа/пересылки — возвращается в исходящее тело как src="cid:…". Последнее опаснее всего: escapeBody экранирует &/</> (это защита XML-текста SOAP), но не ", поэтому cid вида a" onerror=… вырвался бы из атрибута и уехал обработчиком события получателю — уже после DOMPurify, где его никто не поймает.

Поэтому один и тот же алфавит проверяется на каждой границе:

  1. санитайзер — markInlineCids (до DOMPurify) и повторно хук afterSanitizeAttributes (после);
  2. IPC — assertCid в main/ipc/mail.ts (вместе с assertId(messageId));
  3. провайдер — getInlineImage отказывает невалидному cid; исходящее тело дополнительно прогоняется через sanitizeOutgoingCids (вырезает оба наших маркера — data-cid и data-inline-state, — и обезвреживает любой cid: вне алфавита прозрачным GIF'ом).

Проверок три — определение одно: src/shared/cid.ts.

// src/shared/cid.ts — ЕДИНСТВЕННОЕ определение. Импортируют:
//   renderer/lib/sanitize.ts          → SAFE_CID, MAX_CID_LEN, bareCid
//   main/ipc/mail.ts                  → isSafeCid  (алфавит + длина, в assertCid)
//   main/providers/exchange/provider.ts → SAFE_CID
export const SAFE_CID = /^[A-Za-z0-9._%+=@/-]+$/
export const MAX_CID_LEN = 256
export function bareCid(raw: string): string       // <x@y> → x@y (форма заголовка → форма URL)
export function isSafeCid(cid: string): boolean    // длина + алфавит

Раньше алфавит был скопирован в три места. Дублировать проверки — осознанная defence in depth (каждый слой не доверяет предыдущему). Дублировать определение — баг, который ждёт своего часа: расхождение на один символ даёт либо тихо неработающие картинки (слой A принял cid, слой B отверг — пользователь видит заглушку и никогда не узнает почему), либо дыру в исходящем теле (символ пропустил тот слой, который стоит последним перед проводом). Нормализация тоже общая: bareCid снимает угловые скобки MIME-заголовка Content-ID — если два слоя нормализуют по-разному, валидная картинка просто не найдётся.

Алфавит уже RFC 2392: под него попадают все реальные генераторы (Outlook image001.png@01DA…, Apple Mail UUID, Gmail ii_…, Thunderbird part1.X.Y@host), а кавычки, апострофы, скобки и бэктик отсекаются целыми классами, а не «потому что полезную нагрузку всё равно не дописать». cid, не прошедший проверку, никогда не повод угадывать — он отвергается.

Аватар EX→SMTP: недоверенный From перед неэкранируемым текстом SOAP

Та же угроза «не-экранирующего SOAP-writer'а», что и у escapeBody/ContentId, есть и на фото-пути. Внутренний отправитель приходит legacy DN'ом (/o=…/cn=…, RoutingType=EX), и, чтобы получить аватар, getContactPhoto резолвит его в SMTP через EWS ResolveName (маппинг данных → Фото контактов). Аргумент ResolveName уходит в SOAP как текст элемента, который writer либы не экранирует (тот же изъян, что у ADR-0029), а сам DN авторит отправитель письма — это поверхность SOAP-инъекции из From. Поэтому перед резолвом DN валидируется в resolveToSmtp: отказ, если длина >512, встретился любой из [<>&"'], или строка не имеет формы настоящего legacy DN (^/o=.+/cn=). Последнее — не только анти-инъекция: голый alias без @ (jdoe) не резолвится вовсе, иначе спуфнутый From мог бы ANR-совпасть с реальным коллегой и подставить его фото. Отсечённый гардами мусор и транзиентные ошибки ResolveName не кэшируются.

Текст пользователя в SOAP: экранирование на стороне провайдера (ADR-0064)

ews-javascript-api не экранирует текст элементов (EwsServiceXmlWriter.WriteValue: soapData += value, «todo: validate invalid characters»). Для тела письма это давно закрыто escapeBody (ADR-0029); с ADR-0064 тот же escapeXmlText (& < > + вырезание XML-невалидных управляющих символов) применяется ко всякому пользовательскому тексту, попадающему в SOAP-элемент: тема письма и встречи, место встречи, имя участника, имя создаваемой папки, строка поиска (<m:QueryString>). Иначе тема «Q&A» ломала отправку невалидным XML, а < из скомпрометированного renderer мог бы внедрить разметку в аутентифицированный CreateItem/FindItem. Идентификаторы (атрибутный контекст Id="…") по-прежнему валидируются на границе IPC (assertId; теперь и в mail:search, как в mail:searchAll). Строка поиска ограничена 1024 символами (assertQuery), тема — 2048, тело — 32 МБ (assertDraftText; inline-картинки едут внутри тела как data:), чтобы скомпрометированный renderer не передал main гигантский payload.

Message-ID как недоверенный ввод: два слоя (ADR-0074)

Ревью 2026-09-19: те же два слоя теперь обязательны при восстановлении приглашения после Accept/Move. Невалидный InternetMessageId отвергается до любой записи в ящик; корректный <local@domain> экранируется в атрибуте поискового фильтра. Проверка не добавляет несовместимый с Exchange 2016 pre-write FindItem.

До ADR-0074 весь текст, который OutTalk подставлял в SOAP, приходил изнутри: тему, строку поиска и имя папки писал пользователь через renderer. Message-ID — первый случай, когда значение из чужого письма сохраняется на диск, а потом возвращается в аутентифицированный запрос к серверу. Это ровно модель угроз ADR-0064, только источник теперь внешний: заголовок RFC 5322 проставляет отправляющая сторона, то есть кто угодно в интернете.

Путь значения: письмо снаружи → readInternetMessageId (GetItem) → TodoStore (JSON в userData/plugin-data/) → findByInternetMessageId → SearchFilter.IsEqualTo(EmailMessageSchema.InternetMessageId, …) → атрибут Value="…" в SOAP-запросе сессии, у которой есть доступ к ящику.

Опасность конкретна: ews-javascript-api не экранирует значения атрибутов — EwsServiceXmlWriter.WriteAttributeString склеивает их в строку SOAP как есть (тот же изъян, что у WriteValue для текста элементов, но в атрибутном контексте добавляется кавычка: она закрывает значение, и всё после неё становится разметкой внутри запроса).

Поэтому слоя два, и ни один не заменяет другой:

СлойЧтоГде стоит
ФормаisInternetMessageId(value) (util/ids.ts): строгая <local@domain>, длина ≤ 998 (потолок строки заголовка RFC 5322), запрещены пробелы, управляющие символы, <, >, ", ', & и обратная косая черта внутри частейпри чтении с сервера (не прошло — не сохраняем, ADR-0074), при чтении файла хранилища задач (TodoStore.validSource — файл на диске такой же недоверенный ввод, как IPC), при записи repointLetter (чинит все копии письма во всех задачах, ADR-0090)
ЭкранированиеescapeXmlAttr(text) = escapeXmlText + " → &quot;, ' → &apos;непосредственно перед подстановкой в SearchFilter.IsEqualTo в ExchangeProvider.findByInternetMessageId и recovery applyMeetingAction

Второй слой обязателен ещё и функционально, а не только как defence in depth: законный Message-ID обязан содержать < и >, а голый < внутри XML-атрибута невалиден — без экранирования Exchange ответил бы не результатом поиска, а ошибкой схемы. То есть «проверили форму, значит можно не экранировать» здесь не работает даже теоретически.

Заодно закрыт messageId в снимке письма. isValidItemId (та же charset-проверка, что у assertId на границе IPC) переехал из ipc/mail.ts в общий util/ids.ts и теперь стоит ещё в двух местах: в host-снимке messageSource() (plugins/builtin/types.ts) и в TodoStore.validSource ; conversationId снимка (ADR-0079) под эту проверку не подведён намеренно: в запрос провайдера он не уходит и служит только ключом группировки, поэтому проверяется как непрозрачный токен (OPAQUE_TOKEN: 1–512 символов без управляющих) — и в messageSource(), и в validSource. Причина та же смена свойства данных: раньше сохранённый id уходил только в openMessage, а теперь main сам бьёт им в EWS (EmailMessage.Bind → ItemId → атрибут Id="…"). Идентификаторы валидируются, а не экранируются — у них есть строгая форма (base64, опционально url-safe), и отвергнуть кривой id дешевле, чем пытаться его обезвредить.

Личные контакты: запись в ящик из окна (ADR-0117)

Раздел «Контакты» — первый путь, по которому окно не только читает, но и создаёт, правит и удаляет элементы ящика, не являющиеся письмами. Скомпрометированное окно могло бы попробовать три вещи: протащить разметку в SOAP-запрос, удалить через «удаление контакта» что-то другое, подсунуть в карточку исполняемое содержимое. Каждой закрыта своя граница.

Хвостовые пробелы строк заметки срезаются построчно (split('\n'), trimEnd), без регулярного выражения с откатом: прежний [ \t]+$ квадратичен, и враждебная строка в сотню килобайт занимала main на минуты. Найдено ревью безопасности; покрыто contacts.personal.test.ts («огромная заметка из пробелов отвергается сразу»). Заметки в список не попадают вовсе (IPC вырезает notes из ответа mail:contacts): по окну разъезжает минимум содержимого.

Папки личных контактов: запись только в папки дерева (ADR-0118)

С папками контактов окно получило три новых действия над ящиком: создать папку, положить новый контакт в названную папку и перенести контакт. Все три принимают идентификатор папки от окна. Скомпрометированное окно могло бы подставить туда id Входящих, скрытой или служебной папки, а в перенос — id письма. Граница такая: main проверяет форму, провайдер — смысл, и смысл он проверяет по данным сервера, а не по слову окна.

УгрозаЗащитаГде

Число запросов ограничено. Окно не может заставить main обходить ящик без конца. Дерево — один GetFolder и не больше двух страниц FindFolder по 500. В дереве не больше 100 папок. Список контактов по папкам — по одной странице на папку плюс общий запас в 7 страниц и не больше 2000 контактов. Каждая запись в папку добавляет одно чтение дерева — те же пределы. Так цена одного вызова из окна остаётся ограниченной.

Что осознанно не защищено. Дерево читается перед записью, а не в той же транзакции: папку, которую удалили в Outlook между чтением дерева и записью, отвергнет уже сам сервер. Удалять и переименовывать папки контактов OutTalk не умеет, поэтому эти операции не открыты окну вовсе. Живой проверки EWS-пути на Exchange не было (Exchange: протокол EWS → Папки контактов).

Копия каталога организации на устройстве (ADR-0172)

С этапа P2 OutTalk держит у себя весь каталог организации — как Outlook в режиме кэширования. Это персональные данные сотен и тысяч людей (имена, должности, отделы, телефоны), поэтому у копии четыре рубежа: сеть, разбор, диск и окно.

Сеть: пароль уходит только на узел EWS

Скачивание — providers/exchange/oab-download.ts, подробности протокола — Exchange: протокол EWS → Адресная книга: вся организация.

  • Только узел EWS и только https. Autodiscover — строго https://<узел EWS>/autodiscover/autodiscover.svc; oab.xml и файл — только если адрес книги от Autodiscover лежит на том же узле, по https и без учётных данных в адресе. Из двух адресов книги (InternalOABUrl, затем ExternalOABUrl) берётся первый, что проходит это правило; не проходит ни один — книга не запрашивается (unsafe-url). Имя файла из oab.xml — только простое *.lzx (OAB_FILE_NAME: без /, .., ?), итоговый адрес обязан лежать в папке книги. Адрес с другим узлом не запрашивается вовсе.
  • Тот же транспорт и вход, что у ящика. Прокси, TLS (rejectUnauthorized = !ignoreCertErrors), Basic — заголовком, NTLM — рукопожатием поставщика входа транспорта; без перенаправлений. Своих сетевых настроек у книги нет.
  • Пределы. Ответы Autodiscover и oab.xml — до 4 МиБ; файл — до 200 МиБ (заранее по size и в потоке по своему счёту байт), не больше обещанного size; тишина в теле ответа дольше 120 с или скачивание дольше 10 минут — обрыв (свои сторожа: тайм-аут Axios после заголовков уже не действует); закрытие потока до конца — обрыв, а не «скачано».
  • 401 не взводит предохранитель пароля. У папки книги на сервере часто выключен вход Basic, а пароль только что принял EWS. 401 здесь — «к книге не пустили» (forbidden): книга остаётся поиском на сервере, следующая попытка — через сутки или по «Обновить». Неудачное рукопожатие NTLM (папка книги предлагает только Negotiate/Kerberos) — тоже «не пустили». Повторов на 401 нет, учётная запись в домене не блокируется. Если папка книги принимает только вход Windows или включена расширенная защита (Extended Protection), ящик со входом Basic остаётся в режиме поиска на сервере; пароль никуда, кроме узла EWS, при этом не уходит. Если предохранитель уже сработал по почте (authLocked), книга сервер не спрашивает.
  • Пауза сервера (ADR-0125) — скачивание не начинается. Все запросы книги идут в фоновой полосе очереди и только после того, как окно открыло книгу (Скорость).

Разбор: файл — враждебный ввод, и разбирается он не в главном потоке

Файл приходит с сервера, но формат сложный (LZX DELTA, таблицы свойств, записи переменной длины), поэтому он разбирается как недоверенный (providers/exchange/oab-records.ts):

  • размер и SHA-1 сверяются с oab.xml до распаковки, uncompressedsize — с TargetSize контейнера; CRC каждого блока обязателен;
  • пределы контейнера: блок до 8 МиБ, весь распакованный файл до 256 МиБ, число блоков — не больше ⌈TargetSize/BlockMax⌉ + 16, сумма блоков равна TargetSize;
  • каждое чтение записи — в границах её cbSize; выход за край — bad-record, а не чтение чужой памяти;
  • из записи берутся только нужные поля; сертификаты, X500 и SIP-адреса, GUID, фото и всё прочее перешагиваются без копирования; строки — без управляющих символов, до 200 знаков (телефоны — 64); список адресов фильтруется до smtp: уже при чтении (X500 и SIP не попадают даже в память), другие адреса — не больше 8; адрес X500 (0x3003) не используется никогда; записей — не больше 200 000;
  • общий бюджет времени — 60 с;
  • разбор идёт в потоке-работнике (oab-worker.ts) с пределом памяти 768 МиБ: зависание или исчерпание памяти убивает поток, а не main. Работник не имеет ни сети, ни диска, ни Electron — только байты на входе и записи (или код ошибки) на выходе.

Ошибка — код из короткого списка, без имени файла и без значений из записей.

Окно: только срезы и только своего ящика

  • Каналы addressBook:org:* — те же права, что у писем ящика (guardedAccount). Окно называет только номер ящика; номер входа main выводит сам и в окно не отдаёт.
  • Запрос среза проверяется в main (normalizeOrgQuery: известные списки и поля фильтров, limit ≤ 500, offset ≤ 1 000 000, строки ≤ 200 без управляющих символов); адрес записи — normalizeSmtp.
  • Окну уходят только DirectoryEntry — поля для поиска (псевдоним, другие адреса, имя и фамилия отдельно) остаются в main; ответы main окно проверяет ещё раз (normalizeOrgPage, normalizeOrgStatus).

Журналы

В журнал (oab, addressbook) — только коды ошибок, HTTP-статусы, этап (autodiscover, oab.xml, file), размеры, время, число записей и признаки (fresh, hasCopy, совпал ли SHA). Ни адресов, ни имён, ни имени файла книги, ни адреса сервера книги, ни значений из записей.

Адрес сервера — только https:// (ADR-0064)

EWS URL аккаунта и baseUrl плагинов (Jira, Confluence) проверяются одной чистой функцией util/service-url.ts → validServiceUrl: https:// без userinfo/query/hash; http:// — только для loopback (локальный тестовый стаб/E2E). WebCredentials шлёт Basic превентивно, а Jira/Confluence — Bearer-PAT, поэтому http:// означал бы пароль/токен открытым текстом на каждом запросе. Проверка стоит на обеих границах: при сохранении (accounts/secrets.ts → isCredentials, plugin-settings.ts → validSettingUrl) и в точке использования (exchange/ews.ts → buildService, jira/handler.ts → readJiraConfig, confluence/handler.ts → readConfluenceConfig) — подменённый на диске файл настроек не обходит её. Вставленная из браузера ссылка приводится к корню сервера до проверки (serviceRoot, ADR-0071): срезаются путь UI сервиса, query и fragment — но не userinfo. Логин с паролем в адресе намеренно остаётся в значении, чтобы его отверг validServiceUrl: молчаливая «чистка» спрятала бы ровно то, ради чего эта проверка стоит. mail:accounts:test/add валидируют форму до первого сетевого запроса. Форма аккаунта поясняет требование под полем EWS URL. Секреты аккаунта дополнительно требуют безопасный бэкенд safeStorage (тот же SAFE_BACKENDS, что у ключей локальной БД: на Linux basic_text отвергается).

IMAP / SMTP: данные сервера — недоверенный ввод (ADR-0127)

Сервер IMAP — такой же внешний источник, как отправитель письма: он объявляет размеры литералов, присылает структуру письма, имена файлов, Content-ID и текст ответов. ImapProvider (src/main/providers/imap/) исходит из того, что сервер может быть враждебным или сломанным.

  • Секреты. ImapCredentials лежат в том же хранилище safeStorage, что и Exchange (accounts/secrets.ts); форма проверяется isImapCredentials (точный набор ключей, хост — имя или IP, не URL) до записи и до сети. Пароль не возвращается в окно никогда: mail:accounts:connection отдаёт ImapConnectionSettings без пароля.
  • Шифрование обязательно. Варианта «без TLS» в типах нет. starttls = обязательный апгрейд: imapflow с doSTARTTLS: true обрывает соединение, если сервер не предложил STARTTLS, и ловит инъекцию открытого текста между ответом на STARTTLS и рукопожатием; nodemailer с requireTLS: true не отправит AUTH без апгрейда. TLS ≥ 1.2. rejectUnauthorized выключается только галочкой «Игнорировать ошибки сертификата» с красным предупреждением в форме.
  • Ничего лишнего наружу. ID сообщает только имя: clientInfo = { name: 'OutTalk', version: '', vendor: '', 'support-url': '' } — imapflow подмешивает свои версию, поставщика и адрес поддержки, а пустые значения выбрасывает; EHLO [127.0.0.1] вместо имени компьютера; Message-ID — <uuid@домен-отправителя>; X-Mailer не ставится; системный прокси не используется.
  • Журнал. logger: false у imapflow, logger: false, debug: false у nodemailer — библиотеки не пишут ни команд, ни ответов, ни пароля. Наши записи содержат только коды ошибок, без адресов и текста ответов сервера; текст ответа сервера не попадает и в сообщение об ошибке.
  • Память main ограничена. Литерал IMAP ≤ 16 МБ, ответ ≤ 32 МБ, строка ≤ 4 МБ (превышение рвёт соединение, а не растит кучу); тело письма ≤ 4 МБ, вложение ≤ 50 МБ, inline-картинка ≤ 8 МБ, перенос вложений в пересылку/черновик ≤ 25 МБ; папок ≤ 2000, страница ≤ 200, совпадений поиска ≤ 10 000; разбор BODYSTRUCTURE — не глубже 32 уровней и не больше 2000 узлов. Таймауты: соединение 30 с, приветствие 16 с, тишина сокета 120 с.
  • Структура письма. Тип части сводится к токену тип/подтип, имя файла очищается от управляющих символов и разделителей пути, Content-ID принимается только из isSafeCid, inline-картинка — только из белого списка растровых типов (без SVG). HTML тела в main не «чистится» — единственный санитайзер остаётся последним шагом в renderer (DOMPurify).
  • Исходящее. Тело проходит общий providers/outgoing-body.ts (то же, что у Exchange): опасные cid: нейтрализуются, внутренние data-* вычищаются. MailComposer и SMTP-транспорт работают с disableFileAccess/disableUrlAccess — содержимое письма не может заставить main прочитать файл или сходить по URL. Bcc не попадает в отправляемое письмо (только в конверт и в копию «Отправленных»). Разбор чужого HTML для цитаты — indexOf, текстовая альтернатива — линейный util/html-text.ts: никаких регулярных выражений с откатом над входом отправителя (ADR-0070).
  • Идентификаторы. Пути папок, UID и номера частей упаковываются в base64url (providers/imap/ids.ts) и при распаковке проверяются (длина пути ≤ 512, без управляющих символов, номер части по грамматике), UIDVALIDITY защищает от открытия чужого письма после сброса папки. Папка с некодируемым путём пропускается в списке, а не роняет аккаунт.
  • Отказ сервера не выдаётся за успех. imapflow 2.x сообщает о неудаче STORE/EXPUNGE/MOVE/SEARCH/APPEND значением false; провайдер превращает его в ошибку. Иначе, например, «удалено» разошлось бы по окнам, а письмо осталось на сервере; неудавшийся SEARCH по Message-ID не считается «письма нет».
  • Зависимости. imapflow 2.0.6 и nodemailer 10.0.10 закреплены точно, выбраны не самые свежие выпуски (осторожность с цепочкой поставок); npm audit и npm audit signatures — при добавлении (ADR-0127 §1).

Предохранители сборки — Electron Fuses (ADR-0064)

build/afterPack.cjs переключает fuses в бинарнике каждой платформы (@electron/fuses, до ad-hoc подписи на macOS): RunAsNode=off (нельзя запустить OutTalk как Node — ELECTRON_RUN_AS_NODE=1 OutTalk -e … работал бы под identity приложения и его TCC-грантами), EnableNodeOptionsEnvironmentVariable=off, EnableNodeCliInspectArguments=off (никакого отладчика к main), OnlyLoadAppFromAsar=on, EnableCookieEncryption=on (cookie, которые может поставить удалённая картинка письма, лежат в jar Chromium зашифрованными ключом ОС — ADR-0065). EmbeddedAsarIntegrityValidation остаётся off до появления настоящей подписи кода (Фаза 2) — без неё хеш нечем защитить. GrantFileProtocolExtraPrivileges остаётся on: renderer грузится через loadFile (file://), и без этой привилегии модульный скрипт Vite блокируется CORS; выключить можно только после перевода renderer на собственную схему app://. Dev-режим и smoke-скрипт используют electron из node_modules, fuses их не касаются.

Плагин пишет сам и говорит за чужой объект (ADR-0092, ADR-0093)

Две новые границы, каждая — смена свойства данных, а не «ещё одна возможность».

Кадр просит показать действия над СВОИМ объектом

Обращение Jira рисует кадр Jira: рамки хоста вокруг него нет, значит и предложить над ним действия других плагинов хост сам не может. Просит владелец — jira.itemActions { key } → ctx.showItemActions({ key, title }) → push plugin:itemActions в главное окно. Что здесь важно:

  • pluginId подставляет main по вызывающему плагину. Кадр не может назваться чужим плагином и подсунуть чужой объект в панель.
  • Подпись берёт обработчик, а не кадр: title приходит от сервера владельца (key · summary), обрезается до 2048 символов в main и рисуется через textContent. Это первый случай, когда текст со стороннего сервера, полученный одним плагином, показывается в интерфейсе, который собирает хост для другого; сервер недоступен — подписью остаётся сам ключ.
  • key ≤ 256 и не уходит в провайдера. Это собственный ключ плагина, а не идентификатор письма: в SOAP-запрос он не подставляется, поэтому проверяется как ограниченная строка, а pluginId — тем же шаблоном, что и реестр (PLUGIN_ID), иначе он ни к чему не разрешится.
  • Открывает объект только владелец. todo.openExternal { id, key, pluginId } берёт вложение с задачи (а не из аргументов кадра) и идёт через openPluginItem в брокере, где заново проверяется «включён ∧ встроенный ∧ ровно этот id ∧ у обработчика есть openItem». Куда именно вести — решает владелец (Jira открывает свой issueUrl через safeOpenExternal).
  • Личность вложения — пара «владелец + ключ», и склеивает её ровно одно место — attachmentIdentity в plugins/todo-identity.ts (вынесено из хранилища ADR-0094: читателей у правила стало двое — хранилище и слияние задач между устройствами). Две склейки разошлись бы молча: «убрать из задачи» переставало бы работать, ничего заметно не ломая.

Панель (components/plugins/PluginItemActionsDialog.tsx) исключает действия самого владельца (excludePluginId) — кадр узнаёт о существовании других плагинов только после того, как человек выбрал действие.

Кадр отдаёт чужой текст на опознание (ADR-0107)

Вставленная ссылка — первый случай, когда в плагин приходит строка из буфера обмена, и приходит она не тому, кто её получил. Границы:

  • Опознаёт не проситель. Кадр задач присылает только todo.attachLink { id, url } (authorizePluginData, url ≤ 2048 символов) и не называет владельца: опрос ведёт main (resolveLinkOf), pluginId в ответе подставляет он же. Кадр не может ни выбрать, кого спросить, ни выдать чужой объект за узнанный.
  • Спрашиваются только включённые плагины и только объявленная возможность. resolvePluginLink в брокере повторяет обычные проверки (включён ∧ встроенный ∧ contributes.links.capability ∈ capabilities ∧ есть обработчик). Выключенный плагин не получает вставленный адрес вовсе.
  • Опрашиваемый видит только адрес. Ни задачи, ни ящика, ни письма в аргументах нет; контекст строится от главного окна, поэтому возможность остаётся main-window-only, как и все данные плагина.
  • Ответ ограничен и остаётся текстом: key ≤ 128 символов, title ≤ 200 после trim() (пустая подпись → сам ключ); в интерфейсе подпись рисуется через textContent, как и подпись объекта из ADR-0092.
  • Сеть — только своя. Confluence отвечает лишь про адрес, начинающийся с его собственного baseUrl, и ходит за заголовком своим же клиентом (Bearer/Basic из keychain, redirect: 'error', 15 с, тело ≤ 8 МБ). Чужой хост не вызывает ни одного запроса: иначе вставленная ссылка превратилась бы в SSRF-пробник от имени пользователя.
  • Адрес не сохраняется. В задаче остаётся то же вложение-указатель { pluginId, key, title }, что и у объекта из панели действий, — не URL. Открывает его потом владелец через openPluginItem, где проверки прогоняются заново.
  • Отказ — молчаливый и полный. Исключение плагина при разборе проглатывается (спрашиваем следующего), «не узнал никто» — not_found без подробностей о том, какие разделы опрашивались.

Люди на задаче и на пункте: кадр выбирает, но не называет

Задачи в папке «Задачи» ящика — по умолчанию (ADR-0123, этап 3)

Владелец решил включать хранение в ящике сразу, без вопроса о согласии (ADR-0123, решение владельца 1). Это пересматривает принцип раздела ниже («решает человек, и по умолчанию — нет»), поэтому вместо вопроса — честный текст там, где человек его увидит:

  • у переключателя «Где хранить задачи» (с ADR-0155 — в Настройках, «Плагины › Задачи», TodoStoragePanel; с ADR-0136 до него — в разделе ящика; ещё раньше — поле storage в форме плагина) — предупреждение: содержимое задач (темы и идентификаторы писем, адреса и имена людей, тексты заметок, время работы) видит всякий, у кого есть доступ к ящику, включая администратора почты; «Только на этом компьютере» выключает хранение в ящике;
  • строка состояния раздела называет ящик, в котором лежат задачи.

На сервере лежит то же, что уезжало в скрытый документ, но теперь это обычные задачи ящика: их видят Outlook, телефон и делегаты, у которых открыта папка «Задачи». Надстройка (люди, письма, пункты, связи) разбирается в main как недоверенный ввод (Архитектура плагинов → Задачи в папке «Задачи»). Задача попадает только в ящик своего письма, человека или встречи или в ящик, в котором открыт раздел (подставляет main, ADR-0136); ящик, названный кадром, сверяется со списком ящиков, умеющих задачи, и с правами окна. Задача из ящика, который здесь не подключён, в чужой ящик сама не уезжает — она ждёт выбора человека. Старый документ при переезде только читается и получает отметку; удалять его части этот шаг не умеет.

Содержимое задач уезжает в почтовый ящик — только по явной просьбе (ADR-0094)

С этапа 3 ADR-0123 этот перенос не ведётся — раздел описывает старые версии и формат документа, нужный для переезда.

До ADR-0094 задачи не покидали компьютер вовсе. Теперь их можно переносить между устройствами, и транспорт — тот же роуминг через ящик, что у настроек: записи UserConfiguration с именами OutTalk.Tasks (опись) и OutTalk.Tasks.<gen>.1…8 (части под именем поколения записи, ADR-0115; старые документы — OutTalk.Tasks.1…8). Это переносит содержимое задач на сервер, поэтому здесь важно не «как защищено», а что именно уезжает и кто решает.

Решает человек, и по умолчанию — «нет». Настройка плагина «Переносить задачи между устройствами» (sync, значения off/on) стоит в off, пока её не переключили руками в доверенных Настройках. Никакой автоматики «включим, раз подключён один ящик» нет: содержимое задач до сих пор не покидало машину, и включать такое за человека нельзя, каким бы удобным оно ни было. Подпись поля называет последствие прямо, а не эвфемизмом.

Что уезжает (полный список — в ADR-0094): заголовки задач, в том числе набранные руками; темы привязанных писем и оба их идентификатора — текущий и долговечный Message-ID, по которому то же письмо находится в любом ящике, куда оно приходило; идентификаторы переписок; адреса и имена отправителей; адреса и имена исполнителя, постановщика, участников, исполнителей пунктов (ADR-0116) и привязанных контактов; названия пунктов, их отметки и сроки; темы, идентификаторы, начало и конец привязанных встреч; тексты заметок целиком; ключи объектов других плагинов; времена создания, изменения и закрытия задачи и дата каждой строки заметки — то есть восстановимая хронология работы человека.

Чего не уезжает: учётных данных, секретов плагинов, тел писем и вложений, локальных номеров учётных записей (на границе они заменяются адресом ящика). Последнее держится не аккуратностью кода, а поимённым списком переносимых полей на границе (ADR-0111): toDocument не копирует задачу скопом, поэтому незнакомое местное поле — а внутри него мог лежать местный номер учётной записи — в общий документ не попадает. С ADR-0116 это касается и пунктов: они собираются поимённо (SUBTASK_FIELDS) в обе стороны, а исполнитель пункта уезжает адресом ящика, не номером. Человек тоже собирается поимённо (PERSON_FIELDS) в обе стороны, а приехавший человек без адреса ящика (mailbox не строка) отбрасывается, а не заводится с «ящиком undefined». Остаточный риск — откат на версию до ADR-0116: она везёт пункты «как есть» и выгрузит исполнителя пункта с местным номером учётной записи; новая версия такого человека отбросит, но номер уже побывал в ящике; поле, забытое в списке, роняет проверку типов, а не утекает.

Кто это прочитает. Запись UserConfiguration лежит в самом ящике, а не в приватном хранилище приложения: её видит любой клиент этого ящика, любой делегат и администратор почты. Заметка при этом — свободный текст, куда люди пишут и то, чему на сервере быть не следует. Это и есть главная причина спрашивать, а не включать самим.

Ящик называет только якорь. Задачи общие на устройство, а роуминг живёт в конкретном ящике, поэтому перенос работает, только когда подключён ровно один ящик; при нескольких он выключен — иначе задачи обо всех ящиках молча уехали бы в один, а если это ящики разных организаций, то это утечка, о которой не просили. Якорь захватывается в начале обмена и перепроверяется перед самой записью: между проверкой и записью стоят сетевые ожидания, и подключённый в это окно второй ящик не должен успеть отправить свои задачи в чужой. Спрашивать реестр учётных записей во время сборки документа запрещено конструкцией — имя ящика может дать только захваченный якорь.

Смена ящика под тем же номером учётной записи не смешивает ящики. Подключение можно переназначить на другой ящик, сохранив номер учётной записи (ADR-0078) — и тогда письма прежнего ящика, записанные в задачах под этим номером, выгрузились бы как принадлежащие новому, то есть темы и адреса одного ящика уехали бы в другой. Поэтому пара «номер ↔ адрес» помнится (plugin-data/com.outtalk.todo.anchor.json), и при расхождении такие ссылки заранее переводятся в ext:<прежний адрес> — на чужой ящик они уже не претендуют.

Подпись устройства — случайная метка, заведённая один раз (plugin-data/device.json). Она нужна только для отладки и в решениях слияния не участвует; брать имя машины или путь профиля нельзя — в нём логин операционной системы, а документ читает любой клиент ящика.

Ящик, которого здесь нет. Приехавшая задача может ссылаться на ящик, на этом устройстве не подключённый; такая ссылка получает синтетический номер ext:<адрес>. Ни одно действие с ним провайдера не беспокоит: assertLocalAccount в обработчике плагина отвечает понятным «Это из ящика, который на этом устройстве не подключён» — раньше, чем номер дошёл бы до проверки прав и превратился в отказ, выглядящий как поломка. Фоновая дозапись личностей писем такие ссылки пропускает по той же причине.

Приехавший документ — недоверенный ввод. Части сверяются по sha256 из манифеста; поколение и карта seen из описи (ADR-0115) проверяются формой (gen — ^[a-z0-9]{8,32}$, метка устройства — validDevice, ^[A-Za-z0-9-]{1,64}$, не больше 16 записей); кривые записи seen отбрасываются поштучно, и устройство, чья последняя запись в карте не значится, сольёт такой документ без удалений с чужой стороны (безопасная сторона отказа); опись более новой версии (v > 2 или больше частей, чем MAX_PARTS) не перезаписывается «лечением» — иначе чужой документ мог бы откатить формат у всех устройств; пределы (≤ 1000 задач, ≤ 4000 связей, ≤ 256 КБ на запись) проверяются по ходу склейки, до слияния; негодная задача выбрасывается поштучно, а не отвергает документ целиком (иначе одна испорченная запись заклинила бы перенос навсегда — документ в ящике никто не чинит); сравнение коллекций идёт по ключам личности, а не перебором. Разобранные задачи проходят те же валидаторы validItem/validRelation, что и локальный файл хранилища. С ADR-0111 к этому добавлено правило приёма: из приехавшей задачи берутся только знакомые поля, перечисленные поимённо (включая вложенные — письмо, ссылку, человека). Незнакомое поле не «сохраняется на всякий случай»: пройдя мимо собственных проверок, оно легло бы в локальный файл в чужом виде и заклинило бы его у следующей версии приложения — ровно этот сценарий и случился 28.09.2026. А с ADR-0112 симметрично ведёт себя и локальный файл: негодная запись откладывается в карантин (байт в байт, с возвратом в файл при каждой записи), а целиком отвергается только файл негодной структуры или версии новее известной.

S/MIME: расшифровка только в main (ADR-0130)

Подробно — S/MIME. Коротко о границах:

  • Ключ. Основной путь на macOS — /usr/bin/security cms -D: ключ остаётся в Связке ключей, расшифровывает инструмент Apple, доступ к ключу разрешает сам человек в окне macOS. На Windows — EnvelopedCms.Decrypt() через PowerShell с фиксированным скриптом. Запасной путь — загруженный .p12: закрытый ключ хранится только зашифрованным safeStorage (userData/smime-keys.json, 0600); без безопасного бэкенда загрузка отказывается всегда. Пароль .p12 используется один раз. Файл выбирает диалог main, окно получает одноразовый жетон — ни пути, ни байтов.
  • Подпроцесс. Абсолютный путь, spawn без оболочки, фиксированные аргументы; CMS — только на stdin; минимальное окружение (без NODE_*, ELECTRON_*, DYLD_*); вход ≤ 32 МБ, выход ≤ 64 МБ, таймаут 120 с. stderr сводится к причине и выбрасывается — в нём могут быть имена ключей.
  • Разбор. Весь CMS/.p12 недоверенный: der.ts проверяет форму, пределы — MIME 32 МБ, расшифровка 48 МБ, .p12 1 МБ, итерации KDF ≤ 2 млн; любой сбой — типизированный отказ без ключевого материала.
  • Где живёт расшифрованное. Только память main (SmimeService, ≤ 8 писем, ≤ 10 минут, затирание байтов частей). Кэш деталей main видит только конверт; SQLite ничего не получает; временных файлов нет — Quick Look и «Открыть» для частей зашифрованного письма отключены (saveAttachmentToTemp отказывает по id smime_<n>), остаётся «Скачать».
  • Рендер. Расшифрованный HTML идёт тем же путём, что любое письмо: DOMPurify, CSP, блокировка внешних картинок. Строку «Подписано» рисует приложение по вердикту main.
  • IPC. smime:* — только главное окно (authorizeMainWindow), закреплено тестом smime-ipc-auth-contract.test.ts.
  • Остаточный риск: строки JS (base64 ключа после safeStorage.decryptString) затереть нельзя; отзыв сертификатов не проверяется.

Доверие к подписи — то, чему доверяет компьютер (дополнение 2026-10-02 к ADR-0130)

«✓ Подписано» означает: подпись цела, адрес в сертификате = From, сертификат для почты, и операционная система доверяет его цепочке (macOS security verify-cert -p smime, Windows X509Chain; Linux — корни среды выполнения). Что из этого следует:

  • Мы доверяем тому же, чему доверяет ОС, — включая корни, добавленные пользователем или администратором (корпоративный центр, помеченный доверенным в Связке ключей; корень, разосланный групповой политикой). Так делают «Почта» и Outlook, и этого ждёт владелец. Обратная сторона: кто сумел добавить корень в доверенные этого пользователя (вредоносная программа с правами пользователя, перехватывающий прокси, слишком широкий корпоративный центр), тот может выпустить сертификат на любой адрес — и письмо от чужого имени покажется «Подписано». Но такой корень уже доверен этому компьютеру для HTTPS и всего остального; отдельной защиты почта тут не даст, а свой список корней разошёлся бы с системой.
  • Доверие к центру не равно «любой адрес»: адрес по-прежнему сверяется с From, назначение сертификата — почта; несовпадение — отдельная предупреждающая строка.
  • Отзыв не проверяется (macOS -L — без сети, Windows RevocationMode = NoCheck): отозванный, но ещё не истёкший сертификат будет «Подписано». Плюс: на macOS (-L) и Linux открытие письма не делает сетевых запросов и не выдаёт, что письмо прочитано. Подсказка у строки говорит об отзыве прямо.
  • Остаточный риск Windows: X509Chain в Windows PowerShell (.NET Framework) не умеет запретить догрузку недостающего промежуточного сертификата по адресу из самого сертификата (AIA). Отправитель, положивший туда свой адрес и не вложивший промежуточный сертификат, может узнать о прочтении (запрос и IP) — тот же канал, ради которого блокируются внешние картинки. Мера — UrlRetrievalTimeout = 1 мс (попытка обрывается сразу; цепочка без промежуточного не строится → «не проверен»). Полностью отключить можно только флагом CryptoAPI вне .NET Framework — не сделано. На «Подписано» не влияет.
  • Подпроцесс: абсолютный путь, без оболочки, фиксированные аргументы (только наши пути к временным файлам и дата, которую форматируем мы); сертификаты — во временном каталоге mkdtemp (0700), файлы 0600 (wx), удаляются сразу при любом исходе (на Windows — stdin, без файлов); таймаут 15 с, вывод ≤ 64 КБ, ≤ 8 промежуточных по ≤ 16 КБ, минимальное окружение; stderr не читается в сообщения, решает код выхода. Сертификаты — публичные данные; ничего секретного на диск не попадает.
  • Кэш ответов — 10 минут, только «доверяет / не доверяет», сбрасывается при smime:changed и «Проверить»; «система не ответила» не кэшируется и никогда не даёт «Подписано».
  • Сертификаты корреспондентов для шифрования ответа (ADR-0131) запоминаются только с подписи «Подписано» — значит, с тем же решением ОС.

Отправка S/MIME (ADR-0131)

  • Ключи не покидают ОС/main. Окно шлёт текст письма и два флага (mail:smime:send); main проверяет форму каждого поля (assertSmimeSend: текст, адреса, вложения, булевы флаги, id) и копирует его поле за полем.
  • Никакого молчаливого понижения. Шифрование включено, а у получателя нет годного сертификата → отказ с перечнем адресов. Ответ на зашифрованное письмо (или переоткрытый зашифрованный черновик) без шифрования → отказ DOWNGRADE_REFUSED, если окно не передало downgradeConfirmed — флаг ставит только явное подтверждение в диалоге. Правило проверено тестом и в renderer (smime-compose.test.ts), и в main (send.test.ts). Единственное допустимое «меньше»: зашифрованное без подписи — только когда своей личности для подписи нет; окно говорит об этом пометкой с причиной, а явно запрошенную подпись (sign: true), которую сделать нельзя, main отклоняет (дополнение 2026-10-02).
  • Подпись проверяется всегда. security cms -S -N при несовпадении имени подписывает другой личностью (проверено на Mac) — поэтому подпись системы и своя проходят тот же верификатор, что входящие, и подписавший обязан быть именно выбранным своим сертификатом (сравнение DER); иначе — подпись выбрасывается, дальше — загруженный .p12 или отказ (больше системных попыток нет).
  • Сертификат получателя — только с его адресом, действующий, keyEncipherment, почтовый, RSA; источники — системное хранилище, проверенная подпись (valid и адрес = From), справочник Exchange. Кэш корреспондентов — 0600, ограничен, без ключей (сертификаты публичны, но список говорит, кто пишет, — поэтому только в main).
  • Открытый текст зашифрованного письма: не уходит на сервер (ни как черновик, ни как цитата серверного ответа), не пишется в журнал (только коды ошибок), не попадает в SQLite (у зашифрованного письма нет превью), не ложится во временные файлы; буферы открытого текста и перенесённых частей затираются после шифрования.
  • Подпроцесс — как при расшифровке: абсолютный путь, без оболочки, данные на stdin, ограничения ввода/вывода, таймаут, минимальное окружение; из «внешних» значений в командной строке — адрес получателя для find-certificate -e (safeEmailArg: без ведущего -, пробелов, кавычек) и для cms -S -N — адрес или CN выбранного своего сертификата (safeNickArg: без ведущего - и управляющих символов, ≤ 128). Свой сертификат ищется без адреса в командной строке (find-identity + find-certificate -a -p, SHA-1 считает main). Windows получает только отпечаток SHA-1 (на stdin, шаблон ^[0-9A-F]{40}$).
  • Скрытая копия для подписанных/зашифрованных писем отклоняется — её адрес попал бы в RecipientInfos, видимые всем.
  • Обычные каналы закрыты для конверта. Существующие каналы mail:sendDraft, mail:saveDraft, mail:createReply, mail:createForward отказывают (MailError('invalid')) для S/MIME-конверта (smime.hint = 'pkcs7'): ни открытый текст поверх зашифрованного черновика, ни серверный ответ на зашифрованное письмо. Признак берётся из памяти SmimeService, затем из кэша деталей, затем из карты признаков smimeHints (ADR-0145: признак письма, которое main уже читал, живёт дольше тела), в крайнем случае — одним getMessage (его ответ тоже запоминается в карте); ошибка провайдера при этой проверке считается «не конверт» (окно и так шлёт такие письма только через mail:smime:*). Если признака нет и в карте, сначала идёт узкий запрос провайдера probeSmimeEnvelope (класс письма и список вложений, без тела, ADR-0146); полное чтение — только если узкий не решил (unknown: обычный класс и одинокий smime.p7m — решает тело) или его у провайдера нет (smimeEnvelopeOf, main/compose-prep.ts). Та же проверка стоит в подготовке ответа, которую main начинает в compose:open (ADR-0146): конверт сервер не цитирует, окно собирает ответ из расшифровки. Там она строгая (strict): окно исходное письмо не читает, поэтому «не удалось узнать» — отказ окну, а не «не конверт» (иначе ответ на зашифрованное письмо мог бы открыться без шифрования по умолчанию).

Почему ревизия — HMAC с ключом процесса, а не случайный номер в accounts.json. Проверено: от revision не зависит ничего на диске — привязка локальной БД её исключает (ADR-0050), а кэши, где она часть ключа (account-cache, LRU тел и фото, single-flight записей, менеджер репозиториев, снимок в окне), живут в памяти и умирают с процессом. Поэтому стабильность нужна только в пределах одного запуска, и HMAC её даёт: одинаковые данные входа → одинаковая ревизия, у всех ящиков одного входа она общая и меняется у всех сразу при смене пароля или настроек входа. Плюсы перед номером в файле: формат accounts.json и account-secrets.json не меняется (прежние версии открывают те же файлы, чтение их не переписывает), ревизию невозможно «забыть» обновить на одном из путей записи секрета, а откат секрета при сбое реестра возвращает и прежнюю ревизию. После перезапуска ревизия другая — окна в этот момент тоже новые.

Принятые остаточные риски.

  • Проверка страницы надстройки и внутренняя сеть. Запросы в частные сети (10/8, 172.16/12, 192.168/16) разрешены сознательно: корпоративные надстройки живут там, полный запрет сломал бы проверку. Манифест разворачивает администратор Exchange, запрос — GET без кук и без входа, только https, ответ в окно не попадает (только код, схема входа, откуда office.js). DNS rebinding: имя проверяется нашим dns.lookup, а запрос делает сетевой стек Chromium со своим резолвом — между ними злонамеренный DNS может сменить ответ. Окно узкое, проверку человек запускает сам, и ответ всё равно не выходит за пределы кода и заголовков.
  • todo.pickTasks и форма объекта. Главное окно авторизовано на все ящики (оно читает их почту), поэтому «объект этого ящика» проверяется по форме (письмо — годный id, человек — годный адрес, встреча — годный id), а не по существованию. Скомпрометированное главное окно может назвать выдуманное письмо — но ему и так доступна вся почта всех ящиков.
  • OUTTALK_DEBUG в упакованной сборке. Чтобы открыть DevTools, переменную нужно задать при запуске приложения — это может только тот, кто уже запускает программы от имени пользователя (а значит, и читает его файлы). Удалённо её не задать; плагины её не видят, а главное окно в «Разработчик › Параметры запуска» видит лишь, что она задана (без значения). С ADR-0155 она ещё и включает режим разработчика на время запуска — это тоже только видимость. Сценарий диагностики «запустить упакованное приложение с DevTools» описан в Отладке, поэтому флаг оставлен; --inspect, NODE_OPTIONS и ELECTRON_RUN_AS_NODE по-прежнему закрыты предохранителями сборки.

Известные ограничения (осознанно не исправлены)

1. Обновление: целостность есть, подлинность издателя — нет

Приложение само скачивает и ставит обновления на Windows (ADR-0041). Сборка не подписана (нет Authenticode), поэтому electron-updater может проверить только SHA512 из latest.yml, полученного по HTTPS из публичного репозитория релизов outtalk-releases.

Что это даёт: файл нельзя подменить или повредить в пути — TLS закрывает канал, хеш закрывает содержимое. Скачанный установщик бит-в-бит тот, что описан в фиде.

Чего это НЕ даёт: ответа на вопрос «кто издатель». Цепочка доверия замыкается на факте «latest.yml лежит в нашем репозитории», а не на криптографической подписи разработчика. Отсюда прямое следствие, которое надо назвать вслух:

Право записи в mdanshin/outtalk-releases = выполнение произвольного кода на машине каждого пользователя Windows. Приложение скачает и запустит то, что там опубликовано, — без единого вопроса пользователю.

Как это удерживается в узде (обязательные условия, не «рекомендации»):

  • список лиц с правом записи в outtalk-releases — минимальный (в идеале один владелец), внешних коллабораторов нет;
  • публикующий токен — fine-grained PAT только на этот репозиторий, права Contents: Read and write, конечный срок жизни; он не переиспользуется для других задач и хранится единственной копией — в секрете RELEASES_TOKEN приватного репозитория кода;
  • 2FA на GitHub-аккаунте, публикующем релизы, — обязательна (компрометация аккаунта = компрометация всех клиентов).

Условие снятия риска — подпись кода. Authenticode (Windows) добавляет проверку издателя к проверке хеша и заодно убирает предупреждение SmartScreen; Developer ID + нотаризация (macOS) включают тот же electron-updater и там. До тех пор macOS намеренно не имеет авто-установки (Squirrel.Mac всё равно отверг бы неподписанное обновление), а checker.ts защищён allowlist'ом ориджинов: скомпрометированный фид не может увести «Скачать» на произвольный URL. См. Дистрибуция и обновления, ADR-0041.

Что renderer не может в принципе. Каналы update:* не принимают URL — фид берётся из app-update.yml (кладёт electron-builder), страница загрузки — из allowlist в main. Скомпрометированный renderer не превращает «Обновить» в «скачай что угодно откуда угодно».

Подавить сообщение об обновлении тоже нельзя — молча. Обратная сторона доставки исправлений: тот, кто сидит между приложением и фидом (captive portal, перехватывающий прокси), не имеет права превратить «не знаю» в «у вас последняя версия» — иначе клиент навсегда останется на уязвимой версии, не сказав ни слова. Поэтому «последняя версия» объявляется только после состоявшегося сравнения версий: сетевой сбой, ответ не-200 и ответ 200, в котором нет поля version, дают stage: 'error' с видимым текстом (update/checker.ts, зафиксировано checker.test.ts). Тем же правилом живёт dev-сборка: она не проверяет обновления вовсе и говорит об этом прямо (canCheck: false), вместо того чтобы показать успокаивающую строку без единого запроса — ADR-0041 (уточнение 2026-09-18), Дистрибуция и обновления.

Подпись приложения

Локальные сборки без сертификата Apple используют ad-hoc подпись и снятие карантина (scripts/reinstall.sh). Windows-сборки не подписаны (SmartScreen предупреждает при первой установке). Для распространения без предупреждений — Developer ID + нотаризация (macOS) и Authenticode (Windows) — см. Сборка и запуск, Дистрибуция и обновления.

Ограничения сетевых ответов плагинов (ревью 2026-09-19)

Jira/Confluence держат таймаут 15 секунд до конца чтения тела, включая ошибочные HTTP-ответы. Превышение 8 МБ, оборванный поток и timeout возвращают ошибку network; они не превращаются в пустой результат или успешную мутацию. Завышенный Content-Length и переполнение потока отменяют чтение; reader lock освобождается. Отклонённые изображения Confluence также отменяются.

Бюджет пагинации считается по запросам, независимо от числа валидных строк: поиск Jira — максимум 5 страниц по 100, участники группы — 4 по 50, пространства Confluence — 4 по 50. Сервер не может продлить цикл malformed-строками или бесконечным total / isLast=false. Неполный поиск Jira возвращает truncated=true.
