S/MIME: зашифрованные и подписанные письма

OutTalk читает письма S/MIME — зашифрованные и подписанные — так же, как «Почта» на Mac и Outlook: расшифровывает ключом, который уже лежит в системе, и проверяет подпись (ADR-0130). И отправляет их: подписывает ключом из системы, шифрует для получателей и для себя; ответ на зашифрованное письмо шифруется сам (ADR-0131, раздел «Отправка» ниже).

Microsoft IRM/RMS (письма с .rpmsg, «Не пересылать», «Только для сотрудников») — это другое шифрование, с сервером прав. Его не читает и «Почта» на Mac; OutTalk тоже.

Что такое S/MIME (кратко)

S/MIME (RFC 8551) упаковывает письмо в CMS (Cryptographic Message Syntax, RFC 5652):

Что видно снаружиЧто внутриКак называет Exchange
application/pkcs7-mime; smime-type=enveloped-dataEnvelopedData: письмо зашифровано случайным ключом (CEK), CEK зашифрован открытым ключом каждого получателяIPM.Note.SMIME
application/pkcs7-mime; smime-type=authEnveloped-dataAuthEnvelopedData (RFC 5083): то же, но AES-GCM с проверкой целостностиIPM.Note.SMIME
application/pkcs7-mime; smime-type=signed-dataSignedData с вложенным содержимым («непрозрачная» подпись)IPM.Note.SMIME
multipart/signed; protocol="application/pkcs7-signature"письмо открытым текстом + отдельная часть smime.p7s с SignedData без содержимого («открытая» подпись)IPM.Note.SMIME.MultipartSigned

Слои вкладываются: Outlook по умолчанию подписывает, потом шифрует — внутри расшифрованного конверта лежит подписанное письмо. OutTalk снимает до четырёх слоёв подряд (smime/open.ts).

Путь письма

provider.getMessage(id)          ← обычный GetItem / FETCH; видит только «это S/MIME» (smime.hint)
        │
main: mail:message               ← кэш деталей main хранит ТОЛЬКО конверт
        │
SmimeService.open(...)           ← только по клику; фоновый прогрев конверт не вскрывает
        ├─ размер конверта из списка вложений > 32 МБ → «слишком большое», ничего не качаем
        ├─ provider.getMessageMime(id)      ← исходный MIME: EWS MimeContent / IMAP BODY[]
        ├─ unwrapSmime: слой за слоем
        │     ├─ EnvelopedData → системное хранилище ключей → загруженные .p12
        │     └─ SignedData   → проверка подписи и цепочки
        └─ renderEntity → тот же parseAttachedMessage, что у письма во вложении (ADR-0129)
                          → bodyHtml + части smime_<n> (localOnly, в памяти)
        │
renderer                         ← тот же путь, что у любого письма: DOMPurify, CSP,
                                   блокировка внешних картинок, тёмная тема

Расшифрованное письмо не делает послаблений: его HTML санитайзится DOMPurify в renderer, внешние картинки заблокированы до «Загрузить», CSP та же. Строка статуса S/MIME рисуется приложением, а не письмом, и подделать её содержимым письма нельзя.

Откуда берётся ключ

Порядок: сначала системное хранилище, затем загруженные файлы.

macOS — Связка ключей (основной путь)

OutTalk запускает /usr/bin/security cms -D — подписанный Apple инструмент, которым пользуется и сама система. Он разбирает CMS и расшифровывает его ключами из связок пользователя — теми же, которыми пользуется «Почта». Экспортировать ничего не нужно.

  • Первый раз macOS спросит: «OutTalk/security хочет получить доступ к ключу…». Это окно самой macOS, приложение его не рисует и пароль от связки не видит. Нажмите «Разрешить всегда» — тогда вопрос не повторится.
  • Если нажать «Запретить», письмо покажет «Нет доступа к ключу — система отказала». Откройте письмо ещё раз и разрешите.
  • Кнопка «Проверить» в настройках вызывает security find-identity -p smime: показывает сертификаты для почты, у которых есть ключ. Ключи при этом не трогаются, поэтому вопроса доступа не будет.

.p12: кроме предела 2 млн итераций на одну деривацию, у всего файла общий бюджет — 8 млн (IterationBudget): специально собранный файл не заморозит main.

Почему подпись проверяем сами, а не тем же инструментом. security cms -D -h 0 печатает статус подписанта (SigningCertNotTrusted, DigestMismatch), но (1) это текст, предназначенный человеку, и его формат не документирован; (2) с открытой подписью (multipart/signed) инструменту нужен файл с подписанной частью (-c content) — то есть расшифрованное содержимое на диске; (3) на Windows и Linux нужна та же проверка. Поэтому подпись проверяет pkijs (ниже) — одинаково на всех системах, без временных файлов.

Windows — хранилище сертификатов

PowerShell (%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoProfile -NonInteractive -NoLogo -EncodedCommand …) с фиксированным скриптом: System.Security.Cryptography.Pkcs.EnvelopedCms.Decode + Decrypt() — .NET сам ищет получателя в хранилищах «Личные» (CurrentUser\My, затем LocalMachine\My). CMS передаётся base64 на stdin, результат — base64 на stdout. Скрипт закодирован в -EncodedCommand и не содержит ничего из письма. HRESULT ошибки переводится в причину (CRYPT_E_RECIPIENT_NOT_FOUND → no-key, ERROR_CANCELLED → denied, …). Смарт-карта/токен может показать системный запрос ПИН — это окно Windows.

⚠️ Проверено только на имитации. Путь Windows покрыт тестами с подменённым процессом; на настоящей Windows-машине он не запускался. Если там что-то не так, письмо всё равно откроется загруженным .p12.

Linux

Общего хранилища ключей нет — только загруженные .p12.

Загруженные файлы .p12 / .pfx (запасной путь)

Нужен, если ключа нет в системе (например, он лежит только на другом компьютере) и на Linux. Настройки → «Безопасность и шифрование» → «Сертификаты для подписи и шифрования» → «Добавить сертификат из файла».

  • Файл выбирается в окне main; renderer получает одноразовый жетон и имя файла — ни путь, ни байты в окно не попадают. Жетон живёт 5 минут и тратится первой попыткой.
  • Пароль файла уходит в main один раз, открывает файл и не сохраняется.
  • На диск (userData/smime-keys.json, права 0600, атомарная запись) ложатся: сертификат — открыто (он публичен, его несёт каждое подписанное письмо), закрытый ключ (PKCS#8) — зашифрованным через safeStorage (Связка ключей / DPAPI / libsecret).
  • Если безопасного системного шифрования нет (Linux без keyring — бэкенд basic_text), загрузка отказывается — всегда, не только в собранном приложении. «Режима разработки» для закрытого ключа нет.
  • Одно хранилище на профиль, не на ящик. CMS сам называет нужный ключ (издатель + серийный номер или идентификатор ключа), поэтому подходящий ключ находится, через какой бы ящик ни пришло письмо; человек с одним сертификатом на два ящика загружает его один раз.
  • Сертификатов может быть несколько (до 50). Старые не удаляйте: старые письма зашифрованы старым сертификатом, и после его замены открываются только им. Повторная загрузка того же сертификата заменяет запись.
  • Закрытый ключ расшифровывается из safeStorage только когда письмо называет именно его сертификат, и только на время расшифровки CEK.

Проверка подписи

smime/cms-verify.ts, библиотека pkijs поверх WebCrypto Node:

  1. Найти сертификат подписавшего в самом письме (IssuerAndSerialNumber или SubjectKeyIdentifier).
  2. Проверить хеш содержимого (message-digest) и подпись над подписанными атрибутами.
  3. Сертификат должен быть почтовым: расширения EKU нет либо в нём есть emailProtection; в сертификате должен быть адрес, и он должен совпасть с From (open.ts). Иначе — не выше untrusted.
  4. Отдельно — доверие решает ОС (дополнение 2026-10-02 к ADR-0130, smime/os-trust.ts), как в «Почте» и Outlook. Момент проверки — signingTime, но не позже «сейчас». Отзыв (CRL/OCSP) не проверяется.
    • macOS: /usr/bin/security verify-cert -c <лист> -c <промежуточные…> -p smime -L -q -d <момент> — системные и пользовательские настройки доверия (центр, «помеченный как доверенный для этой учётной записи» в связке «Вход», засчитывается). -L — без сети. Сертификаты — во временных файлах 0600 в личном каталоге 0700, который удаляется сразу. Исход — код выхода: 0 доверяет, 1 нет, прочее — «система не ответила».
    • Windows: X509Chain в фиксированном скрипте PowerShell; ApplicationPolicy = emailProtection, RevocationMode = NoCheck, промежуточные из письма — ExtraStore, UrlRetrievalTimeout = 1 мс (догрузку по AIA .NET Framework запретить не умеет — см. Безопасность); сертификаты base64 на stdin.
    • Linux (и e2e с OUTTALK_SMIME_SYSTEM=0): цепочка строится в процессе (pkijs) до корней, которые видит среда выполнения (tls.getCACertificates('system')).
    • Не почтовый, истёкший или без адреса сертификат до ОС не доходит. Ответ ОС кэшируется на 10 минут (по отпечатку цепочки и дню), сбрасывается при smime:changed и по «Проверить»; «Проверить» заодно перечитывает открытые S/MIME-письма.

Открытая подпись проверяется над точными байтами первой части multipart/signed (разбор на сырых байтах, smime/mime.ts); если почтовый узел по дороге превратил CRLF в LF, повторяем над каноническим CRLF.

СостояниеСтрока в письме

При нескольких подписях (подпись внутри и снаружи шифра) показывается худшая. У каждой строки подписи есть подсказка, и она заканчивается честным «Отзыв сертификата не проверяется.»; подсказка доступна и с клавиатуры (строка в порядке Tab), и экранному диктору (скрытый текст).

Отправка: подпись и шифрование (ADR-0131)

Что видит человек

  • В окне письма справа внизу — пара переключателей «Шифровать» (замок) и «Подписать» (печать). Включённый — подсвечен индиго, замок закрыт; выключенный — серый контур, замок открыт. У каждого — подсказка, что он делает. В узком окне остаются только значки. «Шифровать» включает и «Подписать» — если есть чем подписать. Шифрование подпись не требует (как в Outlook): если своего сертификата для подписи нет, «Подписать» показан выключенным, подсказка говорит почему, а над кнопками — спокойная пометка «Письмо будет зашифровано без подписи» с причиной; письмо уходит зашифрованным без подписи (дополнение ADR-0131 от 2026-10-02).
  • Ответ и пересылка зашифрованного письма шифруются сами — «Шифровать» уже нажат, «Подписать» — если есть чем подписать. Выключить шифрование такого ответа можно, но только после вопроса «Отправить ответ без шифрования?» с объяснением, что цитата исходного письма уйдёт открытой. После этого над кнопками остаётся спокойная плашка «Ответ уйдёт без шифрования» с кнопкой «Зашифровать снова».
  • Пока шифрование включено, у получателя в поле «Кому»/«Копия» тихий замок — сертификат есть; жёлтая «пилюля» со щитом — нет, просрочен или не годится. Подсказка на получателе говорит это словами. В конце строки «Тема» — пометка «Тема не шифруется» (в узком окне — значок открытого замка; полное пояснение — в подсказке).
  • Всё, что мешает отправке, написано целиком в плашке над кнопками — сразу, ещё до нажатия «Отправить»: «У получателя нет сертификата» (кого именно, и кнопки «Убрать получателя» / «Отправить без шифрования…»), «Не найден ваш сертификат» / «Ваш сертификат не подходит для шифрования» — с причиной («Выключить шифрование»), «Нет вашего ключа для подписи» — для письма только с подписью, с причиной («Не подписывать»). «Отправить» в таком состоянии ничего не отправляет — плашка мягко появляется ещё раз. Вопрос «Отправить без шифрования?» задаётся в той же плашке; по умолчанию в фокусе «Оставить шифрование».
  • В списке писем у зашифрованного письма — маленький замок в конце строки темы (подсказка «Защищено S/MIME — зашифровано или подписано», в доступном имени строки — «Защищено S/MIME») и «Текст защищён S/MIME» вместо превью. Слово не «Зашифровано»: Exchange хранит письмо, подписанное «непрозрачной» подписью, под тем же классом IPM.Note.SMIME, что и зашифрованное, и до вскрытия их не различить; точный статус — в области чтения; скрепки нет — «вложение» smime.p7m это сам конверт. Поле списка — MessageSummary.smime ('encrypted' | 'signed'). Для просто подписанных писем значка в списке нет намеренно: список не знает, цела ли подпись, а там, где подписывают всё, значок стоял бы на каждой строке; проверенный статус показывает область чтения.
  • Настройки → «Безопасность и шифрование»: строки «Подписывать все письма» (security.smime.signAll) и «Шифровать, когда у всех получателей есть сертификаты» (security.smime.encryptAuto) — для ящика из переключателя «Ящик» в шапке страницы (карточка начинается «● Для ящика <адрес>», значок ноутбука — только на этом компьютере; ADR-0155). Обе выключены. Вторая только включает переключатель (если все сертификаты нашлись и вы его не трогали), но никогда не выключает.

Конверт или нет: проверка перед ответом (ADR-0146)

Прежде чем просить сервер построить ответ или пересылку (mail:createReply/mail:createForward и подготовка, которую main начинает в compose:open), main решает, не конверт ли S/MIME исходное письмо: конверт сервер процитировать не может, и ответ собирается из расшифровки (mail:smime:prepareResponse). Решает smimeEnvelopeOf(known, provider, id) (main/compose-prep.ts), от дешёвого к дорогому:

ШагОткудаСеть
1память main: расшифровка SmimeService.composeSource, затем detailCache — smime.hint === 'pkcs7'нет
2необязательный метод провайдера probeSmimeEnvelope(id) → envelope / plain / unknownExchange: один GetItem с IdOnly + ItemClass + Attachments — без тела и без байтов вложений
3getMessage(id) — только если шаг 2 ответил unknown или метода у провайдера нетполное чтение

Вердикт Exchange — smimeProbeVerdict(класс, вложения) (providers/exchange/smime.ts): IPM.Note.SMIME и IPM.Note.SMIME.*, кроме …MultipartSigned, а также IPM.Note.Secure / IPM.Note.Secure.Sign — envelope (и зашифрованное, и «непрозрачно» подписанное сервер не процитирует); …MultipartSigned — plain; обычный класс с единственным вложением smime.p7m типа application/pkcs7-mime — unknown, потому что эту форму различает только тело (см. smimeHintOf); всё остальное — plain. Узкий запрос заодно запоминает ChangeKey письма, и следующий CreateReply/CreateForward обходится без своего GetItem. Сбой шага 2 — переход к шагу 3; сбой шага 3 — «не конверт», как и раньше (сервер просто построит ответ с пустой цитатой, а открытый текст зашифрованного письма на сервер всё равно не уйдёт — его там нет). IMAP и демо метода не объявляют.

Что внутри письма

From / To / Cc / Subject / Date / Message-ID / In-Reply-To / References / Thread-Topic / Thread-Index   ← открыто
MIME-Version: 1.0
Content-Type: application/pkcs7-mime; smime-type=enveloped-data; name="smime.p7m"       ← шифр
  └─ (после расшифровки) multipart/signed; protocol="application/pkcs7-signature"; micalg=sha-256
        ├─ письмо: multipart/mixed → multipart/related → HTML + текст + картинки, файлы
        └─ smime.p7s: SignedData без содержимого (SHA-256, время подписи, SMIMECapabilities)

Подписанное без шифрования — только средний слой (multipart/signed), Exchange-класс IPM.Note.SMIME.MultipartSigned.

Тема письма не шифруется. Стандарт S/MIME оставляет заголовки снаружи: по ним сервер доставляет письмо и собирает беседу. Шифруются текст, цитата и вложения. Не пишите секрет в тему. Снаружи же лежат Thread-Topic (та же тема без «Re:») и Thread-Index (по нему видно, когда началась беседа и когда отправлен ответ).

Беседа и пометка «отвечено»

Ответ и пересылка зашифрованного письма остаются в беседе — как у Outlook: In-Reply-To/References на Message-ID оригинала, Thread-Topic — тема без «Re:», Thread-Index — индекс беседы оригинала (у Exchange — прочитанный с сервера PidTagConversationIndex) плюс один уровень ответа по [MS-OXOMSG]. После успешной отправки оригинал получает пометку «Вы ответили / Вы переслали»: в Exchange — те же свойства, что ставит Outlook (PidTagLastVerbExecuted, PidTagLastVerbExecutionTime, PidTagIconIndex), в IMAP — \Answered / $Forwarded, если ящик их разрешает. Не вышло — письмо всё равно отправлено. Подробно — ADR-0131 §6а–6б.

Обычный ответ, переехавший в другой ящик через «От:» (ADR-0137), может уйти и зашифрованным: In-Reply-To/References тогда ставит main по связи окна (replyLink → DraftInput.thread; composeMessage берёт их, когда у письма нет своих), а «Вы ответили» отмечает провайдер исходного ящика. Thread-Index у такого ответа нет — беседа Outlook у него своя, связь только заголовками RFC 5322.

Сертификат годится, только если: в нём адрес получателя; он действует сейчас; keyUsage нет или есть keyEncipherment; назначение — почта (EKU нет или есть emailProtection); ключ RSA. Цепочка до корня не обязательна — так же шифруют Outlook и «Почта»; важно, откуда сертификат взят. Из письма, на которое отвечаете, сертификат не берётся никогда (кроме проверенной подписи, см. п. 3).

Свой сертификат: как он находится

Свои сертификаты (с ключом) main собирает все, а адреса сверяет сам (smime/own-identity.ts):

ГдеКак
macOSSHA-1 личностей из security find-identity -p smime ↔ SHA-1, который main сам считает по каждому сертификату security find-certificate -a -p. Адрес на командную строку не попадает. find-certificate -e для своего сертификата больше не используется: он сравнивает адрес с учётом регистра и не находит JDoe@COMPANY.COM для jdoe@company.com
WindowsCurrentUser\My — сертификаты с ключом
Файлзагруженные .p12
  • Адреса сертификата — rfc822Name из SAN и emailAddress субъекта, без учёта регистра. UPN (otherName, например JDoe@corp.company.com) — не почтовый адрес и не считается. Так же сопоставляются сертификаты получателей, подписи входящих писем и кэш корреспондентов.
  • Свои адреса — адрес ящика и его другие SMTP-адреса: у Exchange — ResolveNames своего адреса (основной + EmailAddresses), кэш 30 мин; Exchange отдаёт не больше трёх адресов (первые три из AD, порядок задаёт AD) — псевдоним за их пределами не распознаётся; у IMAP — только адрес ящика. Сертификат на псевдоним (i.ivanov@company.com при ящике ivanov@company.com) — ваш. From письма при этом остаётся адресом ящика, поэтому программа получателя может написать «адрес подписи не совпадает с отправителем» — это ожидаемо.
  • Назначение: подпись — keyUsage нет или есть digitalSignature/nonRepudiation; шифрование на себя — нет или есть keyEncipherment, ключ RSA. Сертификат «только для шифрования» годится для копии в «Отправленных», но не для подписи.
  • Когда не подходит ничего, окно письма называет причину: нет сертификата; «нашёлся ваш сертификат на адрес …, а ящик — …»; «годится только для шифрования» / «только для подписи»; «срок истёк …»; «не предназначен для почты».
  • «Проверить» (Настройки → «Безопасность и шифрование», панель сертификатов) показывает каждый свой сертификат — имя, адреса (совпавшие выделены), назначение, срок, источник и отметку «Этот ящик» / «Другой адрес»; сверху — вывод одной фразой («есть сертификат только для шифрования: письма будут уходить зашифрованными, но без подписи»). Ключи не трогаются — macOS ничего не спрашивает.
  • Память: «можно ли подписать» — 60 с, свой сертификат шифрования — 5 мин (нет — 30 с), списки сертификатов системы — 2 мин. Импорт/удаление сертификата и «Проверить» сбрасывают всё сразу.

Ящик из «От:» (ADR-0137)

Письмо уходит из ящика, выбранного в строке «От:», — и подписывается и шифруется сертификатом этого ящика:

  • Чей сертификат. selfOf(accountId) (main/mailbox-self.ts) называет имя и адрес ящика, из которого уходит письмо; main ищет свой сертификат по этому адресу (и его псевдонимам, см. выше) — одинаково для любого ящика, без различия «свой» или открытый логином другого ящика. У второго демо-ящика адрес свой (demo2@company.com).
  • Замки — для любого ящика. Окно письма спрашивает статус своего сертификата (mail:smime:status без получателей) сразу при открытии, при каждой смене ящика в «От:» и по smime:changed. Нет годного сертификата ящика — «Шифровать» и «Подписать» неактивны с объяснением: «Нет сертификата ящика … — зашифровать (подписать) письмо из этого ящика нельзя. Сертификат добавляется в Настройках → «Безопасность и шифрование».»; не подходит — «Сертификат ящика … не подходит: …». Отказ без подтверждения main проверяет и сам, как в ADR-0131. Настройки «Подписывать все письма» и «Шифровать, когда у всех получателей есть сертификаты» берутся у нового ящика.
  • Ответ на зашифрованное письмо в другой ящик не переносится. Его текст и цитата собраны из расшифровки ключом исходного ящика: строка «От:» у такого письма неактивна с подсказкой «Ответ на зашифрованное письмо уходит только из ящика, в который пришло письмо: его текст расшифрован ключом этого ящика.», и main отказывает сам: compose:moveFrom проверяет не только флаг окна smimeOrigin, но и само исходное письмо (isSmimeEnvelope по намерению окна) — окно, «забывшее» флаг, ответ всё равно не увезёт.
  • Зашифрованное письмо переезжает зашифрованным. Если письмо хранится только зашифрованным (draftSaveMode → encrypted, например на черновике ответа включили «Шифровать»), в новом ящике оно сохраняется через saveSmimeDraft — зашифрованным на сертификат нового ящика; нет его — переезд не удаётся, письмо остаётся в прежнем ящике, «От:» прежний. Уже сохранённый на сервере черновик-конверт (smime.hint = 'pkcs7') main не переносит — он зашифрован на сертификат старого ящика, и снять его провайдером нельзя: «Зашифрованный черновик нельзя перенести в другой ящик: он зашифрован на сертификат этого ящика.»

Кто подписывает

  1. Mac — Связка ключей: /usr/bin/security cms -S -N <имя> -H SHA256 -G -P -T, где имя — адрес выбранного сертификата так, как он в нём записан (затем его CN — только если по адресу личность не нашлась; подпись чужой личностью сразу останавливает попытки); содержимое — на stdin, подпись — со stdout. При первой подписи macOS спросит доступ к ключу — «Разрешить всегда».
  2. Windows — хранилище «Личные»: PowerShell, SignedCms/CmsSigner; сертификат выбирается по отпечатку, отпечаток и содержимое — на stdin. ⚠️ Проверено только подменой процесса.
  3. Иначе — загруженный .p12.
  4. Нечем подписать — зашифрованное письмо уходит без подписи (application/pkcs7-mime; smime-type=enveloped-data прямо вокруг письма, без multipart/signed); письмо только с подписью — не уходит, окно называет причину.

⚠️ Найдено на настоящем Mac: если -N не совпал ни с одной личностью, security cms -S не ошибается, а подписывает другой личностью из связки. Поэтому OutTalk проверяет каждую подпись перед отправкой: подпись цела над этими байтами, и подписал именно выбранный сертификат (сравнение целиком). Нет — подпись выбрасывается, дальше — загруженный .p12 или отказ (больше системных попыток нет).

Черновики

Черновик зашифрованного письма (и ответа на зашифрованное — даже если шифрование потом выключили) хранится на сервере, но только зашифрованным на ваш собственный сертификат — открытого текста на сервере нет никогда. Он лежит в обычных «Черновиках»: OutTalk открывает его тем же путём, что зашифрованное письмо (ключ из Связки), Outlook и «Почта» на другом компьютере — тоже. Переоткрытый зашифрованный черновик остаётся «секретным»: шифрование включено, выключение — с подтверждением. Если ваш сертификат не найден, сохранить такой черновик нельзя: композер объясняет, и второе закрытие закрывает окно без сохранения. Почему не локально — ADR-0131 §7. «Ваш собственный сертификат» здесь — сертификат ящика из строки «От:» (ADR-0137).

Проверка у получателя (живой тест владельца)

  1. Получите в OutTalk подписанное письмо от коллеги с S/MIME (Outlook или «Почта»), откройте его — строка «✓ Подписано». Его сертификат запомнится; если «Почта» уже переписывалась с ним, сертификат найдётся и в Связке ключей.
  2. Ответьте на это письмо, включите «Шифровать» — у его адреса появится замок. Отправьте.
  3. У коллеги: Outlook покажет значок замка и красную ленту «зашифровано»; «Почта» на Mac — значок замка в заголовке письма. Текст должен открыться без ошибок.
  4. Откройте своё письмо в «Отправленных» OutTalk — «🔒 Зашифровано», текст читается (копия зашифрована и на ваш сертификат).
  5. Попросите коллегу ответить зашифрованным — ответ OutTalk на него сам включит оба переключателя.
  6. Для подписи без шифрования: отправьте себе на другой ящик письмо с одним «Подписать» — Outlook/«Почта» покажут подпись проверенной.

Ограничения

  • Открыто подписанное письмо, которое не удалось проверить (конверт больше 32 МБ, сервер не отдал MIME, MIME не разбирается) остаётся читаемым, как его прислал сервер, со строкой «Подпись не удалось проверить»; зашифрованное или непрозрачное в той же ситуации показывает только строку статуса — снаружи конверта читать нечего.
  • «Создать встречу из письма» не переносит текст зашифрованного письма: тело встречи хранится на сервере и рассылается участникам.
  • Ответ и пересылка конверта S/MIME строятся в main из расшифровки, с цитатой и файлами (ADR-0131); если письмо не удалось расшифровать — ответить из него нельзя (цитировать нечего), напишите новое. Цитату main собирает quoteHtml → buildQuoteHtml(src, DEFAULT_QUOTE_TEMPLATE) (@shared/quote-template) — в стандартном виде Outlook, как у IMAP и как предварительная цитата композера (ADR-0150); шаблон цитаты ящика, узнанный по черновикам сервера, к ней не применяется. В диалоге главного окна эта цитата видна под подписью сразу, пока main готовит ответ (поле закрыто до конца подготовки); отдельное окно, которому main не отдал preview (конверт S/MIME), ждёт подготовки с заглушкой цитаты под подписью: шапка из строки списка (отправитель, дата, тема — их сервер видит и так) и скелет тела; текст расшифровки в неё не попадает. Ответ на открыто подписанное письмо по-прежнему строит сервер — его текст серверу виден.
  • Поиск по тексту зашифрованных писем невозможен — у сервера нет текста.
  • Плагины получают письмо от провайдера, то есть конверт, а не расшифровку (это осознанно).
  • Отзыв сертификатов не проверяется.
  • Тема исходящего зашифрованного письма не шифруется (так устроен стандарт).
  • Получатели с ECDH-ключом (KeyAgreeRecipientInfo) пока не поддерживаются — их сертификат считается «не годится».
  • Отзыв сертификатов получателей не проверяется.
  • Демо-режим держит загруженные ключи только в памяти; системное хранилище в e2e выключено (OUTTALK_SMIME_SYSTEM=0), чтобы прогон не трогал настоящую Связку ключей — ни ключи, ни оценку доверия (подпись тогда проверяется до корней среды выполнения). Подписанное письмо для e2e — OUTTALK_DEMO_SMIME_SIGNED_FILE.

Как экспортировать .p12 (если ключа нет в системе)

Mac. «Связка ключей» (Программы → Утилиты) → слева «Вход» → вверху «Мои сертификаты» → сертификат со своим адресом (с треугольником — внутри ключ) → правый клик → «Экспортировать…» → формат «Обмен личной информацией (.p12)» → задать пароль.

Windows. Win+R → certmgr.msc → «Личное» → «Сертификаты» → правый клик по своему сертификату → «Все задачи» → «Экспорт…» → «Да, экспортировать закрытый ключ» → PFX → задать пароль.

После загрузки файл можно удалить с диска.
